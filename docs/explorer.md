# Конструктор отчётов (/explorer) — OLAP-отчёты iiko

## Что это

Конструктор OLAP-отчётов iikoOffice, перенесённый в сервис. Пользователь собирает отчёт
так же, как в iikoOffice: выбирает тип отчёта (продажи, проводки, доставки, контроль
хранения), период, раскладывает поля из каталога iiko по «Строкам», «Столбцам»,
«Показателям» и «Фильтрам» и жмёт «Построить». Сервис запрашивает данные у iiko
(`POST /v2/reports/olap`) и показывает сводную таблицу с группами и итогами, как грид
iikoOffice.

**Зачем.** Готовые страницы сервиса закрывают частые вопросы, но уникальные — списания по
причинам и документам, удаления позиций и кто их авторизовал, заказы «без выручки»,
продажи по часам и кассам — раньше можно было посмотреть только в iikoOffice. Теперь любой
срез из 279 полей продаж и 116 полей проводок строится на сайте, выгружается в Excel,
сохраняется и доступен ИИ-агентам по MCP (инструменты `analytics_explorer_*`).

**Что умеет:**

- каталог полей iiko с категориями как в iikoOffice, поиском и группой «Часто
  используемые»; перетаскивание полей в зоны или добавление кнопками;
- фильтры: список значений (из iiko за период) с режимом «только выбранные / все, кроме»,
  диапазоны чисел, диапазоны дат и времени;
- сводная: вложенные группы строк с итогами, столбцы, колонка «Итого», общий итог,
  сортировка по клику на заголовок, «Развернуть всё / Свернуть», доли в столбце и в строке;
- Excel (сводная, все строки данных, параметры и тела запросов к iiko);
- сохранённые отчёты сервиса (период — пресетом, который пересчитывается, или датами) и
  открытие отчётов, сохранённых в iikoOffice;
- ссылка на сохранённый отчёт `/explorer?report=<id>` — открывает и сразу строит его.

До 2026-09-29 страница была MVP «выручка × время × категория» (`/api/explorer/pivot`,
`core/explorer.py`); она заменена целиком.

## Как работает

### Поток

```
страница /explorer                      агент MCP (analytics_explorer_*)
      |  POST /api/explorer/report  {report_type, rows, columns, measures, filters, период}
      v
core/olap_constructor.run_report
      |- get_catalog(report_type)        каталог полей (кэш 6 ч)
      |- parse_spec                      проверка заявки по каталогу
      |- plan + olap_body                1 или 2 тела POST /v2/reports/olap
      |- olap_client.fetch_olap          кэш 10 мин -> одна сессия iiko -> до 2 запросов параллельно
      '- build_pivot | build_flat        сводная с итогами | список строк с итогами
```

### Каталог полей

`GET /v2/reports/olap/columns?reportType=…` отдаёт по каждому полю id, русское имя из
iikoOffice, тип и три флага: можно ли группировать, агрегировать, фильтровать. Каталог
хранится в памяти 6 часов (меняется только с обновлением iiko). Если iiko недоступен —
запасная копия: сначала последняя живая с постоянного диска (`/kultura/olap_columns_<ТИП>.json`),
затем снимок в репозитории; в ответе `source` = `live` / `disk` / `repo`, страница пишет
«запасная копия». После неудачи iiko 60 секунд не опрашивается, чтобы страница не ждала
таймаут на каждом открытии.

Что добавляет сервис к каталогу iiko:

| Поле | Значение | Откуда правило |
|---|---|---|
| `kind` | `sum` — итог показателя = сумма строк; `server` — итог считает iiko | Явный список `SUM_MEASURES` (выручка, суммы, количества, себестоимость, приход, расход). Всё остальное — `server`: неизвестный новый показатель получит итог от iiko, но никогда неверную сумму |
| `blocked` | поле видно, но недоступно, с причиной | `StartBalance.*` / `FinalBalance.*` — iiko суммирует проводки за всё время и советует запускать ночью (остатки — на /stocks); `PercentOfSummary.*`, `Sum.PartOfSummaryBy*` — доля от раскладки iikoOffice, у нас её даёт переключатель «Доли»; тип `OBJECT` — составное значение |
| `filter_op` | `values` (строки, перечисления, id), `range` (числовые разрезы), `date_range` (даты, время) или нет фильтра | Флаг iiko `filteringAllowed`; поле периода фильтруется выбором периода; у показателей, которые нельзя группировать, фильтра нет — iiko на сервере их не фильтрует (фильтр по `DiscountSum` отвечал HTTP 400, проверено 2026-06-17) |
| `enum` | русские названия кодов перечислений | Таблицы из [iiko-api/kody-bazovykh-tipov.md](iiko-api/kody-bazovykh-tipov.md); в фильтре можно указать и код, и название — в iiko уходит код |
| `hint` | связь с отчётами сервиса | «бар — так во всех отчётах сервиса» (`Store.Name`), «выручка — так на дашборде» (`DishDiscountSumInt`), «сотрудник — так в KPI и ЗП» (`AuthUser`), «порции, не литры» (`DishAmountInt`) |

Панель полей: «Часто используемые», затем категории iiko в удобном порядке, прочие поля,
идентификаторы (ID) — в конце.

### Заявка (контракт API)

`POST /api/explorer/report`, тело JSON:

| Поле | Значение | Обязательно |
|---|---|---|
| `report_type` | `SALES` (по умолчанию), `TRANSACTIONS`, `DELIVERIES`, `STOCK` | нет |
| `rows`, `columns` | id полей с `group`; до 8 строк и 4 столбцов, хотя бы одно поле | да (одно из двух) |
| `measures` | id полей с `agg`, 1–12 | да |
| `filters` | `[{field, op, values \| from/to, include_low, include_high}]`, до 30, по одному на поле; `op`: `in`, `not_in`, `range`, `date_range` | нет |
| `include_deleted` | `false` (по умолчанию) — см. правило 2 | нет |
| `date_from`, `date_to` или `period` | даты включительно `YYYY-MM-DD` или пресет: `yesterday`, `today`, `this_week`, `last_week`, `this_month`, `last_month`, `last_7_days`, `last_30_days`, `this_year`, `last_year` | да |
| `format` | `flat` (по умолчанию) или `pivot` | нет |
| `sort`, `order`, `limit`, `having` | только для `flat`: сортировка по полю, `asc`/`desc`, 1–5000 строк (по умолчанию 200), условия на показатели | нет |

Пример — списания пива по барам и причинам за прошлый месяц:

```json
{"report_type": "TRANSACTIONS", "rows": ["Account.Name", "Contr-Account.Name"],
 "measures": ["Amount.Out", "Sum.Outgoing"],
 "filters": [{"field": "TransactionType", "op": "in", "values": ["WRITEOFF"]},
             {"field": "Product.TopParent", "op": "in", "values": ["Напитки Розлив"]}],
 "period": "last_month", "format": "pivot"}
```

Граница «до» у фильтра `date_range` (дата и время, например `OpenTime`): при
`include_high=true` дата без времени включает **весь день** (`2026-09-22` уходит в iiko как
`2026-09-22T23:59:59.999`), время без секунд — **всю минуту** (`18:30` ->
`18:30:59.999`). Иначе «до 22-го» включало бы только полночь 22-го, а «до 23:59» со страницы
теряло бы последнюю минуту. С секундами или при `include_high=false` граница уходит как
есть (`2026-09-22` -> `2026-09-22T00:00:00.000`, не включая).

Пресеты периода считает сервис: «сегодня» — рабочие сутки бара до 06:00 МСК
(`core/msk_time.business_today`), неделя — понедельник..воскресенье, «последние 7 / 30
дней» — закрытые дни до вчера включительно (незакрытый сегодняшний день не смешивается с
полными).

### Правила сборки запроса к iiko (`olap_body`)

1. **Период** — всегда фильтр `DateRange` по полю периода: продажи и доставки —
   `OpenDate.Typed` (учётный день), проводки — `DateTime.DateTyped`, контроль хранения —
   `EventDate`. `from` — первый день, `to` — последний день **+ 1**: граница iiko
   исключающая, а пользователь выбирает дни включительно. Пример: 21.09—27.09 уходит как
   `from 2026-09-21, to 2026-09-28`. Относительные периоды iiko (`CURRENT_WEEK` и т. п.) не
   используются — даты видны в ответе и в «Как считается».
2. **Удалённые позиции и заказы.** В продажах и доставках, если в заявке нет своего фильтра
   по `DeletedWithWriteoff` / `OrderDeleted` и не сказано `include_deleted=true`,
   добавляется «не удалено» — как в шаблоне OLAP-отчёта iikoOffice и во всех отчётах
   сервиса. Страница всегда шлёт `include_deleted=true`, а эти два фильтра новый отчёт о
   продажах получает обычными фишками — их видно и можно снять (для отчётов об удалениях).
   В «Как считается» автоматические фильтры помечены «(автоматически)».
3. **Строки и столбцы** уходят в iiko одним списком `groupByRowFields`; раскладка по
   столбцам делается в сервисе. Ответ iiko всегда плоский и читается одинаково.
4. **Сортировка, топ-N, условия на показатели** в iiko не отправляются: в теле OLAP-запроса
   их нет ([iiko-api/olap-otchety-v2.md](iiko-api/olap-otchety-v2.md)) — это делает сервис.

### Итоги

Итог показателя `sum` (выручка, суммы, количества, себестоимость, приход, расход) =
**сумма строк группы** — считается в сервисе, точно.

Итог показателя `server` (чеки `UniqOrderId`, средние, проценты, длительности) сложением
строк **неверен**: чек, в котором есть и пиво, и еда, есть и в строке «Розлив», и в строке
«ЕДА», а в итог должен попасть один раз. Такие итоги считает iiko — запрос с
`buildSummary=true` возвращает `summary`: блоки `[ключи, итоги]`, где ключи — префикс
полей группировки в порядке запроса. Префикс даёт не все нужные итоги, поэтому план:

| Показатели `server` | Строки | Столбцы | Запросы |
|---|---|---|---|
| нет | любые | любые | 1: строки + столбцы, без summary |
| есть | есть | нет | 1: строки, summary — итоги групп и общий итог |
| есть | нет | есть | 1: столбцы, summary — общий итог |
| есть | есть | есть | 2 одной сессией, параллельно: `cells` = столбцы + строки (ячейки, итоги столбцов, итоги групп внутри каждого столбца) и `rows` = строки (колонка «Итого» и общий итог) |

Пример (тест `test_pivot_totals_do_not_double_count_checks`): чеки по группам блюд × барам.
У Лиговского строки «Розлив» — 3 чека, «ЕДА» — 1, «(пусто)» — 1; итог столбца — **4**, а не
5: один чек был и с пивом, и с едой.

Если iiko не вернул нужный блок summary, в итоговой ячейке показателя `server` — прочерк, в
предупреждениях — пояснение; сумма строк вместо неё не подставляется никогда. Сверка: общий
итог iiko по показателям `sum` сравнивается с суммой строк; расхождение больше копейки —
предупреждение (значит, разбор summary разошёлся с форматом iiko).

**Доли** (переключатель над таблицей) показываются только у показателей `sum`:
«Доля в столбце» = значение / итог столбца × 100, «Доля в строке» = значение / итог
строки («Итого») × 100, один знак после запятой. У чеков и средних части в итог не
складываются — там остаётся само значение.

### Ответ `format=pivot` (страница)

```json
{"format": "pivot",
 "fields": {"rows": [...], "columns": [...], "measures": [{"id", "name", "type", "kind", "enum"?}]},
 "columns": [["Варшавская"], ["Лиговский"]],
 "tree": {"c": [[550, 1], [1600, 4]], "t": [2150, 5],
          "ch": [{"k": "ЕДА", "c": [[300, 1], [300, 1]], "t": [600, 2]}, ...]},
 "leaf_count": 4, "warnings": [], "meta": {...}}
```

`c` — значения по столбцам (порядок `columns`, внутри — порядок `measures`; `null` — нет
данных), `t` — «Итого» по строке; у корня `c` — итоги столбцов, `t` — общий итог; `ch` — дети
группы. Пустые значения разреза iiko отдаёт двух видов, и это **разные** значения: `null`
— «(пусто)», пустая строка `""` — «(пустая строка)» (фильтр по `null` строки с `""` не
ловит). Оба — в конце списка (сначала пустая строка, потом пусто), при любой сортировке
подписей на странице и в `flat`. Числа —
до 6 знаков (без хвостов 0.30000000000000004); формат на странице: деньги — 2 знака,
количество — до 3, проценты iiko (доля 0..1) × 100, длительности — ч:мм:сс.

`meta`: тип, поле и даты периода (`date_to_exclusive` — граница, ушедшая в iiko), фильтры
словами, какие показатели итогуются сложением и какие — iiko, тела запросов, время данных
iiko и признак кэша, источник каталога.

### Ответ `format=flat` (агенты)

Строки — разрезы, затем показатели; у перечислений — русские названия. `totals` — итоги по
**всем** строкам отчёта (до `having` и `limit`): `sum` — сложением, `server` — общий итог
iiko. `row_count` — строк в отчёте, `matched` — после `having`, `returned` — отдано после
`limit`, `truncated` — были отрезаны. Сортировка по показателю — пустые значения в конце.

### Значения для фильтров

`GET /api/explorer/values?report_type=&field=&period=|date_from=&date_to=&q=&limit=` — лёгкий
запрос: одна группировка по полю за период и самый дешёвый показатель
(`VALUES_MEASURES`). Фильтр «не удалено» не ставится — в списке есть и значения удалённых
позиций. У перечислений к найденным кодам добавляются все известные (можно выбрать и то,
чего за период не было). `has_empty` — есть значения `null` (галочка «(пусто)», фильтр
`null`); пустая строка — обычное значение `""` с подписью «(пустая строка)».

### Отчёты iikoOffice

`GET /api/explorer/presets` — отчёты, сохранённые в iikoOffice (`/v2/reports/olap/presets`,
кэш 10 минут), в виде конфигураций конструктора. Фильтры переносятся как есть (без
автоматического «не удалено»: если в отчёте iikoOffice его нет, iikoOffice показывает
удалённые — и конструктор тоже). Период: пресет iiko (`LAST_MONTH` и т. п.) -> пресет
сервиса, `CUSTOM` -> даты (исключающая граница `to` переводится во включительную). Что не
перенеслось — в `notes`. Отчёт строится через `/v2/reports/olap` с конфигурацией, а не
`byPresetId`: так советует iiko — формат сохранённых конфигураций меняется при обновлениях.
Новый отчёт для агента и сайта можно собрать и сохранить прямо в iikoOffice; Ctrl+Shift+F3
в iikoOffice показывает его параметры в терминах API.

### Сохранённые отчёты сервиса

`GET/POST /api/explorer/saved`, `DELETE /api/explorer/saved/<id>`. Хранится конфигурация, а не
данные: при открытии отчёт строится заново. Период — пресетом (каждый раз свой) или
датами. Проверка при сохранении — структурная, без iiko (сохранение не зависит от его
доступности); поля против каталога проверяются при построении, а при открытии поля,
которых нет в каталоге, отбрасываются с сообщением. Даты периода — настоящие даты
(`2026-13-45` не сохранится), `id` — строка. Файл пишется атомарно под межпроцессным
замком (занят дольше 10 с — ответ 503 «повторите»); не больше 300 отчётов; битый файл —
ошибка, а не молчаливая перезапись пустым.

`include_deleted` без значения сохраняется как `false` — так же, как его понимает
построение отчёта (правило 2). Страница всегда сохраняет `true` вместе с фишками «не
удалено». Отчёт, сохранённый агентом без флага, страница открывает с фишками «не
удалено» (кроме полей, по которым у отчёта свой фильтр) — цифры на странице и у агента
совпадают.

### Excel

`POST /api/explorer/export` (та же заявка) -> `olap_<тип>_<с>_<по>.xlsx`:

- «Отчёт» — сводная как на странице: поля строк колонками, группы с итогами жирным, для
  каждого столбца показатели, затем «Итого», внизу общий итог;
- «Данные» — все строки ответа iiko с автофильтром (для своих сводных в Excel);
- «Параметры» — период, фильтры словами, правило итогов, время данных, тела запросов.

Пределы: до 200 000 строк данных; сводная строится до 50 000 строк, больше — на листе
объяснение, данные всё равно на листе «Данные». Книга пишется в режиме write_only.

Текст из iiko пишется только как текст: названия, комментарии и причины удаления вводит
персонал, и строка «=1+2» иначе стала бы формулой Excel (неверное значение или
HYPERLINK-инъекция). Управляющие символы (`\x0b` и т. п.), которые Excel не хранит,
вырезаются — раньше они роняли выгрузку.

### Пределы и нагрузка на iiko (почему такие)

| Константа | Значение | Почему |
|---|---|---|
| Запросов конструктора одновременно | 2 места на процесс (в проде 2 воркера — до 4) | Тот же сервер iiko обслуживает кассы баров. Сессия берёт места ДО входа в iiko (серия из двух запросов — два) и отдаёт после выхода: ограничены и запросы, и входы (слоты лицензии API). Ждём место 60 с, потом «iiko занят» |
| Таймаут чтения | 120 с | Отчёт за год строится около 14 с, выбросы до 63 с (docs/lessons.md, 2026-08-11); gunicorn обрывает воркер на 180 с |
| Повтор запроса | 1 раз через 1,5 с, только если связь не установилась | Таймаут или обрыв посреди ответа не повторяется: iiko уже считал тяжёлый отчёт |
| Кэш ответов | 10 мин; ключ — вся серия запросов отчёта; до 1 000 000 значений на процесс, серия больше 300 000 значений не кэшируется | Ответы серии всегда из одного похода в iiko: запрос «только строки» совпадает с запросом `rows` отчёта со столбцами, и по отдельности «Итого» взялся бы из старого ответа, а ячейки — из свежего. Значение ответа в памяти ~94 байта (строка из 10 полей ~940 байт) — кэш не больше ~100 МБ на воркер |
| Строк сводной | 20 000 (и 400 000 ячеек) | Больше браузер рисует медленно, а глазами не читается — для этого Excel |
| Полей в строках и столбцах | 8 и 4; больше 7 всего — предупреждение | iiko рекомендует «не более 7 полей» (ogranicheniya-i-rekomendatsii.md) — это совет по нагрузке, не запрет |
| Строк на экране | 2 000 за раз, «Показать ещё» | DOM на десятках тысяч строк тормозит |

Ограничения iiko «запросы последовательно» и «период не длиннее месяца» — рекомендации по
нагрузке, а не лимиты API (прод давно шлёт до 6 запросов параллельно и строит отчёты за
годы); конструктор их соблюдает мягко: пул из двух запросов, без запрета длинных периодов.

### Страница

- Отчёт строится по кнопке «Построить» (или Ctrl+Enter), а не при каждом изменении: каждое
  построение — запрос к боевому iiko. Изменили раскладку после построения — таблица
  приглушается, вверху «Параметры изменились — нажмите «Построить»».
- Поле кладётся в зону перетаскиванием или нажатием: всплывающее меню с «В строки», «В
  столбцы», «В показатели», «Фильтр…»; недоступное действие погашено с причиной.
  Поле переезжает между строками и столбцами, а не дублируется; порядок — стрелками или
  перетаскиванием.
- На телефоне панель полей — лист снизу, открывается кнопкой «+ поле» у зоны; окна —
  листы снизу.
- Последняя раскладка помнится в браузере (localStorage) — только удобство.
- Открыли другой отчёт, пока строится прошлый, — ответ прошлого не показывается, новый
  строится сразу после него.
- iiko не вернул ни одной строки — вместо таблицы «Нет данных» с периодом и подсказкой
  проверить фильтры (в том числе «не удалено»); переключатель долей и «Развернуть всё»
  при этом скрыты.
- Пояснения — в «Как считается» под таблицей, свёрнуто (правило проекта): период и
  граница для iiko, фильтры, правило итогов, доли, тела запросов, время данных.

### MCP

Инструменты домена `analytics` (описания — [core/mcp/tools/analytics.py](../core/mcp/tools/analytics.py)):

| Инструмент | Маршрут | Что |
|---|---|---|
| `analytics_explorer_columns` | `GET /api/explorer/columns` | Каталог полей (`compact`, `q`, `tag`) |
| `analytics_explorer_values` | `GET /api/explorer/values` | Значения поля за период |
| `analytics_explorer_report` | `POST /api/explorer/report` | Отчёт (`format=flat` для агента) |
| `analytics_explorer_export` | `POST /api/explorer/export` | Excel |
| `analytics_explorer_presets` | `GET /api/explorer/presets` | Отчёты iikoOffice |
| `analytics_explorer_saved_list` | `GET /api/explorer/saved` | Сохранённые отчёты |
| `analytics_explorer_saved_save` | `POST /api/explorer/saved` | Сохранить (только по прямой просьбе владельца) |
| `analytics_explorer_saved_delete` | `DELETE /api/explorer/saved/<id>` | Удалить (только по прямой просьбе владельца) |

Проект агента, который по вопросу обычным языком сам собирает такие отчёты, — [olap-agent.md](olap-agent.md).

### Что не перенесено из iikoOffice

- Графики — только таблица и Excel.
- Промежуточные итоги по уровням столбцов: при нескольких полях в столбцах каждая
  комбинация — свой столбец, итог — общий «Итого».
- Псевдопоказатели «% по столбцу / строке» iiko — заменены переключателем «Доли».
- Остатки через OLAP (`StartBalance`, `FinalBalance`) — запрещены как тяжёлые; остатки —
  на странице «Остатки».
- Проваливание из ячейки в чеки.

### Проверить на живом iiko

Код проверен на поддельном iiko, повторяющем формат из документации. На живом сервере ещё
не проверялись: разбор `summary` (итоги показателей `server`; при расхождении страница
покажет предупреждение), тип отчёта `STOCK` через v2 (в документации v2 его нет, каталог
v2 его отдаёт) и каталог `DELIVERIES` (запасной копии нет).
