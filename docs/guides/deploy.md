# Деплой на прод

GitHub Actions **Deploy production** (`.github/workflows/deploy.yml`) запускается
после обновления `main` и вручную кнопкой **Run workflow**. Автодеплой начинает
работать после однократной установки серверного скрипта и добавления двух Secrets.
Само наличие workflow в репозитории ещё не означает, что сервер подключён.

## Адреса и данные

| Что | Значение |
|---|---|
| Прод | https://beerkultura.ru |
| VPS Selectel | `139.100.200.92`, `ssh root@139.100.200.92` |
| Репозиторий | `/opt/beer`, владелец `deploy:deploy`, ветка `main` |
| Приложение | `beer-app`, gunicorn на 10000 |
| TLS | `beer-caddy`, Caddy на 80/443 |
| Постоянные данные | `/srv/kultura` → `/kultura` |
| Данные приложения | `/srv/beer/data` → `/app/data` |
| Секреты | `/opt/beer/.env`, `/srv/beer/secrets` → `/app/secrets:ro` |

## Как работает выпуск

1. GitHub берёт конкретный SHA из `main`, устанавливает зависимости и выполняет
   `python -m pytest -q tests --ignore=tests/debug`, тесты скрипта деплоя и проверку JS.
   `tests/debug/` — ручные диагностические скрипты iiko, их ошибки fixtures штатные.
2. Только после успешных тестов отдельная задача подключается к VPS по SSH.
   Ключи доступны только этой задаче; код приложения в ней не запускается.
3. Сервер принимает только `deploy <полный SHA>`, проверяет чистое рабочее дерево,
   ветку `main`, fast-forward и совпадение SHA с текущим `main` на GitHub.
   Устаревший запуск завершится ошибкой: следует дождаться нового или нажать кнопку снова.
4. Текущий образ сохраняется как `beer-abc-analysis:previous`. Новый собирается с
   меткой `org.opencontainers.image.revision=<SHA>` и тегом `release-<SHA>`.
   Во время сборки старый контейнер продолжает обслуживать сайт.
5. Обновляется только `app`. Проверяется ID образа работающего контейнера и несколько
   ответов `200` от `/login` напрямую и через Caddy с проверкой TLS.
6. Если сборка не удалась, работающий контейнер не заменяется. Если запуск или проверка
   новой версии не удались, восстанавливается прежний образ с прежним Compose-файлом.
   Workflow остаётся красным даже при успешном восстановлении: новая версия не выпущена.

Деплои выполняются последовательно; повторное нажатие не прерывает текущую сборку.
На VPS дополнительно используется `flock`. Пересоздание контейнера может дать
краткий перерыв в работе; это не blue-green deployment.

## Однократное подключение

В существующей root SSH-сессии, после появления workflow в `main`:

```bash
cd /opt/beer &&
runuser -u deploy -- git pull --ff-only origin main &&
bash scripts/deploy/install.sh
```

Установщик не перезапускает приложение. Он устанавливает root-owned скрипт
`/usr/local/sbin/beer-deploy`, генерирует отдельный ed25519-ключ и добавляет его
публичную часть в `/root/.ssh/authorized_keys` с `restrict` и forced command.
Этот ключ не позволяет открыть shell, выполнить другую команду или создать туннель.
Обычный доступ администратора остаётся как прежде. Повторная установка сохраняет ключ.

Открыть [Settings → Secrets and variables → Actions](https://github.com/wwworm666/beer-abc-analysis/settings/secrets/actions)
и добавить два **Repository secrets**:

| Имя | Содержимое |
|---|---|
| `BEER_DEPLOY_SSH_KEY` | Весь файл `/root/.ssh/beer_github_actions`, включая BEGIN/END |
| `BEER_DEPLOY_KNOWN_HOSTS` | Весь файл `/var/lib/beer-deploy/known_hosts` |

Показать их по очереди в своей SSH-сессии:

```bash
cat /root/.ssh/beer_github_actions
cat /var/lib/beer-deploy/known_hosts
```

Приватный ключ копируется напрямую в GitHub Secret — не в чат, файл репозитория
или скриншот. Host key берётся из уже аутентифицированной SSH-сессии сервера;
workflow использует `StrictHostKeyChecking=yes`, без слепого `ssh-keyscan`.

Перед подключением workflow проверяет оба секрета одновременно. Переносы CRLF,
переносы терминала и экранированные Markdown-границы ключа нормализуются;
полноту ключа затем проверяет настоящий `ssh-keygen`. Обрезанный ключ не
восстанавливается автоматически. В лог попадает только отпечаток публичного ключа.
Первоначальный ключ, раскрытый при настройке, явно отклоняется: нужен новый ключ.

### Проверка сервера и копирование ключа из PowerShell

Чтобы не выделять ключ в терминале вручную, открыть новую вкладку PowerShell
на Windows и выполнить:

```powershell
$beerKey = ssh root@139.100.200.92 "cd /opt/beer && runuser -u deploy -- git pull --ff-only origin main >&2 && bash scripts/deploy/install.sh >&2 && python3 scripts/deploy/check_server.py --copy-key"
if ($LASTEXITCODE -eq 0) {
    ($beerKey -join "`n") | Set-Clipboard
    Write-Host 'Ключ скопирован. Вставьте его в BEER_DEPLOY_SSH_KEY на GitHub.'
} else {
    Write-Host 'Проверка не прошла. Пришлите только строки OK/FAIL из отчёта.'
}
Remove-Variable beerKey -ErrorAction SilentlyContinue
```

Проверка собирает результаты Git, владельцев файлов, Compose, работающих
контейнеров, HTTP/HTTPS, изменений `data/`, исходных SSH-файлов, отзыва раскрытого
ключа и входа через ограниченный ключ. Отчёт идёт в stderr; stdout содержит
только приватный ключ и только после всех успешных проверок. Приложение не
перезапускается. В GitHub нужно вставить буфер в существующий Secret и сохранить.
Содержимое буфера не отправлять в чат.

Теперь открыть [Actions → Deploy production](https://github.com/wwworm666/beer-abc-analysis/actions/workflows/deploy.yml),
нажать **Run workflow**, оставить `main` и запустить. Это первый сквозной тест
подключения. До установки ключа и Secrets deployment job сообщает о незавершённой настройке.

## Повседневный процесс

Изменения из рабочей ветки сначала попадают в `main`. Это автоматически запускает
выпуск; workflow сам ветки не сливает. Слияния должны проходить обычное ревью проекта.
Кнопка **Run workflow** повторяет выпуск текущего `main` с компьютера или телефона
через браузер GitHub. Запуски с других веток не получают deployment job.

Результат и этап ошибки видны в Actions. Подробные логи приложения сохраняются
на VPS в `/var/lib/beer-deploy/release-*/app-failure.log`, а не в публичном GitHub.
После зелёного запуска нужно проверить изменённый сценарий под своей учётной записью:
`200` от страницы входа не проверяет расчёт зарплаты или обмен с iiko.

Ручной выпуск проверенного текущего SHA из root-сессии:

```bash
/usr/local/sbin/beer-deploy deploy <полный_SHA_текущего_main>
```

Если менялся `scripts/deploy/beer-deploy.sh`, его root-owned установленную копию
обновляет администратор повторным запуском `bash scripts/deploy/install.sh`.
Автоматически заменять свой привилегированный скрипт процесс не пытается.

## Данные, конфигурация и откат

Host-маунты перекрывают содержимое образа: `data/` из Git не обновляет боевые JSON
и базы. Скрипт останавливает релиз, если в `data/` есть изменения относительно
известного работающего коммита (для образов до первой автоматической сборки —
относительно серверного checkout). Такие релизы требуют ручной проверки и переноса
нужных файлов. Кнопка не копирует, не очищает и не восстанавливает `/srv/kultura`.

Сидирование копирует отсутствующий файл из `/app/data` в `/kultura` один раз.
Планы, KPI-цели и другие изменяемые бизнес-данные редактируются через сайт.
Новые обязательные переменные `.env`, изменения Caddy и миграции данных подготавливает
администратор отдельно. После изменения Caddyfile контейнер пересоздаётся, чтобы
подхватить актуальный файл bind mount и загрузить конфигурацию:

```bash
cd /opt/beer && docker compose up -d --force-recreate caddy
```

Для `.env` достаточно `docker compose up -d app`; для ручного обновления кода
без установленного скрипта обязательно `docker compose up -d --build app`.
В `.dockerignore` исключены `.env`, `.env.*` (включая резервные копии) и `secrets/`.

Быстрый ручной откат последнего успешного автоматического выпуска без пересборки:

```bash
release_dir=$(cat /var/lib/beer-deploy/last-release) &&
docker image tag "$(cat "$release_dir/image-before.txt")" beer-abc-analysis:latest &&
docker compose --project-directory /opt/beer -f "$release_dir/compose-before.yml" \
  up -d --no-build --no-deps --force-recreate app
```

Затем проверить `/login` и сам сценарий. История Git остаётся на `main`: откатывается
образ, а не checkout. Автоматический откат не отменяет изменений, которые приложение
уже записало в базы. Выпускаемые теги образов не удаляются автоматически; при нехватке
диска администратор удаляет только заведомо ненужные версии.

Ночной пересчёт зарплаты и `/me` закрывает предыдущий месяц 7-го числа. Более поздний
деплой сам не пересчитает закрытый месяц: экспорт Google обновляется кнопкой на
`/salary`, а замороженный снимок `/me` требует отдельного решения.
