# Главный дашборд

## Что это

Основной дашборд системы с 15 метриками эффективности баров. Показывает выручку, доли категорий, наценку, прибыль, списания баллов за выбранный период.

## Выбор периода — шапка фильтров

### Один контрол

Одна полоса на всех вкладках ([`period_controls.js`](../static/js/dashboard/modules/period_controls.js),
[`filter_menus.js`](../static/js/dashboard/modules/filter_menus.js)):

```
[ Культура - Кременчугская ▾ | ‹  Неделя 32  3—9 авг ▾  › |        Excel  PDF ]
```

В строке ровно два выбора: заведение и период. **Переключателя гранулярности,
кнопки «Сегодня» и счётчика дней нет** — всё это живёт в выпадающем списке периода,
где выбор занимает один клик. Внутри полосы у контролов нет своих рамок: их
разделяют вертикальные линии, поэтому полоса читается как один элемент.

Подпись периода — это **название** («Неделя 32», «Август 2026», «III квартал 2026»)
плюс **какие это числа** («3—9 авг»). Для незавершённого периода подсказка
показывает прошедшую часть — ровно тот диапазон, за который на экране есть факт:
идущий месяц это «1—12 авг», закрытый — «июль».

### Список быстрого выбора

Клик по подписи открывает список. На десктопе — выпадашка 272px у подписи,
на телефоне — нижний лист во всю ширину (одна разметка, разные стили).

| Пункт | Период | Гранулярность |
|-------|--------|---------------|
| Сегодня | текущий день | day |
| Вчера | предыдущий день | day |
| Эта неделя | пн..вс текущей | week |
| Прошлая неделя | пн..вс предыдущей | week |
| Этот месяц | 1-е..последнее | month |
| Прошлый месяц | предыдущий целиком | month |
| Квартал | календарный квартал | quarter |
| Год | 01.01..31.12 | year |
| Свой период | календарь Flatpickr | custom |

**Гранулярность задаёт сам пресет**, отдельного переключателя нет: выбрал
«Прошлая неделя» — стрелки дальше листают неделями. Активный пункт подсвечивается
(`matchPreset` сверяет границы периода с пресетами).

### Шаг стрелки

| Гранулярность | Границы | Шаг |
|---------------|---------|-----|
| День | сам день | ±1 день |
| Неделя | пн..вс (ISO-8601) | ±7 дней |
| Месяц | 1-е..последнее число | ±1 календарный месяц |
| Квартал | янв-мар / апр-июн / июл-сен / окт-дек | ±3 месяца |
| Год | 01.01..31.12 | ±1 календарный год |
| Произвольный | как выбрано в календаре | ±длина периода |

Диапазон из календаря, совпавший с натуральными границами (например 01.08–31.08),
распознаётся как месяц — стрелки продолжают листать месяцами (`detectGranularity`).
Стрелка «вперёд» гаснет на текущем периоде: данных дальше нет.

**Клавиатура:** `←`/`→` листают период, `Esc` закрывает список.

### Дефолт — последняя ЗАВЕРШЁННАЯ неделя

`defaultPeriod()` в [`period_model.js`](../static/js/dashboard/core/period_model.js).
Причина: у незавершённой недели факт есть только за прошедшие дни, а план урезается
пропорционально всему периоду — процент выполнения выглядел бы провалом.

Период **не персистится**: дашборд всегда открывается на последней завершённой
неделе. До 2026-08-11 дефолт задавали три места (localStorage, `/api/weeks`,
datepicker), они перетирали друг друга и давали лишний OLAP-запрос на старте.

### Гранулярности по вкладкам

| Вкладка | Доступно | Почему |
|---------|----------|--------|
| Аналитика | все | `/api/dashboard-analytics` принимает любой диапазон, план считается пропорционально |
| Выручка | все | эндпоинт получает явные границы периода (`period_from`/`period_to`) |
| Планы | месяц, год | планы хранятся помесячно (`venue_YYYY-MM`); год = сумма месячных планов, только просмотр |
| Сравнение | выбор периода скрыт | у вкладки свои Период 1 / Период 2 |

Неприменимые пункты списка **гаснут**, а не исчезают: список не должен «прыгать»
при переключении вкладок. При переходе на вкладку, где текущая гранулярность
недоступна, период сам переключается на месяц, в который он попадал
(`snapToAllowedGranularity`).

### Заведение и выгрузка

Данные о заведениях по-прежнему держит **скрытый** `<select id="venue-selector">` —
его наполняет [`venue_selector.js`](../static/js/dashboard/modules/venue_selector.js),
он же владеет событием `change`. Список в шапке — только вид над ним: при выборе
он выставляет `select.value` и шлёт `change`. Так логика загрузки заведений не
задублирована.

Выгрузка: на десктопе две текстовые кнопки без рамок, на телефоне одна иконка,
открывающая тот же выбор Excel/PDF нижним листом (клик просто нажимает исходные
кнопки, поэтому `export.js` менять не пришлось).

### Дебаунс листания

Клик по стрелке обновляет подпись мгновенно, но период применяется через **350 мс**
после последнего клика (`APPLY_DEBOUNCE_MS`). Иначе быстрое пролистывание пяти
недель дало бы пять холодных OLAP-запросов при двух воркерах gunicorn.

Дополнительно [`analytics.js`](../static/js/dashboard/modules/analytics.js) нумерует
запросы (`_requestSeq`) и игнорирует ответ, если период уже сменился — быстрый
ответ из кэша иначе обгонял бы медленный холодный и рисовал не тот период.

### Незавершённый период

`progressBadge()` возвращает «прошло 3 из 7 дней». Отдельного бейджа в шапке нет
(макет), поэтому текст уходит в `title` подсказки диапазона.

Считается по **календарным** дням, сегодняшний день считается прошедшим целиком.
Это оценка для предупреждения, а не основа расчётов: план урезается сервером по
**взвешенным** дням (пт/сб = 2.0, [`core/day_weights.py`](../core/day_weights.py)),
поэтому доли расходятся — на коротких периодах заметно.

### Ключ периода

`period.key` = `YYYY-MM-DD_YYYY-MM-DD` (как `WeeksGenerator.period_to_key`).

Формат выбран так намеренно:
- совпадает с ключами недель из `/api/weeks` — `charts.js`/`trends.js` продолжают
  находить неделю по ключу;
- **не похож** на ключ плана (`YYYY-MM` или `venue_YYYY-MM`). Это критично:
  `POST /api/comments/<venue>/<key>` пишет комментарий в файл планов
  ([`routes/dashboard.py`](../routes/dashboard.py) `save_comment`), и ключ вида
  `2026-08` перезаписал бы боевой план;
- безопасен для имени файла экспорта (`core/export_manager.py`).

## Дизайн (редизайн 2026-08-11)

### Группы метрик — по типу показателя, 4 группы по 4

`METRIC_GROUPS` в [`config.js`](../static/js/dashboard/core/config.js).
Одна группировка на оба экрана:

| Группа | Метрики |
|--------|---------|
| Выручка | **Выручка**, розлив, фасовка, кухня |
| Чек и прибыль | Чеки, средний чек, прибыль, списания баллов |
| Структура | Доля розлива, доля фасовки, доля кухни, активность кранов |
| Наценка | **% наценки**, розлив, фасовка, кухня |

**Почему по типу, а не по направлению.** 16 делится на 4×4 без остатка, поэтому в
сетке из 4 колонок каждая строка заполнена целиком. При группировке по направлению
(розлив/фасовка/кухня по 3 метрики) справа оставалась пустая четверть ряда — экран
выглядел недоделанным. Побочная выгода: один тип показателя по всем направлениям
стоит в одном ряду, и розлив/фасовка/кухня сравниваются глазом.

Внутри группы **итог идёт первым** (Выручка, затем разбивка; % наценки, затем
разбивка). Порядок массива `METRICS` = порядок на экране.

`HEADLINE_METRIC_IDS` — выручка, чеки, средний чек: на мобильном они рисуются
крупно в блоке «Главное» и исключаются из аккордеонов, чтобы не дублироваться.

### Десктоп

- Группа = разделитель «НАЗВАНИЕ ——————» над сеткой карточек (плашек-заголовков нет).
  Справа в разделителе — **легенда шкал** «сейчас / было», одна на группу вместо
  подписи в каждой карточке: так на трек остаётся почти вся ширина карточки.
  Легенда появляется только у групп, где вторая шкала реально загрузилась.
- Карточка: название, значение, **две шкалы одной длины** — текущий период (акцент)
  и предыдущий (серый `--bar-prev`), у каждой процент справа. Внизу отклонение и план.
- Точки-индикатора на десктопе **нет**: статус несёт цветной процент выполнения.
  Отклонение — нейтральное: знак +/- уже показывает направление, а второй цвет на
  16 карточках превращал экран в рябь.
- Каретка раскрытия по сотрудникам — в правом ВЕРХНЕМ углу (снизу налезала на подвал).
- Hover: подъём на 2px и тень.

### Мобильный (≤768px)

- Карточка «Выполнение плана»: средний процент, шкала, светофор «N отстают /
  N близко / N в плане».
- «Главное» — выручка крупной карточкой, чеки и средний чек парой.
- «Показатели» — свёрнутые группы-аккордеоны с общим процентом группы
  (среднее по метрикам группы, у которых есть план). Метрики «Главного» в
  аккордеоны не попадают.
- Верхние вкладки скрыты, вместо них нижняя таб-панель (`.bottom-tabs`).
  Оба набора кнопок синхронизирует `main.js setupTabs`.
- Панель периода — три строки, **ничего не спрятано**: гранулярность во всю
  ширину, ниже стрелки с датой (тоже во всю ширину — иначе дата обрезается),
  ниже «Сегодня» и бейдж незавершённого периода. Клик по дате открывает календарь,
  как на десктопе.
- Бар и две круглые кнопки экспорта — одной строкой.

Обе версии разметки строятся из **одних** данных (`analytics.buildStats`) и
переключаются CSS (`.mv-desktop` / `.mv-mobile`), поэтому цифры совпадают
по определению.

### Единая высота контролов — обязательное условие

`--control-h: 44px` для селектора бара, кнопок гранулярности, стрелок, подписи
периода, «Сегодня» и кнопок экспорта. `.controls-row` выравнивает группы по
нижнему краю, поэтому любой контрол выше одной строки разводит подписи «Бар» и
«Период» по разным уровням. По этой же причине бейдж незавершённого периода лежит
ВНУТРИ строки панели, а не под ней.

**Ловушка специфичности.** В [`base.css`](../static/dashboard/styles/base.css) есть
правило `.controls-row .control-group:not(...)` — селектор из трёх классов. Оно
нужно другим вкладкам, использующим `.controls-row`, но по специфичности побеждало
однокласcовые `.control-group-period` / `.control-group-venue`: панель периода
получала ширину селектора бара, не влезала, `flex-wrap` рвал её на два ряда, и
подписи разъезжались по высоте. На мобильном то же правило (оно вне медиазапроса)
ставило период в строку с экспортом — кнопки наезжали на дату. Поэтому бар и период
исключены из него через `:not()`, а не переопределены.

### Предыдущий период

Вторая шкала грузится **отдельным запросом после** отрисовки текущего периода
(`loadPreviousPeriod`): пользователь видит цифры сразу, сравнение доезжает через
секунду. Предыдущий период = `shiftPeriod(period, -1)`, процент считается от
**его собственного** плана. Если запрос упал — вторая шкала просто не появляется.

## Как работает

### 15 метрик дашборда

Все метрики рассчитываются из ОДНОГО комплексного OLAP запроса (`get_all_sales_report`):

```python
# core/dashboard_analysis.py
def calculate_metrics(self, all_sales_data):
    # Разделяем по категориям на основе DishGroup.TopParent
    draft_records = []    # "Напитки Розлив"
    bottles_records = []  # "Напитки Фасовка"
    kitchen_records = []  # "ЕДА" (строго эта группа)
    other_records = []    # Всё остальное: НАБОРЫ, Чай/Кофе, Газ и Пэт, ...

    # Выручка по категориям (итог = все 4 категории)
    total_revenue = draft_revenue + bottles_revenue + kitchen_revenue + other_revenue

    # Доли категорий (%): 4 доли в сумме дают 100%,
    # на дашборде отображаются только розлив/фасовка/кухня
    draft_share = draft_revenue / total_revenue * 100
    ...

    # Чеки (уникальные заказы) и средний чек — по ВСЕМ записям
    total_checks = self._count_unique_orders(all_records)
    avg_check = total_revenue / total_checks

    # Наценка — агрегатом, как строка «Итого» в OLAP iiko:
    # (Σ выручка - Σ себестоимость) / Σ себестоимость
    draft_markup = self._calculate_markup(draft_records)
    ...
    avg_markup = self._calculate_markup(all_records)

    # Прибыль (маржа) — по всем 4 категориям
    total_margin = draft + bottles + kitchen + other

    # Списания баллов
    loyalty_points = self._sum_discounts(all_records)
```

### Категории (DishGroup.TopParent)

| Категория | Группы iiko 1-го уровня | Отображается |
|-----------|-------------------------|--------------|
| Розлив | Напитки Розлив | да |
| Фасовка | Напитки Фасовка | да |
| Кухня | ЕДА (строго) | да |
| Прочее | всё остальное: НАБОРЫ, Чай/Кофе, Газ и Пэт, ... | **нет** (only backend: `other_revenue`, `other_share`, `other_markup`) |

До 2026-07-16 «Кухня» включала всё, что не напитки (НАБОРЫ с наценкой ~500%
и Чай/Кофе ~800% завышали наценку кухни: 197% вместо честных 174% по ЕДЕ).

### Таблица метрик

| № | Метрика | Формула | Ед. изм. |
|---|---------|---------|----------|
| 1 | Выручка | Σ(DishDiscountSumInt) по всем записям | ₽ |
| 2 | Чеки | count(DISTINCT UniqOrderId.Id) | шт |
| 3 | Средний чек | Выручка / Чеки | ₽ |
| 4 | Доля розлива | Розлив / Выручка × 100 | % |
| 5 | Доля фасовки | Фасовка / Выручка × 100 | % |
| 6 | Доля кухни | Кухня (ЕДА) / Выручка × 100 | % |
| 7 | Выручка розлив | Σ(DishDiscountSumInt) для розлива | ₽ |
| 8 | Выручка фасовка | Σ(DishDiscountSumInt) для фасовки | ₽ |
| 9 | Выручка кухня | Σ(DishDiscountSumInt) для группы ЕДА | ₽ |
| 10 | % наценки | (Σ выручка − Σ Cost) / Σ Cost, все записи | % |
| 11 | Прибыль | Выручка - Себестоимость (все 4 категории) | ₽ |
| 12 | Наценка розлив | (Σ выручка − Σ Cost) / Σ Cost для розлива | % |
| 13 | Наценка фасовка | (Σ выручка − Σ Cost) / Σ Cost для фасовки | % |
| 14 | Наценка кухня | (Σ выручка − Σ Cost) / Σ Cost для ЕДА | % |
| 15 | Списания баллов | Σ(DiscountSum) | баллов |

**Наценка = агрегат, а не среднее построчных MarkUp.** Формула совпадает со строкой
«Итого» OLAP-отчёта iiko: строки с нулевой себестоимостью (позиции без техкарты)
участвуют выручкой в числителе. `calculate_metrics` возвращает наценку дробью
(2.2448 = 224.48%), округление до 4 знаков; фронт и месячный отчёт умножают на 100.

### Планы выручки

#### Пропорциональный расчёт

Планы хранятся как месячные значения, для произвольного периода рассчитываются пропорционально:

```python
# core/plans_manager.py:455-559
def calculate_plan_for_period(self, venue_key, start_date_str, end_date_str):
    # 1. Находим все месяцы в периоде
    months_data = self._get_months_in_period(start_date, end_date)
    # Returns: [(year, month, ratio), ...]

    # 2. Для каждого месяца берём пропорциональную долю
    for year, month, ratio in months_data:
        month_plan = self.get_monthly_plan(venue_key, year, month)

        # Абсолютные метрики (выручка, прибыль, чеки) суммируем пропорционально
        for metric in ['revenue', 'profit', 'checks']:
            result[metric] += month_plan[metric] * ratio

        # Относительные метрики (доли, наценки) усредняем с весом
        for metric in ['draftShare', 'markupPercent']:
            weighted_sums[metric] += month_plan[metric] * ratio

    # 3. Рассчитываем средневзвешенные относительные метрики
    if total_weight > 0:
        for metric in relative_metrics:
            result[metric] = weighted_sums[metric] / total_weight
```

### Тренды по неделям

#### Агрегация по неделям

```python
# core/trends_analyzer.py
def calculate_trend(self, daily_data, metric_field):
    """
    daily_data: {date: {metric: value, ...}, ...}
    Returns: {week_number: aggregated_value, ...}
    """
    weekly_data = {}
    for date_str, data in daily_data.items():
        week_num = datetime.fromisoformat(date_str).isocalendar()[1]
        if week_num not in weekly_data:
            weekly_data[week_num] = 0
        weekly_data[week_num] += data.get(metric_field, 0)

    return weekly_data
```

### Основная аналитика

```
POST /api/dashboard-analytics
Body: {
    "bar": "bolshoy" | "ligovskiy" | "kremenchugskaya" | "varshavskaya" | "all" | "",

```

> Имена полей — `bar`/`date_from`/`date_to` (snake_case). До 2026-08-11 в этом
> документе была указана неверная сигнатура `venue`/`dateFrom`/`dateTo`.

**Пустой период отдаёт нули, а не ошибку.** Закрытый день, будущая дата или день
без продаж возвращают HTTP 200 с нулевыми метриками, и результат кэшируется.
Ошибкой (500) остаётся только реальный сбой iiko. До 2026-08-11 пустой ответ
приравнивался к сбою: листание стрелкой упиралось в красную ошибку на любом дне
без продаж, и каждый клик шёл в iiko заново (пустое не кэшировалось).

Ограничения на длину периода нет. Замеры 2026-08-11 (бар «Все», холодный запрос,
полный путь эндпоинта включая расчёт метрик и активность кранов):

| Период | OLAP | Строк | JSON | Эндпоинт целиком |
|--------|------|-------|------|------------------|
| 1 день | 0.5 с | 346 | 0.2 МБ | 1.5 с |
| 1 неделя | 0.7 с | 1 971 | 0.9 МБ | 1.6 с |
| 1 месяц | 1.9 с | 9 106 | 4.1 МБ | 2.5 с |
| 1 год | 14.2 с | 81 435 | 36.6 МБ | 21.3 с |

Год укладывается в `gunicorn --timeout 180` и после первого запроса отдаётся из
кэша за 0.1 с. Разбивать год на месяцы не требуется. Память: ~78 МБ на
закэшированный годовой ответ (~176 МБ пик при разборе JSON).

### Метрики выручки

```
POST /api/revenue-metrics
Body: {
    "bar": "...",
    "date_from": "YYYY-MM-DD",     # диапазон, за который есть ФАКТ
    "date_to":   "YYYY-MM-DD",     #   (у незавершённого периода обрезан по сегодня)
    "period_from": "YYYY-MM-DD",   # границы ВСЕГО периода: к ним привязаны
    "period_to":   "YYYY-MM-DD"    #   план и горизонт прогноза
}
```

Разделение диапазонов нужно, чтобы «Ожидаемая» экстраполировалась до конца периода,
а «% выполнения» считался от плана за весь период — на любой гранулярности, не
только на месяце. Без `period_from`/`period_to` (старые открытые вкладки) полным
периодом считается календарный месяц `date_from`, как было раньше; на месячном
периоде обе ветки дают идентичные числа (проверено паритет-тестом).
