# Главный дашборд

## Что это

Основной дашборд системы с 20 метриками эффективности баров. Показывает выручку, доли категорий, наценку, прибыль, списания баллов, а с 2026-09-04 — чеки с картой лояльности и без карты за выбранный период.

Живёт на **`/dashboard`**. Главная страница сайта (`/`) с 24.08.2026 — личный
кабинет [`/me`](me.md); ссылка «Дашборд» в сайдбаре ведёт сюда.

## Выбор периода — шапка фильтров

### Один контрол

Одна полоса на всех вкладках ([`period_controls.js`](../static/js/dashboard/modules/period_controls.js),
[`filter_menus.js`](../static/js/dashboard/modules/filter_menus.js)):

```
[ Культура - Кременчугская ▾ | ‹  Неделя 32  3—9 авг ▾  › |        Excel  PDF ]
```

В строке ровно два выбора: заведение и период. **Переключателя гранулярности,
кнопки «Сегодня» и счётчика дней нет** — всё это живёт в выпадающем списке периода,
где выбор занимает один клик. Внутри полосы у контролов нет своих рамок: их
разделяют вертикальные линии, поэтому полоса читается как один элемент.

Подпись периода — это **название** («Неделя 32», «Август 2026», «III квартал 2026»)
плюс **какие это числа** («3—9 авг»). Для незавершённого периода подсказка
показывает прошедшую часть — ровно тот диапазон, за который на экране есть факт:
идущий месяц это «1—12 авг», закрытый — «июль».

### Список быстрого выбора

Клик по подписи открывает список. На десктопе — выпадашка 272px у подписи,
на телефоне — нижний лист во всю ширину (одна разметка, разные стили).

| Пункт | Период | Гранулярность |
|-------|--------|---------------|
| Сегодня | текущий день | day |
| Вчера | предыдущий день | day |
| Эта неделя | пн..вс текущей | week |
| Прошлая неделя | пн..вс предыдущей | week |
| Этот месяц | 1-е..последнее | month |
| Прошлый месяц | предыдущий целиком | month |
| Квартал | календарный квартал | quarter |
| Год | 01.01..31.12 | year |
| Свой период | календарь Flatpickr | custom |

**Гранулярность задаёт сам пресет**, отдельного переключателя нет: выбрал
«Прошлая неделя» — стрелки дальше листают неделями. Активный пункт подсвечивается
(`matchPreset` сверяет границы периода с пресетами).

### Шаг стрелки

| Гранулярность | Границы | Шаг |
|---------------|---------|-----|
| День | сам день | ±1 день |
| Неделя | пн..вс (ISO-8601) | ±7 дней |
| Месяц | 1-е..последнее число | ±1 календарный месяц |
| Квартал | янв-мар / апр-июн / июл-сен / окт-дек | ±3 месяца |
| Год | 01.01..31.12 | ±1 календарный год |
| Произвольный | как выбрано в календаре | ±длина периода |

Диапазон из календаря, совпавший с натуральными границами (например 01.08–31.08),
распознаётся как месяц — стрелки продолжают листать месяцами (`detectGranularity`).
Стрелка «вперёд» гаснет на текущем периоде: данных дальше нет.

**Клавиатура:** `←`/`→` листают период, `Esc` закрывает список.

### Дефолт — последняя ЗАВЕРШЁННАЯ неделя

`defaultPeriod()` в [`period_model.js`](../static/js/dashboard/core/period_model.js).
Причина: у незавершённой недели факт есть только за прошедшие дни, а план урезается
пропорционально всему периоду — процент выполнения выглядел бы провалом.

Период **не персистится**: дашборд всегда открывается на последней завершённой
неделе. До 2026-08-11 дефолт задавали три места (localStorage, `/api/weeks`,
datepicker), они перетирали друг друга и давали лишний OLAP-запрос на старте.

### Гранулярности по вкладкам

| Вкладка | Доступно | Почему |
|---------|----------|--------|
| Аналитика | все | `/api/dashboard-analytics` принимает любой диапазон, план считается пропорционально |
| Выручка | все | эндпоинт получает явные границы периода (`period_from`/`period_to`) |
| Планы | месяц, год | планы хранятся помесячно (`venue_YYYY-MM`); год = сумма месячных планов, только просмотр |
| Сравнение | выбор периода скрыт | у вкладки свои Период 1 / Период 2 |

Неприменимые пункты списка **гаснут**, а не исчезают: список не должен «прыгать»
при переключении вкладок. При переходе на вкладку, где текущая гранулярность
недоступна, период сам переключается на месяц, в который он попадал
(`snapToAllowedGranularity`).

### Заведение и выгрузка

Данные о заведениях по-прежнему держит **скрытый** `<select id="venue-selector">` —
его наполняет [`venue_selector.js`](../static/js/dashboard/modules/venue_selector.js),
он же владеет событием `change`. Список в шапке — только вид над ним: при выборе
он выставляет `select.value` и шлёт `change`. Так логика загрузки заведений не
задублирована.

Выгрузка: на десктопе две текстовые кнопки без рамок, на телефоне одна иконка,
открывающая тот же выбор Excel/PDF нижним листом (клик просто нажимает исходные
кнопки, поэтому `export.js` менять не пришлось).

### Дебаунс листания

Клик по стрелке обновляет подпись мгновенно, но период применяется через **350 мс**
после последнего клика (`APPLY_DEBOUNCE_MS`). Иначе быстрое пролистывание пяти
недель дало бы пять холодных OLAP-запросов при двух воркерах gunicorn.

Дополнительно [`analytics.js`](../static/js/dashboard/modules/analytics.js) нумерует
запросы (`_requestSeq`) и игнорирует ответ, если период уже сменился — быстрый
ответ из кэша иначе обгонял бы медленный холодный и рисовал не тот период.

### Незавершённый период

`progressBadge()` возвращает «прошло 3 из 7 дней». Отдельного бейджа в шапке нет
(макет), поэтому текст уходит в `title` подсказки диапазона.

Считается по **календарным** дням, сегодняшний день считается прошедшим целиком.
Это оценка для предупреждения, а не основа расчётов: план урезается сервером по
**взвешенным** дням (пт/сб = 2.0, [`core/day_weights.py`](../core/day_weights.py)),
поэтому доли расходятся — на коротких периодах заметно.

### Ключ периода

`period.key` = `YYYY-MM-DD_YYYY-MM-DD` (как `WeeksGenerator.period_to_key`).

Формат выбран так намеренно:
- совпадает с ключами недель из `/api/weeks` — `charts.js`/`trends.js` продолжают
  находить неделю по ключу;
- **не похож** на ключ плана (`YYYY-MM` или `venue_YYYY-MM`). Это критично:
  `POST /api/comments/<venue>/<key>` пишет комментарий в файл планов
  ([`routes/dashboard.py`](../routes/dashboard.py) `save_comment`), и ключ вида
  `2026-08` перезаписал бы боевой план;
- безопасен для имени файла экспорта (`core/export_manager.py`).

## Дизайн (редизайн 2026-08-11)

### Группы метрик — по типу показателя, 5 групп по 4

`METRIC_GROUPS` в [`config.js`](../static/js/dashboard/core/config.js).
Одна группировка на оба экрана:

| Группа | Метрики |
|--------|---------|
| Выручка | **Выручка**, розлив, фасовка, кухня |
| Чек и прибыль | Чеки, средний чек, прибыль, списания баллов |
| Структура | Доля розлива, доля фасовки, доля кухни, активность кранов |
| Наценка | **% наценки**, розлив, фасовка, кухня |
| Лояльность | Чеки с картой, чеки без карты, доля чеков с картой, выручка по картам |

**Почему по типу, а не по направлению.** 20 делится на 5×4 без остатка, поэтому в
сетке из 4 колонок каждая строка заполнена целиком (до 2026-09-04 было 16 = 4×4).
При группировке по направлению (розлив/фасовка/кухня по 3 метрики) справа
оставалась пустая четверть ряда — экран выглядел недоделанным. Побочная выгода:
один тип показателя по всем направлениям стоит в одном ряду, и
розлив/фасовка/кухня сравниваются глазом.

**Группа «Лояльность» стоит последней намеренно** (добавлена 2026-09-04): четыре
её метрики дописаны в конец `METRICS`, поэтому привычные места остальных 16 не
сдвинулись. Планов у этих метрик нет по замыслу первой версии (планы, настройки и
переключатели не заводились, пока не доказана нужда): карточка показывает подвал
«План не задан», в средний процент выполнения плана они не входят — он считается
только по метрикам с планом, а у аккордеона группы на мобильном вместо процента
стоит «—». С 2026-09-04 (4) четыре карточки лояльности раскрываются, как остальные
(входят в `EXPANDABLE_METRICS` и `EMPLOYEE_METRICS`): вкладка «Сотрудники» (ключи
из `_breakdown_row`) и секции метрики («Гости», «Дни», «Бары», «Карта» — набор
зависит от карточки), см. «Детали внутри карточки».
Наведение на название любой из четырёх метрик показывает формулу простым языком:
это `title` из поля `hint` в `config.js` (`hintAttr` в `analytics.js`, во всех
путях отрисовки — десктопная карточка, мобильные «Главное» и строки аккордеона).
Что именно считают эти метрики — раздел «Чеки с картой лояльности / без карты»
ниже.

Внутри группы **итог идёт первым** (Выручка, затем разбивка; % наценки, затем
разбивка). Порядок массива `METRICS` = порядок на экране.

`HEADLINE_METRIC_IDS` — выручка, чеки, средний чек: на мобильном они рисуются
крупно в блоке «Главное» и исключаются из аккордеонов, чтобы не дублироваться.
Метрики лояльности в «Главное» не входят.

### Десктоп (макет 7a)

Страница собрана из панелей одного уровня — шапка (76px), шапка фильтров (56px),
строка вкладок (56px), карточки. Ритм: 14px после шапки, 24px после фильтров,
16px после вкладок, 26px между группами, 12px от заголовка группы до сетки.

**Шкала радиусов — один радиус на уровень:**

| Уровень | Радиус | Что |
|---------|--------|-----|
| Панели и карточки | 14px | шапка, шапка фильтров, строка вкладок, карточка метрики, выпадающий список |
| Кнопки внутри панелей | 10px | стрелки периода, подпись периода, кнопки экспорта, пункты списка, кнопка меню |
| Таблетки и шкалы | 999px | вкладки, треки шкал, свотчи легенды |

- Заголовок группы — **только название и линия**. Легенда шкал «сейчас / было»
  стоит **один раз на страницу**, в строке вкладок, и появляется, когда
  догрузился предыдущий период.
- Строка вкладок: вкладки-таблетки, справа легенда, разделитель и «выполнение
  плана N%» словами (без плашки-бейджа).
- Карточка: строка заголовка (название + каретка раскрытия справа), значение 28px,
  две шкалы одной длины, подвал **отделён линией** — отклонение и план.
- Процент выполнения окрашен по **статусу плана**, отклонение — по **знаку**
  (плюс зелёный, минус красный). Это разные вопросы, поэтому цвета разные.
- Точки-индикатора на десктопе нет: статус несёт процент.
- Hover карточки: подъём на 2px и тень.

### Мобильный (≤768px)

- Карточка «Выполнение плана»: средний процент, шкала, светофор «N отстают /
  N близко / N в плане».
- «Главное» — выручка крупной карточкой, чеки и средний чек парой. Тап по
  карточке или строке аккордеона раскрывает разбивку по сотрудникам, как на
  десктопе (раздел «Разбивка карточки по сотрудникам»).
- «Показатели» — свёрнутые группы-аккордеоны с общим процентом группы
  (среднее по метрикам группы, у которых есть план; у группы без планов —
  «Лояльность» — вместо процента «—»). Метрики «Главного» в аккордеоны не
  попадают.
- Верхние вкладки скрыты, вместо них нижняя таб-панель (`.bottom-tabs`).
  Оба набора кнопок синхронизирует `main.js setupTabs`.
- Шапка фильтров — две строки (макет 6a): заведение и иконка выгрузки, ниже
  период со стрелками во всю ширину. Списки заведения, периода и выгрузки
  открываются нижним листом.

#### Где лежат стили каркаса и почему

Правила шапки фильтров и нижней таб-панели для `≤768px` живут в
[`base.css`](../static/dashboard/styles/base.css) (блок «МОБИЛЬНЫЙ КАРКАС» в
конце файла), а НЕ в `mobile.css`, где остался только адаптив контента.

Причина: каркас должен ехать вместе с разметкой. Если эти правила лежат в
отдельном файле и он не доехал до устройства (фильтр в сети, сбой загрузки,
блокировщик), телефон получает десктопную полосу — одна строка высотой 56px,
в которую содержимое не влезает: контролы вылетают за край на ~140px и наезжают
друг на друга. Потеря `mobile.css` теперь портит только вид карточек и таблиц,
но не управление страницей.

Там же два защитных свойства самой полосы: `min-height` вместо жёсткой `height`
и `flex-wrap: wrap` — если полоса окажется уже своего содержимого, она свернётся
в две строки, а не выпустит контролы наружу. Подсказка `.fb-hint` получила
`min-width: 0` с многоточием: flex-элемент с `white-space: nowrap` без этого не
отдаёт ни пикселя и распирает полосу изнутри.

**Ловушка каскада.** Скрытие верхних вкладок записано как `.container .tabs-nav`,
а не `.tabs-nav`: [`tabs.css`](../static/dashboard/styles/tabs.css) подключается
ПОСЛЕ `base.css` и задаёт `.tabs-nav { display: flex }`. При равной специфичности
победил бы он — прежде правило лежало в `mobile.css` и выигрывало по порядку
подключения. Проверяется тестом «мобильный каркас лежит в base.css».

Обе версии разметки строятся из **одних** данных (`analytics.buildStats`) и
переключаются CSS (`.mv-desktop` / `.mv-mobile`), поэтому цифры совпадают
по определению.

### Единая высота контролов — обязательное условие

`--control-h: 44px` для селектора бара, кнопок гранулярности, стрелок, подписи
периода, «Сегодня» и кнопок экспорта. `.controls-row` выравнивает группы по
нижнему краю, поэтому любой контрол выше одной строки разводит подписи «Бар» и
«Период» по разным уровням. По этой же причине бейдж незавершённого периода лежит
ВНУТРИ строки панели, а не под ней.

**Ловушка специфичности.** В [`base.css`](../static/dashboard/styles/base.css) есть
правило `.controls-row .control-group:not(...)` — селектор из трёх классов. Оно
нужно другим вкладкам, использующим `.controls-row`, но по специфичности побеждало
однокласcовые `.control-group-period` / `.control-group-venue`: панель периода
получала ширину селектора бара, не влезала, `flex-wrap` рвал её на два ряда, и
подписи разъезжались по высоте. На мобильном то же правило (оно вне медиазапроса)
ставило период в строку с экспортом — кнопки наезжали на дату. Поэтому бар и период
исключены из него через `:not()`, а не переопределены.

### Предыдущий период

Вторая шкала грузится **отдельным запросом после** отрисовки текущего периода
(`loadPreviousPeriod`): пользователь видит цифры сразу, сравнение доезжает через
секунду. Предыдущий период = `shiftPeriod(period, -1)`, процент считается от
**его собственного** плана. Если запрос упал — вторая шкала просто не появляется.

## Как работает

### Метрики дашборда — один OLAP-запрос

19 из 20 метрик рассчитываются из ОДНОГО комплексного OLAP запроса (`get_all_sales_report`); двадцатая — активность кранов — считается отдельно в `routes/dashboard.py` из `taps_manager` и в таблицу ниже не входит:

```python
# core/dashboard_analysis.py
def calculate_metrics(self, all_sales_data):
    # Разделяем по категориям на основе DishGroup.TopParent
    draft_records = []    # "Напитки Розлив"
    bottles_records = []  # "Напитки Фасовка"
    kitchen_records = []  # "ЕДА" (строго эта группа)
    other_records = []    # Всё остальное: НАБОРЫ, Чай/Кофе, Газ и Пэт, ...

    # Выручка по категориям (итог = все 4 категории)
    total_revenue = draft_revenue + bottles_revenue + kitchen_revenue + other_revenue

    # Доли категорий (%): 4 доли в сумме дают 100%,
    # на дашборде отображаются только розлив/фасовка/кухня
    draft_share = draft_revenue / total_revenue * 100
    ...

    # Чеки (уникальные заказы) и средний чек — по ВСЕМ записям
    total_checks = self._count_unique_orders(all_records)
    avg_check = total_revenue / total_checks

    # Наценка — агрегатом, как строка «Итого» в OLAP iiko:
    # (Σ выручка - Σ себестоимость) / Σ себестоимость
    draft_markup = self._calculate_markup(draft_records)
    ...
    avg_markup = self._calculate_markup(all_records)

    # Прибыль (маржа) — по всем 4 категориям
    total_margin = draft + bottles + kitchen + other

    # Списания баллов
    loyalty_points = self._sum_discounts(all_records)

    # Лояльность (2026-09-04): чеки и выручка с картой / без карты
    card_split = self._card_checks_split(all_records)        # уникальные заказы: {'card', 'nocard'}
    card_checks_share = card_checks / total_checks * 100      # 0, если чеков нет
    card_revenue_split = self.revenue_card_split(all_records) # тот же хелпер, что в месячном отчёте
```

### Категории (DishGroup.TopParent)

| Категория | Группы iiko 1-го уровня | Отображается |
|-----------|-------------------------|--------------|
| Розлив | Напитки Розлив | да |
| Фасовка | Напитки Фасовка | да |
| Кухня | ЕДА (строго) | да |
| Прочее | всё остальное: НАБОРЫ, Чай/Кофе, Газ и Пэт, ... | **нет** (only backend: `other_revenue`, `other_share`, `other_markup`) |

До 2026-07-16 «Кухня» включала всё, что не напитки (НАБОРЫ с наценкой ~500%
и Чай/Кофе ~800% завышали наценку кухни: 197% вместо честных 174% по ЕДЕ).

### Таблица метрик

| № | Метрика | Формула | Ед. изм. |
|---|---------|---------|----------|
| 1 | Выручка | Σ(DishDiscountSumInt) по всем записям | ₽ |
| 2 | Чеки | count(DISTINCT UniqOrderId.Id) | шт |
| 3 | Средний чек | Выручка / Чеки | ₽ |
| 4 | Доля розлива | Розлив / Выручка × 100 | % |
| 5 | Доля фасовки | Фасовка / Выручка × 100 | % |
| 6 | Доля кухни | Кухня (ЕДА) / Выручка × 100 | % |
| 7 | Выручка розлив | Σ(DishDiscountSumInt) для розлива | ₽ |
| 8 | Выручка фасовка | Σ(DishDiscountSumInt) для фасовки | ₽ |
| 9 | Выручка кухня | Σ(DishDiscountSumInt) для группы ЕДА | ₽ |
| 10 | % наценки | (Σ выручка − Σ Cost) / Σ Cost, все записи | % |
| 11 | Прибыль | Выручка - Себестоимость (все 4 категории) | ₽ |
| 12 | Наценка розлив | (Σ выручка − Σ Cost) / Σ Cost для розлива | % |
| 13 | Наценка фасовка | (Σ выручка − Σ Cost) / Σ Cost для фасовки | % |
| 14 | Наценка кухня | (Σ выручка − Σ Cost) / Σ Cost для ЕДА | % |
| 15 | Списания баллов | Σ(DiscountSum) | баллов |
| 16 | Чеки с картой | count(DISTINCT UniqOrderId.Id), у которых Delivery.CustomerCardNumber непусто хотя бы в одной строке | шт |
| 17 | Чеки без карты | Чеки − Чеки с картой | шт |
| 18 | Доля чеков с картой | Чеки с картой / Чеки × 100 (0 при нуле чеков), округление до 2 знаков | % |
| 19 | Выручка по картам | Σ(DishDiscountSumInt) по строкам с непустой Delivery.CustomerCardNumber | ₽ |

**Наценка = агрегат, а не среднее построчных MarkUp.** Формула совпадает со строкой
«Итого» OLAP-отчёта iiko: строки с нулевой себестоимостью (позиции без техкарты)
участвуют выручкой в числителе. `calculate_metrics` возвращает наценку дробью
(2.2448 = 224.48%), округление до 4 знаков; фронт и месячный отчёт умножают на 100.

### Чеки с картой лояльности / без карты (2026-09-04)

Просьба владельца: показать на дашборде число чеков с картой лояльности и без
карты — «похожая метрика есть в месячном отчёте». Там блок «Выручка карты/без
карт» ([monthly-report.md](monthly-report.md)) считается по ОТДЕЛЬНОМУ
OLAP-запросу `get_rfm_report`. Дашборд второго запроса не получил: в его
единственный запрос `get_all_sales_report` (`_build_all_sales_olap_request` в
[`core/olap_reports.py`](../core/olap_reports.py)) добавлено поле группировки
`Delivery.CustomerCardNumber` — карта лояльности на чеке (пусто, если карта не
проведена).

**Признак карты** — непустое после `strip()` значение поля в строке чека; пустая
строка, одни пробелы или отсутствующий ключ = без карты
(`DashboardMetrics.CARD_FIELD`).

| Ключ (API snake / фронт camel) | Формула |
|--------------------------------|---------|
| `card_checks` / `cardChecks` | число уникальных `UniqOrderId.Id`, у которых карта непуста **хотя бы в одной** строке (`_card_checks_split`) |
| `nocard_checks` / `nocardChecks` | `total_checks − card_checks` |
| `card_checks_share` / `cardChecksShare` | `card_checks / total_checks × 100`; 0 при `total_checks == 0`; округление до 2 знаков |
| `card_revenue` / `cardRevenue` | Σ `DishDiscountSumInt` по строкам с непустой картой (`revenue_card_split` — тот же хелпер, что в месячном отчёте), 2 знака |
| `nocard_revenue` / `nocardRevenue` | Σ `DishDiscountSumInt` по строкам с пустой картой; в ответе API есть, карточки на экране нет |

Инварианты: `card_checks + nocard_checks == total_checks` — чеки собираются по
тем же `UniqOrderId.Id`, что и `_count_unique_orders`, поэтому равенство держится
по построению; `card_revenue + nocard_revenue == total_revenue` с точностью
округления.

**Правило «любая строка».** Карта — атрибут заказа, во всех строках одного чека
она одинакова; правило нужно только для детерминированности. Если бы чек имел
пустую карту в одной строке и непустую в другой, он считался бы чеком С картой
(один раз), а его выручка резалась бы построчно. На живых данных таких чеков нет
(замер 2026-09-04 по всем барам: 0 случаев); в тестах случай закреплён явно.

**Замер 2026-09-04** — все бары, разовый скрипт вне репозитория (как в уроке
«Прогноз стоимости запроса — замерять»), один и тот же запрос до и после
добавления поля в `groupByRowFields`:

| Период | Строк OLAP | Выручка, ₽ | Чеков | JSON | OLAP |
|--------|------------|------------|-------|------|------|
| Неделя 24–30.08.2026 | 1 779 -> 1 779 | 1 208 387 -> та же | 843 -> 843 | 772 -> 839 КБ | 0,56 -> 0,81 с |
| Август 2026 | 7 744 -> 7 744 | 5 197 845 -> та же | 3 766 -> 3 766 | 3 356 -> 3 646 КБ | 1,71 -> 1,77 с |

Строки не размножились — поле уровня заказа, а не позиции (урок в
[lessons.md](lessons.md) «Поле уровня заказа в groupByRowFields не размножает
строки»); JSON вырос на 8–9%, время в пределах разброса iiko. Разбивка за неделю:
506 чеков с картой / 337 без, выручка 834 790 / 373 597 ₽. RFM-отчёт за ту же
неделю даёт ровно те же 506 / 337 и 834 790 / 373 597 ₽ — цифры дашборда
совпадают с «Выручка карты/без карт» месячного отчёта по построению. Заказов с
именем гостя, но без карты — 0, поэтому поле `Delivery.CustomerName` не
понадобилось.

### Разбивка карточки по сотрудникам (2026-09-04)

Клик по карточке раскрывает список «По сотрудникам» (метрики из
`EMPLOYEE_METRICS` в `analytics.js`; с 2026-09-04 (4) это вкладка внутри раскрытия,
есть у всех карточек, кроме активности кранов, — см. «Детали внутри карточки»).
На мобильном то же самое: крупная карточка и пара «Главного» и
строки внутри аккордеонов получают тот же `attachCardBehaviour`, каретка стоит в
подписи метрики (`m-caret`), раскрытая карточка пары занимает всю ширину. До
2026-09-04 (3) мобильные элементы рисовались без обработчика и на телефоне не
раскрывались.

**Источник данных — тот же, что у карточки.** `/api/employee-metrics-breakdown`
(`routes/employee.py`) берёт единый OLAP-запрос «Аналитики» из общего кэша
(`load_dashboard_sales` в `routes/dashboard.py`, TTL 10 мин, single-flight) и
раскладывает его строки по полю `AuthUser` («Авторизовал» — кто пробил чек):
`DashboardMetrics.calculate_metrics_by_employee` вызывает обычный
`calculate_metrics` на строках каждого сотрудника. Формулы общие, ответ iiko
один, поэтому сумма выручки, чеков, прибыли и списаний по сотрудникам равна
карточке по построению, а поле `total` ответа — буквально её числа. Поле
`AuthUser` добавлено в `groupByRowFields` запроса: у чека один автор, строки не
размножаются (замер 2026-09-04 по всем барам: неделя 1 779 -> 1 779 строк,
месяц 7 744 -> 7 744, выручка и чеки без изменений, JSON +8–9%, чеков с двумя
авторами 0, строк без автора 0).

До 2026-09-04 разбивка ходила в iiko четырьмя отдельными запросами
(`get_employee_aggregated_metrics` + розлив/фасовка/кухня по официантам) без
кэша: на открытом периоде список обгонял карточку на срок кэша, сбой любого из
четырёх (таймаут 30 с без ретрая) молча обнулял категорию, а раскрытие стоило
около 2 с. Теперь из кэша оно отвечает за миллисекунды. Замер до правки показал,
что арифметика двух путей и так сходилась до рубля; расходился экран.

**Что показывает список.** Топ-5 сотрудников по значению метрики, затем:

| Метрики | После топа | Что значит «Итого» |
|---------|------------|--------------------|
| Складываемые: выручка, чеки, выручка розлив/фасовка/кухня, прибыль, списания баллов (`ADDITIVE_METRICS`) | «Остальные (N)» = итог − показанные. Если скрытых нет, остаток в пределах «рубль на строку» — округление, строка не рисуется | сумма строк выше = карточка |
| Отношения: средний чек, доли, наценки | у каждой строки число чеков сотрудника | итог периода с карточки; подсказка в `title`: это не среднее строк, каждый сотрудник взвешен своей выручкой |

Итог берётся из `total` ответа, а не суммируется на клиенте: счётчики уникальных
(чеки) складывать нельзя, см. lessons.md. Отношения сортируются по значению, так
что техаккаунт с одним чеком (например, `itrestoran`, наценка 370%) может стоять
первым — число чеков рядом с именем показывает, что за этим ничего не стоит.

**Устаревший ответ.** `loadEmployeeData` запоминает ключ «бар + период» на старте
запроса и принимает ответ, только если ключ не изменился (как `_loadAnalyticsImpl`
со своим `seq`). Раньше клик по карточке и стрелка на соседний период в течение
двух секунд оставляли в кэше людей прошлого периода под карточкой нового. При
ошибке кэш сбрасывается, следующий клик повторяет запрос, пользователь видит
сообщение; пустой период раскрывается с «Нет данных», а не игнорирует клик.

### Детали внутри карточки (2026-09-04)

Просьба владельца: «внутрь каждой карточки добавить доп. информацию, например
при нажатии на карточку розлива — топ-5 сортов по проливам в литрах и процентах,
как на странице проливов». Клик по любой из 20 карточек теперь раскрывает
**вкладки-чипсы**: «Сотрудники» (прежняя разбивка, у всех карточек, кроме
кранов) и одна-четыре секции самой метрики. У доли розлива первой открывается
«Литры», у кранов — «Краны», у остальных — «Сотрудники» (`DEFAULT_TAB` в
`analytics.js`). Карточка кранов раньше уводила на `/taps`; теперь она
раскрывается, а переход живёт ссылкой «Открыть краны» внутри секции (решение
владельца 2026-09-04). На телефоне — та же разметка: полоса вкладок
прокручивается горизонтально, раскрытая карточка пары занимает обе колонки.

**Источник данных — тот же, что у карточки.** `POST /api/dashboard-card-details`
(`routes/dashboard.py`) берёт строки единого OLAP-запроса из общего кэша
(`load_dashboard_sales`, TTL 10 мин, single-flight) и считает секции чистыми
функциями [`core/dashboard_details.py`](../core/dashboard_details.py). Суммы,
чеки, маржа, наценка, скидки, локал/импорт и карта считаются **теми же хелперами
`DashboardMetrics`** на подмножествах тех же строк (`_sum_revenue`,
`_count_unique_orders`, `_sum_margin`, `_calculate_markup`, `_sum_discounts`,
`local_import_revenue`, `_card_checks_split`, `revenue_card_split`), а «Итого»
берётся из `calculate_metrics` по всем строкам. Новых обращений к iiko нет и
новых полей в запросе тоже: в строке уже есть `DishName`, `DishGroup.TopParent`,
`DishForeignName` (страна), `OpenDate.Typed`, `Store.Name`, `UniqOrderId.Id`,
`Delivery.CustomerCardNumber`, `AuthUser` и агрегаты.

Две секции считаются из других источников и грузятся **лениво** по клику на
вкладку (в общем ответе приходят заглушкой `lazy: true`):

| Секция | Источник | Почему отдельно |
|--------|----------|-----------------|

**Что показывает каждая карточка.** Строка = «название · доля% · подпись | значение»,
в списке не больше 5 строк, дальше «Остальные (N)» и «Итого». Топ считается по
значению секции; у «Дней» на периоде до 7 дней показываются все дни
хронологически.

| Карточка | Вкладки после «Сотрудники» | Формула строки (словами — она же под заголовком секции) |
|----------|----------------------------|----------------------------------------------------------|
| Выручка | Дни (с планом дня из `daily_plans.json`: «план N ₽ · M%»), Бары (только «Все заведения»), Категории (Розлив/Фасовка/Кухня/Прочее), Дни недели | выручка разреза = Σ `DishDiscountSumInt` его строк; среднее по дню недели = Σ таких дней / число таких календарных дней периода |
| Чеки | Дни, Бары, Дни недели | чеки разреза = уникальные `UniqOrderId.Id`; чек принадлежит одному дню и бару, сумма = карточка |
| Средний чек | Карта (с картой / без), Бары, Дни | выручка / чеки разреза; «Итого» — по всем чекам периода, не среднее строк |
| % наценки | Категории, Лидеры маржи (топ-5 позиций по марже ₽), Слабая наценка | наценка = (Σ выручка − Σ себестоимость) / Σ себестоимость × 100 агрегатом; в «Слабой наценке» только позиции с себестоимостью > 0 и выручкой ≥ 1% разреза, позиции без себестоимости — в заметке |
| Доля розлива | **Литры** (первая), Структура (4 категории) | литры кега = Σ `Amount.Out` проводок `SESSION_WRITEOFF`; доля = литры кега / литры всех кегов × 100 |
| Выручка розлив | Сорта (топ-5 по выручке, объёмы одного сорта сложены), Локал/импорт, Литры | сорт = название блюда без объёма и «с собой» (`extract_beer_info`: «ФестХаус Хеллес (0,5)» и «(0,3)» — один сорт); локал = страна «Россия» |
| Наценка розлив | Лидеры маржи (по сортам), Слабая наценка | как у «% наценки», по строкам розлива |
| Доля фасовки | По штукам (топ-5 по `DishAmountInt`), Локал/импорт, Структура | штуки позиции / штуки фасовки × 100 |
| Выручка фасовка | Позиции (топ-5 по выручке), Локал/импорт | выручка позиции = Σ строк фасовки с этим `DishName`; сумма = карточка |
| Наценка фасовка | Лидеры маржи, Слабая наценка | по строкам фасовки |
| Доля кухни | По порциям, Структура | кухня = строго группа «ЕДА» |
| Выручка кухня | Блюда (топ-5), Дни | по строкам «ЕДА» |
| Наценка кухня | Лидеры маржи, Слабая наценка | блюда без себестоимости (нет техкарты) — в заметке |
| Прибыль | Категории (маржа ₽ и доля), Позиции (топ-5 по марже по всем категориям), Бары | прибыль = Σ (выручка − себестоимость); новые ключи `draft_margin`/`bottles_margin`/`kitchen_margin`/`other_margin` в `calculate_metrics`, сумма = `total_margin` |
| Списания баллов | Категории, Позиции (топ-5 по сумме скидки, «% от цены» = скидка / (выручка + скидка)), Дни | списания = Σ `DiscountSum` — все скидки чека, как и карточка |
| Активность кранов | **Краны** (единственная вкладка): «Простаивали весь период: K из M», 5 кранов с наименьшим числом активных дней, ссылка «Открыть краны» | кран активен в день, если последнее событие до конца дня — `start` или `replace`; активность крана = активных дней / дней × 100 |

| Доля чеков с картой | Бары, Дни (5 худших дней) | с картой / все × 100 в разрезе |
| Выручка по картам | Гости (топ-5 карт по выручке), Карта (с картой / без), Бары | Σ `DishDiscountSumInt` строк с номером карты; сумма по картам = карточка |

**Инварианты.** У складываемых секций (`additive`) Σ строк + «Остальные» = «Итого»
по построению: остаток считается по уже округлённым значениям строк и итога
(`_rest_row`), а не как сумма скрытых, поэтому на экране тождество точное и
держится и когда часть строк никуда не отнесена (например, чеки без карты в
топе гостей). Если все значения целые (чеки, штуки), любой остаток реален и
рисуется всегда — строкой «Остальные (N)», а при отсутствии скрытых строк
«Без разбивки» / «Без даты»; отрицательный остаток — сигнал задвоения (чек
попал в два бара). У денег и литров строки округлялись, и остаток в пределах
«единица на строку» — шум округления, он не показывается. «Итого» складываемой
секции равно карточке (в единицах фронта: деньги и чеки до целого, доли и
наценки до 0,1, литры до 0,1). У отношений (средний чек, наценка, доля,
активность крана) «Итого» — значение карточки с подсказкой, что это не среднее
строк; нулевые строки у отношений — содержание (краны с нулём активных дней),
а у складываемых секций период без данных отдаёт пустые строки («Нет данных»),
а не список нулей. Секция, которую посчитать не удалось, приходит с `error`,
остальные секции карточки живут. У активности кранов все секции ленивые
(`LAZY_ONLY_METRICS`): общий запрос деталей не ходит в OLAP вообще, и краны
показываются даже при недоступном iiko.

**Поведение на экране.** Сотрудники рисуются сразу из клиентского кэша, секции
догружаются в уже раскрытую карточку (`loadCardDetails`) и принимаются, только
если бар и период не сменились и раскрыта всё ещё эта карточка; у карточек с
вкладкой по умолчанию (литры, краны) до прихода секций показывается «Загрузка…»,
а не сотрудники, которых тут же заменили бы. Один запрос на метрику и на ленивую
секцию: повторное раскрытие, пока ответ идёт, ждёт тот же промис
(`_detailsInflight`, `_lazyInflight`) — дубликатов на второй воркер gunicorn нет.
Клики внутри раскрытия не всплывают на карточку (иначе вкладка схлопывала бы
её); переключение вкладки не пересобирает полосу чипсов, прокрутка и фокус
остаются. Ленивая вкладка показывает «Загрузка…», при ошибке — «Не удалось
загрузить»; ошибка не запоминается, следующее раскрытие или клик по вкладке
пробует снова. Если не загрузились секции метрики, под списком сотрудников
стоит заметка «Детали карточки не загрузились», и следующее раскрытие повторяет
запрос. Выбранная вкладка помнится на сессию (`activeTab`); кэш деталей и
ленивых секций сбрасывается вместе с сотрудниками при смене бара, периода и по
«Обновить», а перерисовка сетки забывает раскрытую карточку. Формула секции
показана текстом под заголовком: подсказка в `title` на телефоне не работает.

#### Агрегация по неделям

```python
# core/trends_analyzer.py
def calculate_trend(self, daily_data, metric_field):
    """
    daily_data: {date: {metric: value, ...}, ...}
    Returns: {week_number: aggregated_value, ...}
    """
    weekly_data = {}
    for date_str, data in daily_data.items():
        week_num = datetime.fromisoformat(date_str).isocalendar()[1]
        if week_num not in weekly_data:
            weekly_data[week_num] = 0
        weekly_data[week_num] += data.get(metric_field, 0)

    return weekly_data
```

периоде обе ветки дают идентичные числа (проверено паритет-тестом).

### Планы

UI = единственный путь редактирования. См. подробнее [venues-plans.md](venues-plans.md).

```
GET    /api/plans/<venue>/<period>            — получить план
POST   /api/plans/<venue>/<period>            — создать/обновить план
DELETE /api/plans/<venue>/<period>            — удалить план
GET    /api/plans                             — дамп всех планов (JSON)
GET    /api/plans/calculate/<v>/<from>/<to>   — пропорциональный план за период
GET    /api/plans/export                      — экспорт всех планов в xlsx
GET    /api/plans/daily/<v>/<year>/<month>    — подневная разбивка (страница «Планы по дням»)
POST   /api/plans/daily/<v>/<year>/<month>    — задать override веса дня {date, weight}
DELETE /api/plans/daily/<v>/<year>/<month>/<date> — сброс override веса дня
```

> Подвкладка «Месячные» показывает **только плановые значения** (колонки Метрика | План).
> Факт и план/факт-сравнение живут на вкладках «Аналитика» и «Сравнение» — вкладка «Планы»
> отвечает только за просмотр и редактирование самих планов.
>
> Подвкладка «Планы по дням» (внутри вкладки «Планы») показывает подневную разбивку
> месячного плана и позволяет задать особый вес дня (праздник/закрытый день) с
> авто-ренормализацией остальных дней. Единый расчёт — `core/day_weights.py`.
> Подробнее: [venues-plans.md](venues-plans.md).

```

```

В Excel (openpyxl и CSV-фолбэк) и PDF (reportlab и HTML-фолбэк) после строки
«Списания баллов» идут четыре строки лояльности: «Чеки с картой (шт)», «Чеки без
карты (шт)», «Доля чеков с картой (%)», «Выручка по картам (₽)». Списки метрик
экспорта — `routes/dashboard.py` (`export_excel`, `export_pdf`) и
`core/export_manager.py` (`metric_names`); сравнение периодов
(`core/comparison_calculator.py`, `comparison.js`) знает те же четыре ключа.
Экспорт планов (`plans_export`) не менялся.

В PDF (reportlab и HTML-фолбэк) у метрик без плана — в том числе у четырёх
метрик лояльности — в колонках «План», «% плана» и «Разница» стоит «—», а не
0,00 и красный 0 %: как «План не задан» на экране. В Excel план такой метрики
записан числом 0.
