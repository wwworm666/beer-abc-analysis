## Что это

Менеджер пишет вопрос обычным языком: «какие сорта розлива хуже всего шли на Лиговском в сентябре»,
«средний чек по барам неделя к неделе», «сколько списали пива за месяц и почему». Агент сам
составляет OLAP-запрос к iiko, выполняет его и отвечает таблицей и коротким выводом.

Принцип тот же, что в июньском концепте: **числа — только из iiko и из документированных формул.**
Языковая модель понимает вопрос и оформляет ответ, но ничего не считает.

Как агент «составляет OLAP»: модель не пишет тело запроса с нуля. Она заполняет короткую заявку
(QuerySpec) из выверенного словаря показателей и разрезов, а тело OLAP собирает детерминированный
компилятор. Агент соберёт отчёт под любой вопрос в пределах словаря, но не может ошибиться в имени
поля, забыть фильтр удалённых блюд или неверно сложить чеки.

## Коротко

1. **Данных хватает.** OLAP v2 по продажам (SALES) и проводкам (TRANSACTIONS) закрывает основную
   массу вопросов; остатки, литры, списания, смены, персонал — отдельные методы (карта ниже).
   Сортировки, топ-N, условий «больше чем» и формул в OLAP нет — это делает наш код.
2. **Словарь — главный актив.** `GET /v2/reports/olap/columns` отдаёт все поля с русскими
   названиями как в iikoOffice, типом, флагами и категориями. Поверх него — выверенный словарь
   проекта: что значит «выручка», «чеки», «средний чек», что можно складывать и как.
3. **Три уровня свободы:** рецепты (многошаговые расчёты: литры, неделя к неделе, план/факт) ->
   композиция из словаря (основной режим) -> экспертный режим по живому каталогу полей (владелец).
4. **Сохранённые отчёты iikoOffice читаются по API** (`/v2/reports/olap/presets`): научить агента
   новому отчёту = собрать и сохранить его в iikoOffice.
5. **Где живёт агент.** Сначала — инструменты MCP-платформы (её строят сейчас, `core/mcp/`), а чат —
   приложение Claude у владельца: не нужен свой интерфейс, ключ API и счёт за токены. Затем — чат
   для менеджеров на сайте через Claude API (ключ, бюджет, проверка доступа к API с VPS в РФ).
6. **Главные грабли точности:** чеки нельзя складывать по блюдам, категориям и типам оплат (один
   чек попадает в несколько строк); средние и проценты пересчитываются из сумм; «вчера» — учётный
   день; удалённые блюда отсекаются двумя фильтрами; OLAP показывает только проданное.
7. **Половина фундамента уже есть:** снимки живого каталога полей лежат в репозитории (SALES —
   279 полей, TRANSACTIONS — 116), литры считаются по проводкам «Реализация товаров»
   (`core/draft_kegs.py`), движок метрик дашборда умеет выручку, чеки, наценку и скидки. Писать
   предстоит компилятор заявки в тело OLAP — общего сборщика тел в проекте нет.
8. **Первый шаг — этап 0:** список сохранённых отчётов iikoOffice, слоты лицензии, права и два
   маленьких запроса на живом iiko (нужно разрешение на чтение с прода).

## Что можно получить из iiko по API

Всё — iikoServer API (`https://host:port/resto/api`). iikoCloud API аналитики не даёт: по
документации он работает с заказами доставки, а OLAP был только в устаревшем iiko.biz API. Наш
сервис по отношению к iiko только читает — записей в iiko из `core/` и `routes/` нет.

| Область | Методы чтения | Какие вопросы закрывает | Оговорки |
|---|---|---|---|
| Продажи | OLAP SALES (v2); `reports/sales` (v1, выручка по дням) | Выручка, чеки, средний чек, количество, скидки, себестоимость, наценка — по барам, дням, часам, категориям, сортам, сотрудникам, оплатам | Основной источник агента |
| Склад: движение | OLAP TRANSACTIONS; `reports/storeOperations` (документы склада, XML); `reports/productExpense` (расход по продажам) | Литры, списания по причинам, приходы, перемещения, инвентаризационные расхождения | Литры — канон `core/draft_kegs.py`; `productExpense` в проекте не используется (нужен GUID подразделения) |
| Склад: остатки | `v2/reports/balance/stores?timestamp=` | Сколько пива на складе бара сейчас или на дату — в единицах и деньгах | Нулевые остатки не перечисляются |
| Деньги | `v2/reports/balance/counteragents?timestamp=`; кассовые смены `v2/cashshifts/list`, `v2/cashshifts/payments/list/{id}` | Долг поставщику, остаток на счёте; расхождение кассы, наличные и карты, внесения и изъятия по смене | `v2/cashshifts/closedSessionDocument` — GET, который может создать документ: агенту запрещён |
| Документы | Приходные накладные `documents/export/incomingInvoice` (XML); акты списания, перемещения, приказы о ценах `v2/documents/*` (JSON) | Что и почём закупили, последняя закупочная цена, кто и почему списал, когда меняли цену | У акта списания `cost` только для чтения и бывает пустым |
| Цены | `v2/price` (интервалы цены бар × позиция × размер), ценовые категории, расписания | Какая цена была на дату, каким приказом поставлена, happy hour | |
| Персонал | `employees`, `employees/search`, должности со ставками, оклады на дату, график, явки с оплаченными минутами и суммами | Кто работал, сколько часов, выручка на час персонала | У окладников суммы в явках пусты; дата «по» в графике и явках включительная |
| Журнал событий | `events`, `events/metadata` | Кто удалил позицию, отменил пречек, история заказа по номеру | Нужны модуль лицензии 2200 и право B_VTJ — есть ли у нас, проверить |
| Номенклатура и техкарты | `v2/entities/products/list`, группы, категории, шкалы; `v2/assemblyCharts/*`; `reports/ingredientEntry` | Справочник для сопоставления имён; из чего состоит порция; в какие блюда входит кега | Чтение номенклатуры требует права B_EN; по доке техкарты в API отдают «НЕ ТЕ значения, что отображаются в iikoOffice» (основные единицы) |
| Справочники | `v2/entities/list?rootType=PaymentType\|DiscountType\|OrderType\|…`, `v2/entities/accounts/list`, `corporation/*`, `suppliers` | Названия для сопоставления | `entities/list` по умолчанию включает удалённые; имена системных счетов зависят от `Accept-Language` — фиксировать заголовок |
| Отчёты владельца | OLAP-пресеты `v2/reports/olap/presets`; складские `reports/storeReportPresets` + `storeOperations?presetId=` | «Мой отчёт X за март» | |
| Контроль хранения | OLAP STOCK (v1, пресеты) | Просрочка на момент продажи (кухня) | |

**Чего по API нет:**

- Выгрузки проведённых инвентаризаций, актов реализации и приготовления, возвратных накладных —
  только загрузка; их движение видно косвенно через `storeOperations` и TRANSACTIONS.
- Изъятий за период одним списком (только по сменам), итоговой начисленной зарплаты (премии и
  штрафы — только проводки PENALTY/BONUS в OLAP), сумм платёжных ведомостей (только шапки).
- Прогноза и «причин»; план — только `reports/monthlyIncomePlan`, если план ведётся в iiko (наши
  планы живут в проекте).
- Продления токена в REST v1/v2: срок жизни «обычно 1 час» от входа.

**Даты и границы у методов разные**: `DD.MM.YYYY` в отчётах v1, `yyyy-MM-dd` в v2; граница «по»
исключающая у OLAP, событий и техкарт, включительная у кассовых смен, явок и графика. Это
зашивается в код рецептов, а не в промпт модели.

## Как устроен OLAP-запрос (выжимка для агента)

Полный справочник — [technical/OLAP_REPORT_BUILDING_RULES.md](technical/OLAP_REPORT_BUILDING_RULES.md);
здесь только то, от чего зависит устройство агента.

**Методы.**

| Метод | Что делает | Для агента |
|---|---|---|
| `GET /v2/reports/olap/columns?reportType=SALES\|TRANSACTIONS\|DELIVERIES` | Каталог полей: `FieldName`, русское имя из iikoOffice (`name`), тип, флаги `groupingAllowed` / `aggregationAllowed` / `filteringAllowed`, категории (`tags`). Устаревшие поля не выводятся | Основа словаря и валидатора |
| `POST /v2/reports/olap` | Построить отчёт по телу запроса | Единственный путь исполнения |
| `GET /v2/reports/olap/presets`, `/presets/{stock\|sales\|transactions\|deliveries}` | Сохранённые в iikoOffice отчёты (конфигурации) | Готовые отчёты владельца |
| `GET /v2/reports/olap/byPresetId/{id}?dateFrom&dateTo&summary` | Построить сохранённый отчёт | Не используем: iiko предупреждает, что формат конфигураций меняется при обновлении, и советует передавать конфигурацию из `/presets` в `/v2/reports/olap` |
| `GET /reports/olap?report=...&groupRow&agr&from&to` (v1) | Старый OLAP, ответ XML, **без фильтров** | Только для отчёта STOCK («Контроль хранения»); продажи через v1 не брать — нельзя отсечь удалённые блюда |

**Тело v2:** `reportType`, `buildSummary`, `groupByRowFields`, `groupByColFields`, `aggregateFields`,
`filters`. Больше ключей нет: сортировки, топ-N, пагинации, условий на агрегаты и вычисляемых
полей в запросе не бывает. Ответ: `data` — строки (группировки + агрегаты), `summary` — итоги,
только при `buildSummary=true` (с iiko 9.1.2 по умолчанию `false`).

**Фильтры** — три вида: по значению (`IncludeValues`/`ExcludeValues`, для ENUM и строк), по
диапазону (`Range`, для чисел), по дате (`DateRange`: `periodType` CUSTOM/TODAY/YESTERDAY/
CURRENT_WEEK/LAST_MONTH/…, `from`/`to`, `includeLow` по умолчанию true, `includeHigh` по
умолчанию false). Поле даты: SALES — `OpenDate.Typed` (учётный день), TRANSACTIONS —
`DateTime.DateTyped`.

**Типы отчётов.** SALES — строки заказов (блюдо в чеке): выручка, скидки, количество, чеки,
гости, себестоимость, время, официанты, оплаты. TRANSACTIONS — проводки: склад и деньги
(приход, расход, реализация, списания, перемещения, инвентаризации, ДДС, контрагенты).
DELIVERIES — доставка (у сети её нет). STOCK — контроль хранения (просрочка на момент продажи),
только v1 и пресеты. На нашем сервере живой `/columns` даёт 279 полей SALES (67 агрегируемых,
221 группируемое, 222 фильтруемых) и 116 полей TRANSACTIONS (19 агрегируемых) — в каталоге v1
документации их около 115 и 100. Снимки: `data/olap_all_fields.json` (SALES),
`output/kegs-2026-09-20/source-transaction-columns.json` (TRANSACTIONS, снят 2026-09-20),
`data/olap_stock_fields.json` (STOCK, 20 полей).

| `StartBalance.*`/`FinalBalance.*` — «тяжёлый запрос, рекомендуется запускать только ночью» | Предупреждение о нагрузке | olap-otchety-v1.md, каталог проводок | Агенту запрещены; остатки — `/v2/reports/balance/stores` |
| Токен занимает слот лицензии iikoAPIServer, `logout` освобождает | Лицензия | avtorizatsiya.md | Сейчас каждый `OlapReports()` логинится заново и выходит в `finally`; повтора на 401/403 в коде нет (июньский концепт ошибочно считал, что есть). Агенту — один токен на вопрос, `logout`, перелогин на 401, пауза на 403 |
| `includeHigh=false`: день `to` в отчёт не входит | Поведение по умолчанию | olap-otchety-v2.md:491 | Пользователь говорит включительно — компилятор прибавляет +1 день |

## Как работает: архитектура агента

```
вопрос
  -> [языковая модель]   понимает вопрос, заполняет QuerySpec (строгая JSON-схема),
                          при нужде уточняет «по выручке или в литрах?»
  -> [сопоставление]     «Лиговский», «вайнштефан», «разливное» -> точные значения iiko
  -> [валидатор]         поля по словарю и живому /columns, совместимость показателей
                          и разрезов, оценка размера ответа
  -> [компилятор]        QuerySpec -> одно или несколько тел OLAP v2 (+ предохранители)
  -> [исполнитель]       iiko (токен на вопрос, кэш, не больше 2 запросов одновременно)
  -> [постобработка]     формулы, сортировка, топ-N, «прочее», доли, сравнение периодов,
                          округление
  -> ответ                вывод + таблица + свёрнутый блок «Как считается»
                          (интерпретация, даты, фильтры, формулы, тело запроса, время данных)
```

Модель участвует только в первом и последнем шаге (понять вопрос, оформить ответ). Всё между
ними — обычный код с тестами: один и тот же QuerySpec всегда даёт одно и то же тело запроса и
одни и те же числа.

### Три уровня свободы

| Уровень | Что может модель | Когда | Надёжность |
|---|---|---|---|
| 1. Рецепт | Выбрать готовый расчёт и параметры | Многошаговое: литры, неделя к неделе, план/факт, выручка против часов персонала, «почему упала» | Максимальная: логика написана и протестирована |
| 2. Композиция из словаря | Собрать QuerySpec из выверенных показателей и разрезов | Любые срезы продаж и проводок — основной режим | Высокая: поля, формулы и правила сложения заданы словарём |
| 3. Экспертный режим | Любое поле из живого `/columns` с проверкой флагов | Исследование «а что если» — для владельца | Средняя: у поля нет выверенной семантики, ответ помечается |

Удачные запросы экспертного режима по журналу переносятся в словарь (уровень 2).

## Словарь (семантический слой)

Две части:

- **Автоматическая** — снимки `GET /v2/reports/olap/columns`. Они уже есть
  (`data/olap_all_fields.json` — SALES, `output/kegs-2026-09-20/source-transaction-columns.json` —
  TRANSACTIONS); перенести в `data/olap_agent/`, обновлять раз в неделю и после обновления iiko.
  Расхождение со словарём — запись в журнале, а не падение.
- **Выверенная** — Python-модуль проекта: ключ, поле iiko, русское имя, синонимы, роль
  (показатель/разрез), зерно (чек/строка), правило сложения, единица, оговорки, значение по
  умолчанию для неоднозначных слов. Новых зависимостей не нужно: в образе Python 3.10 без
  pydantic и jsonschema, проверка заявки пишется вручную, как в `core/mcp/spec.py`.

### Показатели (SALES)

| Ключ | Поле iiko | Слова пользователя | Сложение | Оговорка |
|---|---|---|---|---|

| `qty` | `DishAmountInt` | штук, порций, сколько продали | сумма | Единицы блюда (порции), **не литры** |
| `checks` | уникальные `UniqOrderId.Id` (считаем у нас) | чеков, заказов | уникальные | Канон дашборда (`core/dashboard_analysis.py`); `UniqOrderId.OrdersCount` — только если в группировке нет позиций; `OrderNum` — номер чека, не счётчик |
| `guests` | `GuestNum` | гостей | по чекам | Качество зависит от ввода на кассе — оговаривать |
| `cost` | `ProductCostBase.ProductCost` | себестоимость | сумма | Строки с нулевой себестоимостью участвуют выручкой (как в iiko) |
| `avg_check` | формула | средний чек | пересчёт | `revenue / checks` на итоговом зерне |
| `revenue_per_guest` | формула | на гостя | пересчёт | `revenue / guests` |
| `markup_pct` | формула | наценка | пересчёт | `(revenue − cost) / cost × 100` — канон дашборда, как строка «Итого» в iiko; колонку `ProductCostBase.MarkUp` не усредняем |
| `margin` | формула | маржа, валовая прибыль | сумма | `revenue − cost` |
| `discount_pct` | формула | доля скидок | пересчёт | `discount / (revenue + discount) × 100` — канон `core/employee_analysis.py` |

Фудкост (себестоимость в % от выручки) в проекте сейчас нигде не считается; если он нужен агенту,
формулу `cost / revenue × 100` сначала утверждает владелец.

### Разрезы (SALES)

| Ключ | Поле iiko | Слова | Зерно |
|---|---|---|---|
| `day` | `OpenDate.Typed` | по дням, вчера, в понедельник | чек |
| `weekday` | `DayOfWeekOpen` | по дням недели | чек |
| `hour` | `HourOpen` | по часам, в пик | чек |

| `bar` | `Store.Name` (как во всём проекте; совпадает с `Account.Name` в TRANSACTIONS) | бар, точка, ВО, Лиговский… | чек |
| `category1..3` | `DishGroup.TopParent/SecondParent/ThirdParent` | розлив, фасовка, еда; стиль пива (ThirdParent) | строка |
| `dish` | `DishName` | сорт, блюдо, позиция | строка |
| `employee` | `AuthUser` | бармен, кто пробил | чек (по уроку 2026-09-04 строки не размножает) |
| `pay_type` | `PayTypes` | оплата, нал, карта | несколько на чек |
| `discount_type` | `OrderDiscount.Type` (или `ItemSaleEventDiscountType`, как на /discounts, — выбрать при сборке словаря) | скидка, акция, Orderia | несколько на чек |

Сотрудник — `AuthUser`, а не `WaiterName` (пуст для продаж через стойку) и не `OrderWaiter.Name`
(размножает строки): так решено в проекте (docs/lessons.md, аудит OLAP #11). OLAP отдаёт имя, а
не id — связь со стабильным `employee_id` идёт через справочник сотрудников.

TRANSACTIONS (этап 2): день `DateTime.DateTyped`, склад/счёт `Account.Name` (не `Store` — iiko
оптимизирует только `Account.Name`), товар и его группы `Product.*`, тип проводки
`TransactionType` (списание `WRITEOFF`, реализация товаров `SESSION_WRITEOFF`, накладная
`INVOICE`, перемещение `TRANSFER`, инвентаризация `INVENTORY_CORRECTION` — коды из
kody-bazovykh-tipov.md), контрагент `Counteragent.Name`; меры `Amount.In/Out` (в единицах
товара — для кег это литры), `Sum.Incoming/Outgoing`.

Гостевые персональные поля (`Delivery.CustomerName/Phone`, `CardOwner`, номера карт) в словарь
не входят: для аналитики они не нужны, а в чат для менеджеров не должны попадать вовсе.

### Сопоставление имён

Серверный поиск по имени в iiko есть только у сотрудников, поставщиков, групп и терминалов
(регулярные выражения); товары, блюда, скидки и типы оплат — только через свои справочники.
Агенту в любом случае нужен локальный нечёткий поиск: он понимает транслит, сокращения и опечатки.

- **Бары** — `Store.Name` <-> ключи проекта (`core/venues_config.py`), синонимы: ВО = Большой, Лиг,
  Крем, Вар. В проекте три системы имён баров (OLAP, кассовые смены, GUID складов) — перед
  агентом свести в один модуль.
- **Категории** — значения `DishGroup.*` (розлив = «Напитки Розлив», фасовка = «Напитки Фасовка»,
  кухня = «ЕДА»; правило то же, что на /explorer).
- **Сорта и блюда** — нечёткий поиск по `DishName` из кэша номенклатуры: латиница/кириллица
  («вайнштефан» -> Weihenstephaner), объём в названии. Несколько кандидатов — агент переспрашивает
  со списком, а не выбирает сам.
- **Скидки, типы оплат, сотрудники** — значения из лёгких OLAP-запросов «список значений» (одна
  группировка за 90 дней), кэш на сутки.

## QuerySpec — что заполняет модель

```json
{
  "report": "SALES",
  "measures": ["revenue", "qty"],
  "rows": ["dish"],
  "columns": [],
  "filters": [
    {"field": "bar", "op": "in", "values": ["Лиговский"]},
    {"field": "category1", "op": "in", "values": ["розлив"]}
  ],
  "period": {"kind": "month", "value": "2026-09"},
  "compare": null,
  "post": {"sort": "revenue", "order": "asc", "limit": 10, "having": []},
  "mode": "normal",
  "interpretation": "Худшие 10 сортов розлива на Лиговском за сентябрь 2026 по выручке"
}
```

- `measures`, `rows`, `columns`, `filters.field` — перечисления (enum) из словаря: при строгой
  схеме модель физически не может вписать несуществующее поле.
- `values` — свободный текст; превращается в точные значения iiko на шаге сопоставления.
- `period` — не даты, а смысл: `yesterday`, `last_week`, `month`, `last_n_days`, явный диапазон.
  Даты вычисляет наш код (рабочие сутки бара до 06:00 МСК, ISO-неделя), в ответе они всегда явные.
- `compare`: `previous_period` (такой же длины сразу перед), `same_period_last_year`, явный диапазон.
- `post`: сортировка, топ-N и условия на показатели (`having`: «выручка больше 10 000 ₽») —
  выполняются у нас, не в iiko.
- `mode`: `normal`, `deleted` (удаления и отмены — предохранители инвертируются), `expert`.
- `interpretation` — фраза для пользователя «я понял вопрос так»; на расчёт не влияет.

## Компилятор: правила

1. Все поля заявки — из одного типа отчёта; вопрос на стыке продаж и склада — это рецепт
   (два запроса, соединение по дню и бару у нас).
2. Фильтр по дате ставится всегда: `OpenDate.Typed` (SALES) или `DateTime.DateTyped` (TRANSACTIONS),
   `from` — первый день, `to` — последний день +1 (граница исключается), `periodType=CUSTOM`.
   Относительные периоды iiko (`CURRENT_WEEK` и т.п.) не используем: даты считает наш код и
   показывает их в ответе.
3. Предохранители SALES: `DeletedWithWriteoff` и `OrderDeleted` = `NOT_DELETED`. В режиме
   `deleted` — наоборот, удалённые (`DELETED_WITH_WRITEOFF`, `DELETED_WITHOUT_WRITEOFF`) плюс
   поля причины и автора.
4. Формула — это её составляющие: `avg_check` превращается в `revenue` + `checks`, `markup_pct` —
   в `revenue` + `cost`. Средние и проценты iiko не запрашиваются.
5. Условия на показатели (`having`, «скидка больше 0») не уходят в iiko — применяются после.
6. Недели и месяцы — группировка по `day` и сборка у нас (ISO-недели, как на /explorer).
7. Чеки: если в заявке есть `checks` (или `avg_check`), в группировку добавляется
   `UniqOrderId.Id`, и число уникальных чеков считается у нас — по каждой строке результата и
   отдельно по объединению ключей для «итого». Так чеки верны для любого разреза, включая
   категории и сорта (канон дашборда; урок 2026-08-13 «уникальные счётчики не складываются»).
   Итог и его разбивка всегда берутся из одного ответа (урок 2026-09-04).
8. `compare` — второй запрос на период сравнения того же вида; объединение и разницы — у нас.
9. `buildSummary=false` по умолчанию; `StartBalance`/`FinalBalance` запрещены.
10. Оценка размера ответа: произведение числа значений разрезов (дни × бары × сорта…) по
    справочникам. Выше порога — отказ с предложением укрупнить («по неделям вместо дней») или
    сузить период.

## Правила точности

| Правило | Почему | Пример ошибки, которую оно предотвращает |
|---|---|---|
| Чеки не складываются между строками — только уникальные `UniqOrderId.Id` по объединению | Чек с пивом и едой попадает в обе категории; поля позиции размножают строки | «Чеков с розливом + чеков с едой» больше, чем чеков всего |
| Средние и проценты — всегда из сумм на итоговом зерне | Среднее средних неверно при разных весах | Средний чек за неделю как среднее семи дневных |
| Выручка = `DishDiscountSumInt` | Канон проекта; до скидки — отдельный показатель | Выручка с «виртуальными» деньгами скидок |
| «Вчера», «в понедельник» — учётный день (`OpenDate.Typed`); «сегодня» — рабочие сутки бара до 06:00 МСК (`core/msk_time.business_today`) | Так считает iikoOffice и весь проект | Ночные продажи уехали в следующий день |
| Частичный сбой — ошибка в ответе, а не нули | Аудит OLAP #18: сбой одного запроса сейчас местами молча превращается в нули | «Выручка Лиговского 0 ₽» вместо «iiko не ответил» |
| OLAP показывает только проданное | Позиции без продаж в ответе отсутствуют | «Худшие сорта» без тех, что не продались вовсе: нужен рецепт с ассортиментом (краны, номенклатура) |
| Порции — не литры | `DishAmountInt` в единицах блюда | «Продали 120 литров», когда это 120 бокалов разного объёма |
| Сегодняшний день не закрыт | Данные за открытую смену неполные | Сравнение «сегодня против вчера» в 15:00 без оговорки |
| Округление: деньги — до рубля в тексте (копейки в выгрузке), проценты — 1 знак, литры — 1 знак; деление на ноль — «—» | Прозрачность и воспроизводимость | Разные числа в двух ответах на один вопрос |

Правило про чеки уже проверено в проекте (урок 2026-08-13, дашборд считает уникальные
`UniqOrderId.Id`) — агент его наследует, а не открывает заново.

## Исполнитель и нагрузка на iiko

- Слой доступа проекта (`OlapReports.connect/disconnect`, повторы при сетевых сбоях). Сейчас
  каждый вызов логинится заново; агенту — один токен на вопрос (вся серия запросов), `logout`
  в `finally`, перелогин на 401 (токен живёт «обычно 1 час» от входа, продления в REST v1/v2
  нет), пауза и понятная ошибка на 403 (заняты слоты лицензии).
- Кэш `cached_olap` (`extensions.py`: single-flight, пустой ответ кэшируется, сбой — нет) по хэшу
  тела запроса: 10 минут, если период включает сегодня; сутки — для закрытых периодов
  (ретро-правки накладных и смен возможны — в ответе время данных). Закрытые месяцы по
  стандартным показателям — из `monthly_cache` без обращения к iiko.
- Порядок времени по замерам проекта (урок 2026-08-11): месяц — 1,9 с, год — 14 с (81 тыс. строк,
  37 МБ), бывают разовые выбросы до 63 с. Таймаут запроса агента — 120 с (gunicorn обрывает
  воркер на 180 с); пока iiko считает, пользователь видит статус.
- Не больше 2 одновременных запросов агента (флаг `heavy` в MCP-платформе ограничивает
  параллельные тяжёлые вызовы), лимит запросов в час на пользователя.
- Только чтение, белый список методов: `POST /v2/reports/olap` и перечисленные GET. Явно вне
  списка — `GET v2/cashshifts/closedSessionDocument/{id}` (по доке «возвращает существующий
  документ, либо создаёт новый») и `POST documents/check/incomingInventory` (в доке не сказано,
  что документ не сохраняется).

## Постобработка и формулы

Детерминированно, в таком порядке: сопоставление строк двух периодов -> формулы на итоговом
зерне -> условия `having` -> сортировка -> топ-N и строка «Прочее» (как на /explorer) -> доли от
итога (итог чеков — по объединению ключей того же ответа) -> разницы периодов (рубли и %)
-> округление. Каждая формула возвращается текстом с подставленными числами
(«Средний чек = 1 234 567 ₽ / 1 234 чека = 1 000 ₽») — для блока «Как считается».

## Рецепты

| Рецепт | Источник данных | Зачем отдельно |
|---|---|---|
| Литры пива по сортам и барам | Канон проекта: `Σ Amount.Out` проводок `SESSION_WRITEOFF` («Реализация товаров») по кегам с единицей «л» — `core/draft_kegs.py`, `core/draft_loader.py` | В SALES литров нет, а пересчёт порций по названию блюда занижает литры (разные форматы техкарт) |
| Остатки кег и фасовки | `/v2/reports/balance/stores` — `core/stock_snapshot.py`, как /stocks | OLAP-остатки тяжёлые; нулевые остатки balance не перечисляет, минус = пустая полка |
| Списания по причинам | TRANSACTIONS `WRITEOFF` по счёту списания; строки — акты `v2/documents/writeoff` | Деньги списаний надёжнее из OLAP: `cost` в акте только для чтения и бывает пустым |
| Неделя к неделе, месяц к месяцу | Два запроса SALES, выравнивание по дням недели | Сравнение и дельты |
| План/факт | Планы проекта + SALES | Плана в OLAP нет |
| Выручка против часов персонала | SALES по часам + кассовые смены (`v2/cashshifts/list`, как на /employee) или явки | Два источника |
| Цена на дату и кто её поменял | `v2/price` (интервалы цены бар × позиция × размер, ссылка на приказ) | Цены нет в OLAP как справочника |
| «Почему упала выручка» | Серия SALES: чеки × средний чек, по барам, категориям, часам | Разложение на факторы — детерминированное, без «причин» |
| Что не продаётся | Ассортимент (краны, номенклатура) минус SALES | OLAP не видит нулевые продажи |

## Сохранённые отчёты iikoOffice

Владелец собирает отчёт в iikoOffice («OLAP-отчёт по продажам» -> поля -> сохранить). Агент
видит его в `GET /v2/reports/olap/presets` и запускает по просьбе «мой отчёт X за март»: берёт
конфигурацию, подставляет даты и выполняет через `/v2/reports/olap` (так советует iiko — формат
сохранённых конфигураций может меняться при обновлениях). Сочетание клавиш Ctrl+Shift+F3 в
iikoOffice показывает параметры отчёта в терминах API. Пресеты же — готовые кандидаты в эталонные
вопросы и в синонимы словаря.

## Ответ пользователю

- **Видно сразу:** одна-две фразы с главным числом, таблица (до 20 строк, остальное — «Прочее» или
  выгрузка), единицы и подписи колонок, период явными датами.
- **Свёрнуто в «Как считается»** (правило проекта): как понят вопрос, фильтры, формулы с числами,
  тело OLAP-запроса, время данных, «как проверить в iikoOffice».
- **Предупреждения** — строкой под таблицей: «день не закрыт», «порции, не литры», «гостей
  вводят не всегда».
- Если срез совпадает с существующей страницей (/explorer, /discounts, /stocks) — ссылка на неё
  с теми же параметрами.

## Где живёт агент

Ядро (словарь, компилятор, исполнитель, постобработка) — одно. Каналов, через которые с ним
разговаривают, два; запускать по очереди.

### Канал A — MCP-платформа и приложение Claude (первый запуск)

MCP-платформа (`core/mcp/`, решение владельца 2026-09-27) открывает маршруты сервиса ИИ-клиентам:
приложение Claude на компьютере и телефоне, Claude Code, расписания Claude. Правило платформы —
инструмент вызывает тот же маршрут, что и страница. Агенту OLAP в домене `analytics` нужны:

| Инструмент | Маршрут | Что делает |
|---|---|---|
| `analytics_olap_catalog` | `GET /api/olap-agent/catalog` | Словарь: показатели, разрезы, синонимы, правила; поиск по живому `/columns` для экспертного режима |
| `analytics_olap_resolve` | `GET /api/olap-agent/resolve` | «Лиговский», «вайнштефан» -> точные значения iiko, при неоднозначности — кандидаты |
| `analytics_olap_query` | `POST /api/olap-agent/query` | QuerySpec -> вывод, таблица, формулы, тело запроса, предупреждения (`read_only`, `heavy`) |
| `analytics_olap_presets` | `GET /api/olap-agent/presets`, `POST /api/olap-agent/presets/<id>/run` | Отчёты, сохранённые в iikoOffice |

Рецепты этапа 2 — отдельными инструментами. Плюс сценарий (`PromptSpec`) «Вопрос по данным iiko»
с правилами: числа только из инструментов, всегда показывать интерпретацию и даты, при
неоднозначности — переспросить. По правилу покрытия платформы (`tests/test_mcp_coverage.py`)
каждый новый маршрут получает инструмент или запись в исключениях.

Почему первым:

- Не нужны свой чат, ключ API и счёт за токены — работает подписка владельца на Claude.
- Подключение идёт от Claude к нашему серверу, поэтому вопрос доступа к API Anthropic с VPS в РФ
  здесь не возникает.
- Существующие страницы (дашборд, /explorer, планы, остатки, KPI) и так станут инструментами
  платформы: часть вопросов закроется ими, OLAP-инструмент нужен для всего остального.

Ограничения:

- Платформа пока каркас (описание инструментов, права, база; моста, реестра и маршрутов `/mcp`
  ещё нет) — канал A заработает вместе с ней.
- Доступ только у владельца (политика платформы).
- Модель приложения может досчитывать сама — поэтому инструмент отдаёт готовые числа, таблицу и
  формулы, а инструкции домена запрещают собственную арифметику.
- Строгость схемы в MCP не гарантирована так, как в API, — сервер проверяет заявку и возвращает
  понятную ошибку, модель исправляется.

### Канал B — чат для менеджеров (страница /ask, затем Telegram-бот)

Бэкенд сам вызывает Claude API с теми же функциями-инструментами:

- Строгие схемы инструментов (`strict: true`, `additionalProperties: false`, перечисления из
  словаря) — поля заявки гарантированно из словаря.
- Системный промпт = правила + словарь, неизменная часть кэшируется (чтение из кэша стоит около
  0,1 обычной цены входных токенов).
- Цикл вызова инструментов — Tool Runner из Python SDK `anthropic` или свой цикл; вариант —
  MCP-коннектор Messages API (бета) прямо к нашему `/mcp/analytics`, тогда описания инструментов
  живут в одном месте.
- Доступ по аккаунтам сервиса, журнал «вопрос — заявка — запрос — ответ», лимиты на пользователя,
  кнопки «Верно»/«Неверно» под ответом.

Модель: по текущим рекомендациям Anthropic — `claude-opus-5` ($5 / $25 за 1 млн входных/выходных
токенов); `claude-sonnet-5` ($2 / $10) — вариант экономии, решение владельца и только если эталоны
показывают ту же точность. Грубая оценка по прайсу: 2-3 обращения к модели на вопрос, около 8 тыс.
токенов постоянной части (из кэша), 3-5 тыс. токенов результатов, 1,5-3 тыс. токенов ответа — около
$0,10-0,15 за вопрос на Opus 5 и $0,04-0,06 на Sonnet 5; 20 вопросов в день — порядка $60-90 в
месяц на Opus 5. Уточнить по журналу реальных вопросов.

До старта канала B проверить:

1. **Сетевой доступ к API Anthropic с прод-VPS.** Россия не входит в список стран, где Anthropic
   предоставляет API, а исходящий трафик VPS уже блокировался (история с Telegram); возможно,
   понадобится узел вне РФ.
2. **Бюджет и ключ.**
3. **Персональные данные.** Гостевые поля исключены из словаря; отправлять ли во внешний сервис
   имена сотрудников в разрезе «по барменам» — решение владельца.

## План

### Этап 0 — сверка с живым iiko (нужно разрешение на чтение с прода)

Многое проект уже выяснил сам: каталог полей, литры, правило про чеки, время ответа. Осталось
(короткий скрипт только на чтение, `logout` в конце, одна-две минуты):

1. `GET v2/reports/olap/presets` и `reports/storeReportPresets` — какие отчёты уже сохранены в
   iikoOffice (кандидаты в рецепты и эталоны).
2. Свободные слоты лицензии API (`licence/info`) — агент добавит свои входы к синхронизациям.
3. Есть ли модуль событий 2200 и право B_VTJ — от этого зависят вопросы «кто удалил».
4. Что на самом деле лежит в `SoldWithDish` (один день) — для вопросов «что берут вместе».
5. Доля строк продаж с нулевой себестоимостью по категориям (один день) — насколько можно
   верить наценке по сортам.
6. Свежий снимок `/columns` по SALES (дата текущего файла неизвестна).

### Этап 1 — MVP на продажах

- Словарь SALES (около 40 полей), сопоставление баров, категорий и сортов.
- QuerySpec, компилятор, исполнитель, постобработка; тесты «заявка -> тело запроса» без сети.
- Маршруты и три MCP-инструмента (`catalog`, `resolve`, `query`).
- 30 эталонных вопросов: ожидаемая заявка и число, сверенное в iikoOffice за закрытый период.
- Готово, когда эталоны проходят, а неделя вопросов владельца из приложения Claude не дала
  расхождений с iikoOffice.

### Этап 2 — склад и рецепты

- Словарь TRANSACTIONS; рецепты: литры, списания, остатки (через /stocks), неделя к неделе,
  план/факт, «что не продаётся»; сохранённые отчёты iikoOffice.

### Этап 3 — чат для менеджеров

- /ask (затем бот) на Claude API: доступы, журнал, лимиты, отметки «Верно»/«Неверно».
- Перед стартом — три проверки из раздела «Канал B».

### Этап 4 — по необходимости

- Витрина продаж (SQLite: день × бар × позиция × час): скорость и тяжёлые вопросы — что берут
  вместе, сезонность за годы.
- Регулярные сводки по расписанию Claude через тот же MCP.
