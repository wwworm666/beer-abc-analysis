# Авторизация

## Что это

Полноценный вход в приложение. Раньше auth-слоя не было вообще — все страницы и
все API были открыты любому, кто дотянулся до приложения. Теперь:

- **Личный аккаунт на каждого** (бармен / владелец), вход по логину и паролю.
- **«Вход один раз»**: долгая cookie-сессия (180 дней, скользящее продление).
  Плашка входа появляется только когда cookie нет или она протухла.
- После входа — **равные права** на все бизнес-страницы. Флагом `is_admin`
  ограничены: страница управления аккаунтами (`/admin/users`), доступ ИИ-агентов по MCP
  (страница `/admin/mcp` и сами MCP-токены — с 2026-09-27, [mcp.md](mcp.md)) и ручной
  прогон проверки открытия баров без пароля сервера (с 2026-09-27).
- **Явная привязка к сотруднику** (`employee_iiko_id`, v3): админ в `/admin/users`
  связывает аккаунт с сотрудником графика по стабильному id из iiko (выпадающий
  список). Раньше связь была неявной — по совпадению `display_name` с именем
  сотрудника, что хрупко при переименовании; теперь ключ — стабильный id.
  С 2026-08-13 по этой привязке работает личная страница `/me` (свои смены,
  показатели, KPI и деньги) — см. [me.md](me.md). Поэтому привязка стала
  **уникальной**: один сотрудник = один аккаунт (см. ниже).

Решения владельца (зафиксированы): личные аккаунты, у всех пароль, аккаунты
заводит владелец сам; единственное ограничение прав — управление аккаунтами
только для админа (чтобы бармен случайно не залочил вход).

## Как работает

### SECRET_KEY — «вход один раз»

Сессия живёт в подписанном cookie; стабильность ключа подписи критична — при его
смене все cookie становятся недействительными и всех разлогинивает.

`config.get_secret_key()` (приоритет):
1. env `SECRET_KEY` — для явного управления в проде;
2. persistent-файл `{/kultura|data}/secret_key` — генерируется **один раз** и
   переживает рестарты/редеплои (том `/kultura`). Именно он обеспечивает, что
   плашка входа не появляется на каждый заход;
3. если файла нет — сгенерировать и записать. Создание **эксклюзивное**
   (`O_EXCL`): гонку первого старта (2 gunicorn-воркера) выигрывает один,
   проигравший перечитывает уже записанный ключ.

Оба воркера читают один и тот же файл -> одинаковый ключ -> cookie валиден между
воркерами и переживает редеплой.

### Хранилище аккаунтов

`core/auth_manager.py`, SQLite `{/kultura|data}/auth.db` — отдельная база от
`shifts.db`. Пароли хранятся только как хэш (`werkzeug.security`,
`generate_password_hash`/`check_password_hash`). Схема additive (как в
`ShiftsManager`): миграции только `ALTER TABLE ADD COLUMN`, DROP запрещён.
Таблица (v3) `users(id, login UNIQUE COLLATE NOCASE, display_name, short_label,
employee_iiko_id, password_hash, is_admin, active, created_at, last_login_at)`.
`employee_iiko_id` (v3) — стабильный id сотрудника графика из iiko (привязка
аккаунт↔сотрудник; имя резолвится из реестра по id). WAL + `busy_timeout` под
2 воркера. Синглтон `get_auth_manager()`.

Поля аккаунта: **логин** (2-32 символа `[A-Za-z0-9_.-]`, регистронезависим),
**имя** (фамилия и имя, `display_name`), **сокращение** (`short_label`, типа «АН»,
до 12 символов — вводится **вручную**, без авто-генерации из имени: первые буквы
часто совпадают). Пароль не короче `MIN_PASSWORD_LEN` (4 — решение владельца).
Защита последнего админа: нельзя выключить / разжаловать / удалить единственного
активного админа.

**Атомарность инвариантов (cross-process).** `threading.Lock` сериализует только
внутри процесса, а в проде gunicorn 2 воркера = 2 процесса. Поэтому проверки
«последний админ» (`set_active`/`set_admin`/`delete_user`) и «первый владелец»
(`create_first_owner`) делают check+write в одной транзакции под `BEGIN IMMEDIATE`
(`_write_txn`): write-лок берётся сразу, второй воркер ждёт на `busy_timeout` —
два одновременных запроса не могут обойти инвариант (ни обнулить админов, ни
создать двух владельцев на first-run).

### Гейт (`init_auth(app)`)

- `SECRET_KEY` из `config`; cookie: `HttpOnly`, `SameSite=Lax`, `Secure` на проде
  (признак — наличие `/kultura`; переопределяется env `SESSION_COOKIE_SECURE`);
  `PERMANENT_SESSION_LIFETIME=180д`, `SESSION_REFRESH_EACH_REQUEST=True`
  (скользящее продление для активных).
- `ProxyFix(x_for=1, x_proto=1, x_host=1)` — Caddy терминирует TLS и проксирует по
  http на localhost; доверяем `X-Forwarded-*` ровно от одного прокси.
- Глобальный `before_request` (`_auth_gate`): **всё закрыто**, кроме
  `PUBLIC_ENDPOINTS`. Неавторизованный: на `/api/...` -> `401 {auth_required:true}`,
  на странице -> `302` на `/login?next=...`.
- `context_processor` отдаёт `current_user` в шаблоны.

Публичные эндпоинты (`PUBLIC_ENDPOINTS`, по именам эндпоинтов, а не путям):

| Эндпоинт | Почему без входа |
|---|---|
| `auth.login`, `auth.logout`, `auth.setup` | вход, выход, первичная настройка |
| `static`, `serve_manifest` | стили, скрипты, иконки, PWA-манифест |
| `misc.telegram_webhook_handler` | Telegram POST'ит без cookie |
| `taps.taplist_yml`, `taps.kitchen_yml`, `yml_feeds.kitchen_yml` | Яндекс забирает YML-фиды без cookie |
| `mcp.mcp_all`, `mcp.mcp_domain` | MCP-коннекторы `/mcp`, `/mcp/<раздел>` и адреса с режимом `/mcp[/<раздел>]/read`, `/mcp[/<раздел>]/draft` (с 2026-09-27, режимы — с 2026-09-28): у ИИ-клиента Claude нет cookie сайта. Коннектор **сам** проверяет `Authorization: Bearer` (`core/mcp/auth.py`): нет токена — 401 с `WWW-Authenticate`, по которому приложение Claude находит сервер авторизации; токен действует, только пока его владелец — активный администратор. Более глубокий путь под `/mcp` — 404 JSON, а не перенаправление на вход |
| `mcp_oauth.protected_resource_metadata`, `mcp_oauth.authorization_server_metadata`, `mcp_oauth.register_client`, `mcp_oauth.token`, `mcp_oauth.revoke` | OAuth 2.1 для приложения Claude: метаданные, регистрация клиента, выдача и отзыв токена по спецификации открыты без входа (секреты — код с PKCE и токены, а не сессия) |

Сознательно **не** публичны: страница согласия OAuth `mcp_oauth.authorize` (гейт отправит
анонима на `/login?next=…`; согласие даёт только активный администратор) и страница
`/admin/mcp` с её API. Это закреплено тестом `tests/test_mcp_coverage.py`
(`test_public_endpoints_for_mcp`). Если убрать MCP-эндпоинты из списка, гейт ответит на них
401 `{auth_required}` без `WWW-Authenticate`, и приложение Claude не сможет подключиться.

Всё остальное — за гейтом, включая PWA-виджет (`/dashboard/widget`), который работает после
входа (PWA делит cookie-jar браузера).

**MCP-агент и гейт.** Вызов инструмента MCP исполняет обычный маршрут сайта внутри процесса:
мост (`core/mcp/bridge.py`) кладёт в `g._current_user` копию записи владельца токена с
`via_mcp: True` и режимом подключения `mcp_mode`, и гейт, `current_user()` и `admin_required`
видят владельца. Логин не меняется. Перед каждым исполнением мост заново проверяет, что владелец —
активный администратор.

### Потоки входа

- **First-run**: пока в системе 0 аккаунтов, `/login` уводит на `/setup` —
  создание первого владельца (admin). После — `/setup` недоступен.
- **/login** (логин+пароль), **/logout**.
- `next` после входа проходит через `_safe_next` (защита от open-redirect):
  только локальные пути `/...`, не `//`, не схема; с 2026-09-28 целиком
  отклоняются строки с управляющими символами (код ниже 0x20 и DEL) и обратной
  косой `\` — тогда вход ведёт на `/`. Причина: браузер и `urlsplit` выбрасывают
  табуляцию и перевод строки, и `/<TAB>/evil.example` превращался в
  `//evil.example` — переход на чужой сайт сразу после входа. Через этот вход идёт
  OAuth-согласие MCP (`/login?next=/oauth/authorize?...`), поэтому дыру нашла
  проверка безопасности MCP. Закодированный адрес согласия
  (`redirect_uri=https%3A%2F%2F...`) проходит как есть. Тест
  `test_safe_next_rejects_control_chars_and_backslash`.
- Без `next` вход уводит на `/`, а `/` — это 302 на `/me`: после логина человек
  попадает в свой личный кабинет (см. [me.md](me.md)).

### Управление аккаунтами (`/admin/users`, только админ)

| Метод | Путь | Что делает |
|-------|------|-----------|
| GET | `/admin/users` | страница: список + форма создания |
| GET | `/api/auth/users` | список аккаунтов (без хэшей) |
| POST | `/api/auth/users` | создать (login, display_name, short_label, password, is_admin) |
| POST | `/api/auth/users/<id>/profile` | изменить имя и/или сокращение |
| POST | `/api/auth/users/<id>/employee` | привязать к сотруднику графика (employee_iiko_id; пусто = отвязать) |
| POST | `/api/auth/users/<id>/password` | сбросить пароль |
| POST | `/api/auth/users/<id>/active` | вкл/выкл аккаунт; выключение отзывает доступ его ИИ-агентов (ниже) |
| POST | `/api/auth/users/<id>/admin` | выдать/снять админа; снятие отзывает доступ его ИИ-агентов |
| DELETE | `/api/auth/users/<id>` | удалить аккаунт; доступ его ИИ-агентов отзывается |

**Отзыв доступа ИИ-агентов (с 2026-09-28, `_revoke_agent_access` в `routes/auth.py`).** При
удалении аккаунта, его выключении и снятии флага администратора маршрут отзывает все его
MCP-токены (`core.mcp.tokens.revoke_all_for_user`) и все OAuth-подключения
(`core.mcp.oauth.revoke_all_for_user`: гранты, токены и неиспользованные коды). Токены и так
перестают работать (доступ к MCP только у активного администратора, проверка на каждом вызове),
но без отзыва возврат флага оживил бы старые токены. Ошибка отзыва не ломает основное действие:
оно уже выполнено, а токены не пройдут проверку, пока аккаунт не активный администратор. Отзыв
делают только эти маршруты: флаг, поменянный мимо них (прямо в `auth.db`), токены лишь
приостанавливает.

`display_name` подсказывается из реестра графика (datalist) — чтобы совпадал с
именем в сменах.

**Один сотрудник = один аккаунт (с 2026-08-13).** По привязке личная страница
`/me` отдаёт человеку его смены, показатели и ЗАРПЛАТУ, поэтому два аккаунта на
одном `employee_iiko_id` означают, что кто-то видит чужие деньги — причём без
всяких признаков ошибки. `set_employee_link` отклоняет привязку второго аккаунта
к занятому сотруднику; проверка и запись — в одной транзакции под
`BEGIN IMMEDIATE` (как инварианты «последний админ» и «первый владелец»), иначе
два воркера привязали бы двоих одновременно. Отвязка проверок не проходит: снять
привязку можно всегда.

`UNIQUE INDEX` для этого сознательно НЕ используется: в проде мог уже лежать
дубль, а `CREATE UNIQUE INDEX` в `_init_database` упал бы на старте и обрушил
вход всем (DROP в проекте запрещён). Вместо него — `find_duplicate_employee_links()`:
строка в логе при старте `AuthManager` и баннер на `/admin/users`. Плюс страховка
на чтении: при двух активных аккаунтах `/me` не показывает деньги вовсе
(статус `ambiguous_link`), то есть уже существующий дубль перестаёт быть тихим.

`POST /api/auth/users/<id>/employee` дополнительно проверяет, что такой сотрудник
есть в реестре графика (эндпоинт принимал любую строку, хотя список в форме
фильтрованный). Проверка в роуте, а не в `AuthManager`: менеджер работает только с
`auth.db`, и тащить в него `shifts.db` связало бы две независимые базы. Если реестр
недоступен, проверка пропускается — недоступность графика не должна лишать админа
управления аккаунтами.

Выпадающий список показывает тёзкам хвост id (`Иванов Иван · id ...9c1f7a`),
полный GUID в `title` и пометки «не в реестре» / «скрыт»: при двух карточках iiko
с одинаковым ФИО без этого админ физически не различал опции.

### Доступ агентов (`/admin/mcp`, только админ, с 2026-09-27)

Страница управления доступом ИИ-агентов владельца по MCP (пункт меню «Доступ агентов» рядом с
«Аккаунты», виден только администратору). Всё устройство — [mcp.md](mcp.md), пошагово для
владельца — [guides/mcp-connect.md](guides/mcp-connect.md).

| Метод | Путь | Что делает |
|-------|------|-----------|
| GET | `/admin/mcp` | страница: коннекторы, выпуск токена, токены, OAuth-приложения, журнал, настройки |
| GET / POST | `/api/admin/mcp/tokens` | список статических токенов / выпуск (токен показывается один раз) |
| DELETE | `/api/admin/mcp/tokens/<id>` | отозвать токен |
| GET | `/api/admin/mcp/grants` | подключённые OAuth-приложения (приложение Claude, расписания) |
| DELETE | `/api/admin/mcp/grants/<client_id>` | отключить приложение: все его токены гаснут |
| GET | `/api/admin/mcp/audit` | журнал вызовов инструментов |
| GET / PUT | `/api/admin/mcp/settings` | чат Telegram для отчётов агентов, разрешённые хосты OAuth |

Все маршруты — `@admin_required`, и все исключены из MCP (агент не управляет доступом к себе).
Правило доступа агентов: MCP-токен действует, только пока его владелец — существующий
**активный администратор**; проверка на каждом вызове. Выключение аккаунта, снятие флага
администратора и удаление через `/admin/users` ещё и отзывают все его токены и OAuth-подключения
(см. «Отзыв доступа ИИ-агентов» выше): вернули флаг — нужен новый токен. Отдельный токен или
приложение отзываются кнопками «Отозвать» / «Отключить» на `/admin/mcp`. В списке токенов
действующий токен неработающего владельца показан «владелец отключён», «владелец не админ» или
«владелец удалён». У токена есть режим доступа (полный, чтение и черновики, только чтение) —
см. [mcp.md](mcp.md), «Режимы доступа».

Создание и удаление аккаунтов, пароли, флаги администратора и активности, а с 2026-09-28 и
привязка аккаунта к сотруднику (от неё зависит, чью зарплату человек видит на `/me`) агенту не
открыты (исключения MCP с причиной «управление доступом остаётся только в интерфейсе»). Открыты
список аккаунтов, имя и сокращение — это данные, а не доступ.

### Ручной прогон проверки открытия баров (`POST /api/admin/open-check/run-now`)

Маршрут за общим гейтом (не публичный). С 2026-09-27 активный администратор — вошедший на
сайт или его MCP-агент — проходит **без** пароля сервера; остальным вошедшим нужен заголовок
`X-Remote-Pass: <REMOTE_PASS>`. Причина: весь интерфейс открыт владельцу по MCP, а пароль из
`.env` агенту не передаётся. Проверено на голом Flask с гейтом:

| Кто | Ответ |
|---|---|
| без входа, даже с верным `X-Remote-Pass` | 401 `{auth_required}` от гейта |
| вошедший не-админ без пароля | 403 `forbidden` |
| вошедший не-админ с верным паролем | 200, прогон |
| вошедший активный админ (или его MCP-агент) | 200, прогон |
| `REMOTE_PASS` не задан, не-админ | 503 |

Прогон рассылает сообщения людям — подробности в [open-check-bot.md](open-check-bot.md).

### Безопасность (осознанная позиция)

- **CSRF**: отдельных токенов нет; защита — `SameSite=Lax`, при которой браузер не
  шлёт cookie на кросс-сайтовые POST/PUT/DELETE. Для внутреннего инструмента
  достаточно. `/logout` — GET, но единственный его эффект (выход) для CSRF
  безвреден.
- **Пароли** — только хэш; `verify_credentials` не раскрывает, что именно неверно.
- **Неактивный/удалённый юзер с живой сессией**: при следующем запросе гейт видит
  `active=0`/отсутствие и рвёт сессию.
- **Сброс пароля НЕ убивает старые сессии** (сессия живёт до 180 дней). Чтобы
  немедленно выкинуть человека (увольнение, утечка), **выключи его аккаунт**
  (`/admin/users` -> «Выключить») — это рвёт его сессию на следующем запросе; при
  необходимости потом включи обратно с новым паролем. Сброса пароля одного для
  отзыва доступа недостаточно.
- **Нет ограничения попыток входа и мин. длина пароля 4** — осознанный принятый
  риск (внутренний инструмент за Caddy/HTTPS, доверенная команда, логины не
  публичны). При желании усилить — поднять `MIN_PASSWORD_LEN` и добавить
  rate-limit на `/login`.
- Приложение прикрыто на сетевом уровне (Selectel VPS + Caddy); auth — второй слой.
- **ИИ-агенты по MCP** (с 2026-09-27) ходят не по cookie, а по Bearer-токену: статическому
  (Claude Code) или OAuth (приложение Claude). Токены хранятся только как sha256, действуют
  только у активного администратора, все вызовы пишутся в журнал `/admin/mcp`. Чтобы немедленно
  отрезать агента — отозвать токен или отключить приложение на `/admin/mcp`; выключение аккаунта,
  снятие админа и удаление через `/admin/users` отзывают все его токены и подключения.
  Задачи по расписанию подключаются в режимах «Только чтение» или «Чтение и черновики» — тогда
  сервер сам не исполнит утверждение, отправку и удаление ([mcp.md](mcp.md)).

## Деплой

- Том `/kultura` хранит `auth.db` и `secret_key` — переживают редеплой (код
  запекается в образ, данные — на томе).
- **Первый вход**: открыть `/login` -> форма создания владельца. Либо
  автоматизировать через env `AUTH_BOOTSTRAP_LOGIN` / `AUTH_BOOTSTRAP_PASSWORD`
  (+ опционально `AUTH_BOOTSTRAP_NAME`) — создаст admin на первом старте.
- `SECRET_KEY`: можно задать в `.env` для явного контроля; иначе генерируется в
  `/kultura/secret_key` один раз. **Не ротировать** без причины — разлогинит всех.
