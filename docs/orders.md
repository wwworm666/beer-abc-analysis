# orders.md — Заказы поставщикам (`/api/orders/*`)

> Этап 1 редизайна страницы «Заказы и остатки»
> ([docs/planning/stocks-order-redesign-2026-09-10.md](planning/stocks-order-redesign-2026-09-10.md)).
> Заказ стал серверной сущностью: общий черновик на всех управляющих, «Отправлено»,
> «Приехало», автоматическое «Оприходовано» по накладным iiko, текст для чата и вычет
> «в пути» из рекомендации. Интерфейс — вкладка «К отправке» и колонка «Заказ» на
> экране «К заказу» страницы `/stocks` (см. [stocks.md](stocks.md)).

## Что это

До этапа 1 корзина заказа жила в памяти вкладки браузера: терялась при перезагрузке,
не была видна коллегам, результатом был CSV, а назавтра страница снова просила то, что
уже заказано. Теперь:

| Понятие | Что это | Где живёт |
|---|---|---|
| Черновик | Позиции к заказу по поставщику по всем барам сразу; один на сеть, редактируют все три управляющих; помнит автора и время последней правки | `drafts[supplier]` в `orders.json` |
| Заказ | Черновик после нажатия «Отправлено поставщику»: состав, кто и когда отправил, ожидаемая дата поставки | `orders[]` в `orders.json` |
| «В пути» | Количество по открытым заказам (`sent`, `received`), ещё не оприходованное в iiko; вычитается из рекомендации, чтобы не заказать второй раз | считается из `orders[]` |
| Текст заказа | Готовое сообщение в чат поставщику: по барам, «название — количество единица», ожидаемая дата | генерируется из черновика/заказа |

Пока все поставщики принимают заказ в чате (решение владельца 2026-09-10); канал
заказа (сайт, телефон) отложен на самый конец.

## Как работает

### Модель

```
drafts[supplier] = {supplier, updated_at, updated_by,
                    items: {"<product_id>|<bar>": {product_id, bar, name, unit, kind,
                            qty, recommended, updated_at, updated_by}}}
orders[]         = {id, supplier, status, items: [{product_id, bar, name, unit, kind, qty,
                    received_qty?, posted_at?}],
                    sent_at, sent_by, sent_by_name, expected_at, note?,
                    received_at?, received_by?, posted_at?, cancelled_at?, cancelled_by?}
```

- Ключ позиции черновика — `product_id|bar`: одна и та же позиция для двух баров — две
  строки одного сообщения поставщику.
- `bar` всегда конкретный (из `extensions.BARS`): заказ приезжает на склад бара. В режиме
  «Общая» инпуты «В заказ» заблокированы, `draft_qty` показывается как сумма по барам.
- `qty <= 0` (в том числе пустое поле, мусор, NaN) удаляет позицию; пустой черновик
  поставщика исчезает целиком.
- `id` заказа: `ord-YYYYMMDD-xxxxxx` (дата отправки + 6 hex).
- Автор (`updated_by`, `sent_by`, ...) — логин из `core.auth_guard.current_user()`,
  `sent_by_name` — отображаемое имя; без сессии — `unknown`.

### Статусы заказа

```
sent ──(«Приехало», вручную)──> received ──(накладная в iiko, авто)──> posted
  │                                 │
  └────────(«Отменить»)─────────────┴──> cancelled
```

| Статус | Как ставится | Считается «в пути» |
|---|---|---|
| `sent` | кнопка «Отправлено поставщику» (черновик → заказ) | да |
| `received` | кнопка «Приехало» при приёмке; можно указать факт по позициям (`received_qty`) | да, по факту, если введён |
| `posted` | автоматически: у всех позиций есть `posted_at` (см. сверку) | нет |
| `cancelled` | кнопка «Отменить заказ»; нельзя для `posted` | нет |

Почему `received` остаётся «в пути»: бармен скидывает накладную бухгалтерии, и она
приходует её в iiko с задержкой (решение владельца). Пока накладной нет, остаток в iiko
не вырос, и без вычета страница заказала бы то же самое ещё раз.

### Сверка с приходами iiko (`reconcile_with_operations`)

Вызывается при каждом расчёте `order-board` на операциях снимка сети
(`documentType = INCOMING_INVOICE`, `incoming = true`, окно 30 дней). Позиция заказа
считается оприходованной, если есть приход по её `product_id` на склад её бара
(`_BAR_ID_MAP` → `_STORE_ID_MAP`) с датой **не раньше дня отправки**; `posted_at` —
ближайшая такая дата. Когда оприходованы все позиции, заказ становится `posted`.

Ограничения (осознанно, для первой версии):
- накладная не связывается с конкретным заказом: два открытых заказа одного товара
  на один бар закроет одна накладная (обе позиции получат одинаковый `posted_at`);
- количество по накладной не сверяется с заказанным;
- сбой файла заказов не роняет доску: `on_order` и `draft_qty` становятся нулями,
  в лог пишется `[ORDERS] orders context unavailable`.

### «В пути» в рекомендации

В `order-board` (см. [stocks.md](stocks.md), раздел «К заказу»):

```
on_order      = сумма qty (или received_qty) по открытым заказам товара на склад бара
effective     = stock + on_order
target_stock  = avg_sales × (horizon_days + SAFETY_DAYS)   horizon_days — до поставки,
                                                            следующей за ближайшей
recommended   = ceil(max(0, target_stock − effective) / pack_size) × pack_size
urgency       = critical, если stock < 0 (учётная ошибка не лечится заказом);
                иначе _urgency_level(effective, days_to_delivery, ...)
days_left     = stock / avg_sales   (по физическому остатку на полке)
```

Пример. Среда, остаток 4 шт, расход 1.5 шт/день, срок поставки 2 дня при доставке пн–пт:
ближайшая поставка пятница, следующая понедельник (горизонт 5 дней), цель
`1.5 × (5 + 3) = 12`, рекомендация `12 − 4 = 8`, срочность `medium` (хватит на 2.7 дня <
2 + 3). После отправки заказа на 10 шт: `effective = 14 ≥ 12` → рекомендация 0, срочность
`low`, «хватит дн.» по-прежнему 2.7. Черновик на рекомендацию не влияет — только
отправленное.

Для «Общая» `on_order` суммируется по всем барам. Позиция несёт `open_orders[]`
(`order_id, supplier, qty, expected_at, status`) для подсказки «в пути N» под остатком.

### Ожидаемая дата поставки (`core/supplier_calendar.py`)

Большинство поставщиков не возят в субботу и воскресенье, но принимают заказ в
воскресенье на понедельник; поставка может задержаться на один-два дня, регламентировать
это нельзя (решения владельца).

```
next_delivery_date(sent_on, lead_time_days, delivery_weekdays = пн–пт)
    идём по календарным дням после sent_on; каждый день доставки уменьшает
    lead_time_days; lead_time_days < 1 считается как 1
```

| Отправлен | lead_time | Ожидается |
|---|---|---|
| пт 11.09 | 1 | пн 14.09 |
| вс 13.09 | 1 | пн 14.09 |
| ср 09.09 | 3 | пн 14.09 |
| чт 10.09 | 1 | пт 11.09 |

`lead_time_days` и `delivery_weekdays` берутся из справочника поставщиков
([suppliers.md](suppliers.md)) по имени или написанию (незаведённый поставщик: 3 дня,
пн–пт); дату можно передать явно в `POST /api/orders/send`. Дата ориентировочная: в UI
помечена «(ориентировочно)», заказ подсвечивается «Задерживается N дн.» только когда
`today − expected_at > ORDER_OVERDUE_GRACE_DAYS` (2 дня; `is_overdue`). `horizon_days`
(сколько дней должен покрыть заказ до следующей поставки) с этапа 2 используется в
формуле рекомендации ([stocks.md](stocks.md)).

### Текст заказа (`order_text`)

```
Заказ, чт 10.09
Поставщик: ООО "Май"
Большой пр. В.О:
- Кола 0.5 — 12 шт
Лиговский:
- Кола 0.5 — 3 шт
- Яблоко — 1.5 кг
Ожидаемая поставка: пн 14.09 (ориентировочно)
```

Бары в порядке `extensions.BARS`, позиции по названию, целые количества без «.0».
Один и тот же текст у черновика (без строки поставки) и у отправленного заказа. Кнопка
«Скопировать текст» использует `navigator.clipboard`, без HTTPS — выделяет текст для
Ctrl+C. CSV остался запасной кнопкой: чистый CSV с заголовком первой строкой, удвоенными
кавычками и локальной датой.

### API

Все ответы — JSON; ошибки `{error, ...}`. Автор действий — текущий пользователь сессии.

| Метод и путь | Тело | Ответ | Ошибки |
|---|---|---|---|
| `GET /api/orders/draft` | — | `{drafts: [{supplier, updated_at, updated_by, items[], total_qty, text}], bars}` | — |
| `POST /api/orders/draft` | `{supplier, product_id, bar, qty, name?, unit?, kind?, recommended?}` | как GET | 400: нет поставщика / `product_id`; бар не из `BARS`; `qty` не число или < 0; `kind` не из `bottle/draft/kitchen` |
| `POST /api/orders/draft/batch` | `{items: [как выше, каждая со своим supplier]}` | как GET | 400 с номером позиции (`позиция 1: ...`) |
| `POST /api/orders/draft/clear` | `{supplier?}` | как GET + `removed` | — |
| `POST /api/orders/send` | `{supplier, expected_at?, note?}` | `{order}` с `text` | 400: дата не `YYYY-MM-DD`; 409: черновик пуст |
| `GET /api/orders?days=30&status=sent,received` | — | `{orders[], days, overdue_grace_days}`; открытые всегда, закрытые за `days` (1..365) | 400: `days` не число, неизвестный статус (`known_statuses`) |
| `GET /api/orders/<id>` | — | `{order}` | 404 |
| `POST /api/orders/<id>/received` | `{items?: [{product_id, bar, qty}], note?}` | `{order}` | 404; 400: `items` не список; 409: заказ не открыт |
| `POST /api/orders/<id>/cancel` | `{note?}` | `{order}` | 404; 409: уже оприходован |

### Интерфейс

- **К заказу**: «в пути N» под остатком (подсказка — по каким заказам и когда ожидается),
  инпут «Заказ» пишет в общий черновик сразу (одна позиция — один запрос), «Взять N» кладёт
  рекомендацию одним тапом, «Взять рекомендации» по группе и «Взять все рекомендации» —
  одним батчем. Строка запоминает бар, для которого построена: поздний ответ или смена
  бара в селекте не отправят позицию не в тот бар. Липкая панель «Заказ: N поз. · M
  поставщиков · К отправке» и счётчик на вкладке показывают состояние черновика.
- **Фасовка** и **Меню кухни**: те же инпуты (`product_id` из ответа), то же число, что
  на доске. **Таплист** инпута «Для заказа» больше не имеет: кеги заказываются со
  «Сводного заказа» в литрах.
- **К отправке** (до 2026-09-11 — «Формирование заказа»): карточки черновика по поставщикам (правка количества, «Убрать»,
  текст, «Скопировать текст», «Отправлено поставщику», «CSV», «Убрать черновик»),
  «Очистить весь черновик»; блок «В пути» (статус, кто и когда отправил, ожидаемая дата,
  «Приехало», «Отменить заказ», состав и текст в `<details>`); «История за 30 дней»
  (`posted` и `cancelled`). Черновик и заказы грузятся при открытии страницы, до выбора
  бара.

### Конкурентность

Файл общий для двух gunicorn-воркеров: каждое изменение — `threading.Lock` +
`portalocker`-lock + перечитывание файла внутри блокировки + атомарная запись
(паттерн `core/meeting_notes.py`). Двое управляющих, правящих одну карточку, не теряют
правки друг друга (последняя по позиции побеждает, по разным позициям — обе остаются);
в карточке видно «Изменён 10.09 11:05 (login)».
