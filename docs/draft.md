# Анализ проливов разливного (/draft)

## Что это

Страница «Анализ проливов» показывает, сколько литров разливного продано по каждому кегу,
сколько это дало денег и что с кегами случилось помимо продажи — списания, недостача по
инвентаризациям, приход и баланс склада. Там же разрез по барменам — те же литры и деньги
в разрезе людей: прежняя страница `/waiters` слита сюда 13.08.2026. Экран один, без
вкладок; оформление по макету владельца от 14.08.2026.

Ключевое отличие от прежней реализации: **литры берутся из проводок iiko**, а не
перемножением количества порций на объём, вытащенный регексом из названия блюда.
Раньше «ФестХаус Хеллес (0,5)» разбирался по скобкам, и всё держалось на дисциплине
названий: позиция без объёма в названии молча считалась как 0,5 л.

Строка таблицы — **кег**, то есть товар со склада, который закупается и инвентаризуется.
Раньше строкой был сорт по очищенному названию блюда. На данных за 3,5 месяца это
74 сорта против 75 кегов, поэтому состав строк практически не изменился, но ключ стал
тем же объектом, что в накладных.

## Откуда берутся данные

### 1. Литры и потери — OLAP по проводкам (TRANSACTIONS)

`get_draft_writeoff_report(date_from, date_to, bar_name)`. Одна строка ответа =
склад x кег x учётный день x тип проводки.

```
groupByRowFields: Account.Name, Product.Id, Product.Name,
                  Product.MeasureUnit, DateTime.DateTyped, TransactionType
aggregateFields:  Amount.Out, Amount.In, Sum.Outgoing
filters:          DateTime.DateTyped (DateRange, to эксклюзивна),
                  Product.TopParent = ['Напитки Розлив'],
                  Account.Name = [бар]  — если выбран конкретный бар
```

Смысл типов проводок (проверено на живых данных 2026-08-13):

| TransactionType | Что это | Где на странице |
|---|---|---|
| `SESSION_WRITEOFF` | списание кега по техкарте при продаже через кассу | «Продано», основная таблица |
| `WRITEOFF` | акты списания | «Списано актами» |
| `INVENTORY_CORRECTION` | расхождения инвентаризаций (недостача в `Amount.Out`, излишки в `Amount.In`) | «Недостача по инвентаризациям» |
| `INVOICE` | приход по накладным | «Приход по накладным» |
| `TRANSFER` | перемещения между барами | отдельные строки баланса |

Склад берётся из `Account.Name`, а не из `Store`: iiko прямо предупреждает, что `Store` —
это «первый попавшийся склад проводки», а `Account.Name` вычисляется быстро и однозначно
([olap-otchety-v1.md](iiko-api/olap-otchety-v1.md), блок про `StartBalanceOptimizable`).

Список баров **не захардкожен** — он берётся из данных. Служебные счета
(«Расход продуктов», «Недостача инвентаризации», «Задолженность перед поставщиками»)
в агрегаты не попадают: за 3,5 месяца у всех таких строк и приход, и расход нулевые.

### 2. Деньги и бармены — OLAP по продажам (SALES)

`get_draft_sales_by_dish(date_from, date_to, bar_name)` — отдельный запрос, чтобы не
менять поведение `get_draft_sales_report`, на котором висят другие модули. Отличия:

```
groupByRowFields: Store.Name, AuthUser, DishId, DishName
aggregateFields:  DishAmountInt, DishDiscountSumInt, ProductCostBase.ProductCost
filters:          OpenDate.Typed (DateRange, to эксклюзивна),
                  DishGroup.TopParent = ['Напитки Розлив'],
                  DeletedWithWriteoff = NOT_DELETED, OrderDeleted = NOT_DELETED,
                  Store.Name = [бар] — если выбран конкретный бар
```

- `DishId` — для связки с кегом по GUID;
- `AuthUser` — разрез по барменам на той же странице;
- `DishGroup.ThirdParent` и `DishForeignName` не запрашиваются (не используются);
- из агрегатов убраны `UniqOrderId`, `DiscountSum`, `ProductCostBase.OneItem` и
  `ProductCostBase.MarkUp` — наценка считается от сумм, а не берётся построчно;
- **`OpenDate.Typed` в группировке нет**: деньги нигде не разбиваются по дням (недельные
  корзины XYZ приходят из проводок), а день умножал число строк на длину периода. Фильтр
  периода при этом на месте, суммы не меняются. Замер 2026-08-13: неделя по всем барам —
  280 строк вместо 504, 3,5 месяца — 1157 строк вместо 7398.

Фильтр `NOT_DELETED` здесь правильный: у удалённых позиций нет выручки. Их литры при
этом не теряются — они приходят актами списания (см. ниже про «удалено со списанием»).

### 3. Связка «блюдо -> кег» и объём порции — технологические карты

`get_dish_ingredient_map(date_from, date_to)` — `GET /v2/assemblyCharts/getAll` с
`includePreparedCharts=true`, ответ сворачивается в `{dish_guid: [[ingredient_guid, amount], ...]}`.
Это заменяет ручной `data/dish_to_keg_mapping.json` (175 строк, поддерживался руками)
данными самого iiko.

`amount` — норма закладки ингредиента на одну порцию блюда в его основных единицах, то
есть для кега это объём порции. Число нужно дважды: для связки (какой кег в блюде) и как
объём при раскладке литров по барменам. Отсюда правила выбора строк:

- **ревизия одна, последняя по `dateFrom`.** `getAll` отдаёт все карты, чей интервал
  действия пересекает период; складывать их нельзя — 0,5 л + 0,5 л дало бы литровую
  порцию;
- внутри одной карты строки с одинаковым `productId` складываются (так iiko считает
  списание);
- строки с непустым `productSizeSpecification` («раздельные» карты по размерам)
  пропускаются: разрешить размер нечем, `DishSize.*` в этой базе пуст. Розлив разведён
  отдельными блюдами на каждый объём, поэтому на его картах таких строк нет — за неделю
  04-10.08 из 2902 блюд пропущено 443 строки, и ни одно блюдо розлива объёма не потеряло.

Что из ингредиентов кег, определяется **не по названию и не по единице измерения из
номенклатуры**, а по участию в проводках разливного: кег — тот `Product.Id`, который
пришёл в ответе проводок. Благодаря этому:

- не нужна номенклатура (её OLAP-версия отдаёт только товары с операциями за 30 дней и
  на старых периодах неполна);
- сама отсекается посуда: у литровых позиций «с собой» в техкарте лежит ещё
  «бутылка ПЭТ без пробки 1,0л», 1 шт.

Кэш связки на диске 24 ч (`data/cache/assembly_map_v2_{from}_{to}.json`, на проде
`/kultura/cache/`), запись атомарная. Префикс `v2` — потому что смысл `amount`
изменился: до 13.08.2026 это была сумма норм по всем ревизиям и размерам (годилась только
для связки), файл v1 дал бы завышенные объёмы, поэтому старые файлы не читаются. Если iiko недоступен, берётся самый свежий
сохранённый файл, даже протухший: техкарты разливного стабильны, а без связки таблица
теряет все деньги.

## Формулы

Все считаются от сумм за период — никаких средних по средним.

```
Литры продано           = сумма Amount.Out проводок SESSION_WRITEOFF (ЕИ «л»)
Литры списано актами     = сумма Amount.Out проводок WRITEOFF
Недостача инвентаризации = сумма Amount.Out - сумма Amount.In проводок INVENTORY_CORRECTION
Приход                   = сумма Amount.In проводок INVOICE
Изменение остатка кегов  = приход + перемещения(приход)
                           - продано - списано - недостача - перемещения(расход)
Доля по литрам, %        = литры позиции / литры всех позиций разреза x 100
Доля в выручке, %        = выручка позиции / выручка всех позиций разреза x 100
Наценка, %               = (выручка - себестоимость) / себестоимость x 100
Маржа                    = выручка - себестоимость
Цена за литр             = выручка / литры
Средний объём порции     = литры / порции
Литров в неделю          = литры / (дней в периоде / 7)
```

### ABC

Три буквы: выручка, наценка, маржа.

- **По выручке** — накопленная доля (Парето): A до 80%, B до 95%, дальше C.
  Накопленный процент отдаётся отдельным полем `RevenueCumulativePercent` и в подписи
  «% от выручки» не участвует — там своя доля позиции.
- **По наценке и марже** — перцентили: верхняя треть A, середина B, нижняя C. Порог
  Парето здесь не подходит, потому что это не доли целого. Позиция с неизвестной
  наценкой (себестоимость 0) получает C и в ранжировании не участвует.

### XYZ

Измеряет, насколько ровно позиция продавалась **в те недели, когда стояла на кране**.

```
неделя      = 7-дневное окно от начала периода (не календарная неделя)
берутся     только полные окна и только те, в которые были продажи
CV, %       = стандартное отклонение недельных литров / среднее x 100
X: CV <= 30%      Y: CV <= 60%      Z: CV > 60%
если активных недель меньше 3 — категория не присваивается (прочерк)
```

Почему недели без продаж не считаются нулями: на кранах постоянная ротация — из 71 кега
за 3,5 месяца все 14 недель продавались только 12. Если считать пустые недели, каждая
сезонная позиция получает «нестабильный спрос» просто за короткий срок на кране. Срок
присутствия — отдельный факт, он показан как «на кране N из M нед.».

Почему пороги абсолютные, а не перцентильные: при перцентилях позиция с идеально ровными
продажами получала Z только потому, что рядом кто-то ровнее, а единственная позиция в
разрезе получала Z всегда. Значения 30/60 выведены из живых данных за 14 недель
(2026-05-01..08-12, 57 кегов с 3+ активными неделями): CV от 10% до 102%, медиана 56%,
у флагмана «ФестХаус Хеллес» 13%, у ротационного хвоста 90-102%. Порог даёт X=14%,
Y=51%, Z=35% позиций и читается словами: до 30% недельный объём предсказуем, свыше 60%
может отличаться больше чем в полтора раза.

## Разрез по барменам

Прежняя страница `/waiters` слита сюда 13.08.2026: она жила над тем же отчётом iiko по
розливу, показывала те же литры/порции/выручку и отличалась только тем, что литры считала
регексом по названию блюда. `/waiters` отдаёт 301 на `/draft`.

**Кто такой бармен.** Поле `AuthUser` («Авторизовал») — кто пробил позицию в кассе. Это
единый ключ сотрудника во всех отчётах проекта (аудит OLAP #11), но он не гарантирует, что
человек сам наливал; на странице это написано прямым текстом. Строки без автора попадают
в строку «Не указан» и **не выбрасываются** — их литры есть в проводках, и выброс порвал бы
тождество с итогом по кегам. Прежний расчёт молча выкидывал три служебных имени.

**Литры.** В проводках автора нет (там склад x кег x день x тип), поэтому объём порции
берётся из техкарты, а результат приводится к факту списания кега:

```
объём порции         = норма закладки кега на 1 порцию из техкарты
raw(строка продажи)  = порций x объём порции
factor(кег)          = литры кега по проводкам SESSION_WRITEOFF / сумма raw по кегу
литры(строка)        = raw(строка) x factor(кег)
```

Нормировка нужна потому, что техкарта и факт списания могут расходиться: в документе бывает
коэффициент списания, карта могла смениться внутри периода, iiko округляет. За 3,5 месяца
расхождение больше 1% нашлось у 2 кегов из 74, максимум 5,1% — эти цифры показываются
подсказкой под таблицей, а не прячутся. Побочный эффект нормировки — тождество:

```
сумма литров по барменам = сумма литров по кегам
```

Деньги делятся между кегами тем же `_keg_shares`, что и в разрезе кегов, поэтому выручка
и порции тоже совпадают между таблицами до нуля.

**Вырожденные случаи** (все с диагностикой на странице):

| Случай | Что делаем |
|---|---|
| у блюда нет нормы закладки (в карте только строки размеров) | `raw = 0`, блюдо в список «позиции без нормы закладки», его литры расходятся по остальным блюдам того же кега |
| ни у одного блюда кега нет нормы | литры кега делятся между барменами пропорционально порциям |
| продажа кега есть в проводках, а строки продаж нет (граница учётного дня) | литры показываются строкой «не отнесено ни к одному бармену» |

**Что в таблице:** литры, доля по литрам, порции, число разных кегов, выручка, маржа,
наценка, цена за литр. В карточке бармена — те же метрики плюс средний объём порции, доля
в выручке и раскладка «что наливал» по кегам.

Чего в таблице сознательно нет: «Кег 30 л» (деление литров на 30 при реальных кегах 20/30/50
не значит ничего) и «сортов пива» — вместо него число кегов.

## Границы периода

Период в интерфейсе включительный с двух сторон. К iiko уходит `date_to + 1 день`,
потому что правая граница `DateRange` эксклюзивная. Это единая конвенция проекта, она же
применяется и к `OpenDate.Typed` в продажах, и к `DateTime.DateTyped` в проводках
(проверено: запрос `to=2026-08-11` возвращает дни 04-10 августа).

## Что показывает страница

Экран один, без вкладок: сверху фильтры, дальше сводка, кеги, бармены и баланс склада.
Всё приходит ОДНИМ ответом `/api/draft-kegs`, поэтому сортировка, поиск и карточки
работают мгновенно и запросов не делают. Оформление — по макету владельца
(Claude Design, 14.08.2026), устроено так же, как `/me`: своя шапка с гамбургером
(открывает общий сайдбар), токены `--dr-*` на `body.draft-page`, IBM Plex Sans для
текста и IBM Plex Mono для чисел, светлая и тёмная темы.

**Фильтры:** бар (Общая + четыре точки) и период. Период — список пресетов (прошлая
и текущая неделя, вчера, сегодня, прошлый и текущий месяц, 30 и 90 дней) плюс «свой
период» двумя датами: расчёт умеет любой диапазон, и отнимать это у страницы нельзя.
Справа под фильтрами — строка разреза и чип «обновлено ЧЧ:ММ» (время, когда данные
реально забраны из iiko, а не момент клика: ответ живёт в кэше 10 минут).

**Сводка** (семь плиток): продано (л), выручка, всего порций, цена за литр, объём
порции, наценка, барменов.

**Позиции по кегам:** литры, порции, доля по литрам со шкалой, выручка, цена за литр,
наценка, ABC (цвет по первой букве — месту в выручке), XYZ. Колонки с числами
сортируются кликом по заголовку, есть поиск по названию и строка «Итого · N кегов».
Клик по строке открывает карточку кега.

**Бармены по объёму:** литры, доля, порции, сколько разных кегов, выручка, маржа,
наценка, цена за литр, итог. Клик по строке — карточка бармена.

**Баланс кегов:** приход по накладным, перемещения, продано через кассу, списано актами,
недостача по инвентаризациям — каждая строка со шкалой и знаком, у потерь рядом доля от
проданного. Внизу «изменение остатка кегов».

Про недостачу важно понимать: в неё попадают и настоящие потери (пена, промывка линий,
недолив в кеге), и недокрут остатка кега на кране в момент пересчёта. Поэтому она
подаётся как факт расхождения, а не как готовая цифра потерь. На данных 01.05-12.08
недостача составила 1057 л — 9,2% от проданного объёма.

**Где именно расхождения:** кеги с потерями — акты, недостача, процент к проданному по
этому кегу. Первые восемь видны сразу, остальные под «ещё N кегов». Цвет плашки: до 10%
спокойный, до 30% янтарный, выше красный (пороги от факта — недостача по всем барам за
3,5 месяца 9,2%). Излишек (недостача с минусом) полосой не рисуется: это не потеря.

**Карточка кега:** продажи (литры, порции, доли, «на кране N из M недель», литров в
неделю), деньги, **кто наливал** — разбивка по барменам с долей кега, потери по этому
кегу, разбор ABC по каждой из трёх букв и XYZ с коэффициентом вариации. Из строки
бармена открывается его карточка.

**Карточка бармена:** налив (литры, порции, доли, средний объём порции, кегов), деньги
и **что наливал** — разбивка по кегам. Из строки кега открывается карточка кега.

**Диагностика** под баланcом печатается только когда есть о чём говорить: XYZ не
рассчитан, литры без бармена, блюда без нормы закладки, кеги с расхождением техкарты и
факта, блюда без связки с кегом.

## Дефекты прежней реализации, устранённые вместе с переходом

Аудит 2026-08-13 (18 находок). Шесть показывали пользователю неверные числа:

| Что было | Что стало |
|---|---|
| XYZ на периоде по умолчанию (одна календарная неделя) выдавал всем CV=100 и раздавал X/Y/Z по порядку сортировки по литрам | При меньше чем 3 активных неделях категории нет; пороги абсолютные |
| Подпись «% от выручки» показывала накопленный процент ABC: у последней позиции всегда «100%», у Ригеле 52,3% при своей доле 10,3% | Своя доля позиции; накопленный процент подписан отдельно |
| Наценка — невзвешенное среднее построчных процентов, до +43,6 п.п. мимо (449,9% против 406,2%); она же задавала букву ABC | От сумм за период |
| Недели календарные: 7 дней не с понедельника давали 2 недели и вдвое занижали «литров в неделю» (121,5 вместо 243) | 7-дневные окна от начала периода |
| В сводном разрезе CV смешивал разброс между барами с разбросом по неделям (8 строк вместо 2 точек) | CV по недельным итогам разреза |
| `onclick='showBeerDetails(${JSON.stringify(beer)})'` рвался на апострофе: строка «Gravity It's Mango» не открывалась | Передаётся индекс, названия экранируются |

Остальное: дробные порции больше не обрезаются до целого (`int()` превращал 1501,33 в
1501); ошибка от сервера показывается вместо общего «ошибка при получении данных»; пустой
ответ не оставляет пустую страницу без сообщения; появился кэш OLAP (`cached_olap`,
10 мин, single-flight), которого у страницы не было; из запроса убраны поля, которые
никто не читал; исчезли поля `Kegs30L`/`Kegs50L` — они считались от «30 л» и «50 л»,
хотя кеги бывают 20/30/50 л, и на страницу всё равно не выводились.

Второй парсер объёма (`core/waiter_analysis.py`, три паттерна вместо пяти и
противоположная политика — выбрасывал нераспознанное вместо 0,5 л) удалён вместе со страницей
`/waiters`: разрез по барменам считается из техкарт на той же странице.

```bash

```

Вёрстку смотреть глазами обязательно: тесты не видят, что блок уехал. Локальный приём —
Playwright по фикстуре `tests/fixtures/draft_kegs_sample.json` (см. [[lessons]] про
скриншоты вёрстки): поднять Flask с заглушкой `/api/draft-kegs`, снять светлую и тёмную
тему плюс телефон.

Ручная сверка литров с iiko: OLAP по проводкам в iikoOffice, фильтр по группе
«Напитки Розлив», тип проводки «Списание при продаже», единица измерения «л».

Проверка тождества вкладок глазами: открыть период, сравнить «Продано» на «По кегам» и
«По барменам» — цифры обязаны совпадать до копейки. Если под таблицей барменов появилась
подсказка про «не отнесено» — это и есть та разница, она объясняется там же.
