# Orderia cashapi — программа лояльности (внешняя система)

## Что это

`loyalty.orderia.ru` — внешняя система лояльности сети (карты, бонусы, привязка
к Telegram). Не наш код, не iiko: отдельный сервис на PHP + MySQL со своим HTTP-API
в разделе `/cashapi/`.

**Зачем нам:** это единственный известный источник **справочника карт**. В
[guests.md](../guests.md) зафиксировано, что серверный API iiko справочника гостей не
отдаёт — гость существует для нас, только если хоть раз купил (решение владельца от
2026-07-15, «новая карта по первой покупке»). Всё, что зарегистрировалось и ни разу
не пробило чек, в витрине `guests.db` невидимо в принципе. Orderia видит именно этот
слой.

**Статус: интеграция есть** (с 2026-08-12). Клиент — `core/orderia_client.py`, синк —
`guest_sync.sync_never_cards()` в ночном прогоне витрины гостей, хранение — таблица
`never_cards` в `guests.db` (схема v2), показ — вкладка «Не купившие» на `/guests`.
Разбор данных ниже сделан по живым ответам `never.php` (срез 2026-08-11, 326 записей).
Раздел [«Что неизвестно»](#что-неизвестно) — честный список оставшихся дыр.

**Данные источника принимаются не на веру.** Счётчик покупок в Orderia ошибается: на
срезе из 326 карт 22 нашлись среди покупателей iiko. Поэтому каждая карта сверяется с
витриной чеков, и «не купившими» считаются только те, кого в iiko действительно нет —
см. [guests.md](../guests.md), раздел «Сверка Orderia с витриной».

## Доступ

| Параметр | Значение |
|---|---|
| База | `https://loyalty.orderia.ru/cashapi/` |
| Авторизация | HTTP Basic (логин `loyalty`) |
| Формат ответа | JSON, `Content-Type` не проверялся |
| Пароль | **в репозиторий не пишем** — рунбук `C:\KULT\ctr\selectel-migration-credentials.md` |
| Переменные окружения | `ORDERIA_LOGIN`, `ORDERIA_PASSWORD`, необязательный `ORDERIA_BASE_URL` |

Без логина и пароля интеграция просто выключена: `orderia_client.is_configured()` отдаёт
`False`, синк не стартует, вкладка «Не купившие» показывает причину вместо пустых нулей
(тот же паттерн, что у Tuya в `/temperature`).

**Откуда ходить.** С рабочего Windows-ПК под включённым VPN/DPI-обходом хост
недоступен — соединение висит до таймаута. С прод-сервера Selectel открывается штатно:
проверено 2026-08-12, без авторизации `HTTP 401` за 60 мс, с авторизацией `HTTP 200`
за 46 мс. То есть для интеграции с прода помех нет, а локальная разведка требует либо
выключить туннель, либо ходить через сервер:

```bash
# с прод-сервера (SSH только через Tailscale, см. remote-sync.md)
ssh deploy@100.67.213.21 'curl -sS -u loyalty:<пароль> https://loyalty.orderia.ru/cashapi/never.php'
```

Пароль в командной строке виден в списке процессов. Чтобы не светить — отдать curl
конфиг через stdin:

```bash
printf 'user = "loyalty:%s"\n' "$PASS" | ssh deploy@100.67.213.21 \
  'curl -sS -K - https://loyalty.orderia.ru/cashapi/never.php'
```

Basic-auth в URL вида `https://loyalty:пароль@loyalty.orderia.ru/...` работает, но
пароль утекает в историю команд, логи прокси и `Referer`. При интеграции — только
через заголовок и переменные окружения (`ORDERIA_LOGIN` / `ORDERIA_PASSWORD` по
образцу `IIKO_LOGIN` / `IIKO_PASSWORD`).

### `never.php` пропал 12 августа 2026

Эндпоинт перестал существовать в течение дня, между 01:06 и 12:20 МСК. Ночью он
отвечал `200` (123 878 байт, 326 записей), к полудню — `404` и **с авторизацией, и
без неё**. Заодно с него снялась басик-авторизация: раньше запрос без пароля получал
`401`, теперь сразу `404`.

Замер с прод-сервера 2026-08-12, 12:20 МСК:

| Путь | С авторизацией | Без авторизации |
|---|---|---|
| `/` | 200 | 200 |
| `/cashapi/` | 403 | 403 |
| `/cashapi/never.php` | 404 | 404 |
| `/cashapi/index.php` | 404 | 404 |

Сайт жив, каталог `/cashapi/` на месте (403 — запрет листинга, то есть каталог
существует), а файла больше нет. На блокировку по IP не похоже: `/` с того же адреса
отдаёт 200. Похоже на переезд или переименование внутри `/cashapi/` — возможно,
Orderia что-то перестраивает, раз одновременно исчезла и басик-авторизация.

**Что делать:** запросить у Orderia актуальный адрес (и заодно список остальных
эндпоинтов — вопрос 1 в [«Что неизвестно»](#что-неизвестно)). Новый путь задаётся без
правок кода: `ORDERIA_BASE_URL` в `.env`, если каталог сменился, либо константа
`never.php` в `core/orderia_client.py`, если сменилось имя файла.

**Как система это переживает:** штатно. Клиент возвращает `None`, синк фиксирует
ошибку в `never_sync` и НЕ трогает сохранённый срез, вкладка «Не купившие» показывает
причину вместо пустых нулей.

Диагностика 2026-08-12, которая отделила «файл убрали» от «забанили наш IP»: запрос к
заведомо несуществующему имени в том же каталоге отвечает **тем же** `404`, что и
`never.php`, каталог отдаёт `403` (nginx с выключенным листингом обслуживает локацию
нормально), корень — `200`. При блокировке по IP ответ был бы одинаковым везде.
Значит файла действительно нет.

**Срез на проде залит вручную.** Живой ответ, снятый 2026-08-11 22:06 UTC (326 записей),
загружен разовым импортом, чтобы вкладка работала до появления нового адреса. В
`fetched_at` стоит РЕАЛЬНЫЙ момент снятия, а не время импорта, а `never_sync.status`
оставлен `error` — поэтому вкладка показывает дату среза и предупреждение, что
обновления не проходят. Ночной синк этот срез не затрёт: при ошибке источника данные
не трогаются.

Имена других файлов в `/cashapi/` намеренно не перебирались: это сканирование чужого
сервиса, а ответ поставщик даёт одним письмом.

## `never.php` — карты без покупок

Отдаёт JSON-массив объектов: все карты за всю историю (2024-02-29 … 2026-08-11) одним
куском. `Content-Type: application/json; charset=utf-8`.

**Параметров запроса не принимает — проверено.** Перебраны `limit`, `offset`, `count`,
`page`, `id`, `date_from`, `from`+`to`, `start`: во всех девяти случаях ответ побайтово
одинаковый (`HTTP 200`, 123 878 байт, 326 записей). Ни фильтрации, ни пагинации, ни
выборки по одной карте — только полный дамп. Последствия в [ловушке 7](#7-только-полный-дамп-без-фильтров-и-пагинации).

### Поля

Все значения — **строки**, включая числовые (PHP `json_encode` без `JSON_NUMERIC_CHECK`).
Приводить типы обязан потребитель.

| Поле | Пример | Смысл | Заполненность |
|---|---|---|---|
| `id` | `"2647"` | Первичный ключ записи, автоинкремент. Уникален | 100% |
| `cardnum` | `"2002639"` | Номер карты. **Не уникален** — см. ловушки | 100% |
| `name` | `"Дарья"` | Имя (из Telegram-профиля, судя по содержимому) | 100% |
| `lastname` | `"Ткаченко"` | Фамилия | 42% |
| `phone` | `"79112365853"` | Телефон, **не валидирован** | 100%, но 2 записи — мусор |
| `balance` | `"20000"` | Бонусный баланс. Единица измерения не подтверждена | 100% |
| `check_sum` | `"0"` | Сумма покупок. В этом отчёте всегда `0` | 100% |
| `check_count` | `"0"` | Количество чеков. В этом отчёте всегда `0` | 100% |
| `last_date` | `"2025-04-03 22:58:55"` | Дата регистрации карты (не «последняя активность» — активности нет) | 100% |
| `telegram` | `"767539168"` | Telegram user id | 97% (317 из 326) |
| `coeff_calc` | `"5"` | Коэффициент начисления. Всегда `5` во всей выборке | 100% |
| `dated` | `"2025-04-03 22:58:55"` | Служебная отметка времени. **Не дата регистрации** — см. ловушки | 100% |

### Критерий выборки подтверждается данными

У всех 326 записей `check_count = "0"` и `check_sum = "0"`. Отчёт действительно
«зарегистрировался и ни разу не купил», а не «давно не покупал».

### Порядок записей

Массив отсортирован по возрастанию `id` — и одновременно по возрастанию `last_date`
(проверено: обе последовательности монотонны). То есть `id` хронологичен, и
инкрементальная выборка «всё, что новее последнего виденного `id`» корректна.

## Ловушки

### 1. `dated` — не дата регистрации, и часовой пояс в нём плавает

Разбор 326 записей по соотношению `dated` и `last_date`:

| Класс | Записей | Что это |
|---|---|---|
| `dated == last_date` | 227 | Норма |
| `dated == "2024-06-29 15:19:52"` | 51 | Одна и та же секунда у полусотни карт — бэкфилл при миграции данных |
| `dated == last_date + 3:00:00` | 48 | Расхождение **ровно на 3 часа** (10799–10801 с) |

Три часа — это MSK − UTC. Часть записей пишет одно поле по времени сервера, другое по
UTC; расхождение встречается только в диапазоне регистраций 2026-03-27 … 2026-07-25 и
не покрывает его целиком, так что это не «правило по датам», а несогласованность
внутри системы.

**Вывод: датой регистрации считать `last_date`.** По `dated` нельзя строить ни
хронологию, ни инкрементальную выборку — на 51 записи он врёт на два года, на 48 на
три часа.

### 2. `cardnum` не уникален и не выводится из `id`

Номер карты `2002639` выдан трём записям — `id` 2647, 2648, 2649:

```
2647  Дарья   79112365853  2025-04-03 22:56:55
2648  Alexei  79992128676  2025-04-03 22:57:55
2649  Дарья   79112365853  2025-04-03 22:58:55
```

Три регистрации подряд с шагом ровно в минуту, один номер карты на всех, между двумя
попытками одного человека вклинился другой. Похоже на сбой выдачи номера, а не на
дубль клиента.

Соблазн вычислить одно поле из другого не работает: смещение `id − (cardnum − 2000000)`
дрейфует по выборке — 1, 5, 6, 7, 8, 9, 10, 17. Плюс аномалия: у `id = 1712` номер
`20017111` — **восемь** знаков вместо семи (у всех остальных семь).

**Вывод: ключ записи — только `id`. `cardnum` — отображаемый реквизит, не идентификатор.**

Это правило стоило отдельного бага при интеграции: сшивка карт с витриной по номеру
привязала к одному покупателю три чужие записи и посчитала его выручку трижды. Теперь
номер используется как запасной ключ, только если он **уникален в текущем срезе**
(`_classify_never_card` в `core/guest_analytics.py`), а денежные агрегаты копятся по
`guest_id` витрины, а не по строкам источника. Урок записан в
[lessons.md](../lessons.md) «Чужой идентификатор не первичный ключ».

### 3. Телефоны не валидируются на входе

313 из 326 — нормальный российский формат `7XXXXXXXXXX`. Остальное:

- 4 записи с ведущим `+` (`+79110319116`) — формат плавает, нормализация обязательна;
- 7 записей иной длины (11–13 цифр) — среди них реальные зарубежные (`38268847632`
  Черногория, `9647705331213` Ирак);
- 2 записи — вообще не телефоны: `7om/catalog` и `7r_j\x1d931CJp` (id 1902 и 1892).

Второй случай — печатаемый мусор с управляющим символом `\x1d` и обрывок URL-пути в
первом. Это не опечатки посетителей, а следы автоматического сканирования формы
регистрации. Отдельно: 9 записей с именем `Jane Doe` и пустым `telegram` — болванки
того же происхождения.

**Вывод: перед любой рассылкой или выгрузкой фильтровать по маске телефона; `Jane Doe`
с пустым `telegram` отбрасывать.**

### 4. Номинал приветственного бонуса менялся

`balance` принимает ровно два значения, и они разделены по дате чисто, без пересечения:

| `balance` | Период регистраций | Записей |
|---|---|---|
| `20000` | 2024-02-29 … 2026-02-14 | 250 |
| `40000` | 2026-02-18 … 2026-08-11 | 76 |

Последняя «двадцатка» — 14 февраля 2026, первая «сороковка» — 18 февраля. Раз у всех
этих карт покупок не было, баланс никто не тратил: это начисление при регистрации.

Единица измерения **не подтверждена**. Гипотеза — копейки (200 и 400 рублей), но
проверить не на чем: в выборке нет ни одной карты с расходом. Не закладываться в код,
пока не подтверждено на карте с покупками.

### 5. Кодирование ответа

- Кириллица не экранирована (`JSON_UNESCAPED_UNICODE` включён), а слэш экранируется
  как `\/` (`JSON_UNESCAPED_SLASHES` выключен) — штатное поведение PHP, стандартный
  JSON-парсер разберёт корректно.
- В именах встречаются эмодзи и экзотика: `Мару🐈‍⬛♏️`, `ϟϟ𝙺𝚊𝚕'𝚝𝚜𝚒𝚝ϟϟ`, `tanya ‧₊˚彡`,
  а также `ᅠ ᅠ` (Hangul filler — визуально пустое имя). При выгрузке в CSV/Excel это
  требует UTF-8 с BOM, при отрисовке в UI — экранирования.

### 6. Нет привязки к точке

В ответе нет ни бара, ни кассы, ни источника регистрации. Понять, где выдают карты,
которые не работают, по этому эндпоинту нельзя. Для разреза по точкам нужен либо
другой эндпоинт, либо связка по чекам на стороне iiko (которой у этих карт нет).

### 7. Только полный дамп, без фильтров и пагинации

Эндпоинт игнорирует любые параметры (проверено девятью вариантами, см. выше). Отсюда
три следствия для будущей интеграции:

- **Ответ растёт без ограничений.** Сейчас 123 878 байт на 326 записей — примерно
  380 байт на карту. При том же потоке (10–13 мёртвых регистраций в месяц) это
  ещё лет пять некритично, но потолка у ответа нет вообще.
- **Инкрементальная выборка — только на нашей стороне.** «Что нового с прошлого раза»
  считается сравнением с сохранённым максимальным `id` (он хронологичен, см.
  [«Порядок записей»](#порядок-записей)), а не запросом к API.
- **Дешевле, чем кажется.** Полный ответ приходит за ~46 мс, так что опрос раз в
  сутки ничего не стоит; городить кэш ради экономии смысла нет.

## Что известно о числах

Срез от 2026-08-11: **326 карт** без единой покупки, поток стабильный — 10–13
регистраций в месяц, всплески по 20 в мае 2025 и мае 2026.

**Знаменателя нет.** Общее число выданных карт этот эндпоинт не отдаёт, поэтому
конверсию «регистрация → первая покупка» посчитать не из чего: 326 может быть и 5%
базы, и 40%. Для оценки нужен либо эндпоинт с полным списком карт, либо счётчик
активных карт из iiko (`guests.db` знает только покупавших).

## Что неизвестно

Список открытых вопросов — закрывать при следующем заходе:

1. **Полный список эндпоинтов `/cashapi/`.** Известен один — его дал владелец.
   Запросить документацию у Orderia. Перебирать имена эндпоинтов на боевом API
   поставщика намеренно не стали: это сканирование чужого сервиса, а ответ на вопрос
   поставщик даёт одним письмом.
2. **Единица измерения `balance`** — копейки или бонусные единицы (см. ловушку 4).
3. **Смысл `coeff_calc`.** Значение `5` у всех 326 записей. Гипотеза — процент
   начисления, но выборка вырожденная: это значение по умолчанию для карт без покупок,
   и различий в ней быть не может.
4. **Общее число карт** — знаменатель для конверсии.
5. **Есть ли методы записи** (начисление, блокировка карты) или API только на чтение.
6. **Связь `cardnum` с полем карты в чеках iiko** — совпадает ли номер, по которому
   можно сшить Orderia с `guests.db`.

Закрыто 2026-08-12: доступность с прод-сервера (открывается, 200 за 46 мс) и наличие
параметров у `never.php` (не принимает, всегда полный дамп).
