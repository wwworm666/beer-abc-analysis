# API Saby (СБИС) и сверка входящих УПД (этап 2 приёмки)

**Кратко.** API Saby — вход в кабинет Saby для программы: сервис сам забирал бы входящие
УПД поставщиков (строки, цены, коды маркировки) и сверял их со сканами приёмки на РЦ.
Но коды маркировки из подписанных УПД уже видны через True API Честного ЗНАКа, который
сервис читает (`chz_test/chz.py`, бесплатно, без новых договоров). Рекомендация: этап 2
начать с Честного ЗНАКа, параллельно узнать у менеджера Saby условия API (вопросы — в
«Открытых вопросах»); Saby подключать, если нужна сверка **до** подписи УПД, цены или
немаркированные позиции.

Справочник по итогам исследования от 2026-10-04. Кода интеграции с Saby пока нет. Справку saby.ru, sbis.ru и online.sbis.ru из среды разработки открыть нельзя: её закрывает прокси. Поэтому сведения о справке взяты из выдачи поиска, а код клиентов прочитан на GitHub и PyPI. Утверждения без пометки имеют высокую уверенность. У остальных уверенность указана в скобках.

Секреты (логины, пароли, ключи приложения, sid, токены) в репозиторий не кладутся, только в переменные окружения сервера. В примерах ниже все значения заменены на `<...>`.

## Что это

- Saby (бывший СБИС, компания «Тензор») — оператор ЭДО. Через Saby поставщики присылают сети электронные УПД.
- У API ЭДО Saby протокол JSON-RPC 2.0 поверх HTTPS. Имя команды передаётся в поле `method` (`СБИС.<Команда>`), параметры и поля названы по-русски. [saby.ru/help/integration/api](https://saby.ru/help/integration/api), [list_doc](https://saby.ru/help/integration/api/all_methods/list_doc/)
- Задача этапа 2: получить входящие УПД поставщиков (XML формата ФНС) с кодами маркировки и сравнить их со сканами DataMatrix, которые сделаны на РЦ на этапе 1 (ключ `gtin|serial`).
- API Saby не отдаёт строки товаров в JSON, только реквизиты шапки и ссылки на файлы. Позиции, количества, цены и коды берутся разбором XML УПД (уверенность: средняя, это вывод: ни в каталоге из 45 команд, ни в найденных клиентах такого метода нет). [sbis-mcp-ru sbis_commands.tsv](https://raw.githubusercontent.com/ilyautov/sbis-mcp-ru/main/scripts/sbis_commands.tsv)
- Есть альтернатива: True API Честного ЗНАКА. Сервис уже читает через него входящие УПД с кодами (`chz_test/chz.py`), но только после подписи покупателем, без цен и без немаркированных строк (см. раздел «Альтернатива: True API Честного знака»).

## Доступ и авторизация

### Адреса

| Назначение | Адрес | Уверенность |
|---|---|---|
| Вход, выход, проверка сессии, аккаунты | `https://online.sbis.ru/auth/service/` | высокая |
| Команды ЭДО | `https://online.sbis.ru/service/?srv=1` | высокая |
| Сервисная авторизация приложения | `/oauth/service/`. Хост в источниках разный: `online.sbis.ru`, `api.sbis.ru` (официальный клиент saby/vok), `online.saby.ru` | средняя |
| Файлы вложений | подписанные ссылки `https://disk.sbis.ru/disk/api/...` из ответа | высокая |
| Тестовый стенд | `https://fix-online.sbis.ru`, файлы на `fix-disk.sbis.ru` | высокая для адресов |
| Резервный домен | `online.saby.ru`: обработка Saby для 1С переходит на него при сетевой ошибке | средняя |

Источники: [auth_one](https://saby.ru/help/integration/api/all_methods/auth_one), [techreq_edo](https://saby.ru/help/integration/api/techreq_edo), [vo2_core API.obj.1c](https://github.com/saby-integration/vo2_core/blob/cb282b39a3ee7e74b285523f42cc94d047a5f196/vo2/API/API.obj.1c), [saby/vok client.py](https://github.com/saby/vok/blob/8b070a32ff7e20e3c7f005d4a19d1469344360bc/client-py/sabyvok/client.py), [Citeck ecos-edi-sbis](https://github.com/Citeck/ecos-docs/blob/3a58f313d893785f8076316668e5ca3899f707e9/docs/integration/EDI_integration/ecos-edi-sbis-lib.rst).

Заголовки:
- `Content-Type: application/json; charset=utf-8`. Так в справке и в vo2_core. В рабочих сторонних клиентах встречается и `application/json-rpc`.
- `X-SBISSessionID: <sid>` — в каждом запросе после входа.
- `X-SBISAccessToken: <token>` — при входе приложением по OAuth (уверенность: средняя).

### Способ 1. Логин и пароль: СБИС.Аутентифицировать

```
POST https://online.sbis.ru/auth/service/
Content-Type: application/json; charset=utf-8

{"jsonrpc":"2.0","method":"СБИС.Аутентифицировать",
 "params":{"Параметр":{"Логин":"<логин>","Пароль":"<пароль>"}},"id":0}
```

- В ответе `result` приходит строка сессии (sid). [auth_one](https://saby.ru/help/integration/api/all_methods/auth_one)
- `Параметр.НомерАккаунта` необязателен. Он нужен, если один логин открывает несколько кабинетов. Без него вход выполняется в тот кабинет, куда пользователь заходил последним.
- В сторонних клиентах встречаются три формы тела: плоские Логин и Пароль, «Параметры», «Параметр». Брать нужно форму из справки, то есть «Параметр». Её независимо подтверждает PHP-клиент [magdv/sbis](https://github.com/magdv/sbis/blob/74d04c7d41be5d559e9c8505561691487f13635c/src/Entities/Auth/AuthParams.php).
- Пользователю нужны права на API (уверенность: средняя). [sequence/right](https://saby.ru/help/integration/api/sequence/right), [README sbis-mcp-ru](https://raw.githubusercontent.com/ilyautov/sbis-mcp-ru/main/README.md)

### Способ 2. Сервисный ключ приложения (OAuth): рекомендуется для фоновой сверки

Приложение настраивается в кабинете: Настройки → Политики безопасности → Подключения к Saby → добавить. Там задаются название, описание, адрес или IP внешней системы (пустое поле значит «с любого адреса») и сервисный доступ: «Разрешён полностью» или «С ограничением по правам» (уверенность: средняя; не подтверждено, что пункт лежит в блоке «Система» и что есть отдельный тип «по сервисному ключу»). В карточке приложения появятся `app_client_id`, `app_secret`, `secret_key`. [add_app](https://saby.ru/help/integration/api/auth/add_app), [auth/service](https://saby.ru/help/integration/api/auth/service)

```
POST https://online.sbis.ru/oauth/service/      (хост уточнить, см. таблицу адресов)
Content-Type: application/json; charset=utf-8

{"app_client_id":"<...>","app_secret":"<...>","secret_key":"<...>"}
```

- Названия полей ответа в источниках расходятся (уверенность: средняя):
  - saby/vok читает `access_token` и `sid` и шлёт оба заголовка, `X-SBISAccessToken` и `X-SBISSessionId`;
  - vo2_core берёт `sid` и дальше работает с ним как с обычной сессией (`X-SBISSessionID` на `/service/?srv=1`);
  - sbis-api-client 0.0.3 читает `token` и `sid`.

  На первом запуске нужно залогировать структуру ответа (имена ключей, без значений) и передавать оба заголовка.
- Выход: `POST /oauth/service/` с телом `{"event":"exit","token":"<...>"}` (уверенность: средняя). [sbis-api-client](https://pypi.org/project/sbis-api-client/)
- Срок жизни токена не найден ни в одном источнике.
- Почему этот способ лучше для сервера (это наш вывод, в справке такой рекомендации нет):
  - пароль сотрудника не хранится на сервере;
  - подтверждение входа по коду на сервисный режим не действует;
  - IP и права приложения можно ограничить.

### Способ 3. Сертификат ЭП: СБИС.АутентифицироватьПоСертификату

- Передаётся `Сертификат.ДвоичныеДанные` (X.509 DER в Base64). Ответ приходит зашифрованным на этот сертификат по ГОСТ 28147-89, расшифровать его можно только средством криптозащиты.
- Перед входом обычно вызывают `СБИС.СписокСертификатовДляАутентификации`.
- Для нашего сервера без КриптоПро этот способ не подходит. [authinput_ep](https://saby.ru/help/integration/api/all_methods/authinput_ep)

Есть и другие способы входа: интерактивный OAuth и `СБИС.ExternalAuth`. Нам они не нужны.

### Сессия и лимиты

- Сессия по умолчанию живёт 21 день, срок меняется в настройках безопасности аккаунта. Кроме того, сессия аннулируется через 24 часа без активности (уверенность: средняя). Saby советует входить заново при HTTP 401 или раз в сутки. Сверка запускается реже раза в сутки, поэтому обработка 401 (повторный вход и повтор запроса) обязательна. [sequence/auth](https://saby.ru/help/integration/api/sequence/auth), [error_solution/401](https://saby.ru/help/integration/api/error_solution/401)
- Не входить перед каждым запросом, а хранить sid в БД или кэше. `СБИС.Аутентифицировать` можно вызывать не чаще 300 раз в минуту. При превышении доступ с IP блокируется на 20 минут (уверенность: средняя).
- `СБИС.ПроверитьСессию` на `/auth/service/` отвечает `СессияАктивна = "Да"` (уверенность: средняя: метод видно только в коде vo2_core, в выдаче справки он не найден).
- Выход: `СБИС.Выход` на `/auth/service/` с тем же `X-SBISSessionID`.
- Лимиты со страницы техтребований (уверенность: средняя, источник один, выдача поиска):
  - не больше 5 активных сессий (в одной выдаче «на устройство», в другой «у пользователя»);
  - не больше 5 параллельных потоков, иначе система ограничивает потоки или блокирует сессию;
  - не больше 4 096 запросов в одном соединении;
  - HTTP-запрос до 100 МБ, вложение до 73 МБ, в документе до 10 вложений.

  Вывод для нас: запросы к Saby идти последовательно, через одну общую сессию, под отдельным пользователем или приложением, чтобы сервис и люди не выбивали друг другу сессии. [techreq_edo](https://saby.ru/help/integration/api/techreq_edo)
- Обработка 1С передаёт заголовок `X-Timeout` в миллисекундах (уверенность: средняя).

### Подтверждение входа (2FA)

- Если в аккаунте включено подтверждение входа, логин и пароль не дают сессию сразу. `Идентификатор` и временную сессию берут из `addinfo` ответа. Потом временная сессия передаётся в `X-SBISSessionID` при вызове `СБИС.ОтправитьКодАутентификации` и `СБИС.ПодтвердитьВход` (`Идентификатор`, `Код`). `ПодтвердитьВход` возвращает sid. [send_code_auth](https://saby.ru/help/integration/api/all_methods/send_code_auth), [accept_enter](https://saby.ru/help/integration/api/all_methods/accept_enter)
- Код приходит пушем или как последние цифры входящего звонка. Для работы по расписанию это не подходит.
- Как обойти:
  - входить приложением;
  - завести отдельного пользователя без 2FA;
  - разрешить вход без подтверждения из доверенных сетей (это настраивает администратор; уверенность: средняя). [another/auth](https://saby.ru/help/another/auth)
- Коды 303, 759, 775 и 756 не воспроизводить в своём клиенте:
  - «303 + dump» относятся к ExtSdk2, это другой продукт;
  - 759, 775 и 756 — внутренние коды обработки 1С, а не ответы сервера.

### Аккаунты и юрлица

- `СБИС.СписокАккаунтов` (`/auth/service/`) возвращает `НазваниеАккаунта` и `НомерАккаунта`.
- `СБИС.ПереключитьАккаунт` принимает `НомерАккаунта` и возвращает новую сессию. [list_of_acc](https://saby.ru/help/integration/api/all_methods/list_of_acc), [change_acc](https://saby.ru/help/integration/api/all_methods/change_acc)
- Документы фильтруются по `НашаОрганизация: {"СвЮЛ": {"ИНН": "<ИНН>", "КПП": "<КПП>"}}`.

### Тариф и стоимость

- Чтобы начать, нужно зарегистрироваться и подключить тариф сервиса ЭДО. Входящие документы не тарифицируются. [api](https://saby.ru/help/integration/api), [edo/tariffs](https://saby.ru/edo/tariffs)
- Утверждение «API входит в любой тариф ЭДО» опровергнуто для минимального тарифа. По сайтам партнёров, «ЭДО Старт» (100 исходящих в год) не включает средства интеграции и роуминг (уверенность: низкая–средняя). Если у владельца только бесплатный приём или «ЭДО Старт», API может быть закрыт. Проверить в кабинете или у менеджера. [tariffs/info](https://saby.ru/tariffs/info), [sbis.spb.ru edo-start](https://sbis.spb.ru/sbis-power/edo-start/)
- Цены в выдаче поиска противоречат друг другу (уверенность: низкая):
  - 200 документов — 3 000 ₽ в год, по другой выдаче 2 300 ₽;
  - 500 — 5 200 ₽ или 4 500 ₽;
  - 1 200 — 11 800 ₽ или 9 400 ₽;
  - 3 000 — 28 000 ₽.
- Отдельно платные API Saby (МЧД 87 000 ₽, «Всё о компаниях», «Максимум+API») для приёмки не нужны. «СБИС Коннект» — это локальный обмен через папку, а не доступ к API.
- Тестовый аккаунт (копия рабочего) платный: подключается через менеджера, ссылка-приглашение действует 10 дней, цена не найдена. [start/test_saby](https://saby.ru/help/start/test_saby) Для этапа 2 нужны только команды чтения, поэтому разумно работать в боевом кабинете (вывод).

## Входящие УПД: методы

### Сводка

| Команда | Адрес | Назначение | Уверенность |
|---|---|---|---|
| `СБИС.СписокДокументов` | `/service/?srv=1` | входящие документы отгрузки за период (`Тип = "ДокОтгрВх"`) | высокая |
| `СБИС.СписокИзменений` | `/service/?srv=1` | лента событий с курсором `ИдентификаторСобытия`, «только новое» | высокая |
| `СБИС.СписокДокументовПоСобытиям` | `/service/?srv=1` | реестры «Входящие» и т. п. с фильтрами по состоянию и типу вложения | средняя |
| `СБИС.ПрочитатьДокумент` | `/service/?srv=1` | последняя редакция документа: вложения, этапы, состояние, ссылки | высокая для запроса, средняя для ДопПоля |
| HTTP GET `Вложение.Файл.Ссылка` | `disk.sbis.ru` | скачать XML УПД | высокая |
| `СБИС.СформироватьHTMLИзXML` | — | только строит HTML из XML, строки товаров не отдаёт | средняя |

### СБИС.СписокДокументов

- Документы возвращаются по дате, со сведениями о вложениях последней редакции, постранично.
- `Тип` обязателен: `ДокОтгрВх` — входящие («Приход (Поступление)»), `ДокОтгрИсх` — исходящие. [list_doc](https://saby.ru/help/integration/api/all_methods/list_doc/), [doc_guide](https://saby.ru/help/integration/api/doc_guide)
- Поля `Фильтр`:
  - `ДатаС`, `ДатаПо` — строки `ДД.ММ.ГГГГ`;
  - `Тип`;
  - `Состояние`;
  - `Маска` — ищет по номеру и примечанию, в номере должна быть хотя бы одна цифра;
  - `НашаОрганизация`;
  - `Контрагент` (можно с `ДопПоля: "СФилиалами"`);
  - `ДопПоля`;
  - `Навигация` — передаётся внутри `Фильтр`.

```
POST https://online.sbis.ru/service/?srv=1
Content-Type: application/json; charset=utf-8
X-SBISSessionID: <sid>

{"jsonrpc":"2.0","method":"СБИС.СписокДокументов","params":{"Фильтр":{
  "ДатаС":"01.10.2026","ДатаПо":"03.10.2026","Тип":"ДокОтгрВх",
  "НашаОрганизация":{"СвЮЛ":{"ИНН":"<ИНН>","КПП":"<КПП>"}},
  "Контрагент":{"СвЮЛ":{"ИНН":"<ИНН поставщика>"}},
  "Навигация":{"РазмерСтраницы":"200","Страница":"0"}}},"id":0}
```

- Ответ лежит в `result.Документ[]`.
- Поля документа (по обезличенному образцу из [драйвера VadimGrigorev](https://github.com/VadimGrigorev/project-free-Russian-retail/blob/main/Modules/FreeForms/ДрайверыЭДО/SBIS/Драйвер.sf)):
  - `Идентификатор`, `Тип`, `Название`, `Номер`, `Дата`, `ДатаВремяСоздания`, `Сумма`;
  - `Направление` (`"Входящий"`), `Удален`;
  - `Контрагент.СвЮЛ{ИНН,КПП,Название}`, `НашаОрганизация`, `Ответственный`, `Регламент`;
  - `Редакция[]{Актуален,ДатаВремя,Идентификатор}`;
  - `Состояние{Код,Название,...}`;
  - `СсылкаНаPDF`, `СсылкаНаАрхив`, `Расширение`;
  - `Вложение[]`.
- Поля вложения: `Тип`, `Подтип`, `ВерсияФормата`, `Номер`, `Дата`, `Сумма`, `Направление`, `Служебный`, `Удален`, `Зашифрован`, `ТипШифрования`, `Упакован`, `СсылкаНаHTML`, `СсылкаНаPDF`, `Файл{Имя,Ссылка,Хеш}`. Ссылка на XML УПД есть уже в списке, поэтому `ПрочитатьДокумент` нужен только когда её нет.
- Если у юрлица несколько КПП или филиалов, драйвер делает отдельный запрос на каждый КПП и убирает дубли по `Идентификатор`. В комментарии драйвера сказано, что СБИС может отдавать дубли в запросах с разными фильтрами.
- Строковые значения фильтра `Состояние` из драйвера (уверенность: низкая): «Неотправленные», «Не получен ответ», «Требующие ответа», «Утвержденные», «Отклоненные», «С ошибками».

### Навигация (постраничный вывод)

- Запрос: `Навигация{РазмерСтраницы, Страница}`. Ответ: `Навигация{Страница, ЕстьЕще, РазмерСтраницы}`. Следующие страницы запрашивать, пока `ЕстьЕще == "Да"`.
- `Страница` считается с 0. `РазмерСтраницы` от 1 до 200.
- Значение по умолчанию различается: 20 на странице `СписокДокументов`, 25 на странице «Объект Навигация». Поэтому `РазмерСтраницы` всегда передавать явно (уверенность: средняя).
- Сервер принимает значения и строками, и числами (так по коду клиентов). [navigation](https://saby.ru/help/integration/api/all_methods/navigation)

### СБИС.СписокИзменений (инкрементальная загрузка)

- Метод возвращает документы, по которым были события документооборота.
- Первый вызов делается с `ДатаВремяС` в формате `"ДД.ММ.ГГГГ ЧЧ.ММ.СС"`. Без неё период начинается за месяц до запроса. `ДатаВремяПо` по умолчанию равна времени запроса минус 1 минута (уверенность: средняя: этот сниппет выдавался рядом со страницей метода для «Отчётности»).
- Следующие порции запрашиваются по `ИдентификаторСобытия` последнего события. [changeslist](https://saby.ru/help/integration/api/all_methods/changeslist)

```
{"jsonrpc":"2.0","method":"СБИС.СписокИзменений","params":{"Фильтр":{
  "ДатаВремяС":"01.10.2026 00.00.00","ПолныйСертификатЭП":"Нет",
  "Навигация":{"РазмерСтраницы":"100"}}},"id":0}
```

```
{"jsonrpc":"2.0","method":"СБИС.СписокИзменений","params":{"Фильтр":{
  "ИдентификаторСобытия":"<Документ[-1].Событие[-1].Идентификатор>",
  "ПолныйСертификатЭП":"Нет","Навигация":{"РазмерСтраницы":"100"}}},"id":0}
```

- Повторять, пока `ЕстьЕще == "Да"`, затем сохранить идентификатор и `ДатаВремя` последнего события.
- Если событие-курсор удалено на сервере, vo2_core повторяет запрос по `ДатаВремяС`.
- Не передавать одновременно `ИдентификаторСобытия` и `Страница`: так делает vscherbo, и это расходится со справкой.
- Метод не поддерживает `Страница = "-1"` и `ВернутьРазмерСписка` (по истории изменений API; уверенность: средняя). [history](https://saby.ru/help/integration/api/history)
- Можно фильтровать по `НашаОрганизация`. Фильтр по `Тип` или `Регламент` в этом методе не подтверждён.
- Элемент ответа: `Документ{Идентификатор, Направление, Тип, Номер, ДатаВремяСоздания, Контрагент, Редакция[], Удален, Событие[]{Название, Идентификатор, ДатаВремя, Вложение[]}}`.
- Правила обработки из справки (их цитирует [vscherbo/sbis](https://github.com/vscherbo/sbis/blob/2f7c20ed77cb404a8df9490fbb2a5998bf0e39c0/sbis.py)):
  - входящий документ создаёт событие «Получение»;
  - «Уведомление об удалении на стороне отправителя» → пометить документ удалённым;
  - «Получение соглашения об аннулировании» → решает ответственный;
  - прочие события пропускать;
  - брать редакцию с `Актуален == "Да"`.

  [sequence/newdoc](https://saby.ru/help/integration/api/sequence/newdoc), [incom_doc](https://saby.ru/help/integration/api/sequence/incom_doc/)
- Уточнение: в vo2_core этот метод используется для обновления статусов, а реестр входящих строится через `СписокДокументовПоСобытиям` (уверенность: средняя).

### СБИС.СписокДокументовПоСобытиям

- Фильтр:
  - `ДатаС`, `ДатаПо`;
  - `ТипРеестра` («Входящие» и др.; точный список не подтверждён);
  - `ТипВложения` (через запятую);
  - `Состояние`;
  - `ДопПоля` (`"Этап,Лицо2"`, плюс `",Расширение"` для статусов в госсистеме);
  - `НашаОрганизация`, `Контрагент`, `Маска`;
  - `Навигация` внутри `Фильтр`.
- Ответ: `result.Реестр[]{Документ, ДатаВремя}` и `result.Навигация`.
- vo2_core читает статус маркировки из `Расширение.СостояниеМарк.Название` (уверенность: средняя). [events_doc](https://saby.ru/help/integration/api/all_methods/events_doc), [vo2_core СписочныеМетоды.1c](https://github.com/saby-integration/vo2_core/blob/master/vo2/ОбщиеФункции/Прочее/СписочныеМетоды.1c)

### СБИС.ПрочитатьДокумент

```
{"jsonrpc":"2.0","method":"СБИС.ПрочитатьДокумент","params":{"Документ":{
  "Идентификатор":"<uuid>","ДопПоля":"ДополнительныеПоля"}},"id":0}
```

- Ответ:
  - `result.Вложение[]` (`Тип`, `Направление`, `Служебный`, `Удален`, `Файл.Ссылка`, `СсылкаНаHTML`, `СсылкаНаPDF`);
  - `result.Этап[]` с `Действие[]` (у `ДокОтгрВх` есть этап «Утверждение» с действиями «Утвердить», «Отклонить», «Переназначить» и служебный этап «Извещение о получении»);
  - `result.Состояние{Код,Название}`;
  - `result.СсылкаНаPDF`.
- Значения `ДопПоля` в коде: `"ДополнительныеПоля"`, `"ЭтапВернутьВсеСертификаты"`. Модификаторы перечисляются через запятую без пробелов.
- Что `ДопПоля: "Расширение"` в этом методе возвращает статус ГИС МТ, не подтверждено (уверенность: низкая).
- Меняет ли чтение статус входящего документа, не выяснено. [read_doc](https://saby.ru/help/integration/api/all_methods/read_doc)

### Выбор вложения УПД

- Брать вложение, у которого:
  - `Тип` из набора `УпдСчфДоп`, `УпдДоп`, `УпдСчфДопПокуп`, `УпдДопПокуп`;
  - `Направление = "Входящий"`;
  - `Удален = "Нет"`;
  - `Служебный = "Нет"`.
- Имя файла продавца начинается с `ON_NSCHFDOPPR`. В старых УПД с маркировкой (5.01) префикс был `ON_NSCHFDOPPRMARK_`. Версию формата определять по `Файл/@ВерсФорм` в самом XML, а не по имени файла или `ВерсияФормата` из образца: образец в драйвере сделан под 5.01.

### Скачивание XML

- Обычный `GET` по `Вложение[].Файл.Ссылка`. Ссылка подписанная: `...?object=simple_file_sd&uuid=...&expire_date=...&diskhmac=...`.
- Все найденные клиенты, включая vo2_core, передают `X-SBISSessionID`. У vo2_core есть флаг, позволяющий его не передавать, но передавать безопасно.
- Ссылки на файлы и подписи действуют один месяц, потом `HTTP 403`. Поэтому ссылки не хранить, а перед скачиванием заново получать через `СписокДокументов` или `ПрочитатьДокумент`. [read_doc](https://saby.ru/help/integration/api/all_methods/read_doc)
- Кодировку брать из пролога XML: обычно `windows-1251`, бывают `utf-8` и `utf-16`.
- `Упакован = "Да"`, вероятно, означает zip (не проверено). `Зашифрован` или `ТипШифрования` требуют отдельной обработки.

## Что внутри УПД (маркировка)

### Версии формата

- Действующий формат — 5.03 по приказу ФНС № ЕД-7-26/970@. По открытым источникам, с 01.04.2025 ФНС допускает только его (уверенность: средняя: страницы со сроками недоступны).
- В 2026 году XSD обновили под НДС 22% (редакция `…_05_03_05`), номер версии остался 5.03.
- Документ продавца:
  - префикс файла `ON_NSCHFDOPPR`;
  - КНД 1115131;
  - `ВерсФорм="5.03"`;
  - `Документ/@Функция` ∈ `СЧФ | СЧФДОП | ДОП | СвРК | СвЗК`.
- Титул покупателя: `ON_NSCHFDOPPOK`, КНД 1115132.
- Имя файла (ИдФайл) ГИС МТ использует как ID документа. [XDTO 5.03.01](https://raw.githubusercontent.com/PyzhovIakov/Jira/HEAD/УТ/src/XDTOPackages/ON_NSCHFDOPPR_1_997_01_05_03_01/Package.xdto), [5.03.05](https://raw.githubusercontent.com/alexPisar/honest_mark_system/HEAD/Reporter/XsdClasses/ON_NSCHFDOPPR_1_997_01_05_03_05.cs)
- ГИС МТ принимает для пива титул продавца версий 5.02 и 5.03 в Windows-1251 (True API v.637). Значит, парсер должен принимать 5.02 и 5.03. В старой истории встречается 5.01.

### Шапка

- В 5.03 номер и дата: `СвСчФакт/@НомерДок` и `@ДатаДок`. В 5.01 было `@НомерСчФ` и `@ДатаСчФ`. Код vscherbo на 5.03 упадёт (уверенность: средняя). [infostart 2355880](https://infostart.ru/1c/tools/2355880/), [ediweb kb/2047](https://ediweb.com/ru-ru/support/kb/2047)
- Покупатель может быть и юрлицом, и ИП. Разбирать оба варианта: om1-saby для юрлица падает.

### Строки товара: `Файл/Документ/ТаблСчФакт/СведТов`

- Атрибуты строки (по XSD 5.03):
  - `НомСтр` — обязателен, до 6 цифр;
  - `НаимТов` — до 2 000 символов;
  - `ОКЕИ_Тов`, `НаимЕдИзм`;
  - `КолТов` — decimal, до 11 знаков после запятой;
  - `ЦенаТов`, `СтТовБезНДС`;
  - `НалСт` — обязателен;
  - `СтТовУчНал`.
- `ДопСведТов`:
  - `@КодТов` — код продавца, до 100 символов; GTIN он быть не обязан;
  - `@АртикулТов` — до 50;
  - `@ГТИН` — ровно 14 символов, необязателен. Атрибут есть с версии 5.02, в 5.01 его нет;
  - `@КодКат`, `@КодВидТов`, `@КодТовОКПД2`.

  В поштучном УПД `@ГТИН` может отсутствовать. Тогда GTIN берётся из каждого кода (символы 3–16).

### Коды маркировки: `СведТов/ДопСведТов/НомСредИдентТов` (0..n на строку)

| Где | Что | Ограничение |
|---|---|---|
| `@ИдентТрансУпак` | транспортная упаковка (SSCC) | атрибут, до 255 |
| `КИЗ` (повторяется) | код единицы | элемент, до 255 |
| `НомУпак` (повторяется) | код групповой упаковки (КИГУ) или вторичной упаковки | элемент, до 255 |
| `@КолВедМарк` | количество при объёмно-сортовом учёте | integer |
| `@ПрПартМарк` | признак партии | до 55 |

- `КИЗ` и `НомУпак` идут как choice внутри одного `НомСредИдентТов`.
- ГИС МТ читает код из любого из трёх мест (`products[].code` в True API), поэтому разбор должен:
  - читать все три;
  - брать все `КИЗ` и `НомУпак` строки, а не первый найденный.

  [CIS.EDM InvoiceItemIdentificationNumber.cs](https://raw.githubusercontent.com/spoleto-software/CIS.EDM/master/src/CIS.EDM/Models.V5_03/Seller/InvoiceItemIdentificationNumber.cs), [ediweb kb/1497](https://ediweb.com/ru-ru/support/kb/1497)
- Какой тег используют реальные поставщики сети, не проверено.

Иллюстрация структуры (не реальный документ, значения условные):

```xml
<СведТов НомСтр="1" НаимТов="<наименование>" ОКЕИ_Тов="796" КолТов="2" ЦенаТов="<цена>" НалСт="<ставка>" ...>
  <ДопСведТов КодТов="<код поставщика>">
    <НомСредИдентТов>
      <КИЗ>01<GTIN-14>21<серийный номер></КИЗ>
      <КИЗ>01<GTIN-14>21<серийный номер></КИЗ>
    </НомСредИдентТов>
  </ДопСведТов>
</СведТов>
```

### Формат кода в УПД

- В УПД кладут код идентификации (КИ) без криптохвоста: `01` + GTIN (14) + `21` + серийный номер. Группа `93` и прочее после GS в документ не передаются.
- По данным сети: в выгрузке ЧЗ 5 849 пивных КИ на балансе, из них 444 кеги. У всех серийный номер 7 символов, КИ 25 символов. Утверждение «у кег серийник 13 символов» опровергнуто. [chz_test/debug/pg15_csv](../../chz_test/debug/pg15_csv/)
- Ключ сравнения — `gtin|serial`: `chz.py::_cis_key`, тот же ключ в `core/receiving_codes.py`. Скан этапа 1 сопоставим с УПД напрямую.
- Скобки вокруг AI недопустимы (ошибка 03 в True API).
- В реальных серийниках встречаются `' " & < > % ( ) ; = ?`. Поэтому:
  - сравнивать коды только после XML-разбора, не по сырому тексту;
  - разбор «человекочитаемого» ввода `(01)…(21)…` в `core/receiving_codes.py` режет
    серийник по `(` — это касается только кода, набранного в таком виде; код со сканера
    или камеры начинается с `01` и не затрагивается.

### Объёмно-сортовой учёт (ОСУ)

- В строке только GTIN и количество, без КИ. Два способа записи:
  - `ДопСведТов/@ГТИН` + `НомСредИдентТов/@КолВедМарк` (5.02 и 5.03);
  - строка `02[gtin]37[count]` (в True API `02[gtin]37[count]3103[netWeight]`) в `НомУпак`.
- По ediweb, в одной позиции нельзя одновременно указывать `ГТИН`/`КолВедМарк` и `КИЗ`/`ИдентТрансУпак` (уверенность: средняя).
- True API помечает такие строки `codeType=OSU` и возвращает `gtin` и `quantity`. GTIN может принадлежать групповой упаковке.
- У сети ОСУ-строки приходят от Метро и в старых поставках. Сверка по ним возможна только по паре «GTIN + количество». [docs/chz-stock-integration.md §1.5](../chz-stock-integration.md)

### Агрегаты (короба, упаковки)

- Поставщик может указать вместо кодов единиц SSCC (`ИдентТрансУпак`) или КИГУ (`НомУпак`).
- КИГУ имеет тот же вид `01+GTIN+21+7 символов`, что и КИ единицы. У 32 из 5 849 кодов сети есть parent. `_cis_key` учтёт такой код как бутылку с чужим GTIN.
- Отличать агрегат по `packageType` или `generalPackageType` из `/cises/info`.
- Раскрывать через `POST /cises/aggregated/list`: 1–1 000 кодов за запрос, возвращается первый слой вложений.
- В `doc/{docId}/info` у параметра `body` указано: «по умолчанию передаётся информация о 50 дочерних КМ». Скрыты дочерние коды только для группы «Духи», поэтому у пива они, вероятно, приходят (уверенность: средняя).

### Количество по кегам

`КолТов` и `ОКЕИ_Тов` задаёт поставщик, единицей могут быть и литры. Поштучную сверку кег вести по числу КИ на GTIN, а не по `КолТов`. Это рекомендация: на реальных УПД не проверено (уверенность: низкая).

### Сроки поэкземплярного учёта пива

- Кеги — с 01.03.2025, для продукции, произведённой или ввезённой с этой даты. Подтверждено и текстом про CONNECT_TAP в True API v.637.
- Потребительская упаковка — с 01.09.2025 по ПП № 2173, с периодом «при наличии технической возможности» до 01.12.2025 по ПП № 1415 (уверенность: средняя; в документах репозитория стоят обе даты).
- Безалкогольное пиво с 01.03.2026 и ЭПД при перевозке пива с 01.09.2026 — не подтверждены.
- Итог на октябрь 2026: свежие УПД должны приходить поштучно, ОСУ остаётся у старого остатка и отстающих поставщиков.

### Двухступенчатая проверка у пива: FIXATION

- До отгрузки поставщик подаёт в ГИС МТ «УПД (отгрузка продукции)», тип `FIXATION`, только с титулом продавца. ID документа: `FIX_<ИдФайл>`. Коды получают особое состояние `MOVING_BY_UD` («Отгружен»). Статус кода остаётся `INTRODUCED`, коды с баланса продавца не уходят.
- `FIXATION_CANCEL` подаёт только отправитель, после этого состояние «Отгружен» снимается.
- Связь с двусторонним УПД подтверждают коды ошибок:
  - 271 — МОД грузополучателя не совпадает с исходным документом;
  - 273 — код не отгружен;
  - 274 — код уже отгружен;
  - 277 — содержание отличается от указанного при отгрузке.
- По открытым источникам, с 01.12.2025 двусторонний УПД без успешного FIXATION обрабатывается с ошибкой (уверенность: средняя, источник один).
- Источник по FIXATION: локальная копия True API v.637, `chz_test/чз/docs.cr11pt.ru.html` (справочник типов документов, раздел 4.1.1, FIXATION_CANCEL, справочник статусов КИ).

- `ON_NSCHFDOPPOK`, путь `Документ/СодФХЖ4/СвПрин/КодСодОпер/@КодИтога`:
  - 1 — принято без расхождений;
  - 2 — принято с расхождениями;

  Ссылка `РеквДокРасх` необязательна. Строк и кодов в титуле нет, поэтому принять часть кодов в нём нельзя. [XDTO ON_NSCHFDOPPOK 5.03](https://raw.githubusercontent.com/PyzhovIakov/Jira/HEAD/УТ/src/XDTOPackages/ON_NSCHFDOPPOK_1_997_02_05_03_01/Package.xdto)

  - не больше 50 запросов в секунду от участника;
  - запросы идут на бар-ПК по SSH: одна команда за раз, до 180 с на пакет, во время ночного обновления (`refresh.lock`) запрос откладывается ([docs/receiving.md](../receiving.md)).

### Методы (по локальной копии True API v.637.0 от 25.03.2026)

**Список документов**

```
GET /api/v4/true-api/doc/list?pg=beer&receiverInn=<ИНН>&documentType=UNIVERSAL_TRANSFER_DOCUMENT&limit=1000
```

- Параметры:
  - `pg` — обязателен;
  - `documentType` — можно массив: `UNIVERSAL_TRANSFER_DOCUMENT`, `UNIVERSAL_TRANSFER_DOCUMENT_FIX`, `UNIVERSAL_CORRECTION_DOCUMENT`, `UNIVERSAL_CORRECTION_DOCUMENT_FIX`, `FIXATION`;
  - `documentStatus`;
  - `documentFormat`;
  - `dateFrom` и `dateTo` — фильтруют по дате документа, а не по `receivedAt`;
  - `senderInn` или `receiverInn` — по документации обязателен один из них. На практике работает и без них (так в chz.py и в [FMU-API](https://github.com/shrayky/FMU-API/blob/b552485e84a7cc9b27f2524a0b87eba31649ee9b/src/Infrastructure/TrueApiIntegration/Services/GisMtDocumentsClient.cs)), но передавать стоит;
  - `limit` — до 1 000;
  - `order`;
  - пагинация: `did` + `orderedColumnValue` + `pageDir=NEXT`.
- Ответ: `number` (ID = ИдФайл), `docDate`, `receivedAt`, `type`, `status`, `senderInn`, `senderName`, `receiverInn`, `invoiceNumber`, `input` (`true` = входящий), `errors`.

**Содержимое документа**

```
GET /api/v4/true-api/doc/{docId}/info?pg=beer&body=true
```

- Тело: `upd`, `updDate`, `updFix`, `function`, `knd`, `sellerInfo{name,inn,kpp,address,edoOperatorName}`, `buyerInfo{...}`, `sumNds`, `tax`, `acceptanceCode`, `contract`, `products[]`, `productsTotal`.
- Элемент `products[]`:
  - `code` — из `КИЗ`, `НомУпак` или `ИдентТрансУпак`;
  - `name` = `НаимТов`;
  - `article` = `КодТов`;
  - `codeType` — `EXEMPLARY` или `OSU`;
  - `gtin` и `quantity` — только для ОСУ;
  - `strNum` = `НомСтр`.
- На верхнем уровне ответа: `senderMod`, `receiverMod`.
- По умолчанию в ответе до 36 000 кодов; есть `limit` и `pageNumber`.
- Для УКД тело содержит `elementType` со значениями `BEFORE` и `AFTER`.

**Остальные методы**

- `POST /api/v3/true-api/cises/info` — до 1 000 КИ за запрос. Формат тела — в разделе 5.1.2 локальной копии, в chz.py он уже реализован.
  - Поля ответа: `ownerInn`, `ownerName`, `status`, `statusEx` (`MOVING_BY_UD`), `ownerMod`, `gtin`, `packageType` / `generalPackageType`, `parent`, `child`, `connectDate`, `volumeSpecialPack`.
  - `applicationMod` — место нанесения кода (производитель или импортёр), а не поставщик.
  - Метод может вернуть 422 «Отсутствует доступ к сведениям», если нет согласия владельца кода (разделы 5.1.2 и 5.8).
- `POST <стенд>/cises/aggregated/list` — дочерние КИ агрегата, первый слой.
- `POST <стенд>/doc/validator/create` и `/api/v3/true-api/doc/validator/status` — предварительная проверка XML УПД «до осуществления приёмки продукции со стороны покупателя». Ответ `VERIFIED` или `NOT_VALID` с перечнем ошибок. Может ли покупатель подать сюда XML продавца из Saby, не проверено.
- `GET /documents/edo/tpr/ud?fileId=<ИдФайл | FIX_ИдФайл>` — квитанция обработки: почему УПД обработан с ошибкой.
- `/cises/history` — история одного кода с `docId` событий, удобна для разбора спорного кода.
- `/api/v4/true-api/cises/search` для сверки поставки не годится: нет фильтра по УПД, коды в состоянии «Отгружен» числятся на поставщике.

### Главные ограничения

1. **Двусторонний УПД попадает в ГИС МТ только после подписи покупателя.** Для `UNIVERSAL_TRANSFER_DOCUMENT` обязательны `second_product_document` и `second_signature`. В справочнике статусов `IN_PROGRESS` означает «Проверяется», а не «ждёт подписи». Поэтому идея из `docs/chz-stock-integration.md` (TODO п. 5: `doc/list?documentStatus=IN_PROGRESS`) и урок 14 в `docs/lessons.md` неверны, их нужно поправить.
2. **Нет цен по строке, ставок, единиц, `КолТов` и немаркированных строк.** `sumNds` — итог по всему документу, включая строки без маркировки.
3. **Виден ли покупателю FIXATION в `doc/list`, неизвестно.** Проверить одним запросом с бар-ПК:
   `GET /api/v4/true-api/doc/list?pg=beer&receiverInn=<ИНН>&documentType=FIXATION&limit=10`
   Если документы вернутся, вызвать `doc/{FIX_...}/info?body=true`. FIXATION поставщик может отменить.
4. **`cises/info` по чужим, ещё не принятым кодам не проверен.** Возможен ответ 422. `MOVING_BY_UD` ставит и `CIS_NOTICE` при экспорте, но для поставки в бар это почти всегда FIXATION.
