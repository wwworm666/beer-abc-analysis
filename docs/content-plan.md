# Контент-план — раздел «Гости» (`/content-plan`, `/api/content-plan/*`)

> Этап «только интерфейс» (2026-09-26, правки по ревью 2026-09-27). Хранение, статусы,
> проверки готовности, предпросмотр, утверждение и журнал работают по-настоящему.
> Отправки нет ни в одну площадку: утверждённая публикация сама никуда не уходит,
> её выход отмечают вручную. Решение владельца: «Делай, пока без интеграций с картами,
> тг и инстаграмом, просто интерфейс».
> С 2026-09-27 черновики плана может готовить ИИ-агент владельца через MCP-платформу
> ([mcp.md](mcp.md)): его материалы помечены «ИИ», правила для него — бриф сети (раздел
> «ИИ-агент» ниже). Утверждает по-прежнему только владелец.

## Что это

План публикаций и рассылок сети на месяц: посты в Telegram-каналах баров, посты в общем
Instagram и рассылки через бота. Страница живёт в разделе сайдбара **«Гости»** рядом с
«Отзывами» ([reviews.md](reviews.md)) и «Маркетингом» ([guests.md](guests.md)); над всеми
тремя страницами стоит общая полоса «Требует внимания» (описана в [reviews.md](reviews.md),
раздел «Полоса «Требует внимания»»).

### Как владелец работает с планом

Концепция владельца (дословно): «Целевой режим — одна основная сессия подготовки на месяц,
а не ежедневная работа SMM-оператора».

| Когда | Что делается | Чем в интерфейсе |
|---|---|---|
| Начало месяца, одна сессия | собрать план: темы, бары, площадки, даты; заполнить тексты и фото; проверить итоговые версии | «Скопировать прошлый месяц», «Добавить материал», карточка материала, предпросмотр |
| Конец сессии | утвердить **только подготовленное** | «Утвердить готовые» |
| В течение месяца | исключения: перенос, пауза бара или сети, новый повод, отметка выхода, повтор после ошибки | карточка, «Пауза», полоса «Требует внимания» |

Главное правило утверждения, тоже словами владельца: «кнопка утверждает конкретные
подготовленные материалы, а не даёт системе разрешение самостоятельно дописывать
оставшиеся черновики. Незаконченные карточки остаются видны, но не уходят в публикацию».
Поэтому «Утвердить готовые» берёт только черновики без единой недостачи, а всё остальное
показывает списком «Останутся черновиками» с причинами.

### Материал и размещение

- **Материал** — тема или пост: название, текст, фото и видео. «Рассказать о новой кухне»
  без размещений — уже материал, но его сводка — «Только тема»; когда размещения появятся,
  экран покажет, чего не хватает до публикации (текста, фото, аудитории, времени).
- **Размещение** — выход материала в конкретную площадку, для конкретного бара (или всей
  сети), в конкретный день и час. У одного материала много размещений: «Октоберфест» —
  в четыре Telegram-канала баров и в Instagram сети.

Таблица показывает материалы (одна строка — одна тема со всеми размещениями), календарь —
размещения на их фактических датах: анонс в Telegram во вторник, версия для Instagram в
среду, напоминание через бота в пятницу.

### Два типа материала

| Тип (`kind`) | Что утверждается | Для чего |
|---|---|---|
| `fixed` — «Готовая публикация» | готовые текст и файлы; выходят ровно такими, какими их утвердили | истории о барах, команда, заранее известные события, кухня |
| `live` — «С актуальными данными» | **шаблон** с подстановками; данные (таплист бара) подставляются в момент выхода | «В пятницу в 16:00 опубликовать текущий таплист каждого бара» |

Для `live` владелец поставил жёсткое условие: «Произвольно менять остальной текст или
придумывать описания система не должна. Если достоверных данных нет — публикация
останавливается и появляется сообщение о проблеме». Отсюда правила остановки в разделе
«Живые данные».

## Как работает

### Модель данных

Файл: `{version: 1, materials: {id: M}, log: [...]}`. Все даты и время — наивные
московские строки (`core/msk_time`): дата `YYYY-MM-DD`, время `HH:MM`, метка
`YYYY-MM-DDTHH:MM`. День недели: 0 — понедельник. Id: `m_`, `p_`, `s_` + 12 hex.

Материал `M`:

| Поле | Смысл |
|---|---|
| `id`, `month` | месяц плана `YYYY-MM`; если есть дата темы, месяц = её месяц (пересчитывается при правке и сдвиге) |
| `title` | до 200 знаков, пробелы схлопываются, пустое нельзя |
| `kind`, `live_source` | `fixed` / `live`; источник данных только у `live` (единственный — `taplist`) |
| `planned_date` | дата темы — ориентир, пока нет размещений; задаёт месяц |
| `base_text` | общий текст (или шаблон у `live`), до 10 000 знаков |
| `media` | `[{name, kind, size, original_name, uploaded_at, uploaded_by}]`, до 20 файлов |
| `media_required` | «Нужно фото»: влияет только на готовность |
| `note` | заметка для команды, до 2000 знаков, в публикацию не уходит |
| `series` | `{id, weekdays}` у материалов одной серии повторов |
| `copied_from`, `source_review_id` | откуда копия; из какого отзыва сделан материал |
| `origin` | `human` или `agent` — кто создал запись: люди или ИИ-агент через MCP; ставит сервер при создании, не редактируется (раздел «ИИ-агент») |
| `agent_rationale` | «Почему этот пост» — пояснение к посту (повод, рубрика, откуда факты), до 2000 знаков, в публикацию не уходит |
| `shot_list` | «Что снять» — список кадров для команды, до 2000 знаков, в публикацию не уходит |
| `placements` | размещения (ниже) |
| `created_*`, `updated_*` | кто и когда; действие через MCP подписано «<login> · агент» |

В ответе API у материала есть и вычисляемое поле `agent_draft` — «черновик ИИ» (раздел
«ИИ-агент»).

Размещение:

| Поле | Смысл |
|---|---|
| `channel` | `telegram` / `instagram` / `bot` |
| `bar` | ключ бара или `all` («Вся сеть») |
| `date`, `time` | день и час выхода; могут быть пустыми у черновика |
| `text` | своя версия текста; `null` — берётся общий текст материала |
| `media` | своя подборка файлов (имена); `null` — все файлы материала |
| `audience` | `{segment}` — только у бота |
| `status` | хранимый статус (ниже) |
| `approved_at`, `approved_by`, `approved_snapshot` | утверждение и снимок `{text, media}` на его момент |
| `published_at`, `published_by`, `failed_error` | отметка выхода, текст ошибки отправки |

Итоговый текст и файлы размещения:

```
effective_text  = placement.text, если он не null, иначе material.base_text
effective_media = placement.media (только те имена, которые ещё есть у материала),
                  если не null, иначе все файлы материала
```

Лимиты хранения (`TITLE_MAX` 200, `TEXT_MAX` 10 000, `NOTE_MAX` 2000,
`MATERIAL_MEDIA_MAX` 20) — не платформенные, это защита от опечаток и разбухания файла.
10 000 — больше самого длинного поста (4096) с запасом на черновик; 20 файлов — два
максимума площадки (10), чтобы держать разные подборки для разных размещений.

### Площадки, бары и аудитории

Числа — факты платформ, а не наши настройки. Длина считается в символах Unicode (`len`),
для кириллицы и латиницы это совпадает со счётчиком в браузере (JS считает суррогатную
пару одним символом, как сервер).

| Площадка | Бар | Текст | Файлы |
|---|---|---|---|
| Telegram (`TG`) | обязателен конкретный бар: у каждого бара свой канал | 4096 без файлов (`sendMessage`); 1024, если есть фото или видео (подпись `caption`) | до 10 (`sendMediaGroup`), по умолчанию не обязательны |
| Instagram (`IG`) | `all` — один аккаунт сети; можно указать бар | 2200 (подпись) | от 1 до 10, хотя бы один файл обязателен |
| Бот | `all` или бар (охват рассылки) | как Telegram | как Telegram |

Бары и короткие имена: Большой пр. В.О — `ВО`, Лиговский — `Лиг`, Кременчугская —
`Крем`, Варшавская — `Вар`; вся сеть — `Сеть`.

Аудитории рассылки бота (`AUDIENCES`): «Все подписчики бота», «Подписчики, выбравшие
бар» (нужен конкретный бар), «Были в баре за последние 30 дней», «Не были 60 дней и
дольше». Размер аудитории неизвестен, пока бот не подключён: в ответе `size: null` и
пояснение «Бот не подключён: размер аудитории появится после интеграции».

Владелец отдельно потребовал: «Выбор всех площадок не должен незаметно включать личную
рассылку всей базе». Поэтому рассылка через бота добавляется только отдельным
размещением с явно выбранной аудиторией, «Все бары» в форме относится только к Telegram,
а утверждение рассылки требует отдельного подтверждения (см. «Утверждение»).

### Статусы (хранятся) и состояния для экрана (вычисляются)

Хранимый `status`:

| Статус | Смысл |
|---|---|
| `draft` | черновик |
| `approved` | утверждено, ждёт времени выхода |
| `paused` | утверждено, но остановлено |
| `published` | вышло (пока отмечается вручную) |
| `failed` | ошибка отправки — зарезервировано для будущей отправки, сейчас не возникает |
| `cancelled` | отменено, остаётся для истории |

`display_state` считается при каждом чтении и не хранится:

| Условие | `display_state` | Подпись |
|---|---|---|
| `draft`, чего-то не хватает | `incomplete` | «Не хватает: …» |
| `draft`, всё заполнено | `ready` | «Готово к утверждению» |
| `approved`, время впереди | `scheduled` | «Запланировано»; у `live` — «Шаблон утверждён, данные — при выходе» |
| `approved`, время прошло | `overdue` | «Время вышло, выход не отмечен» — пока отправки нет, это напоминание отметить выход вручную |
| `paused` / `published` / `failed` / `cancelled` | то же имя | «На паузе» / «Вышло» / «Ошибка отправки» / «Отменено» |

Край: утверждённое размещение без даты или времени (старые данные) считается `scheduled`.

Время сравнивается с точностью до минуты как строка `YYYY-MM-DDTHH:MM` с текущей минутой
по Москве: публикация на 16:00 «в прошлом» с 16:01 (в 16:00 ещё нет).

Цвет на экране выбирается по `display_state`, а не по тону сервера: у `scheduled` и
`published` тон одинаковый (`success`), но это разные состояния. Вид состояний
(`STATE_HUE` в `content_plan.js`, классы `gh-cp-st-*`): черновики — контуром
(`incomplete` пунктир, оранжевый; `ready` контур, акцент), `scheduled` — спокойная
графитовая заливка, `overdue` — оранжевая заливка, `paused` — серый пунктир,
`published` — зелёная заливка, `failed` — красная заливка, `cancelled` — серый,
зачёркнуто. Легенда над таблицей и в календаре та же, что на чипах.

### Готовность черновика

Проверяется только у `draft` (у остальных статусов список пуст). Коды идут строго в этом
порядке — в нём же они печатаются в «Не хватает: …»:

| # | Код | Условие | Текст |
|---|---|---|---|
| 1 | `no_live_source` | `live` без источника | не выбран источник данных |
| 2 | `no_text` / `no_template` | итоговый текст пустой (после обрезки пробелов); `no_template` — у `live` | нет текста / нет шаблона |
| 3 | `bad_placeholder` | у `live` в тексте `{…}` не из списка подстановок; по строке на каждую неизвестную | неизвестная подстановка {x} |
| 4 | `no_media` | файлов нет, а площадка Instagram или у материала «Нужно фото» | нет фото |
| 5 | `too_many_media` | файлов больше 10 | больше 10 файлов |
| 6 | `text_too_long` | только `fixed`: длина больше предела (1024, если у Telegram/бота есть файлы, иначе 4096; Instagram 2200) | текст длиннее N знаков |
| 7 | `no_bar` | `live` на `all` (любая площадка); Telegram на `all`; бот с аудиторией «выбравшие бар» на `all` | для таплиста выберите бар / не выбран бар |
| 8 | `no_audience` | бот без аудитории | не выбрана аудитория |
| 9 | `no_date`, `no_time` | нет даты, нет времени | нет даты / нет времени |
| 10 | `in_past` | дата и время раньше текущей минуты по Москве | время выхода уже прошло |

`ready` = статус `draft` и список пуст.

У `live` длина в готовности не проверяется: подставленный таплист заранее неизвестен, его
длина видна в предпросмотре размещения и в «Проверить на текущих данных».

Пример (сейчас 7 октября 12:00): Telegram ВО, общий текст 1100 знаков, у материала одно
фото, 9 октября 16:00. Файл есть, поэтому предел — подпись 1024: «Не хватает: текст
длиннее 1024 знаков». Уберите фото из подборки этого размещения — предел станет 4096,
и размещение будет готово.

### Сводка материала (колонка «Готовность»)

`material_summary` — первое сработавшее правило. Отменённые размещения не учитываются,
кроме случая «отменены все». `total` — число неотменённых, `ready` — из них готовых,
`counts` — по всем состояниям, `rule` — номер правила, `state` — какое состояние оно
описывает (`empty` для правила 1): по `state` экран выбирает цвет.

| # | Условие | Подпись | Тон |
|---|---|---|---|
| 1 | размещений нет | «Только тема» | muted |
| 2 | все отменены | «Отменено» | muted |
| 3 | есть ошибка отправки | «Ошибка отправки: N» | danger |
| 4 | есть незаполненные | «Не хватает: …» | warning |
| 5 | есть просроченные | «Время вышло: N» | warning |
| 6 | есть готовые | «Готово к утверждению»; если есть и запланированные — «Готово к утверждению: N из M», M = total | accent |
| 7 | все вышли | «Вышло» | success |
| 8 | часть вышла, остальные запланированы или на паузе | «Вышло: N из M» | success |
| 9 | есть на паузе | «На паузе: N» | muted |
| 10 | иначе (все запланированы) | «Запланировано»; у `live` — «Шаблон утверждён, данные — при выходе» | success |

Правило 4 для нескольких размещений говорит, **где** чего не хватает: одинаковые причины
собраны вместе, группы через «; », места — площадка и бар; причина, которой не хватает во
всех неотменённых размещениях, пишется «— везде». С одним размещением — просто список.
Пример: Instagram без фото, TG Вар без времени, TG Лиг готов → «Не хватает: нет фото —
IG Сеть; нет времени — TG Вар». Та же разбивка лежит в `summary.missing`
(`[{code, text, where, everywhere}]`) и показывается в подсказке таблицы (строка в
таблице обрезается до двух строк).

Примеры правил 6 и 8: два готовых и один запланированный → «Готово к утверждению: 2 из 3»;
Telegram вышел, Instagram утверждён → «Вышло: 1 из 2».

**Дата материала** (колонка «Дата», группировка по неделям) = самая ранняя дата
неотменённых размещений, иначе дата темы, иначе нет даты.

### Правила редактирования

«Подпись содержания» размещения — всё, что уходит в публикацию: площадка, бар, сегмент
аудитории, итоговый текст, итоговые файлы, тип материала, источник данных. Перед правкой
и после неё подписи сравниваются.

| Правка | Что происходит с утверждённым / на паузе / с ошибкой |
|---|---|
| подпись содержания изменилась (текст, файлы, бар, аудитория, площадка, тип, источник) | размещение возвращается в черновик, утверждение и снимок снимаются, в журнале `unapprove_auto`, ответ несёт `unapproved: [id]`, экран показывает предупреждение со списком |
| правка общего текста | снимает утверждение только у размещений, берущих общий текст; размещения со своей версией не трогаются |
| загрузка файла | снимает утверждение у размещений с набором «все файлы» (у них изменились итоговые файлы); со своей подборкой — нет. Экран предупреждает до загрузки и оставляет несгораемый тост после |
| удаление файла | убирает имя из подборок размещений, **кроме вышедших и отменённых**; снимает утверждение там, где файл входил в итог |
| перенос даты или времени | утверждение сохраняется; новое время в прошлом у утверждённого или на паузе — 400 «Нельзя перенести утверждённую публикацию в прошлое»; стереть дату или время у утверждённого нельзя (400, сначала снять утверждение) |
| название, заметка, дата темы, «Нужно фото» | не содержание: утверждение не трогают («Нужно фото» влияет только на готовность черновика) |
| вышедшее или отменённое размещение | не редактируется (400 «Размещение уже вышло» / «Размещение отменено») |
| удаление материала с вышедшими размещениями | 409: отмените остальные, материал оставьте для истории |

`failed` снимается в черновик по тем же правилам, иначе повтор отправки ушёл бы со старым
снимком при новом тексте. Смена типа `live` → `fixed` очищает источник данных; тип `fixed`
вместе с источником — 400.

Любая ошибка внутри записи (например, перенос в прошлое) отменяет всю правку: файл не
пишется.

### Утверждение

`POST /api/content-plan/approve {placement_ids, confirm_bot}`:

- утверждаются только черновики, у которых список готовности пуст; остальные уходят в
  `skipped` с причинами («уже не черновик (…)», «размещение не найдено», тексты
  недостающего);
- если среди запрошенных есть рассылка бота, нужен `confirm_bot = true`, иначе 400
  «Подтвердите аудиторию рассылки» и **ничего** не утверждается;
- на момент утверждения пишется снимок `approved_snapshot = {text, media}` — итоговый
  текст и файлы.

Диалог «Утвердить готовые» (`GET /approve-preview?month=&bar=&channel=` под текущими
фильтрами) показывает три списка:

1. «Уйдут в публикацию» — по площадкам; одинаковые строки (материал, дата, время,
   площадка) на нескольких барах собраны в одну строку со списком баров;
2. «Рассылки через бота» — каждая с аудиторией и размером «неизвестно: бот не
   подключён» и **неотмеченным** флажком: утверждаются только отмеченные, и только
   тогда запрос несёт `confirm_bot = true`;
3. «Останутся черновиками» — с причинами.

Размещения месяца для диалога: материал относится к месяцу или дата размещения в месяце;
фильтр бара X берёт размещения бара X и размещения на всю сеть. Строки материалов с
актуальными данными помечены «шаблон · данные при выходе». Кнопка «Утвердить» на
отдельном размещении бота открывает то же подтверждение аудитории.

### Действия и переходы статусов

`POST /placements/<pid>/action {action}`; любой другой переход — 409 с текстом «… (сейчас:
<статус>)».

| Действие | Из | В | Особенности |
|---|---|---|---|
| `pause` | approved | paused | |
| `resume` | paused | approved | 400 «Время выхода прошло — перенесите дату», если время прошло |
| `unapprove` | approved, paused | draft | снимок и отметки утверждения стираются |
| `mark_published` | approved, paused, failed | published | пишутся `published_at`, `published_by`; дальше размещение только для чтения |
| `cancel` | draft, approved, paused, failed | cancelled | остаётся в плане; при снятии паузы, повторе и копировании не учитывается |
| `restore` | cancelled | draft | утверждение не возвращается |
| `retry` | failed | approved | `failed_error` очищается |

Удаление размещения (`DELETE /placements/<pid>`) — из любого статуса, кроме `published`
(409: вышедшее остаётся в истории). «Отменить размещения» в массовых действиях отменяет
все отменяемые размещения выбранных материалов.

### Пауза по бару и по сети

Меню «Пауза» → `POST /bulk-pause {bar, action}`:

| `bar` | Какие размещения трогаются |
|---|---|
| `all` | все размещения сети, любых баров и сетевые |
| бар X | только размещения с `bar == X`; сетевые (`all`) **не** трогаются: общий Instagram не должен останавливаться из-за одного бара |

Пауза ставится только утверждённым с временем впереди. Снятие паузы пропускает те, чьё
время уже прошло, и перечисляет их в `skipped` («… время выхода прошло») — их нужно
перенести. В журнале `bulk_pause` / `bulk_resume` с указанием охвата.

### Перенос материала

«Сдвинуть на N дней» (`POST /materials/<id>/shift {days}`, массово — `POST /bulk`):
сдвигаются дата темы и даты всех невышедших и неотменённых размещений. `days` — целое от
−60 до 60, не 0 (60 дней — два месяца: дальше это уже планирование другого месяца). Если
утверждённое или стоящее на паузе размещение оказалось бы в прошлом — 400, не сдвигается
ничего. Черновик может уехать в прошлое: он покажет «время выхода уже прошло».
Утверждение при сдвиге сохраняется. Месяц материала следует за датой темы.

### Повтор по дням недели (серия)

«Повторять в этом месяце по дням недели» (`POST /materials/<id>/repeat {weekdays, month}`):

- на каждую дату месяца с выбранным днём недели, **не раньше сегодняшнего дня** и не
  занятую этой серией (дата темы, дата материала или дата неотменённого размещения любого
  материала серии, включая источник), создаётся копия;
- копия: то же название, тип, источник, текст, ссылки на те же файлы, «Нужно фото»,
  заметка, «Почему этот пост», «Что снять»; размещения источника (кроме отменённых) —
  черновиками **на дату копии**, со своими текстами, подборками, аудиторией и временем;
  утверждение не копируется; `origin` копии — по тому, кто нажал «Повторить» (человек —
  `human`, агент через MCP — `agent`), а не по источнику;
- источник и все копии становятся одной серией `{id, weekdays}`; дни недели объединяются
  с прежними;
- агент в режиме «Чтение и черновики» (задача по расписанию) повторяет только свой черновик ИИ
  (`guard_draft_mode`, иначе 409); его копии — тоже черновики агента, «Удалить черновики ИИ» за
  месяц повтора уберёт и их.

Край: все размещения копии встают на один день — день повтора. Анонс «за 4 дня до
события» внутри повтора не воспроизводится; повтор рассчитан на однодневные рубрики
(«Таплист пятницы»). Если подходящих дней нет, ответ `created: []` и тост «Новых дат нет».

### Копирование месяца

«Скопировать прошлый месяц» (`POST /copy-month {from, to, with_content}`, `from` по
умолчанию — месяц перед `to`). Правила дат показываются в диалоге с сервера
(`copy_rules` = `COPY_RULES`), а не своим текстом в JS: однажды текст в JS уже разошёлся
с кодом.

Проверки: `to` не раньше текущего месяца (400 «Нельзя копировать в прошедший месяц»),
месяцы разные (400), в `to` ещё нет копий материалов `from` (409 «Этот месяц уже
скопирован»; чтобы скопировать заново, удалите копии). Копируются материалы с
`month == from`. Все копии — черновики, утверждение не переносится, отменённые размещения
не копируются.

#### Обычный материал: опорная дата и сдвиг

```
опора  = copy_anchor(материал):
         1) дата темы;
         2) нет её — самая ранняя дата неотменённого размещения ВНУТРИ месяца-источника;
         3) нет и таких — самая ранняя дата неотменённого размещения;
         4) дат нет — материал копируется без дат.
новая опора = тот же день недели с тем же номером n в месяце, n = (день − 1) // 7 + 1;
              если n-го нет (5-я пятница) — последний такой день, с заметкой
сдвиг  = новая опора − опора (в днях; всегда кратен 7)
каждая дата материала (дата темы и все размещения) + сдвиг
```

Сдвиг кратен 7, поэтому у каждой даты сохраняются день недели, порядок и интервалы.
Переносить каждую дату отдельно по правилу «n-й день недели» нельзя: даты одного
материала из разных «недель месяца» (1–7, 8–14, …) расходятся, и анонс может оказаться
после события.

Пример 1 (из теста): «Событие», дата темы — сб 3 октября (1-я суббота); анонс TG ВО
ср 30 сентября, Instagram чт 1 октября, бот пт 2 октября, TG Лиг сб 3 октября. В ноябре
1-я суббота — 7 ноября, сдвиг +35 дней: размещения 4, 5, 6 и 7 ноября — те же среда,
четверг, пятница, суббота, тот же порядок.

Пример 2 (почему не каждая дата отдельно): дата темы — пн 5 октября, анонс TG — сб
3 октября, напоминание ботом — пн 5 октября. По отдельности: сб 3 октября (1-я суббота)
→ 7 ноября, пн 5 октября (1-й понедельник) → 2 ноября — анонс после напоминания. С опорой:
5 октября → 2 ноября (1-й понедельник), сдвиг +28: анонс → сб 31 октября, бот → пн
2 ноября. Порядок и интервал 2 дня сохранены, а 31 октября вне ноября — заметка «… 31 окт —
вне месяца «ноябрь 2026»: даты сдвинуты вместе с опорной, порядок и интервалы размещений
сохранены».

Почему опора — дата темы, а не самая ранняя дата: дата темы задаёт месяц материала
(`month := месяц planned_date`), и только так дата темы копии гарантированно остаётся в
месяце назначения. Иначе у копии `month` был бы ноябрь, а дата темы — в октябре, и первая
же посторонняя правка перенесла бы материал в другой месяц.

**Край (замечание проверки 2026-09-27, работает так по замыслу).** Размещение копии может
оказаться в месяце **до** месяца назначения:

- дата темы позже анонса в начале месяца (пример 2): TG копии — 31 октября;
- у материала нет даты темы, а единственное размещение стоит в прошлом месяце: октябрьский
  материал с размещением на сб 26 сентября. Внутри октября дат нет, поэтому опора —
  26 сентября (4-я суббота сентября), она переносится на 4-ю субботу октября — 24 октября.
  Копия принадлежит плану ноября, а её размещение стоит 24 октября.

В обоих случаях есть заметка «вне месяца», но копия видна и в октябре: в календаре
октября, в диалоге «Утвердить готовые» октября (он берёт размещения, датированные
месяцем) и в таблице октября при фильтре состояния с пометкой «план: ноябрь 2026». Если
такая дата уже прошла, будет ещё и заметка «дата уже прошла». Что делать: прочитать
заметки после копирования и перенести копию («Сдвинуть на N дней», например +28 или +35)
или поправить даты размещений.

#### Серия: объединение дней

Материалы с общим `series.id` не переносятся по опоре, а создаются заново на каждый день
месяца назначения с днём недели серии (дни недели — объединение по всем дням серии;
здесь, в отличие от повтора, прошедшие дни не пропускаются — о них заметка). Новая серия
получает новый id.

- **Размещения копии** — объединение неотменённых размещений всех дней серии без повторов
  по ключу (площадка, бар, аудитория, время). Разовая отмена одного бара в один день не
  должна пропасть из всего следующего месяца.
- **Текст и файлы** — из самого раннего дня серии, где есть неотменённое размещение
  (он же `copied_from`). Подборка файлов размещения, взятого из другого дня, подгоняется
  к файлам копии: выпавшие имена убираются, а если выпали все — подборка становится «все
  файлы» (пустой список значил бы «без фото», а человек выбирал именно фото).

Заметки серии: какие дни отличались набором размещений («9 окт — нет TG Лиг 18:00», «2 окт —
все размещения отменены»); одно место в разные дни с разным временем, если ни в один день
эти времена не стояли вместе («TG ВО — в разные дни разное время (18:00, 19:00): в копию
взято каждое время, лишнее удалите»; два поста в один день так не помечаются); различались
тексты или файлы («в копию взяты из дня 9 окт»); все дни отменены («копии созданы без
размещений»).

Пример (из теста): живой «Таплист пятницы» 9, 16, 23, 30 октября на четыре бара в 18:00;
9 октября Лиговский отменён, 16 октября свой текст. Копия на ноябрь: пятницы 6, 13, 20,
27 ноября, в каждой все четыре бара, шаблон из 9 октября, две заметки.

#### Что копируется

| Что | `with_content = false` (по умолчанию) | `with_content = true` |
|---|---|---|
| общий текст и файлы `fixed` | очищаются (`''`, `[]`) | копируются; файлы общие с источником (те же имена) |
| своя версия текста и подборка у размещений `fixed` | `null` (общий текст, все файлы) | копируются |
| шаблон, файлы и свои версии у `live` | копируются всегда: шаблон — утверждённый дизайн | копируются |
| название, тип, источник, «Нужно фото», заметка | копируются | копируются |
| «Почему этот пост», «Что снять» | идут вместе с содержанием: у `fixed` очищаются, у `live` копируются | копируются |
| площадка, бар, аудитория, время | копируются | копируются |
| статус, утверждение | черновик, без утверждения | черновик, без утверждения |
| отменённые размещения | не копируются | не копируются |
| `source_review_id` | не копируется | не копируется |
| `origin` | по тому, кто копирует: человек — `human`, агент через MCP — `agent` | то же |

Ответ: `{created: n, notes: [...]}`, заметки без повторов. Если в месяце-источнике нет
материалов — `created: 0` и одна заметка.

### Живые данные (таплист)

Единственный источник — таплист бара из нашего сервиса: снимок кранов
(`extensions.taps_manager`) и реестр Untappd (`core/untappd_registry`), сборка строк —
`core/taplist.full_taplist(..., active_only=True)`. Ни iiko, ни цен здесь нет. Ключ бара
переводится в id таплиста: bolshoy → bar1, ligovskiy → bar2, kremenchugskaya → bar3,
varshavskaya → bar4.

Подстановки (`PLACEHOLDERS`):

| Подстановка | Что подставляется |
|---|---|
| `{бар}` | полное название бара |
| `{дата}` | дата выхода, «9 октября» (дата размещения, иначе сегодня) |
| `{таплист}` | строки кранов через перевод строки |
| `{кранов}` | число активных кранов |

Строка крана:

```
{кран}. {пивоварня} — {название}, {стиль}, {крепость}%
```

Пустые части опускаются (без пивоварни — `{кран}. {название}`). Название — из реестра,
иначе имя iiko. Крепость: округление до 0,01 по правилу half-up (`Decimal`, не `round`),
без хвостовых нулей, десятичная запятая: 5.0 → «5», 6.5 → «6,5», 7.255 → «7,26»; 0 и
пусто не пишутся. Краны идут по номеру (числа по возрастанию, затем нечисловые). Пример:
«3. Василеостровская — Тёмное, Stout, 6,5%».

Подстановка делается одним проходом: название пива со скобками «{…}» повторно не
разбирается. Неизвестная подстановка остаётся в тексте как есть и считается проблемой.

**Публикация будет остановлена**, если (любое из):

| Код | Причина |
|---|---|
| `no_live_source` | не выбран источник данных |
| `no_bar` | бар не выбран (`all`): таплист есть только у конкретного бара |
| `no_data` | бар не найден в таплисте / не удалось прочитать данные / на кранах бара нет активных позиций |
| `unverified` | у крана нет проверенной связи с Untappd — «Кран N: <сообщение реестра>» |
| `bad_placeholder` | неизвестная подстановка |
| `text_too_long` | итоговый текст длиннее предела площадки |

Предел длины (`text_limit_for`) — тот же, что у готовой публикации: Telegram и бот — 1024,
если у размещения есть файлы, и 4096 без них; Instagram — 2200. Без площадки (общая
проверка шаблона кнопкой «Проверить на текущих данных») — 4096, это предел сообщения
Telegram. Ответ несёт `limit_note` — откуда взят предел. Пример: подставленный таплист дал
1300 знаков; у размещения TG с фото — «текст длиннее 1024 знаков», без фото — проходит.

Проблемы данных — не ошибка запроса: ответ 200 с `ok: false` и списком `problems`.
Предпросмотр размещения шлёт площадку и наличие файлов этого размещения, поэтому счётчик
«N / предел» в предпросмотре — предел именно его площадки.

### Фото и видео

| Что | Правило | Почему |
|---|---|---|
| Тип | по **сигнатуре** (первые байты), не по расширению и не по `Content-Type`: JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A`, WEBP `RIFF…WEBP`, MP4 `ftyp` в байтах 4..7 | расширение и тип пишет клиент |
| HEIC/AVIF | отклоняются с текстом «сохраните его как JPEG» (у них тоже `ftyp`, бренд в байтах 8..11) | иначе фото с айфона приняли бы как видео |
| MOV | проходит как видео (бренд `qt  `) | браузеры и Telegram его играют |
| Фото | до 10 МБ (`MAX_IMAGE_BYTES`) | предел Telegram Bot API для `sendPhoto`; у Instagram строже (8 МБ, только JPEG) — проверит будущая отправка |
| Видео | до 50 МБ (`MAX_VIDEO_BYTES`) | предел Telegram Bot API на загрузку файла ботом |
| Тело запроса | больше 50 МБ + 64 КБ — 413 до чтения формы | Flask читает форму в память целиком |
| Файлов у материала | до 20 | см. «Модель данных» |
| Имя | `cp_<YYYYMMDD>_<12 hex>.<ext>`, `ext` — `jpg`, `png`, `webp` или `mp4`: префикс раздела, московская дата загрузки, 48 бит случайности | каталог читается глазами; ссылку нельзя угадать |
| Доступ к диску | только через `MediaStore.path()`: имя проверяется регуляркой `NAME_RE` (конец строки `\Z`) до любого обращения к диску, конкатенации пути с пользовательской строкой нет | `../` и обратные слэши отсекаются формой имени |
| Раздача | явный тип по расширению, `X-Content-Type-Options: nosniff`, `Cache-Control: private, max-age=86400`, поддержка Range для перемотки видео | имя неизменно: новая загрузка — новое имя, сутки кэша безопасны |

Порядок загрузки: размер тела (413) → материал есть (404) и не набрал 20 файлов (400) →
сигнатура и размер (400) → запись на диск (через временный файл и `os.replace`) → привязка
к материалу. Если привязка не удалась, записанный файл удаляется — сирот не остаётся.
Перекодировки нет (Pillow в образе нет), файл хранится как есть.

**Общие файлы.** Повтор и копирование с текстами ссылаются на те же имена. Поэтому файл
удаляется с диска, только когда на него не ссылается ни один материал и ни один снимок
утверждения (`_media_referenced`). Удаление из материала не трогает подборки вышедших и
отменённых размещений: их подборка — история.

На экране: перетаскивание в зону или кнопка «Выбрать файлы». Само поле выбора файлов
`#cpFile` живёт **вне** карточки: карточка перерисовывается целиком (автосохранение, ответы
сервера), и поле внутри неё отрывалось бы от страницы, пока открыт системный диалог, —
выбранный файл молча терялся (см. [lessons.md](lessons.md)). Клиент заранее отсекает файлы
больше предела по `type` браузера и грузит по одному.

### Что показывает вышедшее размещение

| Статус | Текст и файлы | `content_source` |
|---|---|---|
| `published`, `failed` со снимком | из снимка утверждения: то, что ушло (или уходило) в площадку | `snapshot` |
| все остальные | текущие `effective_text` / `effective_media` | `current` |

У `approved`/`paused` текущее и снимок совпадают всегда: любое изменение содержания
снимает утверждение. Правка общего текста или удаление файла после выхода вышедшее
размещение не меняет.

Каждое размещение в ответе несёт `media_items: [{name, kind, url, original_name}]`: `kind` —
по расширению имени, `url` — маршрут раздачи. Поэтому ссылка работает и для файла, которого
у материала уже нет (он остался только в снимке и с диска не удалялся); `original_name`
тогда `null`. Экран подписывает такое размещение «Так вышло: текст и файлы на момент
утверждения».

Край: у вышедшего материала с актуальными данными снимок хранит **шаблон**, а не
подставленный таплист. Предпросмотр такого размещения строится по данным на сейчас и
подписан «данные на сейчас, не на момент выхода».

### Месяц в ответе и вид «по всем месяцам»

`GET /api/content-plan?month=M` отдаёт материалы с `month == M` **плюс** материалы других
месяцев, у которых есть размещение с датой в M (`in_month: false`: таблица их не
показывает, календарь показывает их размещения, при фильтре состояния таблица показывает их
с пометкой «план: <месяц>»). `stats`: `materials` — число материалов месяца, `placements` и
`by_state` — размещения материалов месяца и размещения, датированные месяцем.

Вид «по всем месяцам» (`state_payload`): `GET /api/content-plan?state=overdue|failed`
**без** `month` отдаёт материалы **любого** месяца, у которых есть размещение в этом
состоянии, — в том же виде, что месяц, плюс `scope: 'state'` и `state`; `month` — текущий
месяц по Москве, `in_month` у всех `true`, `stats` — по этим материалам. Зачем: счётчики
полосы «Время вышло» и «Ошибки отправки» считают размещения за любой месяц (отправки нет, и
просроченное копится через границу месяца), а вид месяца показал бы по их ссылке пустую
таблицу. С `month`, или с другим `state`, — обычный месяц (фильтр `?state=` применяет
экран).

На экране: только в виде «Таблица»; строки сгруппированы по месяцам; над таблицей чип «Все
месяцы · Время вышло» (или «Ошибки отправки») с крестиком. Выход в обычный месяц —
крестиком, стрелками месяца, кнопкой месяца, переходом в календарь или выбором другого
состояния; фильтр состояния при этом остаётся, а месяц пишется в адрес явно (иначе
перезагрузка снова открыла бы сквозной вид). «Утвердить готовые» и «Скопировать прошлый
месяц» в этом виде выключены: обе операции работают с одним месяцем. Если размещение в
открытой карточке перестало быть просроченным, материал выпадает из списка, а карточка
остаётся на нём. Если сервер не ответил `scope: 'state'`, страница честно остаётся в месяце.

### Экран

**Полоса фильтров:** месяц (стрелки; нажатие на месяц — текущий), бар (общий для раздела,
`localStorage 'gh.bar'`), площадка, вид «Таблица | Календарь», справа «Утвердить готовые» и
«Добавить материал». Под ней баннер «Отправка пока не подключена…» (пока все
`delivery_connected` ложны), сводка месяца и «Бриф для агента», «Скопировать прошлый месяц»,
«Пауза»; рядом со сводкой — чип «Только от ИИ» и «Удалить черновики ИИ», когда в плане есть
материалы агента (раздел «ИИ-агент»).

**Фильтры:** бар X — размещения с `bar == X` и размещения на всю сеть; площадка — по
`channel`; состояние (`?state=`) — по `display_state`. Материал без подходящих размещений
скрыт; тема без размещений видна при фильтрах бара и площадки, но не при фильтре состояния.

**Сводка месяца** (числа сервера, без учёта фильтров): Материалов, Размещений, Готово к
утверждению, Запланировано, Не хватает данных — всегда; Время вышло, На паузе, Ошибки отправки —
только если больше нуля. Нажатие — фильтр этого состояния.

**Таблица:** «Без даты» первыми, затем недели с понедельника по воскресенье (в сквозном
виде — месяцы). Колонки: выбор, дата, материал (метки «Живые данные», «серия: пт», «из
отзыва», «копия», «план: <месяц>», начало текста), размещения чипами (площадка, бар, время;
дата, если отличается от даты материала; скрытые фильтром — «+N»), готовность (сводка;
подсказка — полная подпись, разбивка «чего не хватает и где» и правила). Отмеченные строки
получают панель массовых действий: сдвиг, отмена размещений, удаление (`POST /bulk`, до
500 материалов за раз; каждый материал — своя запись, ошибка по одному не отменяет
остальные и возвращается в `failed`).

**Календарь:** сетка месяца с понедельника; в дне до 4 размещений (`CAL_MAX_PILLS`), дальше
«ещё N»; метка плотности — от 3 **разных материалов** в день (`CAL_DENSE_MIN`; один «Таплист
пятницы» на четыре бара — один материал, а не перегрузка дня; отменённые не считаются);
метка «пост + бот» — в один день и пост (TG/IG), и рассылка бота для пересекающейся
аудитории (одна из них на всю сеть или бар совпадает); темы без размещений в месяце —
отдельной плашкой на дату темы. Слой «Отзывы» (выключен по умолчанию) — «N отз · 4,3» по
`/api/reviews/daily`. Нажатие на пустое место сегодняшнего или будущего дня — новый материал
с этой датой темы. На телефоне вместо сетки — список по дням.

**Карточка материала** (справа, на телефоне — на весь экран; `?open=<id>`): название, тип,
дата темы, готовность; «Содержание» (общий текст или шаблон со счётчиком по самому строгому
пределу среди размещений, берущих общий текст; источник, подстановки кнопками, «Проверить
на текущих данных»; файлы; «Нужно фото»; заметка); «Размещения» (строка на каждое,
недостающее, действия по статусу, редактор: бар, дата, время, аудитория, своя версия
текста, подборка файлов; форма «Добавить размещение»: Telegram — флажки баров и «Все
бары», по размещению на бар; Instagram — по умолчанию «Вся сеть»; бот — только с явной
аудиторией; дата — дата темы, время по умолчанию 12:00); «Предпросмотр» (вкладка на каждое
неотменённое размещение: пузырь Telegram или бота, квадрат Instagram; «N / предел»);
«Повтор и перенос»; «История» (журнал, последние 8 записей и «Показать все»).

**Автосохранение:** тексты уходят через 700 мс после последнего нажатия (`AUTOSAVE_MS`) и
сразу при уходе из поля. Название, пока поле в фокусе, остаётся как набрано (сервер
схлопывает пробелы, и перерисовка съела бы набранный пробел между словами); при уходе из
поля оно нормализуется; пустое название не сохраняется. Если сервер отклонил правку (400),
поля карточки перерисовываются из последнего ответа сервера — в поле не остаётся
несохранённое значение.

**Дата и время** сохраняются только целым значением. Браузер шлёт `change` на каждый
сегмент (день, месяц, год): «2» в дне уже даёт целую, но не ту дату, а перерисовка после
ответа сбрасывала позицию ввода — так утверждённая публикация уезжала на чужой день.
Правила: изменение без нажатия клавиши в этом поле за последнюю 1 с (`DT_TYPING_MS`) — выбор
в календаре браузера, сохраняется сразу; набор с клавиатуры ждёт Enter или ухода из поля;
неполное значение (`validity.badInput`) или год вне 2020–2100 не отправляется — поле
возвращается к сохранённому, тост объясняет; пока идёт набор, карточка не перерисовывается.

**Уход со страницы:** на `pagehide` всё несохранённое (тексты и целые даты) уходит сразу с
`fetch keepalive` (`GH.api(..., {keepalive: true})`) — обычный запрос браузер оборвал бы
вместе со страницей; при скрытии вкладки сохраняются тексты. После каждого успешного
изменения перечитываются план и полоса «Требует внимания».

### Параметры адреса

| Параметр | Значения | Что делает |
|---|---|---|
| `month` | `YYYY-MM` | месяц плана; без него — текущий по Москве |
| `view` | `table` (по умолчанию), `calendar` | вид |
| `open` | id материала | открыть карточку; если материал в другом месяце — страница переключается на его месяц с тостом |
| `state` | `overdue`, `failed`, `incomplete`, `ready`, `scheduled`, `paused` | фильтр состояния (снимаемый чип); `overdue`/`failed` **без** `month` в виде таблицы — вид «по всем месяцам» |
| `origin` | `agent` | фильтр «Только от ИИ»: только материалы, которые создал ИИ-агент |
| `brief` | `1` | открыть карточку «Бриф для агента» |

Ссылки извне: полоса «Требует внимания» ведёт на `?view=calendar`, `?state=failed`,
`?state=overdue`; «Отзывы» — на `?open=<id>` и `?month=<m>&open=<id>`.

### API

Все маршруты за общим гейтом авторизации. Необязательный `?month=YYYY-MM` у изменяющих
запросов задаёт месяц просмотра: по нему считается `in_month` материала в ответе (без
него — `true`). Ошибки: 400 `{error}` — ввод; 404 — нет материала, размещения или файла;
409 — действие недопустимо в текущем статусе; 413 — тело загрузки больше предела видео;
503 `{error, code: 'content_plan_unavailable'}` — файл плана есть, но не читается;
503 `{error, code: 'content_brief_unavailable'}` — то же для файла брифа.

Через MCP (агент владельца) вызываются ровно эти маршруты: мост исполняет их от имени
владельца с `via_mcp: True`, и хранилище само ставит `origin: 'agent'` и подпись
«<login> · агент» — маршрутам ничего передавать не нужно. Инструменты раздела — `content_*`
([mcp.md](mcp.md)).

| `POST /api/content-plan/bulk` | `{material_ids: [..], action: 'shift' \| 'delete' \| 'cancel', days?}` | `{done, failed: [{id, error}]}` | 400: не то действие, пустой список, больше 500, неверный сдвиг |
| `POST /api/content-plan/agent-drafts/delete` | `{month, material_ids?}` — «Удалить черновики ИИ»; без `material_ids` — все черновики агента месяца | `{deleted: [id], skipped: [{id, reason}]}` | 400: нет или неверный месяц, `material_ids` не список, пустой или длиннее 500 |
| `POST /api/content-plan/copy-month` | `{from?, to, with_content?}` | `{created, notes}` | 400 прошедший или совпадающий месяц, формат; 409 уже скопирован |
| `GET /api/content-plan/brief` | — | `{brief, stored, total, schema}`; `stored: false` — файла нет, показана затравка | 503 файл брифа не читается |
| `PUT /api/content-plan/brief` | `{sections: {...частично}}` | `{brief, stored, total, changed}` | 400: неизвестный ключ, раздел, бар или поле, неверный тип, превышен предел; 503 |
| `GET` / `POST /api/content-plan/live-preview` | `source, bar, material_id, placement_id, date, template, channel, has_media` (POST — тем же JSON, для длинного шаблона) | `{ok, text, problems, length, limit, limit_note, channel, has_media, rows, data_at}` | 400 неизвестная площадка, размещение другого материала, неверная дата; 404 |
| `GET /api/content-plan/materials/<id>/log` | — | `{entries}` новые сверху (и у удалённого материала, если записи есть) | 404 |

`live-preview` берёт значения по старшинству: переданный параметр → размещение
(`placement_id`: его шаблон с учётом снимка, бар, дата, площадка, есть ли файлы) →
материал (`material_id`: общий текст, все файлы) → умолчания (дата — сегодня).

### Журнал

Каждое изменение пишет запись `{at, by, action, material_id, placement_id, text}`. Действия:
`create`, `edit`, `delete`, `add_placement`, `edit_placement`, `delete_placement`,
`unapprove_auto`, `approve`, `pause`, `resume`, `unapprove`, `mark_published`, `cancel`,
`restore`, `retry`, `bulk_pause`, `bulk_resume`, `shift`, `repeat`, `copy_month`,
`media_add`, `media_delete`. Хранятся последние 5000 записей (`LOG_MAX`, около года
активной работы четырёх баров; больше — разбухание файла). Автор — `login` сессии; действие
ИИ-агента через MCP — «<login> · агент» (`actor_label`). «Удалить черновики ИИ» пишет `delete`
на каждый удалённый материал с текстом «Удалён черновик агента «…» (массовое удаление черновиков
ИИ)».

### Хранение

Как `core/supplier_directory.py`: запись под `threading.Lock` и межпроцессной файловой
блокировкой, строгое перечитывание файла внутри блокировки, атомарная запись. Удаление
осиротевших файлов — после записи JSON, по принципу «лучшее усилие». Файла нет — пустой
план. Файл есть, но не читается, не JSON или неожиданной структуры —
`ContentPlanUnavailable` (API 503), и файл **никогда** не перезаписывается. Часы хранилища
подменяются (`ContentPlanStore(now_fn=...)`), поэтому тесты детерминированы.

### ИИ-агент (MCP, 2026-09-27)

Владелец подключает к сайту ИИ-агента Claude через MCP-платформу ([mcp.md](mcp.md),
подключение — [guides/mcp-connect.md](guides/mcp-connect.md)). Агент контент-планов работает
через коннектор `/mcp/content` теми же маршрутами, что и страница, и готовит **черновики**: темы,
тексты, размещения, задания на съёмку. Утверждает только владелец. Правила агента — раздел
«Контент и отзывы» в `core/mcp/tools/content.py` (`INSTRUCTIONS`) и сценарии
`content_plan_month`, `content_review_week`, `content_reviews_digest`.

**Как сервер узнаёт агента.** Мост MCP исполняет маршрут от имени владельца и кладёт в
пользователя `via_mcp: True` (`is_agent_user`). Клиент это поле не присылает и подделать через
тело запроса не может: признак берётся только из `current_user()` сервера.

| Что | Правило | Где |
|---|---|---|
| `origin` материала | `agent`, если материал создан через MCP, иначе `human` (`origin_of`); ставится сервером **при создании** записи и больше не меняется. `origin` в теле POST или PATCH — 400 «Происхождение материала (origin) ставит сервер…» (`_reject_origin`): иначе агент мог бы выдать свой черновик за работу людей. Старые материалы без поля читаются как `human` (до 2026-09-27 MCP не было); значение вне `human`/`agent` в файле — файл повреждён (503), неизвестное значение не перезаписывается | `core/content_plan.py` |
| копии | повтор по дням недели и копирование месяца создают **новые** записи; их `origin` — по тому, кто выполнил действие, а не по источнику: человек скопировал материал агента — копии `human`, агент скопировал месяц — копии `agent`. Так «Удалить черновики ИИ» трогает только то, что агент сделал сам | `_copy_material` |
| подпись | действие через MCP подписано «<login> · агент» — в журнале (`by`) и в полях `created_by`, `updated_by`, `approved_by`, `published_by`, `uploaded_by` (`actor_label`) | `core/content_plan.py` |
| «Почему этот пост» (`agent_rationale`) | пояснение: повод, рубрика, бар, откуда факты. Строка до 2000 знаков (`AGENT_TEXT_MAX`, как у заметки: абзац, который владелец прочтёт при проверке; длиннее — это уже второй текст поста). Правка не снимает утверждение — это не содержание публикации | POST/PATCH материалов |
| «Что снять» (`shot_list`) | список кадров для команды: что, в каком баре, время суток, люди в кадре. До 2000 знаков, утверждение не снимает | то же |
| «Черновик ИИ» (`agent_draft` в ответе) | `origin: 'agent'` и все размещения — `draft` или `cancelled`; материал без размещений (тема) — тоже черновик (`is_agent_draft`, `AGENT_DRAFT_RULE`) | `material_json` |

Агенту сервер сообщает пределы полей в ответе плана (`field_limits`: название 200, текст 10 000,
заметка, «почему» и «что снять» — 2000), список `origins` и текст правила черновика
(`agent_draft_rule`) — чтобы он не упирался в 400 вслепую; экран держит те же числа.

**Режим «Чтение и черновики» (коннектор `/mcp/content/draft`, с 2026-09-28).** Задача по
расписанию, которая готовит план, подключается в этом режиме ([mcp.md](mcp.md), «Режимы
доступа»). Из записи ей доступны только инструменты с пометкой `draft_write`; в контент-плане их
пять: создать материал (`POST /materials`), изменить материал (`PATCH /materials/<id>`),
повторить по дням недели (`POST /materials/<id>/repeat`), добавить размещения
(`POST /materials/<id>/placements`) и изменить размещение (`PATCH /placements/<pid>`). Шестой —
черновик ответа на отзыв ([reviews.md](reviews.md)); весь набор закреплён
`tests/test_mcp_modes.py`. Утверждение, отметка «вышло», пауза, отмена, удаление, сдвиг,
копирование месяца, файлы и бриф в этом режиме сервер не исполняет вовсе.

Правило `guard_draft_mode` (`core/content_plan.py`): в режиме `draft` правка материала, повтор по
дням недели, добавление и правка размещений разрешены, только если материал — черновик ИИ
(`is_agent_draft`: `origin: 'agent'` и все размещения `draft` или `cancelled`). Иначе 409 «В режиме
«чтение и черновики» агент меняет только свои черновики: этот материал создан не агентом или в нём
уже есть утверждённые размещения». Новый материал создаётся всегда: через MCP он и так получает
`origin: 'agent'`. Копии повтора — тоже черновики агента: `origin` по тому, кто повторяет, а
размещения копируются черновиками.

Зачем: по расписанию агент читает отзывы гостей и описания пива; «команда», спрятанная в таком
тексте, не должна переносить, менять или снимать утверждение с публикаций владельца. Режим ставит
мост (`g._current_user['mcp_mode']`); у людей на сайте его нет, для них правило не действует.
Пример: агент по расписанию пытается поправить текст материала, который создал владелец, — 409;
добавить размещение в свой новый материал — можно; повторить по пятницам свой новый «Таплист
пятницы» — можно, материал владельца — 409; поправить свой материал, у которого одно размещение
владелец уже утвердил, — 409.

**На экране:**

- пометка «ИИ» у материалов агента — в строке таблицы, на плашках календаря, в шапке карточки и в
  окне «Утвердить готовые»; подсказка: «Материал создал ИИ-агент (через MCP) от имени владельца.
  Проверьте текст, фото и размещения перед утверждением: агент только готовит черновики»;
- в карточке — разделы «Почему этот пост» и «Что снять» с автосохранением (как у текстов, 700 мс)
  и счётчиком до 2000; у материала агента подписи «пояснение агента» и «список кадров от агента»,
  у материала людей поля тоже есть (подписи «по желанию» и «список кадров»);
- рядом со сводкой месяца — чип «Только от ИИ» с числом материалов агента в плане месяца (адрес
  `?origin=agent`): скрывает материалы людей в таблице и календаре; под этим фильтром «Утвердить
  готовые» утверждает только материалы агента (запрос с `origin=agent`). Блок виден, когда в плане
  есть материалы агента или фильтр включён;
- кнопка «Удалить черновики ИИ: N» — когда в плане месяца есть черновики ИИ (в виде «по всем
  месяцам» её нет: удаление — по месяцу);
- кнопка «Бриф для агента» в панели действий — выдвижная карточка брифа (`?brief=1` открывает её
  сразу); одновременно открыта одна выдвижная карточка.

**«Удалить черновики ИИ»** (`POST /api/content-plan/agent-drafts/delete {month, material_ids?}`,
`ContentPlanStore.delete_agent_drafts`):

- удаляются материалы с `month == month`, `origin: 'agent'` и всеми размещениями `draft` или
  `cancelled`; всё — одной записью файла; журнал — `delete` на каждый материал; файлы, на которые
  больше никто не ссылается, удаляются с диска после записи;
- экран передаёт ровно те id, которые назвал в подтверждении (до 8 названий, дальше «и ещё N»):
  если план за это время изменился, лишнего не удалится; агент может вызвать без `material_ids` —
  тогда все черновики агента месяца;
- не удаляется (-> `skipped` с причиной): материал агента, у которого есть утверждённое, стоящее на
  паузе, вышедшее или ошибочное размещение («это уже не черновик»); при переданных id ещё — нет
  такого материала, материал другого месяца, материал людей. Материалы людей без `material_ids`
  не рассматриваются вовсе;
- ответ `{deleted, skipped}`; экран показывает тост с числом удалённых и первой причиной пропуска.

Пример: в плане ноября агент создал 12 материалов; 2 из них владелец утвердил, 1 — тема без
размещений. «Удалить черновики ИИ: 10» удалит 10 (9 с черновыми размещениями и тему), 2
утверждённых останутся.

#### Бриф сети для агента (`core/content_brief.py`)

Постоянные правила сети, по которым агент пишет черновики. Агент читает бриф целиком перед каждым
черновиком (`content_brief_get` = `GET /api/content-plan/brief`). Бриф ничего не публикует и не
утверждает.

Структура (`content_brief.json`, версия 1): текстовые разделы `network` («О сети»), `tone` («Тон и
голос»), `rubrics` («Рубрики»), `rhythm` («Ритм публикаций»), `taboo` («Табу»),
`alcohol_ads_rules` («Реклама алкоголя»), `photo_rules` («Фото и видео»), `notes` («Заметки»);
`examples` — примеры удачных постов списком; `bars` — по каждому из четырёх баров поля
`character` («Характер»), `audience` («Гости»), `hours` («Часы работы»), `kitchen` («Кухня»),
`events` («События»), `photo_spots` («Где снимать»); `updated_at` (МСК, до минуты) и `updated_by`
(«<login>» или «<login> · агент»). Подписи и подсказки полей сервер отдаёт в ответе GET (`schema`) —
их читают и экран, и агент.

Пределы (длина = число символов Unicode, как счётчик в браузере):

| Что | Предел | Почему |
|---|---|---|
| текстовый раздел | 3000 | страница правил: длиннее агент выполняет хуже, а владелец не перечитывает |
| пример поста | 4096 | самый длинный пост плана — сообщение Telegram без фото |
| примеров | 10 | образцов хватает, чтобы уловить голос; больше — архив, а не образец |
| поле бара | 1000 | абзац о баре |
| весь бриф | 40 000 | агент перечитывает бриф целиком; мост MCP обрезает ответ длиннее 60 000 знаков — 40 000 оставляют запас на описание полей (~4 000) и экранирование JSON |

«Весь бриф» — сумма длин всех разделов, примеров и полей баров. Правка, после которой бриф
длиннее 40 000 **и** длиннее, чем был, — 400; правка, которая бриф сокращает, проходит даже сверх
предела. Пределы полей проверяются только у переданных полей. Пример: бриф 39 990 знаков, в «Тон»
дописали 20 -> 40 010 > 40 000 и больше, чем было -> 400 «Бриф длиннее 40 000 знаков (стало бы
40 010)».

Правила слияния (`PUT {sections: {...}}`):

- меняются только переданные поля, остальное остаётся как было;
- текстовый раздел и поле бара заменяются целиком; `null` — пустая строка;
- `examples` заменяется всем списком; пустые примеры (из одних пробелов) отбрасываются;
- `bars` сливается по барам и полям: `{bars: {ligovskiy: {hours: '…'}}}` меняет только часы
  Лиговского;
- неизвестный ключ тела, раздел, бар или поле, неверный тип, превышение предела — 400, не
  сохраняется **ничего** (проверка до записи);
- правка без изменений файл не пишет и `updated_at` не меняет;
- ответ `{brief, stored, total, changed: ['tone', 'bars.ligovskiy.hours', …]}`.

Файла нет — действует затравка в памяти: «О сети» — список баров с названием, адресом и числом
кранов из `core/venues_config`, остальное пусто (`stored: false`, экран пишет «Бриф ещё не
сохранён: в разделе «О сети» — затравка из справочника баров сервиса…»); на диск затравка
попадает вместе с первой правкой. Файл есть, но не
читается, не JSON, неожиданной структуры, с неизвестным разделом, баром, полем или версией новее —
503 `content_brief_unavailable` и на чтение, и на запись; файл **никогда** не перезаписывается.
Хранение — как у плана: `threading.Lock` + файловая блокировка, перечитывание внутри блокировки,
атомарная запись.

Карточка «Бриф для агента» на экране: все поля с автосохранением (одно поле — один PUT) и
счётчиками длины; поля, подписи и пределы — из `schema` ответа сервера; отклонённое значение
остаётся в поле с красным счётчиком, чтобы его можно было сократить; несохранённое уходит при
уходе со страницы. Пустой раздел брифа агент по правилам не додумывает: спрашивает владельца или
явно отмечает допущение.

### Что сломается, если менять неправильно

- **Подпись содержания** (`_content_signature`): убрать из неё поле — и правка этого поля
  после утверждения уйдёт в публикацию без повторного утверждения.
- **Снимок и ссылки на файлы:** если `_media_referenced` перестанет смотреть в снимки,
  удаление файла из материала сотрёт с диска картинку вышедшего поста.
- **Формат времени:** сравнения «прошло / впереди» — строковые по `YYYY-MM-DDTHH:MM` и
  текущей минуте. Секунды, пробел вместо `T` или часовой пояс в строке сломают `overdue`,
  `in_past`, паузу и сдвиг.
- **Пределы 4096 / 1024 / 2200 и 10 файлов** — факты платформ. Поднять их — значит
  утверждать посты, которые площадка отвергнет.
- **Пауза бара** не должна трогать `bar == 'all'`, иначе пауза одного бара остановит общий
  Instagram.
- **Опора копирования:** заменить на «самую раннюю дату» — дата темы копии уйдёт из месяца
  назначения, и материал «переедет» при первой правке. Ключ объединения серии без времени
  склеит разные посты одного бара в день.
- **Подстановка одним проходом:** цепочка `str.replace` разберёт скобки внутри названия
  пива как подстановку.
- **Битый файл:** если `_load` на ошибке вернёт пустой план, следующая запись сотрёт весь
  контент-план.
- **Счётчики полосы и вид «по всем месяцам»:** определения `attention_counts` и
  `state_payload` должны совпадать с подсказками полосы, иначе ссылка откроет не то, что
  посчитано.
- **Имя файла:** `NAME_RE` заканчивается `\Z`; с `$` имя с переводом строки в конце прошло
  бы проверку формы.
- **Экран:** цвет — по `display_state`, не по тону; поле `#cpFile` — вне карточки; дата и
  время — только целым значением. Каждое из этих правил закрывает найденную ошибку.
- **`origin` из тела запроса:** если принять его в POST или PATCH, агент сможет выдать свой
  черновик за работу людей, и «Удалить черновики ИИ» его не тронет (или удалит чужое).
- **`origin` копии по источнику** вместо «кто копирует»: человек, скопировавший месяц с
  материалами агента, получит копии с пометкой «ИИ», и массовое удаление снесёт его работу.
- **«Чинить» неизвестный `origin` в `human`:** следующая запись сотрёт значение, которого эта
  версия не понимает; поэтому битое значение — 503, как у типа материала.
- **Правило черновика ИИ:** если считать черновиком материал с утверждённым или вышедшим
  размещением, «Удалить черновики ИИ» удалит одобренное владельцем, а режим «Чтение и черновики»
  (`guard_draft_mode`) даст расписанию править утверждённое.
- **`guard_draft_mode`:** убрать проверку из правки материала, повтора или размещений — «команда»
  из отзыва через расписание в режиме `draft` перенесёт, размножит или поменяет публикации
  владельца. Добавить её в создание материала — расписание не сможет готовить черновики вовсе.
- **`agent_rationale` и `shot_list` в подписи содержания:** правка пояснения начнёт снимать
  утверждение, хотя в публикацию эти поля не уходят.
- **Бриф:** `_load` на ошибке вернёт затравку вместо исключения — следующая правка перезапишет
  весь бриф затравкой; предел всего брифа ближе к 60 000 — ответ MCP начнёт обрезаться, и агент
  прочтёт бриф не целиком; `examples` слиянием по индексу — удалённый на экране пример вернётся.

### Проверка локально

**Никогда не запускать `app.py` и не импортировать `app`** (в том числе Flask test client
над полным приложением): импорт сразу поднимает все шедулеры и Telegram long-polling с
боевыми токенами из `.env` — локальный `getUpdates` перетягивает апдейты у прода, а
догоняющая проверка открытых смен может написать в рабочий чат (см.
[lessons.md](lessons.md)).

Тесты:

```
py -3 -m pytest tests/test_content_plan.py tests/test_content_brief.py tests/test_guest_reviews.py tests/test_mcp_tools_content.py -q
node tests/test_content_plan_render.mjs
node tests/test_guest_hub_render.mjs
```

Посмотреть страницу — голое Flask-приложение, как в тестах:

1. `PERSISTENT_DATA_DIR` и `TAPS_DATA_PATH` — на временный каталог (скопировать туда
   `taps_data.json` и `iiko_untappd_registry.json`, чтобы работал живой предпросмотр и не
   трогались файлы репозитория);
2. подменить `core.auth_guard.current_user` на тестового пользователя;
3. `Flask(__name__, template_folder='templates', static_folder='static')`,
   `context_processor` с `current_user`, `jinja_env.globals['app_version']`;
4. зарегистрировать только `content_plan_bp`, `reviews_bp` (и `guests_bp`, если нужна
   полоса на `/guests`);
5. `app.run(host='127.0.0.1', port=..., use_reloader=False)`.

Состояния `failed` и `overdue` через API не создать (отправки нет): в тестах их ставят
прямо в файл (`_set` в `tests/test_content_plan.py`).
