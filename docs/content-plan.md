# Контент-план — раздел «Гости» (`/content-plan`, `/api/content-plan/*`)

> Этап «только интерфейс» (2026-09-26, правки по ревью 2026-09-27): хранение, статусы,
> проверки готовности, предпросмотр, утверждение и журнал.
> С 2026-09-27 черновики плана может готовить ИИ-агент владельца через MCP-платформу
> ([mcp.md](mcp.md)): его материалы помечены «ИИ», правила для него — бриф сети (раздел
> «ИИ-агент» ниже). Утверждает по-прежнему только владелец.
> С 2026-09-28 утверждённое может уходить само (раздел «Отправка публикаций»):
> пост в Telegram-канал бара, напоминание владельцу об Instagram, рассылка гостям через
> гостевого бота. Всё выключено, пока владелец не укажет и не проверит каналы и не включит
> отправку («Каналы и отправка»); не подключено — выход отмечают вручную, как раньше.
> Решение владельца: «Давай все доделаем»; Instagram — ручной (без API Meta).

## Что это

План публикаций и рассылок сети на месяц: посты в Telegram-каналах баров, посты в общем
Instagram и рассылки через бота. Страница живёт в разделе сайдбара **«Гости»** рядом с
«Отзывами» ([reviews.md](reviews.md)) и «Маркетингом» ([guests.md](guests.md)); над всеми
тремя страницами стоит общая полоса «Требует внимания» (описана в [reviews.md](reviews.md),
раздел «Полоса «Требует внимания»»).

### Как владелец работает с планом

Концепция владельца (дословно): «Целевой режим — одна основная сессия подготовки на месяц,
а не ежедневная работа SMM-оператора».

| Когда | Что делается | Чем в интерфейсе |
|---|---|---|
| Начало месяца, одна сессия | собрать план: темы, бары, площадки, даты; заполнить тексты и фото; проверить итоговые версии | «Скопировать прошлый месяц», «Добавить материал», карточка материала, предпросмотр |
| Конец сессии | утвердить **только подготовленное** | «Утвердить готовые» |
| В течение месяца | исключения: перенос, пауза бара или сети, новый повод, отметка выхода, повтор после ошибки | карточка, «Пауза», полоса «Требует внимания» |

Главное правило утверждения, тоже словами владельца: «кнопка утверждает конкретные
подготовленные материалы, а не даёт системе разрешение самостоятельно дописывать
оставшиеся черновики. Незаконченные карточки остаются видны, но не уходят в публикацию».
Поэтому «Утвердить готовые» берёт только черновики без единой недостачи, а всё остальное
показывает списком «Останутся черновиками» с причинами.

### Материал и размещение

- **Материал** — тема или пост: название, текст, фото и видео. «Рассказать о новой кухне»
  без размещений — уже материал, но его сводка — «Только тема»; когда размещения появятся,
  экран покажет, чего не хватает до публикации (текста, фото, аудитории, времени).
- **Размещение** — выход материала в конкретную площадку, для конкретного бара (или всей
  сети), в конкретный день и час. У одного материала много размещений: «Октоберфест» —
  в четыре Telegram-канала баров и в Instagram сети.

Таблица показывает материалы (одна строка — одна тема со всеми размещениями), календарь —
размещения на их фактических датах: анонс в Telegram во вторник, версия для Instagram в
среду, напоминание через бота в пятницу.

### Два типа материала

| Тип (`kind`) | Что утверждается | Для чего |
|---|---|---|
| `fixed` — «Готовая публикация» | готовые текст и файлы; выходят ровно такими, какими их утвердили | истории о барах, команда, заранее известные события, кухня |
| `live` — «С актуальными данными» | **шаблон** с подстановками; данные (таплист бара) подставляются в момент выхода | «В пятницу в 16:00 опубликовать текущий таплист каждого бара» |

Для `live` владелец поставил жёсткое условие: «Произвольно менять остальной текст или
придумывать описания система не должна. Если достоверных данных нет — публикация
останавливается и появляется сообщение о проблеме». Отсюда правила остановки в разделе
«Живые данные».

## Как работает

### Модель данных

Файл: `{version: 1, materials: {id: M}, log: [...]}`. Все даты и время — наивные
московские строки (`core/msk_time`): дата `YYYY-MM-DD`, время `HH:MM`, метка
`YYYY-MM-DDTHH:MM`. День недели: 0 — понедельник. Id: `m_`, `p_`, `s_` + 12 hex.

Материал `M`:

| Поле | Смысл |
|---|---|
| `id`, `month` | месяц плана `YYYY-MM`; если есть дата темы, месяц = её месяц (пересчитывается при правке и сдвиге) |
| `title` | до 200 знаков, пробелы схлопываются, пустое нельзя |
| `kind`, `live_source` | `fixed` / `live`; источник данных только у `live` (единственный — `taplist`) |
| `planned_date` | дата темы — ориентир, пока нет размещений; задаёт месяц |
| `base_text` | общий текст (или шаблон у `live`), до 10 000 знаков |
| `media` | `[{name, kind, size, original_name, uploaded_at, uploaded_by}]`, до 20 файлов |
| `media_required` | «Нужно фото»: влияет только на готовность |
| `note` | заметка для команды, до 2000 знаков, в публикацию не уходит |
| `series` | `{id, weekdays}` у материалов одной серии повторов |
| `copied_from`, `source_review_id` | откуда копия; из какого отзыва сделан материал |
| `origin` | `human` или `agent` — кто создал запись: люди или ИИ-агент через MCP; ставит сервер при создании, не редактируется (раздел «ИИ-агент») |
| `agent_rationale` | «Почему этот пост» — пояснение к посту (повод, рубрика, откуда факты), до 2000 знаков, в публикацию не уходит |
| `shot_list` | «Что снять» — список кадров для команды, до 2000 знаков, в публикацию не уходит |
| `agent_original` | только у материалов агента: последняя версия агента `{base_text, placements: {pid: свой текст или null}}` — для учёта правок владельца (раздел «Учёт правок владельца для агента»); в ответах API не отдаётся |
| `placements` | размещения (ниже) |
| `created_*`, `updated_*` | кто и когда; действие через MCP подписано «<login> · агент» |

В ответе API у материала есть и вычисляемое поле `agent_draft` — «черновик ИИ» (раздел
«ИИ-агент»).

Размещение:

| Поле | Смысл |
|---|---|
| `channel` | `telegram` / `instagram` / `bot` |
| `bar` | ключ бара или `all` («Вся сеть») |
| `date`, `time` | день и час выхода; могут быть пустыми у черновика |
| `text` | своя версия текста; `null` — берётся общий текст материала |
| `media` | своя подборка файлов (имена); `null` — все файлы материала |
| `audience` | `{segment}` — только у бота |
| `status` | хранимый статус (ниже) |
| `approved_at`, `approved_by`, `approved_snapshot` | утверждение и снимок `{text, media}` на его момент |
| `published_at`, `published_by`, `failed_error` | отметка выхода (`published_by` = «бот», если отправил бот), текст ошибки отправки |
| `delivery` | ход отправки (раздел «Отправка публикаций»); `null` — отправки не было. В ответе API — без списков получателей, плюс `post_url` |

Итоговый текст и файлы размещения:

```
effective_text  = placement.text, если он не null, иначе material.base_text
effective_media = placement.media (только те имена, которые ещё есть у материала),
                  если не null, иначе все файлы материала
```

Лимиты хранения (`TITLE_MAX` 200, `TEXT_MAX` 10 000, `NOTE_MAX` 2000,
`MATERIAL_MEDIA_MAX` 20) — не платформенные, это защита от опечаток и разбухания файла.
10 000 — больше самого длинного поста (4096) с запасом на черновик; 20 файлов — два
максимума площадки (10), чтобы держать разные подборки для разных размещений.

### Площадки, бары и аудитории

Числа — факты платформ, а не наши настройки. Длина считается в символах Unicode (`len`),
для кириллицы и латиницы это совпадает со счётчиком в браузере (JS считает суррогатную
пару одним символом, как сервер).

| Площадка | Бар | Текст | Файлы |
|---|---|---|---|
| Telegram (`TG`) | обязателен конкретный бар: у каждого бара свой канал | 4096 без файлов (`sendMessage`); 1024, если есть фото или видео (подпись `caption`) | до 10 (`sendMediaGroup`), по умолчанию не обязательны |
| Instagram (`IG`) | `all` — один аккаунт сети; можно указать бар | 2200 (подпись) | от 1 до 10, хотя бы один файл обязателен |
| Бот | `all` или бар (охват рассылки) | как Telegram | как Telegram |

Бары и короткие имена: Большой пр. В.О — `ВО`, Лиговский — `Лиг`, Кременчугская —
`Крем`, Варшавская — `Вар`; вся сеть — `Сеть`.

Аудитории рассылки бота (`AUDIENCES`): «Все подписчики бота», «Подписчики, выбравшие
бар» (нужен конкретный бар), «Были в баре за последние 30 дней», «Не были 60 дней и
дольше». Размер — настоящий, из подписчиков гостевого бота на сейчас (раздел «Размер
аудитории бота»); хранилище без подключённого `audience_fn` (тесты) отдаёт `size: null` и
пояснение «Бот не подключён: размер аудитории появится после интеграции».

Владелец отдельно потребовал: «Выбор всех площадок не должен незаметно включать личную
рассылку всей базе». Поэтому рассылка через бота добавляется только отдельным
размещением с явно выбранной аудиторией, «Все бары» в форме относится только к Telegram,
а утверждение рассылки требует отдельного подтверждения (см. «Утверждение»).

### Статусы (хранятся) и состояния для экрана (вычисляются)

Хранимый `status`:

| Статус | Смысл |
|---|---|
| `draft` | черновик |
| `approved` | утверждено, ждёт времени выхода |
| `paused` | утверждено, но остановлено |
| `published` | вышло: отправил бот или отметили вручную |
| `failed` | ошибка отправки: ставит отправщик, текст — `failed_error` |
| `cancelled` | отменено, остаётся для истории |

`display_state` считается при каждом чтении и не хранится:

| Условие | `display_state` | Подпись |
|---|---|---|
| `draft`, чего-то не хватает | `incomplete` | «Не хватает: …» |
| `draft`, всё заполнено | `ready` | «Готово к утверждению» |
| `approved`, время впереди | `scheduled` | «Запланировано»; у `live` — «Шаблон утверждён, данные — при выходе» |
| `approved`, время прошло | `overdue` | «Время вышло, выход не отмечен» — площадка не подключена к отправке: напоминание отметить выход вручную |
| `approved`, отправляется или в очереди повтора (`in_flight`) | `scheduled` | «Отправляется» / «В очереди на отправку», даже если время прошло |
| `paused` / `published` / `failed` / `cancelled` | то же имя | «На паузе» / «Вышло» / «Ошибка отправки» / «Отменено» |

Край: утверждённое размещение без даты или времени (старые данные) считается `scheduled`.

Подписи с учётом отправки (`delivery_label`): Instagram после напоминания — «Напоминание
отправлено» (время впереди) и «Напоминание отправлено, выход не отмечен» (время прошло);
сбой напоминания — «Напоминание не отправлено: <причина>» — только если напоминание было для
ТЕКУЩЕГО времени поста (`reminder_is_current`: `delivery.reminded_for` = дата и время
размещения; пост перенесли — подписи нет, напоминание взведено заново); рассылка бота — «Вышло:
дошло N из M» (и «· повтор неудавшимся в очереди / идёт»). Пока идёт: «Рассылка идёт: дошло N
из M» (после паузы или отмены — «· остановится после текущей пачки»), между проходами —
«Рассылка идёт: дошло N из M, продолжится в течение минуты»; в очереди («Повторить», «Отправить
сейчас») — «В очереди на отправку: уйдёт в течение минуты». `in_flight`: отправка с отметкой
моложе 10 минут (`SENDING_STALE_MINUTES`) или очередь повтора моложе 120 минут
(`DELIVERY_GRACE_MINUTES`) — те же пороги отправщик считает «зависло» и «опоздало», поэтому
зависшее снова показывается `overdue`. Счётчик полосы «Время вышло» (`attention_counts`)
считает так же.

Время сравнивается с точностью до минуты как строка `YYYY-MM-DDTHH:MM` с текущей минутой
по Москве: публикация на 16:00 «в прошлом» с 16:01 (в 16:00 ещё нет).

Цвет на экране выбирается по `display_state`, а не по тону сервера: у `scheduled` и
`published` тон одинаковый (`success`), но это разные состояния. Вид состояний
(`STATE_HUE` в `content_plan.js`, классы `gh-cp-st-*`): черновики — контуром
(`incomplete` пунктир, оранжевый; `ready` контур, акцент), `scheduled` — спокойная
графитовая заливка, `overdue` — оранжевая заливка, `paused` — серый пунктир,
`published` — зелёная заливка, `failed` — красная заливка, `cancelled` — серый,
зачёркнуто. Легенда над таблицей и в календаре (свёрнута: «Цвета состояний») та же, что на чипах.

### Готовность черновика

Проверяется только у `draft` (у остальных статусов список пуст). Коды идут строго в этом
порядке — в нём же они печатаются в «Не хватает: …»:

| # | Код | Условие | Текст |
|---|---|---|---|
| 1 | `no_live_source` | `live` без источника | не выбран источник данных |
| 2 | `no_text` / `no_template` | итоговый текст пустой (после обрезки пробелов); `no_template` — у `live` | нет текста / нет шаблона |
| 3 | `bad_placeholder` | у `live` в тексте `{…}` не из списка подстановок; по строке на каждую неизвестную | неизвестная подстановка {x} |
| 4 | `no_media` | файлов нет, а площадка Instagram или у материала «Нужно фото» | нет фото |
| 5 | `too_many_media` | файлов больше 10 | больше 10 файлов |
| 6 | `text_too_long` | только `fixed`: длина больше предела (1024, если у Telegram/бота есть файлы, иначе 4096; Instagram 2200) | текст длиннее N знаков |
| 7 | `no_bar` | `live` на `all` (любая площадка); Telegram на `all`; бот с аудиторией «выбравшие бар» на `all` | для таплиста выберите бар / не выбран бар |
| 8 | `no_audience` | бот без аудитории | не выбрана аудитория |
| 9 | `no_date`, `no_time` | нет даты, нет времени | нет даты / нет времени |
| 10 | `in_past` | дата и время раньше текущей минуты по Москве | время выхода уже прошло |

`ready` = статус `draft` и список пуст.

У `live` длина в готовности не проверяется: подставленный таплист заранее неизвестен, его
длина видна в предпросмотре размещения («Пост» -> «Как увидят гости»).

Пример (сейчас 7 октября 12:00): Telegram ВО, общий текст 1100 знаков, у материала одно
фото, 9 октября 16:00. Файл есть, поэтому предел — подпись 1024: «Не хватает: текст
длиннее 1024 знаков». Уберите фото из подборки этого размещения — предел станет 4096,
и размещение будет готово.

### Сводка материала (колонка «Готовность»)

`material_summary` — первое сработавшее правило. Отменённые размещения не учитываются,
кроме случая «отменены все». `total` — число неотменённых, `ready` — из них готовых,
`counts` — по всем состояниям, `rule` — номер правила, `state` — какое состояние оно
описывает (`empty` для правила 1): по `state` экран выбирает цвет.

| # | Условие | Подпись | Тон |
|---|---|---|---|
| 1 | размещений нет | «Только тема» | muted |
| 2 | все отменены | «Отменено» | muted |
| 3 | есть ошибка отправки | «Ошибка отправки: N» | danger |
| 4 | есть незаполненные | «Не хватает: …» | warning |
| 5 | есть просроченные | «Время вышло: N» | warning |
| 6 | есть готовые | «Готово к утверждению»; если есть и запланированные — «Готово к утверждению: N из M», M = total | accent |
| 7 | все вышли | «Вышло» | success |
| 8 | часть вышла, остальные запланированы или на паузе | «Вышло: N из M» | success |
| 9 | есть на паузе | «На паузе: N» | muted |
| 10 | иначе (все запланированы) | «Запланировано»; у `live` — «Шаблон утверждён, данные — при выходе» | success |

Правило 4 для нескольких размещений говорит, **где** чего не хватает: одинаковые причины
собраны вместе, группы через «; », места — площадка и бар; причина, которой не хватает во
всех неотменённых размещениях, пишется «— везде». С одним размещением — просто список.
Пример: Instagram без фото, TG Вар без времени, TG Лиг готов → «Не хватает: нет фото —
IG Сеть; нет времени — TG Вар». Та же разбивка лежит в `summary.missing`
(`[{code, text, where, everywhere}]`) и показывается в подсказке таблицы (строка в
таблице обрезается до двух строк).

Примеры правил 6 и 8: два готовых и один запланированный → «Готово к утверждению: 2 из 3»;
Telegram вышел, Instagram утверждён → «Вышло: 1 из 2».

**Дата материала** (колонка «Дата», группировка по неделям) = самая ранняя дата
неотменённых размещений, иначе дата темы, иначе нет даты.

### Правила редактирования

«Подпись содержания» размещения — всё, что уходит в публикацию: площадка, бар, сегмент
аудитории, итоговый текст, итоговые файлы, тип материала, источник данных. Перед правкой
и после неё подписи сравниваются.

| Правка | Что происходит с утверждённым / на паузе / с ошибкой |
|---|---|
| подпись содержания изменилась (текст, файлы, бар, аудитория, площадка, тип, источник) | размещение возвращается в черновик, утверждение и снимок снимаются, в журнале `unapprove_auto`, ответ несёт `unapproved: [id]`, экран показывает предупреждение со списком |
| правка общего текста | снимает утверждение только у размещений, берущих общий текст; размещения со своей версией не трогаются |
| загрузка файла | снимает утверждение у размещений с набором «все файлы» (у них изменились итоговые файлы); со своей подборкой — нет. Экран предупреждает до загрузки и оставляет несгораемый тост после |
| удаление файла | убирает имя из подборок размещений, **кроме вышедших и отменённых**; снимает утверждение там, где файл входил в итог |
| перенос даты или времени | утверждение сохраняется; новое время в прошлом у утверждённого или на паузе — 400 «Нельзя перенести утверждённую публикацию в прошлое»; стереть дату или время у утверждённого нельзя (400, сначала снять утверждение) |
| название, заметка, дата темы, «Нужно фото» | не содержание: утверждение не трогают («Нужно фото» влияет только на готовность черновика) |
| вышедшее или отменённое размещение | не редактируется (400 «Размещение уже вышло» / «Размещение отменено») |
| удаление материала с вышедшими размещениями | 409: отмените остальные, материал оставьте для истории |

`failed` снимается в черновик по тем же правилам, иначе повтор отправки ушёл бы со старым
снимком при новом тексте. Смена типа `live` → `fixed` очищает источник данных; тип `fixed`
вместе с источником — 400.

Любая ошибка внутри записи (например, перенос в прошлое) отменяет всю правку: файл не
пишется.

### Утверждение

`POST /api/content-plan/approve {placement_ids, confirm_bot}`:

- утверждаются только черновики, у которых список готовности пуст; остальные уходят в
  `skipped` с причинами («уже не черновик (…)», «размещение не найдено», тексты
  недостающего);
- если среди запрошенных есть рассылка бота, нужен `confirm_bot = true`, иначе 400
  «Подтвердите аудиторию рассылки» и **ничего** не утверждается;
- на момент утверждения пишется снимок `approved_snapshot = {text, media}` — итоговый
  текст и файлы.

Диалог «Утвердить готовые» (`GET /approve-preview?month=&bar=&channel=` под текущими
фильтрами) показывает три списка:

1. «Уйдут в публикацию» — по площадкам; одинаковые строки (материал, дата, время,
   площадка) на нескольких барах собраны в одну строку со списком баров;
2. «Рассылки через бота» — каждая с аудиторией и размером «неизвестно: бот не
   подключён» и **неотмеченным** флажком: утверждаются только отмеченные, и только
   тогда запрос несёт `confirm_bot = true`;
3. «Останутся черновиками» — с причинами.

Размещения месяца для диалога: материал относится к месяцу или дата размещения в месяце;
фильтр бара X берёт размещения бара X и размещения на всю сеть. Строки материалов с
актуальными данными помечены «шаблон · данные при выходе». Кнопка «Утвердить» на
отдельном размещении бота открывает то же подтверждение аудитории.

### Действия и переходы статусов

`POST /placements/<pid>/action {action}`; любой другой переход — 409 с текстом «… (сейчас:
<статус>)».

| Действие | Из | В | Особенности |
|---|---|---|---|
| `pause` | approved | paused | |
| `resume` | paused | approved | 400 «Время выхода прошло — перенесите дату», если время прошло |
| `unapprove` | approved, paused | draft | снимок и отметки утверждения стираются |
| `mark_published` | approved, paused, failed | published | пишутся `published_at`, `published_by`; дальше размещение только для чтения |
| `cancel` | draft, approved, paused, failed | cancelled | остаётся в плане; при снятии паузы, повторе и копировании не учитывается |
| `restore` | cancelled | draft | утверждение не возвращается |
| `retry` | failed | approved | `failed_error` очищается; размещение встаёт в очередь отправки (`delivery.state` `queued`, `retry_at` = сейчас): бот отправит в ближайшую минуту, даже если время выхода давно прошло; у рассылки — только тем, кому не дошло |
| `retry_failed` | published (только рассылка бота с `delivery.failed_to`) | published | повтор неудавшимся получателям встаёт в очередь; иначе 409 «повторять некому» |

Пока размещение отправляется (`delivery.state` `sending` и отметка моложе 10 минут),
его действия, правка и удаление, а также удаление и отмена его материала — 409 «Публикация
сейчас отправляется — подождите минуту и обновите страницу».

Удаление размещения (`DELETE /placements/<pid>`) — из любого статуса, кроме `published`
(409: вышедшее остаётся в истории). «Отменить размещения» в массовых действиях отменяет
все отменяемые размещения выбранных материалов.

### Пауза по бару и по сети

Меню «Пауза» → `POST /bulk-pause {bar, action}`:

| `bar` | Какие размещения трогаются |
|---|---|
| `all` | все размещения сети, любых баров и сетевые |
| бар X | только размещения с `bar == X`; сетевые (`all`) **не** трогаются: общий Instagram не должен останавливаться из-за одного бара |

Пауза ставится только утверждённым с временем впереди. Снятие паузы пропускает те, чьё
время уже прошло, и перечисляет их в `skipped` («… время выхода прошло») — их нужно
перенести. В журнале `bulk_pause` / `bulk_resume` с указанием охвата.

### Перенос материала

«Сдвинуть на N дней» (`POST /materials/<id>/shift {days}`, массово — `POST /bulk`):
сдвигаются дата темы и даты всех невышедших и неотменённых размещений. `days` — целое от
−60 до 60, не 0 (60 дней — два месяца: дальше это уже планирование другого месяца). Если
утверждённое или стоящее на паузе размещение оказалось бы в прошлом — 400, не сдвигается
ничего. Черновик может уехать в прошлое: он покажет «время выхода уже прошло».
Утверждение при сдвиге сохраняется. Месяц материала следует за датой темы.

### Повтор по дням недели (серия)

«Повторять в этом месяце по дням недели» (`POST /materials/<id>/repeat {weekdays, month}`):

- на каждую дату месяца с выбранным днём недели, **не раньше сегодняшнего дня** и не
  занятую этой серией (дата темы, дата материала или дата неотменённого размещения любого
  материала серии, включая источник), создаётся копия;
- копия: то же название, тип, источник, текст, ссылки на те же файлы, «Нужно фото»,
  заметка, «Почему этот пост», «Что снять»; размещения источника (кроме отменённых) —
  черновиками **на дату копии**, со своими текстами, подборками, аудиторией и временем;
  утверждение не копируется; `origin` копии — по тому, кто нажал «Повторить» (человек —
  `human`, агент через MCP — `agent`), а не по источнику;
- источник и все копии становятся одной серией `{id, weekdays}`; дни недели объединяются
  с прежними;
- агент в режиме «Чтение и черновики» (задача по расписанию) повторяет только свой черновик ИИ
  (`guard_draft_mode`, иначе 409); его копии — тоже черновики агента, «Удалить черновики ИИ» за
  месяц повтора уберёт и их.

Край: все размещения копии встают на один день — день повтора. Анонс «за 4 дня до
события» внутри повтора не воспроизводится; повтор рассчитан на однодневные рубрики
(«Таплист пятницы»). Если подходящих дней нет, ответ `created: []` и тост «Новых дат нет».

### Копирование месяца

«Скопировать прошлый месяц» (`POST /copy-month {from, to, with_content}`, `from` по
умолчанию — месяц перед `to`). Правила дат показываются в диалоге с сервера
(`copy_rules` = `COPY_RULES`), а не своим текстом в JS: однажды текст в JS уже разошёлся
с кодом.

Проверки: `to` не раньше текущего месяца (400 «Нельзя копировать в прошедший месяц»),
месяцы разные (400), в `to` ещё нет копий материалов `from` (409 «Этот месяц уже
скопирован»; чтобы скопировать заново, удалите копии). Копируются материалы с
`month == from`. Все копии — черновики, утверждение не переносится, отменённые размещения
не копируются.

#### Обычный материал: опорная дата и сдвиг

```
опора  = copy_anchor(материал):
         1) дата темы;
         2) нет её — самая ранняя дата неотменённого размещения ВНУТРИ месяца-источника;
         3) нет и таких — самая ранняя дата неотменённого размещения;
         4) дат нет — материал копируется без дат.
новая опора = тот же день недели с тем же номером n в месяце, n = (день − 1) // 7 + 1;
              если n-го нет (5-я пятница) — последний такой день, с заметкой
сдвиг  = новая опора − опора (в днях; всегда кратен 7)
каждая дата материала (дата темы и все размещения) + сдвиг
```

Сдвиг кратен 7, поэтому у каждой даты сохраняются день недели, порядок и интервалы.
Переносить каждую дату отдельно по правилу «n-й день недели» нельзя: даты одного
материала из разных «недель месяца» (1–7, 8–14, …) расходятся, и анонс может оказаться
после события.

Пример 1 (из теста): «Событие», дата темы — сб 3 октября (1-я суббота); анонс TG ВО
ср 30 сентября, Instagram чт 1 октября, бот пт 2 октября, TG Лиг сб 3 октября. В ноябре
1-я суббота — 7 ноября, сдвиг +35 дней: размещения 4, 5, 6 и 7 ноября — те же среда,
четверг, пятница, суббота, тот же порядок.

Пример 2 (почему не каждая дата отдельно): дата темы — пн 5 октября, анонс TG — сб
3 октября, напоминание ботом — пн 5 октября. По отдельности: сб 3 октября (1-я суббота)
→ 7 ноября, пн 5 октября (1-й понедельник) → 2 ноября — анонс после напоминания. С опорой:
5 октября → 2 ноября (1-й понедельник), сдвиг +28: анонс → сб 31 октября, бот → пн
2 ноября. Порядок и интервал 2 дня сохранены, а 31 октября вне ноября — заметка «… 31 окт —
вне месяца «ноябрь 2026»: даты сдвинуты вместе с опорной, порядок и интервалы размещений
сохранены».

Почему опора — дата темы, а не самая ранняя дата: дата темы задаёт месяц материала
(`month := месяц planned_date`), и только так дата темы копии гарантированно остаётся в
месяце назначения. Иначе у копии `month` был бы ноябрь, а дата темы — в октябре, и первая
же посторонняя правка перенесла бы материал в другой месяц.

**Край (замечание проверки 2026-09-27, работает так по замыслу).** Размещение копии может
оказаться в месяце **до** месяца назначения:

- дата темы позже анонса в начале месяца (пример 2): TG копии — 31 октября;
- у материала нет даты темы, а единственное размещение стоит в прошлом месяце: октябрьский
  материал с размещением на сб 26 сентября. Внутри октября дат нет, поэтому опора —
  26 сентября (4-я суббота сентября), она переносится на 4-ю субботу октября — 24 октября.
  Копия принадлежит плану ноября, а её размещение стоит 24 октября.

В обоих случаях есть заметка «вне месяца», но копия видна и в октябре: в календаре
октября, в диалоге «Утвердить готовые» октября (он берёт размещения, датированные
месяцем) и в таблице октября при фильтре состояния с пометкой «план: ноябрь 2026». Если
такая дата уже прошла, будет ещё и заметка «дата уже прошла». Что делать: прочитать
заметки после копирования и перенести копию («Сдвинуть на N дней», например +28 или +35)
или поправить даты размещений.

#### Серия: объединение дней

Материалы с общим `series.id` не переносятся по опоре, а создаются заново на каждый день
месяца назначения с днём недели серии (дни недели — объединение по всем дням серии;
здесь, в отличие от повтора, прошедшие дни не пропускаются — о них заметка). Новая серия
получает новый id.

- **Размещения копии** — объединение неотменённых размещений всех дней серии без повторов
  по ключу (площадка, бар, аудитория, время). Разовая отмена одного бара в один день не
  должна пропасть из всего следующего месяца.
- **Текст и файлы** — из самого раннего дня серии, где есть неотменённое размещение
  (он же `copied_from`). Подборка файлов размещения, взятого из другого дня, подгоняется
  к файлам копии: выпавшие имена убираются, а если выпали все — подборка становится «все
  файлы» (пустой список значил бы «без фото», а человек выбирал именно фото).

Заметки серии: какие дни отличались набором размещений («9 окт — нет TG Лиг 18:00», «2 окт —
все размещения отменены»); одно место в разные дни с разным временем, если ни в один день
эти времена не стояли вместе («TG ВО — в разные дни разное время (18:00, 19:00): в копию
взято каждое время, лишнее удалите»; два поста в один день так не помечаются); различались
тексты или файлы («в копию взяты из дня 9 окт»); все дни отменены («копии созданы без
размещений»).

Пример (из теста): живой «Таплист пятницы» 9, 16, 23, 30 октября на четыре бара в 18:00;
9 октября Лиговский отменён, 16 октября свой текст. Копия на ноябрь: пятницы 6, 13, 20,
27 ноября, в каждой все четыре бара, шаблон из 9 октября, две заметки.

#### Что копируется

| Что | `with_content = false` (по умолчанию) | `with_content = true` |
|---|---|---|
| общий текст и файлы `fixed` | очищаются (`''`, `[]`) | копируются; файлы общие с источником (те же имена) |
| своя версия текста и подборка у размещений `fixed` | `null` (общий текст, все файлы) | копируются |
| шаблон, файлы и свои версии у `live` | копируются всегда: шаблон — утверждённый дизайн | копируются |
| название, тип, источник, «Нужно фото», заметка | копируются | копируются |
| «Почему этот пост», «Что снять» | идут вместе с содержанием: у `fixed` очищаются, у `live` копируются | копируются |
| площадка, бар, аудитория, время | копируются | копируются |
| статус, утверждение | черновик, без утверждения | черновик, без утверждения |
| отменённые размещения | не копируются | не копируются |
| `source_review_id` | не копируется | не копируется |
| `origin` | по тому, кто копирует: человек — `human`, агент через MCP — `agent` | то же |

Ответ: `{created: n, notes: [...]}`, заметки без повторов. Если в месяце-источнике нет
материалов — `created: 0` и одна заметка.

### Живые данные (таплист)

Единственный источник — таплист бара из нашего сервиса: снимок кранов
(`extensions.taps_manager`, вместе с историей подключений) и реестр Untappd
(`core/untappd_registry`), сборка строк — `core/taplist.full_taplist(..., active_only=True)`,
строка поста — [core/taplist_post.py](../core/taplist_post.py). Ни iiko, ни цен здесь нет. Ключ
бара переводится в id таплиста: bolshoy → bar1, ligovskiy → bar2, kremenchugskaya → bar3,
varshavskaya → bar4.

Подстановки (`PLACEHOLDERS`):

| Подстановка | Что подставляется |
|---|---|
| `{вступление}` | первая строка поста — фраза из набора, своя на каждую неделю и каждый бар (ниже) |
| `{таплист}` | строки кранов через перевод строки |
| `{концовка}` | последняя строка в пару к вступлению; бывает пустой — тогда пост кончается списком |
| `{бар}` | полное название бара |
| `{где}` | бар для фразы: «на Васильевском», «на Лиговском», «на Кременчугской», «на Варшавской» (`BARS[...]['where']`) |
| `{дата}` | дата выхода, «9 октября» (дата размещения, иначе сегодня) |
| `{кранов}` | число активных кранов |

Шаблон «Таплиста пятницы» по умолчанию (`TAPLIST_TEMPLATE`, подсказка в поле и агенту):

```
{вступление}

{таплист}

{концовка}
```

#### Вступление и концовка (решение владельца 2026-10-09)

Владелец: «нужно писать как-нибудь по-разному, чтобы не выглядело шаблонно, типа «Таплист на
сегодня!»». Набор пар «вступление — концовка» — `resources/taplist_post_phrases.json`
(16 вариантов; первые четыре — примеры владельца слово в слово). Внутри фраз работают `{где}`,
`{бар}`, `{дата}`; подставленное значение повторно не разбирается.

Какой вариант (`core/taplist_post.phrase_index`, детерминированно — та же дата и тот же бар
дают ту же фразу, поэтому предпросмотр совпадает с тем, что уйдёт):

```
неделя  = (дата выхода − 5 января 2026) // 7          (понедельник; без прыжка ISO-недели на стыке лет)
сдвиг   = позиция бара (bar1 = 0 … bar4 = 3) × (вариантов // 4)
вариант = (неделя + сдвиг) mod вариантов
```

Пример при 16 вариантах: пятница 9 октября 2026 — неделя 39; ВО (bar1) — 39 mod 16 = 7,
Кременчугская (bar3) — (39 + 8) mod 16 = 15 (номера с нуля; на экране — с единицы). Что
из этого следует:

- в одну пятницу у четырёх баров разные фразы;
- в своём баре фраза повторяется через 16 недель (около четырёх месяцев), две пятницы подряд —
  никогда одна и та же;
- фраза, которая была у одного бара, в соседнем появится не раньше чем через 4 недели;
- пост, перенесённый на другой день той же недели (пн–вс), получает ту же фразу.

Пустая концовка забирает пустые строки перед собой (`OPTIONAL_PLACEHOLDERS`): пост
кончается списком, а текст после `{концовка}` встаёт сразу под список. Длина: вступление —
до 80 знаков, концовка — до 100 (`PHRASE_INTRO_MAX`, `PHRASE_OUTRO_MAX`, проверяет тест
набора); с переводами строк пара добавляет к посту не больше 200 знаков, чтобы подпись к фото
бара на 12 кранов (около 750 знаков) влезала в 1024. Какой вариант выбран — в ответе
предпросмотра (`phrase: {variant, total, intro, outro}`) и на экране под «Как считается» в
«Как увидят гости».

Тон: набор написан голосом примеров владельца — с восклицательными знаками и «Друзья» в
одном варианте; правило брифа «без восклицательных знаков» для этой рубрики владелец
этими примерами отменил. Сменить или добавить фразы — правка файла и деплой; ИИ-агент
своих фраз вместо `{вступление}` не пишет (инструкция раздела и сценарий плана месяца).
Шаблон без `{вступление}` и `{концовка}` выходит как написан. Исключение — прежний шаблон
агента `Таплист пятницы — {бар}, {дата}` + `{таплист}` (`LEGACY_TAPLIST_TEMPLATES`, только
точное совпадение): с ним утверждены пятницы октября, а владелец 2026-10-09 решил «таплист
должен быть по новому шаблону, сегодняшний тоже» — такой шаблон выходит как `TAPLIST_TEMPLATE`
(в ответе предпросмотра `legacy_template: true`, на экране — строка под «Как считается»).

#### Строка крана (формат владельца 2026-10-04)

Владелец: «не нравится идея с картинкой — это должен быть текст: название пива, ссылка на
Untappd, краткая информация, прям супер кратко». Решения 2026-10-04: пивоварня перед
названием, пометка «новинка», цен нет совсем, пост бара с давно не обновлёнными кранами
останавливается.

```
{кран}. {пивоварня и название} — {стиль}, {крепость}%[, новинка]
```

Пример (Варшавская, данные 2026-10-04 и условные новинки):

```
1. Zavod Dopamine — двойной IPA, 7,2%
3. Rodenbach Grand Cru — фламандский красный эль, 6%, новинка
6. Black Sheep Irish Stout — ирландский стаут, 4%
10. Festhaus Helles — светлый лагер, 4,5%
```

| Часть | Откуда и как |
|---|---|
| пивоварня и название | `post_name`: своё название сорта из словаря (`beers`, по id Untappd) — целиком; иначе короткое имя пивоварни (`breweries`) + название Untappd. Пивоварню не пишем, если её короткое имя пустое (марка уже в названии: Black Sheep у «Объединённых пивоварен») или уже есть в названии без учёта регистра — «Palm Spéciale», а не «Palm Palm Spéciale». Пивоварни нет в словаре — её имя Untappd без скобок. Пробелы, в том числе неразрывные из карточек Untappd, схлопываются. Без карточки Untappd — имя кеги из iiko без «КЕГ» и объёма (`iiko_display`: «КЕГ Вудбридж ИПА 30 л» → «Вудбридж ИПА»); такой кран и так останавливает пост |
| ссылка | вся часть «пивоварня и название» — ссылка на карточку Untappd (`untappd_url` проверенной связи). В Telegram это сущность `text_link`: адрес не виден, название кликается; цена ссылки в знаках — ноль, лимит считается по видимому тексту |
| стиль | стиль Untappd по-русски из словаря (`styles`): «Lager - Helles» → «светлый лагер», «IPA - Imperial / Double» → «двойной IPA». IPA остаётся IPA — принятое слово. Нет в словаре или в словаре пусто (мусор реестра вроде «Brewed by …») — стиль не пишем: английский в пост не попадает |
| крепость | округление до 0,01 по правилу half-up (`Decimal`, не `round`), без хвостовых нулей, десятичная запятая: 5.0 → «5», 6.5 → «6,5», 7.255 → «7,26»; 0 и пусто не пишутся |
| новинка | см. ниже |

Пустые части опускаются: без стиля — «{имя} — {крепость}%», без стиля и крепости — только имя.
Краны идут по номеру (числа по возрастанию, затем нечисловые).

С 2026-10-04 **те же строки показывает гостевой бот** @kult_taplist_bot
(`core/taplist_post.bar_message_html`: заголовок «<b>Бар</b>», имя — `<a href>` на Untappd,
разметка HTML). Реестр Untappd — единственный источник правды о пиве: старый справочник
бота по названиям удалён из кода (см. [untappd-links.md](untappd-links.md)). Стоп
`stale_taps` в боте не действует: гость спрашивает краны сам, ему показываются данные на
сейчас.

**Словарь** — [resources/taplist_post_names.json](../resources/taplist_post_names.json): 117 стилей,
160 пивоварен, 60 своих названий (на 2026-10-04 — все стили и пивоварни реестра). Свои названия
убирают из имени Untappd служебные хвосты и второй язык: «Festweisse (TAP04)» → «Schneider Weisse
Festweisse», «Hazy Shade of Summer (ex Poetry of Love, ex/ex Mahatma G.)» → «Rewort Hazy Shade of
Summer», «Rusalka / Русалка» → «Brewlok Русалка». У записи `beers` есть поле `untappd` — исходное
имя для сверки. Пересобрали реестр Untappd (`scripts/build_untappd_registry.py`) — дополните
словарь: `tests/test_taplist_post.py` требует перевод для каждого стиля, короткое имя для каждой
пивоварни и своё название для каждого имени со скобками или косой чертой. Файл читается один раз
на процесс — правка словаря выходит с деплоем.

#### Новинка

Бриф: «сорта, подключённые за последние 7 дней, помечены «новинка»». Новая кега того же сорта
— не новинка: сорт в баре не прерывался. Правило (`new_beer_keys`, константы `NEW_DAYS = 7`,
`NEW_ABSENT_DAYS = 30`): сорт сейчас на кране и **ни на одном кране бара** не стоял в окне
[момент поста − 37 суток; момент поста − 7 суток). Правый край не входит: подключили ровно за 7
суток до поста — ещё новинка.

| Пост 9 октября 16:00 (окно — со 2 сентября 16:00 до 2 октября 16:00) | Новинка? |
|---|---|
| подключили 5 октября, в сентябре в баре не было | да |
| стоит с 20 сентября | нет |
| стоял весь сентябрь, 6 октября — новая кега того же сорта (в том числе кега другого объёма) | нет |
| был в августе, ушёл 20 августа, вернулся 5 октября | да |
| 5 октября на кран 1, а с 10 по 25 сентября стоял на кране 2 | нет |

Сорт — карточка Untappd: кеги 20 и 30 л — разные товары iiko, но одно пиво. Старое событие
без товара iiko считается тем же сортом, если его имя ровно совпадает с именем товара в реестре;
иначе — отдельным сортом по имени (такие события до перехода на товары iiko уходят из окна к
началу ноября 2026). Периоды строятся по истории кранов (`start` / `replace` — новый сорт,
`stop` — кран пуст). Если история обрезана и начинается со снятия, сорт стоял и раньше — не
новинка. Подключение, которого нет в истории, берётся из `started_at`; без него — «давно», не
новинка. Ошибка здесь безопаснее в сторону «не пометили»: пообещать гостю новинку, которой нет,
— хуже.

#### Свежесть кранов (стоп `stale_taps`)

Список честен, только пока бармены отмечают замены на странице кранов. На 2026-10-04
Кременчугская не отмечала замен с 11 августа, Варшавская — с 18 сентября. Решение владельца:
**пост бара не уходит**, если на его странице кранов `STALE_TAPS_DAYS = 14` суток нет ни одного
изменения (подключение, замена или снятие на любом кране; `started_at` тоже считается). Краны
меняются каждую неделю (бриф), две недели без единой отметки значат, что замены перестали
отмечать. Ровно 14 суток — ещё свежо. Текст проблемы: «краны бара не обновлялись 59 дней
(последнее изменение 11 августа) — список мог устареть»; нет ни одной отметки — «на странице
кранов бара нет ни одной отметки о замене кег — список не проверить». Ответ несёт
`taps_changed_at` — последнее изменение.

#### Ссылки при отправке

`render_live` возвращает `entities` — ссылки в итоговом тексте: `{type: 'text_link', offset,
length, url}`, `offset` и `length` в единицах UTF-16 (так их считает Telegram; эмодзи в шаблоне
до `{таплист}` сдвигает всё на 2). Позиция считается тем же проходом, что подстановка, для
каждого `{таплист}` в шаблоне. Отправщик кладёт их в `entities` текста (`caption_entities`
подписи к фото; в альбоме — у первого файла) и выключает предпросмотр ссылки — иначе под постом
встала бы карточка первого пива. Готовая публикация уходит как раньше: без сущностей,
предпросмотр ссылок включён. На экране «Как увидят гости» названия — ссылки (`linkedText`:
только https, по порядку, без наложений); в Instagram ссылок нет, там обычный текст.

**Пост — только текст**, без фото и видео: подпись к фото в Telegram — до 1024 знаков, а
список ВО (21–24 крана) — около 1200. Без файлов предел — 4096.

Подстановка делается одним проходом: название пива со скобками «{…}» повторно не
разбирается. Неизвестная подстановка остаётся в тексте как есть и считается проблемой.

**Публикация будет остановлена**, если (любое из):

| Код | Причина |
|---|---|
| `no_live_source` | не выбран источник данных |
| `no_bar` | бар не выбран (`all`): таплист есть только у конкретного бара |
| `no_data` | бар не найден в таплисте / не удалось прочитать данные / на кранах бара нет активных позиций |
| `stale_taps` | краны бара не обновлялись больше 14 суток (см. «Свежесть кранов») |
| `bad_placeholder` | неизвестная подстановка |
| `text_too_long` | итоговый текст длиннее предела площадки |

**Не останавливает** (с 2026-10-09, владелец: «не останавливаем публикации из-за сомнения в
одном сорте, просто прикрепляем без ссылки»): кран без проверенной связи с Untappd выходит
строкой без ссылки и стиля (имя кеги из iiko без «КЕГ» и объёма), а в ответе — `notes`
`[{code: 'unverified', text: 'Кран N: <сообщение реестра> — выйдет без ссылки на Untappd'}]`;
на экране — строка под «Как увидят гости». Связь добавляется без деплоя: карточку предлагает
ИИ-агент, администратор подтверждает на «Связях с Untappd» (`/taps/untappd`,
[untappd-links.md](untappd-links.md)); товар iiko на кране не выбран — «Уточнить сорт» на
странице бара. До 2026-10-09 такой кран (`unverified`) останавливал пост бара целиком.

Предел длины (`text_limit_for`) — тот же, что у готовой публикации: Telegram и бот — 1024,
если у размещения есть файлы, и 4096 без них; Instagram — 2200. Без площадки (общая
проверка шаблона — так её зовёт агент, `content_live_preview`; экран с 2026-10-04 проверяет
только по размещениям, «Как увидят гости») — 4096, это предел сообщения Telegram. Ответ несёт `limit_note` — откуда взят предел. Пример: подставленный таплист дал
1300 знаков; у размещения TG с фото — «текст длиннее 1024 знаков», без фото — проходит.

Проблемы данных — не ошибка запроса: ответ 200 с `ok: false` и списком `problems`.
Предпросмотр размещения шлёт площадку и наличие файлов этого размещения, поэтому счётчик
«N / предел» в предпросмотре — предел именно его площадки. Ответ: `text`, `entities`,
`problems`, `length`, `limit`, `limit_note`, `rows` (у каждого крана ещё `name` — как в посте,
`untappd_url`, `new`), `data_at`, `taps_changed_at`.

### Фото и видео

| Что | Правило | Почему |
|---|---|---|
| Тип | по **сигнатуре** (первые байты), не по расширению и не по `Content-Type`: JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A`, WEBP `RIFF…WEBP`, MP4 `ftyp` в байтах 4..7 | расширение и тип пишет клиент |
| HEIC/AVIF | отклоняются с текстом «сохраните его как JPEG» (у них тоже `ftyp`, бренд в байтах 8..11) | иначе фото с айфона приняли бы как видео |
| MOV | проходит как видео (бренд `qt  `) | браузеры и Telegram его играют |
| Фото | до 10 МБ (`MAX_IMAGE_BYTES`) | предел Telegram Bot API для `sendPhoto`; у Instagram строже (8 МБ, только JPEG) — проверит будущая отправка |
| Видео | до 50 МБ (`MAX_VIDEO_BYTES`) | предел Telegram Bot API на загрузку файла ботом |
| Тело запроса | больше 50 МБ + 64 КБ — 413 до чтения формы | Flask читает форму в память целиком |
| Файлов у материала | до 20 | см. «Модель данных» |
| Имя | `cp_<YYYYMMDD>_<12 hex>.<ext>`, `ext` — `jpg`, `png`, `webp` или `mp4`: префикс раздела, московская дата загрузки, 48 бит случайности | каталог читается глазами; ссылку нельзя угадать |
| Доступ к диску | только через `MediaStore.path()`: имя проверяется регуляркой `NAME_RE` (конец строки `\Z`) до любого обращения к диску, конкатенации пути с пользовательской строкой нет | `../` и обратные слэши отсекаются формой имени |
| Раздача | явный тип по расширению, `X-Content-Type-Options: nosniff`, `Cache-Control: private, max-age=86400`, поддержка Range для перемотки видео | имя неизменно: новая загрузка — новое имя, сутки кэша безопасны |

Порядок загрузки: размер тела (413) → материал есть (404) и не набрал 20 файлов (400) →
сигнатура и размер (400) → запись на диск (через временный файл и `os.replace`) → привязка
к материалу. Если привязка не удалась, записанный файл удаляется — сирот не остаётся.
Загруженный файл хранится как есть, без перекодировки. Картинку, найденную поиском, сервер
перед записью переводит в JPEG (Pillow) — см. «Картинки к постам».

**Общие файлы.** Повтор и копирование с текстами ссылаются на те же имена. Поэтому файл
удаляется с диска, только когда на него не ссылается ни один материал и ни один снимок
утверждения (`_media_referenced`). Удаление из материала не трогает подборки вышедших и
отменённых размещений: их подборка — история.

На экране: перетаскивание в зону или кнопка «Выбрать файлы». Само поле выбора файлов
`#cpFile` живёт **вне** карточки: карточка перерисовывается целиком (автосохранение, ответы
сервера), и поле внутри неё отрывалось бы от страницы, пока открыт системный диалог, —
выбранный файл молча терялся (см. [lessons.md](lessons.md)). Клиент заранее отсекает файлы
больше предела по `type` браузера и грузит по одному.

### Картинки к постам (с 2026-10-02)

Решение владельца: агент сам находит картинки к постам и сразу добавляет их в план;
поиск не ограничен открытыми лицензиями — каналы баров локальные, на десятки подписчиков.
Граница: фото баров, кранов, блюд и людей по-прежнему снимает команда (`shot_list`, «Нужно
фото»). Чужая картинка там выдавала бы чужое за своё: «у нас брискет 16 часов» с фото чужого
брискета. Картинки из интернета — к историям, праздникам и событиям.

Как агент это делает (три инструмента MCP, раздел «ФОТО» в инструкциях агента):

1. `content_image_search(q, orientation?, site?, page?)` — сервер спрашивает Yandex Search
   API (поиск по картинкам) и отдаёт до 12 вариантов с id поиска.
2. `content_image_search_collage(search_id)` — варианты одной картинкой: сетка 4 x 3,
   над каждой номер, размер оригинала и сайт. Агент выбирает **глазами**, а не по подписи.
3. `content_media_add_found(material_id, candidate)` — сервер сам скачивает выбранный
   вариант, готовит JPEG и кладёт в материал; источник — в `media[].source`.

| Правило | Значение | Почему |
|---|---|---|
| Что ищем | 60 картинок за запрос (`DOCS_ON_PAGE`), без фильтра размера Яндекса | у Яндекса «LARGE» — это 800x600..1600x1200 (самые большие туда не входят), «ENORMOUS» — больше 1600x1200 (отсекает хорошие 1200 px); размер отбираем сами |
| Отсев | повторы адреса; стоки с водяными знаками (`STOCK_DOMAINS`: shutterstock, depositphotos, alamy, lori и др., и их поддомены); большая сторона меньше 1000 px (`MIN_LONG_SIDE`); размер неизвестен — остаётся до скачивания | превью стоков — с надписью поперёк; мелкая картинка в Telegram мутная |
| Вариантов агенту | до 12 (`CANDIDATES_MAX`) | коллаж 4 x 3 влезает в предел картинки для агента (650 КБ < 700 КБ моста) |
| Пример отсева | из 60: 3 повтора, 5 со стоков, 30 мелких → 22 годных, агенту — первые 12 | — |
| Хранение поиска | файл `content_image_search/is_<YYYYMMDD>_<12 hex>.json`, 3 суток (`KEEP_DAYS`), уборка при следующем поиске (и брошенных временных файлов старше часа); вариант — `<id поиска>-<номер>` | прикрепляется только вариант из файла сервера |
| Поисков в сутки | до 150 на всю сеть (`DAILY_LIMIT`) и до 60 на одно подключение (`PER_CALLER_DAILY_LIMIT`: подключение MCP — грант OAuth или статический токен — или вход человека; остальным остаётся не меньше 90), дальше 429. Место бронируется до запроса в Яндекс (файл поиска «pending»), неудачный запрос бронь снимает | запрос платный; петля агента не сожжёт бюджет и не займёт весь предел за остальных; параллельные воркеры не проскочат предел. Считаем по гранту, а не по id OAuth-токена: claude.ai обновляет токен каждый час, и учёт по токену обнулялся бы ежечасно |
| Кто может искать | только администратор (MCP работает от имени владельца); `POST` — это запись (черновик): в коннекторе «Только чтение» поиска нет | платно, пишет файл поиска |
| Превью в коллаже | миниатюра из ответа Яндекса → оригинал (до 6 МБ) → миниатюра по id картинки; меньше 40 px — не превью; каждое превью — не дольше 8 с, весь коллаж — не дольше 25 с; не успело — серая ячейка «no preview» | адрес миниатюры по id собран по образцу — поэтому последний; медленный сайт не держит поток сайта |
| Кэш коллажа | только если все превью получились; запись через уникальный временный файл и `os.replace`; из кэша отдаётся только целый JPEG | временный сбой сайта не оставит серый коллаж на 3 суток; два параллельных запроса не портят файл друг другу |
| Скачивание | адрес разбирается **один раз**, и соединение строится из тех же частей; «\\», данные входа (`user@host`), пробелы и управляющие символы — отказ; нелатинский домен (`пиво.рф`) — в punycode один раз, это же имя идёт в DNS, TLS и `Host`; имя разрешается в IP один раз, все IP — публичные (localhost, внутренние сети, link-local с адресом метаданных облака, 100.64/10, IPv6 с IPv4 внутри — 6to4, NAT64, Teredo — закрыты), сокет открывается на **этот** IP, TLS проверяется по имени хоста; каждая переадресация проверяется заново, не больше 3; до 20 МБ; без распаковки (`Accept-Encoding: identity`); общий срок 30 с держит сторож — по сроку он закрывает сокет; Referer — страница с картинкой | сервер не ходит во внутреннюю сеть: ни через разные разборщики адреса, ни через подмену DNS между проверкой и соединением; сайт, отдающий по байту в 4 с, не держит поток (таймаут сокета отсчитывается заново после каждого байта, сторож — нет) |
| Подготовка | JPEG, PNG, WEBP, GIF (первый кадр); пиксели — по заголовку, до распаковки: JPEG до 40 млн (распаковывается сразу уменьшенным), остальное до 12 млн; распаковка — не больше двух одновременно на процесс, рамка уменьшения при распаковке — по пропорциям картинки; большая сторона меньше 800 px — отказ (400 `image_download_failed`); стороны больше 20 : 1 — отказ (Telegram не примет); прозрачность — на белый; больше 2560 px — уменьшение, поворот по EXIF — после уменьшения; JPEG 88, если больше 10 МБ — качество ниже шагами по 10 | маленький PNG огромного размера («бомба») не съест память; 2560 px хватает Telegram и Instagram; 10 МБ — предел `sendPhoto` |
| Источник | `media[].source` = адрес картинки, страница, сайт, заголовок, запрос, вариант, ширина и высота; `original_name` — «<сайт>.jpg» (сайт до 100 знаков, `FOUND_NAME_SITE_MAX`); журнал: «Добавлена картинка из поиска: <сайт>» | видно, откуда картинка, если владелец захочет заменить; имя с расширением — иначе в архиве для Instagram файл лёг бы как `01_upload.wikimedia.org` (архив дописывает расширение, только если в имени нет точки) и телефон не открыл бы его как фото |
| Режим «Чтение и черновики» | поиск и прикрепление — `draft_write`; прикрепление — только к своему черновику (`guard_draft_mode`, 409 до скачивания) | расписание может готовить картинки, но не трогает материалы владельца |

**Почему вариант, а не адрес.** Агент по расписанию читает отзывы гостей и описания пива.
Если бы сервер скачивал любой адрес из вызова, «команда», внедрённая в отзыв, могла бы
заставить его сходить по своему адресу — с данными в строке запроса или во внутреннюю сеть.
Поэтому адрес сервер берёт только из своего файла поиска, а соединяется только с проверенным
публичным IP.

**Настройка.** Переменные окружения сервера: `YANDEX_SEARCH_API_KEY` — ключ API сервисного
аккаунта Яндекс Облака с доступом к Search API, `YANDEX_SEARCH_FOLDER_ID` — id каталога.
Без них поиск отвечает 503 `image_search_not_configured`, остальной контент-план работает.

1. Ключ создаёт владелец в Yandex AI Studio (aistudio.yandex.ru): у облака должен быть активный
   платёжный аккаунт; «Создать API-ключ» сам заводит сервисный аккаунт с ролью
   `search-api.webSearch.user` на каталог. При ручном создании в консоли облака — та же роль и
   область действия ключа `yc.search-api.execute`. В `.env` идёт секретная часть ключа (не его
   ID); ID каталога копируется кнопкой у имени каталога вверху экрана AI Studio.
2. Обе строки дописать в `/opt/beer/.env`. Копию `.env` держать в `/root/env-backups/`, не в
   `/opt/beer`: лишний файл там останавливает выкладку (docs/guides/deploy.md).
3. Контейнер читает `.env` только при создании: `cd /opt/beer && docker compose up -d --no-build
   --no-deps --force-recreate app` (`--no-build` — взять уже выложенный образ, ничего не собирать;
   не запускать, пока идёт «Deploy production»). `/login` после пересоздания отвечает не сразу:
   `for i in $(seq 30); do c=$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:10000/login);
   [ "$c" = 200 ] && break; sleep 2; done; echo $c` — ждать 200. Если ключи легли до выкладки нового
   образа, контейнер пересоздаст сама выкладка.
4. Проверка без записи в план: `docker exec beer-app sh -c 'test -n "$YANDEX_SEARCH_API_KEY" &&
   test -n "$YANDEX_SEARCH_FOLDER_ID" && echo ok'`, затем один поиск из Python в контейнере
   (`get_finder().search(...)`, `collage(search_id)`, `download('<id>-<n>')`). Файлы поиска
   ложатся в `/srv/kultura/content_image_search/` (в контейнере `/kultura/...`): `is_<дата>_<id>.json`
   есть всегда, `.jpg` коллажа — только если загрузились все превью (его нет — не сбой). Файлы
   старше трёх суток удаляются при следующем поиске, не по таймеру.

Выключить поиск: убрать обе строки и пересоздать контейнер — поиск снова отвечает 503, остальное
работает. Ошибки Яндекса приходят как 502 «Яндекс ответил HTTP …»: 401/403 — ключ неверный или
отозван, у аккаунта нет роли на этот каталог или ID каталога не тот; текст про платёжный аккаунт —
у облака нет активного биллинга; «Яндекс не ответил» — нет исходящего доступа к
`searchapi.api.cloud.yandex.net`. Отдельные варианты, которые «не скачались», — норма: сайт закрыт
от ботов или недоступен из РФ; агент берёт другой вариант.

### Что показывает вышедшее размещение

| Статус | Текст и файлы | `content_source` |
|---|---|---|
| `published`, `failed` со снимком | из снимка утверждения: то, что ушло (или уходило) в площадку | `snapshot` |
| все остальные | текущие `effective_text` / `effective_media` | `current` |

У `approved`/`paused` текущее и снимок совпадают всегда: любое изменение содержания
снимает утверждение. Правка общего текста или удаление файла после выхода вышедшее
размещение не меняет.

Каждое размещение в ответе несёт `media_items: [{name, kind, url, original_name}]`: `kind` —
по расширению имени, `url` — маршрут раздачи. Поэтому ссылка работает и для файла, которого
у материала уже нет (он остался только в снимке и с диска не удалялся); `original_name`
тогда `null`. Экран подписывает такое размещение «Так вышло: текст и файлы на момент
утверждения».

Край: у вышедшего материала с актуальными данными снимок хранит **шаблон**, а не
подставленный таплист. Предпросмотр такого размещения строится по данным на сейчас и
подписан «данные на сейчас, не на момент выхода».

### Отправка публикаций (с 2026-09-28)

Отправщик — [core/content_publisher.py](../core/content_publisher.py); настройки —
[core/content_channels.py](../core/content_channels.py); поток раз в минуту —
[core/content_publisher_scheduler.py](../core/content_publisher_scheduler.py). Всё по умолчанию
выключено: пока владелец не укажет и не проверит канал бара и не включит отправку, ни одна
публикация сама не уходит.

#### Каналы и отправка (настройки)

`content_channels.json`: главный выключатель `enabled` («отправлять утверждённое само»),
канал каждого бара `telegram.<бар>` (`chat` — `@имя` публичного канала, ссылка `t.me/имя` или
числовой id `-100…`; `title` — подпись до 100 знаков; `check` — последняя проверка),
Instagram — `reminder_chat` (чат для напоминаний владельцу; личный чат — только числовым id)
и `reminder_minutes_before` (0..720: за 12 часов — вечером о посте на утро, раньше
напоминание теряет смысл), гостевой бот — `bot.enabled` (рассылки гостям) и `bot.signup`
(кнопки «Подписаться на новости» и «Оставить отзыв» в @kult_taplist_bot: включать, когда
владелец утвердит текст согласия; бот спрашивает `bot_signup_enabled()` — файл, кэш по
mtime, при любой ошибке — «кнопок нет»). `history` — последние 100 изменений (кто и когда
включил отправку).

Пригласительная ссылка (`t.me/+…`) не подходит: бот по ней канал не найдёт. Смена адреса
канала стирает его проверку и момент подключения.

**Адреса по роли** (проверка 2026-09-28, п. 13): канал бара — только канал или группа.
Положительный числовой id — личный чат, в канал бара он не сохраняется (400 «положительный id —
это личный чат, а не канал»); личный чат, найденный проверкой по `@имени` (`getChat` → `type:
private`), — `can_post: false` «Это личный чат, а не канал…», в него посты не уходят. Чат
напоминаний об Instagram не может совпадать с каналом бара (`reminder_conflict`: адрес, `@имя`
без учёта регистра или числовой id, которые вернула проверка канала) — иначе служебная заметка
«пора выложить» ушла бы подписчикам канала: такая правка — 400, ничего не сохраняется.
Совпадение, которое появилось после проверки канала (Telegram вернул тот же id), правки не
блокирует (иначе нельзя было бы даже выключить отправку), но Instagram становится «не подключён:
чат для напоминаний совпадает с каналом бара …», и отправитель такое напоминание не шлёт.

**Проверка канала** (`POST /channels/check`): `getMe` -> `getChat` -> `getChatMember(бот)`.
Бот может публиковать (`can_post`), если он в канале создатель или администратор с правом
«Публикация сообщений» (`can_post_messages`); в группе — участник. Итог сохраняется у бара
вместе с адресом, для которого получен. **Сбой связи** (нет ответа, 429, 5xx) не сохраняется:
`saved: false`, `check.transient: true`, «Telegram временно недоступен — прежняя проверка не
изменилась» (было: случайный сбой выключал рабочий канал, п. 5). **Момент подключения**
(`connected_since`) ставится при первой успешной проверке адреса и больше не сдвигается — ни
провалом, ни повторным успехом того же адреса (`connected_chat`); сбрасывает его только смена
адреса. Иначе пост, время которого было между сбоем и повторной проверкой, считался бы «раньше
подключения» и не уходил. **Тестовое сообщение** (`POST /channels/test`) — «Проверка связи с
сайтом» в канал: его видят подписчики, его можно удалить. **Дошедшее тестовое сообщение —
тоже проверка** (с 2026-10-09): в канал пишет только администратор с правом «Публикация
сообщений», поэтому неподключённый канал подключается в том же запросе — проверка по чату из
ответа Telegram (`check.via: 'test'`, без `getChatMember`), в журнале «Проверка канала Лиг (@…)
по тестовому сообщению: бот может публиковать». Личный чат и ответ без чата не подключают;
подключённый канал повторный тест не трогает (`connected_since` прежний). Ответ — `{ok,
message_id, error, chat, connected}` и настройки, как `GET /channels`. Почему: 2026-10-09 тест
на Лиговском дошёл, а отдельная проверка после него попала в перезапуск сайта при выкладке —
канал с работающим ботом остался не подключён, и «Таплист пятницы» не ушёл.

**Кто может** (п. 7, решение оркестратора 2026-09-28): всё, что может выпустить публикацию
наружу, — только администратор: `PUT /channels`, `POST /channels/check`, `POST /channels/test`,
`POST /publish-now`, `POST /approve`, действия `retry` / `retry_failed` / `resume` размещения,
`POST /bulk-pause` с `action: 'resume'`. Остальным — 403 `{error: 'Только администратор может …',
code: 'admin_required'}`, ничего не меняется. Причина: у каждого бармена личный вход, аккаунты
равны, лимита попыток входа нет. Чтение (каналы, аудитория, zip) и остановка (пауза, отмена) —
всем. MCP работает от имени администратора-владельца — его это не ограничивает.

Два бота (`core/content_channels.py`):

| Бот | Токен | Что делает |
|---|---|---|
| бот каналов (`channel_bot_token`) | `TELEGRAM_CONTENT_BOT_TOKEN` (отдельный бот контента, необязательно), иначе `TELEGRAM_BOT_TOKEN` | посты в каналы баров, проверка канала, тестовое сообщение, напоминание об Instagram |
| гостевой бот (`guest_bot_token`) | только `TELEGRAM_BOT_TOKEN` (@kult_taplist_bot) | рассылки гостям |

Рассылки — только гостевым ботом: гость запускал его, а бот контента в личный чат гостя написать
не может — Telegram ответит 403, и каждый подписчик был бы помечен «заблокировал бота»
(замечание проверки 2026-09-28, тест `test_guest_mailing_uses_only_guest_bot`). `file_id` у
каждого бота свой — кэш загрузок раздельный. Чат напоминаний об Instagram должен был запустить
бота каналов (или это группа, где он есть). Токены в ответы не попадают; `token_source` — бот
каналов (`content`, `taplist` или `null` — «бот не настроен»), `guest_token_source` — гостевой.

**Что подключено** (`delivery` в ответе месяца и настроек):

| Площадка | Подключено, если |
|---|---|
| Telegram, бар X | отправка включена, есть бот каналов, у бара X канал проверен (ok и can_post для текущего адреса) |
| Instagram | отправка включена, есть бот каналов, задан чат для напоминаний и он не совпадает с каналом бара |
| Бот | отправка включена, есть гостевой бот, рассылки гостям включены |

`reason` — почему не подключено: сначала своя настройка («канал не указан», «канал не
проверен», «бот не может публиковать в канале», «не указан чат для напоминаний», «рассылки
гостям выключены»), потом общее («отправка выключена», «бот не настроен», у рассылок —
«гостевой бот не настроен (нет TELEGRAM_BOT_TOKEN)»). `bot_configured` / `guest_bot_configured` —
есть ли бот каналов и гостевой бот. Прежнее поле
`delivery_connected` = `{telegram: хоть один бар, instagram, bot}`. Instagram требует и
токен (контракт называл только выключатель и чат): напоминание шлёт бот.

#### Когда уходит

```
пост   = дата + время размещения
начало = пост; у Instagram — пост минус reminder_minutes_before (время напоминания)
пора   = max(начало, delivery.retry_at) <= сейчас (минута по Москве);
         «Отправить сейчас» и продолжение рассылки — retry_at <= сейчас
поздно = max(пост, retry_at) <= сейчас − 120 минут (GRACE_MINUTES)
```

«Поздно» и «раньше подключения» считаются от времени ПОСТА, не напоминания (п. 3): пост на
16:00, утверждённый в 11:00 при «напоминать за 720 минут» (напоминание — 04:00), раньше
оставался без напоминания («раньше подключения» или «опоздало»); теперь время напоминания
прошло, а пост впереди — напоминание уходит сразу, один раз.

Проход раз в минуту (в начале минуты + 1 с) берёт размещения `approved` (и вышедшие
рассылки бота с повтором в очереди), которым пора. Сначала посты каналов и напоминания, потом
рассылки (п. 8):

| Случай | Что происходит |
|---|---|
| главный выключатель выключен или нет токена | ничего не шлётся и не пишется; в отчёте — skipped |
| площадка не подключена | пропуск: размещение остаётся «Время вышло», как до подключения |
| время поста раньше подключения площадки (`since_for`: самый поздний из моментов включения отправки и готовности площадки) и это не повтор | пропуск: накопленный до подключения хвост отмечают вручную — его не выпускают и не помечают ошибкой |
| поздно | Telegram и бот — `failed` «Время выхода прошло, пока сервер не работал: проверьте и отправьте повторно» (решение владельцу); рассылка, которая уже кому-то дошла, — остановка «дошло N из M»; Instagram — `reminder_late`, напоминание не шлётся |
| Instagram, напоминание для этого времени поста уже было (`reminded_for`) | пропуск — одно напоминание на время поста; пост перенесли (правка, сдвиг) — напоминание взводится заново (п. 4) |
| рассылка, а бюджет прохода исчерпан | начнётся в следующем проходе |
| иначе | отправка |

Пример: пост на 16:00, сервер лежал с 15:50 до 18:30 → в 18:30 ошибка «время выхода
прошло»; «Повторить» ставит `retry_at` = 18:31 → бот отправит в 18:32. Сервер лёг до 17:59 —
пост уходит в 18:00 (опоздание меньше двух часов).

**Бюджет рассылок** (`MAILING_BUDGET_SEC` = 40 с на проход из 60 с; запас — на посты, запись
плана и медленную сеть): рассылка, не уложившаяся в бюджет, сохраняет прогресс и встаёт в очередь
(`delivery.state 'queued'`, `continuation: true`, статус остаётся `approved`), продолжение — в
следующем проходе, только тем, кого нет в `sent_to` (без дублей). Так тысяча гостей с альбомом
из 10 фото (≈ 7 минут отправки при 25 сообщениях в секунду) не задерживает пост канала на 16:05:
он уходит в 16:05, рассылка идёт частями по 40 с с 16:00 до 16:09 (проба 2026-09-28). 429 в
рассылке не ждётся (раньше — до 60 с на получателя): этому гостю не ушло, рассылка продолжится в
следующем проходе с него же. Журнал: `delivery_progress` «Рассылка продолжится в следующем
проходе: дошло N из M» (автор — бот). `published_at` долгой рассылки — время прохода, в котором
она завершилась.

#### Идемпотентность

Перед вызовом Telegram размещение под блокировкой плана помечается
`delivery = {state: 'sending', attempt_id, started_at, heartbeat_at}` — второй отправщик
его не возьмёт. Итог — `published` (`published_at`, `published_by` «бот», `delivery.chat`,
`delivery.message_ids`) или `failed` (`failed_error`); пишется, только если попытка своя
(`attempt_id`). «Отправляется» дольше 10 минут без отметки — процесс умер посреди отправки:
**повторно не отправляется** (пост мог уже выйти), а становится `failed` «Статус отправки
неизвестен: проверьте канал; если поста нет — «Повторить»». Отправляет только планировщик — он
один на сервер (п. 9/10); свою попытку, которая ещё идёт (долгая загрузка видео), он зависшей
не считает (`_ACTIVE_ATTEMPTS` — попытки этого процесса). Рассылка обновляет отметку после каждой
пачки, поэтому живая рассылка «зависшей» тоже не становится.

**Пока отправляется — не меняется** (п. 2): правка текста или файлов материала, сдвиг, правка
размещения, пауза и отмена обычного поста, «Отправить сейчас» — 409 «Публикация сейчас
отправляется — подождите минуту и обновите страницу» (`_guard_not_sending` — и в
автоснятии утверждения `_auto_unapprove`, и в сдвиге). Было: правка посреди рассылки
переводила размещение в черновик и стирала `delivery`, и после повторного утверждения гости
получали рассылку дважды. Если итог всё-таки не записать (попытку потеряли — размещение
изменили в обход защиты или удалили), в журнал материала пишется `auto_failed` с тем, что
ушло: «Пост вышел в канале @… (сообщение N), но размещение изменили во время отправки —
отметьте выход вручную» или «Рассылка остановлена: размещение изменили; дошло N».

| `delivery.state` | Смысл |
|---|---|
| `queued` | ждёт прохода (`retry_at`): повтор, «Отправить сейчас» (`send_now`), продолжение рассылки (`continuation`) |
| `sending` | отправляется |
| `sent` | ушло |
| `partial` | рассылка дошла не всем (или остановлена, когда кому-то уже дошла) — можно «Повторить неудавшимся» |
| `stopped` | рассылку остановили (пауза, отмена, выключатель), не дойдя ни до кого: статус `paused` / `cancelled` / `failed` |
| `failed` | ошибка (`error`) |
| `reminded` / `reminder_failed` / `reminder_late` | Instagram: напоминание ушло / не ушло / опоздало — для времени поста `reminded_for` |

#### Ответы Telegram

| Ответ | Итог |
|---|---|
| соединение не установилось (запрос точно не ушёл) | повторяет транспорт (3 попытки, запасные адреса — `core/open_check_telegram.py`) |
| нет ответа, а запрос мог дойти | повтора нет; пост — `failed` «Telegram не ответил (нет связи): пост мог не выйти — проверьте канал…»; в рассылке — «статус неизвестен» (`unknown_to`), повтор этому гостю не шлётся |
| все пути отказали до отправки (`last_outcome 'not_sent'`) | пост — `failed` «Telegram недоступен (нет соединения): сообщение не отправлено — «Повторить» отправит его»; в рассылке — `failed_to`, «Повторить неудавшимся» безопасен |
| 429 | пост — один повтор через `retry_after`, если ждать не дольше 60 с, иначе ошибка; рассылка не ждёт — продолжение в следующем проходе |
| 5xx | `failed` «Telegram временно не отвечает (ошибка N)» без повтора |
| 403 в рассылке | гость заблокировал бота: `guest_subscribers.mark_blocked` |
| прочие | `failed` с переводом частых описаний («канал или чат не найден», «у бота нет права публиковать»…) и исходным текстом в скобках |

**Без дублей при сбое связи** (п. 1, проверка 2026-09-28): раньше любая ошибка основного пути
(в том числе ReadTimeout — Telegram получил запрос, но ответ не дошёл) вела на запасные адреса с
тем же запросом — в канале выходило 2–4 копии поста. Отправитель публикаций вызывает транспорт с
`safe_resend=True` (`api_call` и `api_call_files`): другой путь пробуется, только если ошибка
доказывает, что запрос не ушёл — `ConnectTimeout`, `SSLError` (рукопожатие), `ConnectionError`
из-за `NewConnectionError` (отказ соединения, DNS). ReadTimeout, обрыв посреди соединения,
`ChunkedEncodingError`, ответ не JSON (страница 5xx прокси) — сразу «ответа нет», `outcome
'unknown'`. Все пути отказали до отправки — `outcome 'not_sent'`. Чтение (`getMe`, `getChat`,
`getChatMember`) повторять безопасно — без ключа. Прочие вызовы транспорта (open-check, бот
таплиста) без ключа ведут себя как раньше; ответ гостю на отзыв (`routes/reviews.py`) передаёт
`safe_resend=True` — это правка раздела отзывов.

#### Что уходит

Текст и файлы — из снимка утверждения (что утвердил владелец). У материала с актуальными
данными шаблон собирается в момент отправки (`render_live` с площадкой и наличием файлов, дата
— дата размещения); стоп-правило — `failed` «Публикация остановлена: <проблемы>», в канал
ничего не уходит. До отправки проверяются пределы (4096 / 1024 / 2200), до 10 файлов, файлы на
диске и их сумма — не больше 50 МБ на сообщение (предел загрузки файла ботом; больше одним
запросом не шлём — память и таймаут).

**Длина — как считает площадка** (`text_units`, п. 12): Telegram и бот считают в единицах
UTF-16 — символ вне основной плоскости Unicode (эмодзи, редкие иероглифы) занимает 2:
`len(text.encode('utf-16-le')) // 2`. Instagram — в символах (`len`). Одно правило — в
готовности черновика, в `render_live` (поле `length`) и в отправителе. Пример: 4000 букв и 60
эмодзи — `len` 4060, Telegram насчитает 4120 > 4096: раньше пост проходил проверку и
отклонялся при отправке. Подсказка у счётчика (`limit_note`) говорит «эмодзи считается за 2
знака, как в Telegram».

| Площадка | Как |
|---|---|
| Telegram-канал бара | без файлов — `sendMessage` (без `parse_mode`, предпросмотр ссылок включён); 1 файл — `sendPhoto` / `sendVideo` с подписью; 2..10 — `sendMediaGroup`, подпись у первого. Живой таплист — со ссылками на Untappd: `entities` у текста, `caption_entities` у подписи, предпросмотр ссылки выключен (раздел «Живые данные (таплист)»). Файлы — multipart с диска; загруженный файл Telegram возвращает с `file_id`, и остальные бары за тот же проход получают его без повторной загрузки |
| Instagram (ручной) | в момент выхода минус `reminder_minutes_before` в чат напоминаний: заголовок «Instagram: пора выложить — «<название>», <дата время>» со ссылкой `https://beerkultura.ru/content-plan?open=<id>`, текст подписи отдельным сообщением (удобно скопировать), фото и видео альбомом без подписи. Размещение остаётся `approved`, напоминание — одно; «вышло» владелец отмечает сам. Сбой — `reminder_failed` без автоповтора (повторить — «Отправить сейчас») |
| Рассылка бота | только гостевым ботом (`TELEGRAM_BOT_TOKEN`); получатели — `guest_subscribers.recipients(сегмент, бар)` на момент первого запуска (список хранится — M не меняется); каждому то же сообщение, не чаще 25 в секунду (лимит Telegram ~30/с на бота, запас на ответы бота гостям; альбом из k файлов — k сообщений). Прогресс — после каждой пачки из 25 (`sent_to`, `failed_to`, `blocked`, `pending`, `heartbeat_at`): сбой посреди рассылки не шлёт повторно тем, кому ушло; получатели прерванной пачки — `unknown_to`, им повтор не шлётся. Три обрыва связи подряд — стоп, остальные в `failed_to`. Итог — `published` и `stats {total, sent, failed, blocked, unsubscribed, unknown}`; дошло не всем — «дошло N из M» и `retry_failed`; никому — `failed`; в аудитории никого — `failed` «В аудитории нет ни одного подписчика». Повтор шлёт только тем, кто всё ещё подписан |

Пример рассылки: 5 подписчиков, у третьего бот заблокирован (403), четвёртому Telegram ответил
400 → `published`, «дошло 3 из 5», третий отмечен заблокированным; «Повторить неудавшимся» → в
следующую минуту сообщение уходит только четвёртому.

**Остановка идущей рассылки** (п. 6; было: выключили всё на 11-м из 200 — ушло ещё 189). Перед
каждой пачкой (25 получателей) отправитель перечитывает настройки: выключены отправка
(`enabled`) или рассылки гостям (`bot.enabled`) — стоп. Пауза и отмена рассылки, которая сейчас
отправляется, не 409, а флаг `delivery.stop_requested` — стоп перед следующей пачкой; ответ
маршрута несёт `notice` «Рассылка остановится после текущей пачки: получившим повторно не
уйдёт», подпись — «· остановится после текущей пачки». Рассылка, которая ждёт продолжения в
следующем проходе и уже кому-то дошла, останавливается паузой или отменой сразу. Между проходами
отправку выключили и включили снова — тоже стоп (`switch_marks`: отметки включения на момент
паузы между проходами). Итог остановки (`stop_mailing`): не получившие — в `failed_to` («Повторить
неудавшимся» доведёт позже), получившие и «статус неизвестен» не трогаются; кому-то дошло —
`published`, `partial`, «Рассылка остановлена (<причина>): дошло N из M»; никому — `stopped` и
статус `paused` / `cancelled` / `failed`. Пример: 60 подписчиков, отправку выключили на 10-м —
первая пачка дошла (25), 35 — в `failed_to`; после включения «Повторить неудавшимся» шлёт только
этим 35.

#### «Отправить сейчас» и «Скачать для Instagram»

`POST /api/content-plan/publish-now {placement_id}` (только администратор): только
утверждённое; отправка включена, площадка подключена, бот настроен, на сервере работает
планировщик (`CONTENT_PUBLISH` не `0`) — иначе 409 с причиной. **Только ставит в очередь**
(п. 9/10): `delivery = {state: 'queued', retry_at: сейчас, send_now: true}`, ответ сразу
`{placement, material, queued: true, message: 'Уйдёт в течение минуты'}`; отправляет
планировщик в ближайший проход (до минуты), у Instagram — напоминание сразу, не за N минут.
Раньше Telegram и Instagram отправлялись прямо в веб-запросе, а рассылка — потоком в
веб-воркере: перезапуск воркера (каждые ~800 запросов, деплой) рвал её, два потока слали 50
сообщений в секунду, долгая загрузка могла быть признана «зависшей». `{дата}` у живых
материалов — сегодняшняя. Журнал: `publish_now` (кто нажал) и затем `auto_publish` /
`auto_failed` / `reminder` (бот). Дата и время размещения не меняются: момент выхода —
`published_at`.

`GET /api/content-plan/materials/<id>/download` — zip: по текстовому файлу на каждое
неотменённое размещение (`NN_<площадка>_<бар>_<дата>_<ЧЧММ>.txt`, только текст подписи),
фото и видео в `files/` (имена — исходные, без пути) и опись `opis.txt` (какое размещение,
когда, какой текст и какие файлы). У вышедших — текст из снимка; у живых — таплист на момент
скачивания (в описи — пометка), если данных нет — шаблон и причина.

#### Размер аудитории бота

`GET /api/content-plan/audience?segment=&bar=` и `audiences[].size` в ответе месяца (у
«выбравших бар» — `size_by_bar`), `audience_info.size` у размещений и в окне утверждения:
`core/guest_subscribers.audience_size` на сейчас (к моменту рассылки может измениться).
«Были за 30 дней» и «не были 60 дней» считают только подписчиков, поделившихся телефоном
(визиты — из базы гостей по телефону). «Выбравшие бар» без бара — `size: null`, «выберите
бар». Модуля подписчиков нет — 0; сбой чтения — `null` с пояснением. Персональных данных в
ответах нет — только числа.

#### Чего нет

Правка вышедшего поста в канале (`editMessageText`) — вне объёма: исправление — новым постом,
старый удаляют руками в Telegram.

### Учёт правок владельца для агента (с 2026-09-28)

Материал, созданный агентом (и копии, сделанные агентом), хранит `agent_original` — последнюю
версию агента: общий текст и свои тексты размещений, добавленных агентом (`null` — берёт общий
текст). Правки самого агента через MCP её обновляют, правки людей — нет. Поэтому «итоговый
текст ≠ версии агента» значит «текст менял человек» (контракт называл поле неизменным — но тогда
собственные доработки агента выглядели бы правками владельца).

`GET /api/content-plan/agent-edits?months=3` (1..12): материалы агента с месяцем не раньше
«текущий − months + 1» (текущий и будущие — всегда), у которых текст менял человек: `original`
и `current` (общий текст и размещения агента: итоговый текст — у вышедших из снимка, `changed`
по каждому), `status` и `status_label` (сводка), `base_text_changed`, `removed_placements`; плюс
материалы агента, удалённые людьми (`removed: true`, название и кто удалил — по журналу;
удаления самого агента не считаются). `counts`: `agent_materials`, `changed`, `unchanged`
(владелец принял как есть), `removed`, `without_original` (созданы до 2026-09-28). Агент читает
это перед планом месяца (`content_agent_edits`), чтобы подстроить тон.

### Компактный вид месяца (с 2026-09-28)

`GET /api/content-plan?month=…&compact=1` (и `?state=…&compact=1`): материалы без текстов,
файлов и справочников — `{id, title, kind, month, in_month, date, origin, agent_draft, summary:
{label, state}, placements: [{id, channel, bar, date, time, display_state}]}` и `stats`. Зачем:
месяц с 20+ материалами в полном виде — больше 100 тыс. знаков, мост MCP режет ответ на 60 тыс.
Агент смотрит месяц компактно, детали — `content_material_get`.

### Месяц в ответе и вид «по всем месяцам»

`GET /api/content-plan?month=M` отдаёт материалы с `month == M` **плюс** материалы других
месяцев, у которых есть размещение с датой в M (`in_month: false`: таблица их не
показывает, календарь показывает их размещения, при фильтре состояния таблица показывает их
с пометкой «план: <месяц>»). `stats`: `materials` — число материалов месяца, `placements` и
`by_state` — размещения материалов месяца и размещения, датированные месяцем.

Вид «по всем месяцам» (`state_payload`): `GET /api/content-plan?state=overdue|failed`
**без** `month` отдаёт материалы **любого** месяца, у которых есть размещение в этом
состоянии, — в том же виде, что месяц, плюс `scope: 'state'` и `state`; `month` — текущий
месяц по Москве, `in_month` у всех `true`, `stats` — по этим материалам. Зачем: счётчики
полосы «Время вышло» и «Ошибки отправки» считают размещения за любой месяц (не подключённые
площадки и ошибки отправки копятся через границу месяца), а вид месяца показал бы по их ссылке пустую
таблицу. С `month`, или с другим `state`, — обычный месяц (фильтр `?state=` применяет
экран).

На экране: только в виде «Таблица»; строки сгруппированы по месяцам; над таблицей чип «Все
месяцы · Время вышло» (или «Ошибки отправки») с крестиком. Выход в обычный месяц —
крестиком, стрелками месяца, кнопкой месяца, переходом в календарь или выбором другого
состояния; фильтр состояния при этом остаётся, а месяц пишется в адрес явно (иначе
перезагрузка снова открыла бы сквозной вид). «Утвердить готовые» и «Скопировать прошлый
месяц» в этом виде выключены: обе операции работают с одним месяцем. Если размещение в
открытой карточке перестало быть просроченным, материал выпадает из списка, а карточка
остаётся на нём. Если сервер не ответил `scope: 'state'`, страница честно остаётся в месяце.

### Экран

Переделан 2026-10-04 по жалобе владельца: «открываешь день, чтобы отредактировать пост, — там
ужас: туда-сюда проверки, всё для ИИ-агента; интерфейс неинтуитивный». Принцип: на виду — план,
пост и его время; служебное агента, редкие действия, пояснения и история — свёрнуты или в меню
(правило «пояснения свёрнуты по умолчанию» из `.claude/CLAUDE.md`).

**Полоса фильтров:** месяц (стрелки; нажатие на месяц — текущий), бар (общий для раздела,
`localStorage 'gh.bar'`; с 2026-09-29 им же считается и «Маркетинг»), площадка, вид «Таблица |
Календарь», справа «Утвердить готовые» и «Добавить материал» (на телефоне — в одну строку). Под
ней баннер о состоянии отправки — по `delivery` ответа: не подключено / подключено (какие
площадки) / выключено владельцем.

**Сводка и два меню** (одна строка): слева сводка месяца, справа меню **«ИИ-агент»** (задания
агенту в Claude — «План на <следующий месяц>», «Проверить неделю», «Разобрать отзывы»; «Бриф для
агента»; «Только от ИИ» с числом материалов агента; «Удалить черновики ИИ: N», когда они есть) и
меню **«Ещё»** («Каналы и отправка», «Скопировать прошлый месяц», «Пауза» — открывает меню
паузы по бару или сети). Раньше это были семь кнопок, красная «Удалить черновики ИИ: 28» и
легенда из восьми состояний над таблицей — до первой строки плана было семь полос управления, на
телефоне — два экрана кнопок.

Статусы отправки у размещения (вышло автоматически со ссылкой `post_url`, «Отправляется», ошибка,
«дошло N из M» и «Повторить неудавшимся», «Отправить сейчас», «Скачать для Instagram») экран
строит по `delivery`, `display_label` и `post_url` ответа.

**Каналы и отправка** (выдвижная карточка; «Ещё» -> «Каналы и отправка», кнопка баннера отправки
или адрес `?channels=1`; `GET` / `PUT /api/content-plan/channels`):

- главный выключатель «Отправлять автоматически» (включение — с подтверждением) и строка
  состояния: какой бот отправляет, включено ли, почему не уходит;
- по каждому бару — поле канала (`@имя`, ссылка `t.me/имя` или id `-100…`), статус
  («Канал не задан» / «Не подключён» / «Можно публиковать» / ошибка с текстом), кнопки
  **«Подключить»** (у подключённого — «Проверить снова»: сначала сохраняется набранный адрес,
  потом сервер спрашивает Telegram) и «Тестовое сообщение» (с подтверждением: его увидят
  подписчики канала). Дошедшее тестовое сообщение подключает канал сразу, ответом сервера
  (статус «Можно публиковать», «проверено … тестовым сообщением», тост «канал подключён»);
  отдельную проверку экран запускает, только если сервер канал не подключил. История:
  2026-10-04 владелец добавил бота в канал после неудачной проверки, тест дошёл, «Проверить» не
  нажал — канал остался не подключён (тогда экран стал проверять после теста); 2026-10-09 эта
  проверка после теста попала в перезапуск сайта при выкладке — и канал снова остался не
  подключён (теперь подключает сам тест, одним запросом);
- Instagram — чат для напоминаний и «Минут заранее» (0..720) с подсказкой, что в личный чат
  бот пишет, только если владелец сам начал с ним разговор;
- «Гостевой бот» — выключатели «Рассылки гостям через бота» (включение — с подтверждением) и
  «Кнопки подписки и отзывов в боте» (`bot.signup`), число подписчиков, согласившихся получать
  новости;
- у каждого блока — «Как считается»: когда площадка подключена, что уходит само (только со
  временем после подключения), правило двух часов, что получает чат напоминаний, кто входит в
  аудитории рассылок. Числа в пояснениях — зеркала констант сервера (проверяет render-тест).

**Баннер отправки** над планом — по `delivery` месяца: не подключено; настроено, но
выключено владельцем; включено, но бот не настроен или ни одна площадка не подключена;
включено — какие площадки уходят сами, какие вручную; настройки не читаются (ошибка).

**Отправка у размещения:** под строкой размещения — строка отправки: «В очереди на
отправку: уйдёт в ближайшую минуту» (или «площадка не подключена — не уйдёт, пока её не
подключат»), «Отправляется с …» (пока идёт отправка, действий нет — итог появится сам),
«Вышло автоматически» со временем и ссылкой на пост (`post_url`), ошибка отправки текстом
сервера, у рассылки — сколько получили, не дошло, заблокировали бота, отписались; у Instagram —
напоминание ушло / не ушло / придёт / не настроено. «Отправить сейчас» (у Instagram — «Напомнить
сейчас»; с подтверждением), «Скачать для Instagram» (zip), «Повторить неудавшимся» (с
подтверждением: получившим и заблокировавшим повторно не уходит). Размер аудитории рассылки —
настоящий (`audience_info.size`, `GET /audience`); у ушедшей — итог рассылки.

**«ИИ-агент» -> «Попросить агента»:** три задания агенту контента в Claude — «План на <следующий
месяц>» (сценарий `content_plan_month`), «Проверить неделю» (`content_review_week`), «Разобрать
отзывы» (`content_reviews_digest`). Пункт — ссылка `https://claude.ai/new?q=<задание>` в новой
вкладке; задание заодно копируется в буфер. Подсказка в меню: нужен коннектор
`kultura-content`, подключённый в Claude (ссылка на «Доступ агентов», `/admin/mcp`).

**Фильтры:** бар X — размещения с `bar == X` и размещения на всю сеть; площадка — по
`channel`; состояние (`?state=`) — по `display_state`; «Только от ИИ» (`?origin=agent`). Материал
без подходящих размещений скрыт; тема без размещений видна при фильтрах бара и площадки, но не
при фильтре состояния. Включённые фильтры состояния и «Только от ИИ» видны снимаемыми чипами над
планом.

**Сводка месяца** (числа сервера, без учёта фильтров): Материалов, Размещений, Готово к
утверждению, Запланировано, Не хватает данных — всегда; Время вышло, На паузе, Ошибки отправки —
только если больше нуля. Нажатие — фильтр этого состояния. На телефоне «Материалов» и
«Размещений» скрыты: первый экран — ближе к плану.

**Таблица:** «Без даты» первыми, затем недели с понедельника по воскресенье (в сквозном
виде — месяцы). Колонки: выбор, дата («сегодня» — у первой строки дня), материал (название и
метки «Живые данные», «серия: пт», «из отзыва», «копия», «план: <месяц>»), размещения чипами,
готовность (сводка; подсказка — полная подпись, разбивка «чего не хватает и где» и правила).
С 2026-10-04 в строке нет пометки «ИИ» (от агента почти весь план — метка ничего не различала) и
начала текста (строка ниже вдвое). **Чипы склеиваются** (`chipGroups`): одна площадка, дата,
время и состояние на нескольких барах — один чип со списком баров: «Таплист пятницы» на четыре
бара — «TG все бары 16:00», а не четыре чипа; другое время или состояние — свой чип. Над таблицей
— свёрнутая легенда «Цвета состояний». Отмеченные строки получают панель массовых действий:
**«Утвердить»** (окно «Утвердить готовые» только по отмеченным материалам, без фильтров: списки
`approve-preview` сервера отфильтрованы по id материала — `onlySelected`), сдвиг, отмена
размещений, удаление (`POST /bulk`, до 500 материалов за раз; каждый материал — своя запись,
ошибка по одному не отменяет остальные и возвращается в `failed`).

**Календарь:** сетка месяца с понедельника; в дне до 4 плашек (`CAL_MAX_PILLS`), дальше
«ещё N»; метка плотности — от 3 **разных материалов** в день (`CAL_DENSE_MIN`; один «Таплист
пятницы» на четыре бара — один материал, а не перегрузка дня; отменённые не считаются);
метка «пост + бот» — в один день и пост (TG/IG), и рассылка бота для пересекающейся
аудитории (одна из них на всю сеть или бар совпадает); темы без размещений в месяце —
отдельной плашкой на дату темы. **Плашка** (с 2026-10-04): время, где (у Telegram — бары, «все»,
если все; у Instagram и бота — площадка и бар) и название. Размещения одного материала в одно
время на одной площадке и в одном состоянии — одна плашка (`pillGroups`; сводка дня считает по
размещениям до склейки). В названии плашки нет приставки «<бар>, <дата> — », с которой агент
начинает названия (`pillTitle`: короткое имя бара, «Сеть» или «Бот» в начале, за ним пробел или
запятая, до 16 знаков до « — »; «Кухня, 14 окт — …» и «Таплист пятницы — …» не трогаются): бар и время в плашке
уже есть, а раньше от названия оставалось «ВО, 1…». Пометки «ИИ» в плашке нет — она в подсказке
вместе с полным названием. Слой «Отзывы» (выключен по умолчанию) — «N отз · 4,3» по
`/api/reviews/daily`. Нажатие на пустое место сегодняшнего или будущего дня — «Новый материал» с
этой датой. На телефоне вместо сетки — список по дням.

**Новый материал** (диалог; «Добавить материал», «+ материал» в дне календаря): название и сразу
где и когда он выйдет — «Где выйдет» (Telegram — бары флажками и «Все бары»; Instagram —
аккаунт сети; бот — охват и аудитория; «Без площадки» — тема без размещений), дата (дата темы у
темы) и время (по умолчанию 12:00). Дата по умолчанию — нажатый день, иначе сегодня (открыт
текущий месяц), иначе первое число открытого месяца. «Создать» — два запроса:
`POST /materials` (дата задаёт месяц плана) и `POST /materials/<id>/placements` (как «Добавить
площадку»); затем открывается карточка — дописать текст и фото. Если размещения не добавились
(например, сервер отклонил данные), материал остаётся, тост называет причину, площадку можно
добавить в карточке. Раньше диалог спрашивал только название.

**Карточка материала** (справа, на телефоне — на весь экран; `?open=<id>`). Порядок — по тому,
что делают чаще:

1. **Шапка:** название (правится на месте) и одна строка — пометка «ИИ» у материала агента и
   сводка сервера («Готово к утверждению», «Не хватает: нет фото — везде»…; подсказка — разбивка
   и правила). Кто и когда менял — в «Истории».
2. **«Куда и когда»** — размещения строками: точка состояния, площадка и бар, бейдж состояния
   (у неготового черновика вместо бейджа — чего не хватает: «Нет фото», «Время выхода уже
   прошло»; у готового бейджа нет — на виду «Утвердить»); **дата и время правятся прямо в
   строке** (правила «Дата и время» ниже; у вышедшего, отменённого и того, что сейчас
   отправляется, — текстом); главное действие строки (`primaryAction`): готовый черновик —
   «Утвердить», ошибка — «Повторить отправку», пауза — «Снять паузу», отменённое — «Вернуть»,
   рассылка дошла не всем — «Повторить неудавшимся», время вышло — «Отправить сейчас» (площадка
   подключена) или «Отметить вышедшим»; у запланированного главного действия нет. Остальное —
   по **«⋯»**: прочие действия (пауза, снять утверждение, отметить вышедшим, отменить, удалить,
   «Отправить сейчас», «Скачать для Instagram») и настройки размещения (бар, аудитория рассылки,
   своя версия текста, подборка файлов). Ниже — **«Добавить площадку»** (форма по кнопке:
   Telegram — флажки баров и «Все бары», по размещению на бар; Instagram — по умолчанию «Вся
   сеть»; бот — только с явной аудиторией; дата — дата темы, время по умолчанию 12:00). У темы
   без размещений здесь дата темы и сразу открытая форма.
3. **«Пост»** — текст (у живого материала — шаблон, подстановки кнопками «Вставить:», правила —
   под «Как считается») со счётчиком по самому строгому пределу среди размещений, берущих общий
   текст; поле растёт по тексту до 520 px (`POST_TEXT_MAX_PX`); подпись «свой текст: TG ВО», если
   у размещений своя версия; фото и видео плитками, последняя — «добавить» (туда же можно
   перетащить файлы; пределы — в подсказке). Переключатель **«Текст | Как увидят гости»**:
   предпросмотр каждого неотменённого размещения (пузырь Telegram или бота, квадрат Instagram,
   «N / предел»; у живого материала — с данными таплиста на сейчас) вместо текста и файлов.
   Предупреждения «правка снимет утверждение» — тихой строкой.
4. Свёрнуто (`<details>`, раскрытое остаётся раскрытым после перерисовки): **«От агента»** (у
   материала людей — «Заметки»; справа — что заполнено): «Почему этот пост», «Что снять»,
   «Заметка для команды»; **«Ещё»**: тип материала (пояснение — под «Как считается»), источник
   данных живого материала, «Нужно фото», «Сдвинуть на N дней», «Повторять в этом месяце по дням
   недели», «Удалить материал»; **«История»** (журнал, последние 8 записей и «Показать все»).
5. **Низ:** отметка сохранения, «Закрыть» и **«Утвердить»** — все готовые размещения материала
   одним нажатием («Утвердить все: 4» или «Утвердить готовые: N», если готовы не все; рассылка
   бота среди них — после подтверждения аудитории; только администратор). «Удалить материал»
   больше не стоит внизу каждой карточки — он в «Ещё».

Раньше карточка шла сверху вниз так: тип материала с двумя абзацами пояснений, дата темы
(«ориентир», которую путали с датой выхода), «Почему этот пост» на 1200 знаков, текст, файлы,
«Нужно фото», заметка, «Что снять», размещения (дата и время — только через «Изменить»), всегда
открытая форма «Добавить размещение», предпросмотр, сдвиг и повтор с пояснениями, история —
около 3400 px, четыре экрана на один пост. Отдельной кнопки «Проверить на текущих данных» у
живого материала больше нет: то же делает «Как увидят гости» для каждого размещения (бар, дата,
площадка и предел — его).

**Автосохранение:** тексты уходят через 700 мс после последнего нажатия (`AUTOSAVE_MS`) и
сразу при уходе из поля. Название, пока поле в фокусе, остаётся как набрано (сервер
схлопывает пробелы, и перерисовка съела бы набранный пробел между словами); при уходе из
поля оно нормализуется; пустое название не сохраняется. Если сервер отклонил правку (400),
поля карточки перерисовываются из последнего ответа сервера — в поле не остаётся
несохранённое значение.

**Дата и время** сохраняются только целым значением. Браузер шлёт `change` на каждый
сегмент (день, месяц, год): «2» в дне уже даёт целую, но не ту дату, а перерисовка после
ответа сбрасывала позицию ввода — так утверждённая публикация уезжала на чужой день.
Правила: изменение без нажатия клавиши в этом поле за последнюю 1 с (`DT_TYPING_MS`) — выбор
в календаре браузера, сохраняется сразу; набор с клавиатуры ждёт Enter или ухода из поля;
неполное значение (`validity.badInput`) или год вне 2020–2100 не отправляется — поле
возвращается к сохранённому, тост объясняет; пока идёт набор, карточка не перерисовывается.

**Уход со страницы:** на `pagehide` всё несохранённое (тексты и целые даты) уходит сразу с
`fetch keepalive` (`GH.api(..., {keepalive: true})`) — обычный запрос браузер оборвал бы
вместе со страницей; при скрытии вкладки сохраняются тексты. После каждого успешного
изменения перечитываются план и полоса «Требует внимания».

### Параметры адреса

| Параметр | Значения | Что делает |
|---|---|---|
| `month` | `YYYY-MM` | месяц плана; без него — текущий по Москве |
| `view` | `table` (по умолчанию), `calendar` | вид |
| `open` | id материала | открыть карточку; если материал в другом месяце — страница переключается на его месяц с тостом |
| `state` | `overdue`, `failed`, `incomplete`, `ready`, `scheduled`, `paused` | фильтр состояния (снимаемый чип); `overdue`/`failed` **без** `month` в виде таблицы — вид «по всем месяцам» |
| `origin` | `agent` | фильтр «Только от ИИ»: только материалы, которые создал ИИ-агент |
| `brief` | `1` | открыть карточку «Бриф для агента» |

Ссылки извне: полоса «Требует внимания» ведёт на `?view=calendar`, `?state=failed`,
`?state=overdue`; «Отзывы» — на `?open=<id>` и `?month=<m>&open=<id>`.

### API

Все маршруты за общим гейтом авторизации. Необязательный `?month=YYYY-MM` у изменяющих
запросов задаёт месяц просмотра: по нему считается `in_month` материала в ответе (без
него — `true`). Ошибки: 400 `{error}` — ввод; 403 `{error, code: 'admin_required'}` — действие,
выпускающее публикацию наружу, не администратором (раздел «Кто может»); 404 — нет материала,
размещения или файла; 409 — действие недопустимо в текущем статусе; 413 — тело загрузки больше
предела видео;
503 `{error, code: 'content_plan_unavailable'}` — файл плана есть, но не читается;
503 `{error, code: 'content_brief_unavailable'}` — то же для файла брифа. Поиск картинок:
503 `image_search_not_configured` (нет ключа Яндекса), 502 `image_search_failed` (Яндекс не
ответил), 429 `image_search_daily_limit`, 400 `image_download_failed` (сайт не отдал картинку,
мелкая, не картинка).

«<login> · агент» — маршрутам ничего передавать не нужно. Инструменты раздела — `content_*`
([mcp.md](mcp.md)).

### Журнал

Каждое изменение пишет запись `{at, by, action, material_id, placement_id, text}`. Действия:
`create`, `edit`, `delete`, `add_placement`, `edit_placement`, `delete_placement`,
`unapprove_auto`, `approve`, `pause`, `resume`, `unapprove`, `mark_published`, `cancel`,
`restore`, `retry`, `retry_failed`, `bulk_pause`, `bulk_resume`, `shift`, `repeat`, `copy_month`,
`media_add`, `media_delete`; отправка (с 2026-09-28): `publish_now` («Отправить сейчас», автор —
кто нажал), `auto_publish` (вышло), `auto_failed` (ошибка, остановка рассылки, потерянная
попытка — что ушло), `reminder` (напоминание об Instagram), `delivery_progress` (рассылка
продолжится в следующем проходе: дошло N из M) — автор «бот». Хранятся последние 5000 записей (`LOG_MAX`, около года
активной работы четырёх баров; больше — разбухание файла). Автор — `login` сессии; действие
ИИ-агента через MCP — «<login> · агент» (`actor_label`). «Удалить черновики ИИ» пишет `delete`
на каждый удалённый материал с текстом «Удалён черновик агента «…» (массовое удаление черновиков
ИИ)».

### Хранение

Как `core/supplier_directory.py`: запись под `threading.Lock` и межпроцессной файловой
блокировкой, строгое перечитывание файла внутри блокировки, атомарная запись. Удаление
осиротевших файлов — после записи JSON, по принципу «лучшее усилие». Файла нет — пустой
план. Файл есть, но не читается, не JSON или неожиданной структуры —
`ContentPlanUnavailable` (API 503), и файл **никогда** не перезаписывается. Часы хранилища
подменяются (`ContentPlanStore(now_fn=...)`), поэтому тесты детерминированы.

### ИИ-агент (MCP, 2026-09-27)

Владелец подключает к сайту ИИ-агента Claude через MCP-платформу ([mcp.md](mcp.md),
подключение — [guides/mcp-connect.md](guides/mcp-connect.md)). Агент контент-планов работает
через коннектор `/mcp/content` теми же маршрутами, что и страница, и готовит **черновики**: темы,
тексты, размещения, задания на съёмку. Утверждает только владелец. Правила агента — раздел
«Контент и отзывы» в `core/mcp/tools/content.py` (`INSTRUCTIONS`) и сценарии
`content_plan_month`, `content_review_week`, `content_reviews_digest`.

**Как сервер узнаёт агента.** Мост MCP исполняет маршрут от имени владельца и кладёт в
пользователя `via_mcp: True` (`is_agent_user`). Клиент это поле не присылает и подделать через
тело запроса не может: признак берётся только из `current_user()` сервера.

| Что | Правило | Где |
|---|---|---|
| `origin` материала | `agent`, если материал создан через MCP, иначе `human` (`origin_of`); ставится сервером **при создании** записи и больше не меняется. `origin` в теле POST или PATCH — 400 «Происхождение материала (origin) ставит сервер…» (`_reject_origin`): иначе агент мог бы выдать свой черновик за работу людей. Старые материалы без поля читаются как `human` (до 2026-09-27 MCP не было); значение вне `human`/`agent` в файле — файл повреждён (503), неизвестное значение не перезаписывается | `core/content_plan.py` |
| копии | повтор по дням недели и копирование месяца создают **новые** записи; их `origin` — по тому, кто выполнил действие, а не по источнику: человек скопировал материал агента — копии `human`, агент скопировал месяц — копии `agent`. Так «Удалить черновики ИИ» трогает только то, что агент сделал сам | `_copy_material` |
| подпись | действие через MCP подписано «<login> · агент» — в журнале (`by`) и в полях `created_by`, `updated_by`, `approved_by`, `published_by`, `uploaded_by` (`actor_label`) | `core/content_plan.py` |
| «Почему этот пост» (`agent_rationale`) | пояснение: повод, рубрика, бар, откуда факты. Строка до 2000 знаков (`AGENT_TEXT_MAX`, как у заметки: абзац, который владелец прочтёт при проверке; длиннее — это уже второй текст поста). Правка не снимает утверждение — это не содержание публикации | POST/PATCH материалов |
| «Что снять» (`shot_list`) | список кадров для команды: что, в каком баре, время суток, люди в кадре. До 2000 знаков, утверждение не снимает | то же |
| «Черновик ИИ» (`agent_draft` в ответе) | `origin: 'agent'` и все размещения — `draft` или `cancelled`; материал без размещений (тема) — тоже черновик (`is_agent_draft`, `AGENT_DRAFT_RULE`) | `material_json` |

Агенту сервер сообщает пределы полей в ответе плана (`field_limits`: название 200, текст 10 000,
заметка, «почему» и «что снять» — 2000), список `origins` и текст правила черновика
(`agent_draft_rule`) — чтобы он не упирался в 400 вслепую; экран держит те же числа.

**Режим «Чтение и черновики» (коннектор `/mcp/content/draft`, с 2026-09-28).** Задача по
расписанию, которая готовит план, подключается в этом режиме ([mcp.md](mcp.md), «Режимы
доступа»). Из записи ей доступны только инструменты с пометкой `draft_write`; в контент-плане их
пять: создать материал (`POST /materials`), изменить материал (`PATCH /materials/<id>`),
повторить по дням недели (`POST /materials/<id>/repeat`), добавить размещения
(`POST /materials/<id>/placements`) и изменить размещение (`PATCH /placements/<pid>`). Шестой —
черновик ответа на отзыв ([reviews.md](reviews.md)); весь набор закреплён
`tests/test_mcp_modes.py`. Утверждение, отметка «вышло», пауза, отмена, удаление, сдвиг,
копирование месяца, файлы и бриф в этом режиме сервер не исполняет вовсе.

Правило `guard_draft_mode` (`core/content_plan.py`): в режиме `draft` правка материала, повтор по
дням недели, добавление и правка размещений разрешены, только если материал — черновик ИИ
(`is_agent_draft`: `origin: 'agent'` и все размещения `draft` или `cancelled`). Иначе 409 «В режиме
«чтение и черновики» агент меняет только свои черновики: этот материал создан не агентом или в нём
уже есть утверждённые размещения». Новый материал создаётся всегда: через MCP он и так получает
`origin: 'agent'`. Копии повтора — тоже черновики агента: `origin` по тому, кто повторяет, а
размещения копируются черновиками.

Зачем: по расписанию агент читает отзывы гостей и описания пива; «команда», спрятанная в таком
тексте, не должна переносить, менять или снимать утверждение с публикаций владельца. Режим ставит
мост (`g._current_user['mcp_mode']`); у людей на сайте его нет, для них правило не действует.
Пример: агент по расписанию пытается поправить текст материала, который создал владелец, — 409;
добавить размещение в свой новый материал — можно; повторить по пятницам свой новый «Таплист
пятницы» — можно, материал владельца — 409; поправить свой материал, у которого одно размещение
владелец уже утвердил, — 409.

**На экране:**

- пометка «ИИ» у материалов агента — в шапке карточки и в окне «Утвердить готовые»; подсказка:
  «Материал создал ИИ-агент (через MCP) от имени владельца. Проверьте текст, фото и размещения
  перед утверждением: агент только готовит черновики». С 2026-10-04 её нет в строках таблицы и на
  плашках календаря (там — в подсказке плашки): от агента почти весь план, метка ничего не
  различала и съедала место названия;
- в карточке — свёрнутый раздел «От агента» (у материала людей — «Заметки»; справа видно, что
  заполнено): «Почему этот пост», «Что снять» и «Заметка для команды» с автосохранением (как у
  текстов, 700 мс) и счётчиком до 2000. Раньше «Почему этот пост» стоял над текстом поста;
- меню «ИИ-агент» рядом со сводкой месяца: задания агенту в Claude («Попросить агента»), «Бриф для
  агента» (выдвижная карточка; `?brief=1` открывает её сразу), «Только от ИИ» с числом материалов
  агента в плане месяца (адрес `?origin=agent`: скрывает материалы людей в таблице и календаре;
  под этим фильтром «Утвердить готовые» утверждает только материалы агента — запрос с
  `origin=agent`; включённый фильтр виден снимаемым чипом над планом) и «Удалить черновики ИИ: N»
  — когда в плане месяца есть черновики ИИ (в виде «по всем месяцам» его нет: удаление — по
  месяцу). Одновременно открыта одна выдвижная карточка.

**«Удалить черновики ИИ»** (`POST /api/content-plan/agent-drafts/delete {month, material_ids?}`,
`ContentPlanStore.delete_agent_drafts`):

- удаляются материалы с `month == month`, `origin: 'agent'` и всеми размещениями `draft` или
  `cancelled`; всё — одной записью файла; журнал — `delete` на каждый материал; файлы, на которые
  больше никто не ссылается, удаляются с диска после записи;
- экран передаёт ровно те id, которые назвал в подтверждении (до 8 названий, дальше «и ещё N»):
  если план за это время изменился, лишнего не удалится; агент может вызвать без `material_ids` —
  тогда все черновики агента месяца;
- не удаляется (-> `skipped` с причиной): материал агента, у которого есть утверждённое, стоящее на
  паузе, вышедшее или ошибочное размещение («это уже не черновик»); при переданных id ещё — нет
  такого материала, материал другого месяца, материал людей. Материалы людей без `material_ids`
  не рассматриваются вовсе;
- ответ `{deleted, skipped}`; экран показывает тост с числом удалённых и первой причиной пропуска.

Пример: в плане ноября агент создал 12 материалов; 2 из них владелец утвердил, 1 — тема без
размещений. «Удалить черновики ИИ: 10» удалит 10 (9 с черновыми размещениями и тему), 2
утверждённых останутся.

#### Бриф сети для агента (`core/content_brief.py`)

Постоянные правила сети, по которым агент пишет черновики. Агент читает бриф целиком перед каждым
черновиком (`content_brief_get` = `GET /api/content-plan/brief`). Бриф ничего не публикует и не
утверждает.

Структура (`content_brief.json`, версия 1): текстовые разделы `network` («О сети»), `tone` («Тон и
голос»), `rubrics` («Рубрики»), `rhythm` («Ритм публикаций»), `taboo` («Табу»),
`alcohol_ads_rules` («Реклама алкоголя»), `photo_rules` («Фото и видео»), `notes` («Заметки»);
`examples` — примеры удачных постов списком; `bars` — по каждому из четырёх баров поля
`character` («Характер»), `audience` («Гости»), `hours` («Часы работы»), `kitchen` («Кухня»),
`events` («События»), `photo_spots` («Где снимать»); `updated_at` (МСК, до минуты) и `updated_by`
(«<login>» или «<login> · агент»). Подписи и подсказки полей сервер отдаёт в ответе GET (`schema`) —
их читают и экран, и агент.

Пределы (длина = число символов Unicode, как счётчик в браузере):

| Что | Предел | Почему |
|---|---|---|
| текстовый раздел | 3000 | страница правил: длиннее агент выполняет хуже, а владелец не перечитывает |
| пример поста | 4096 | самый длинный пост плана — сообщение Telegram без фото |
| примеров | 10 | образцов хватает, чтобы уловить голос; больше — архив, а не образец |
| поле бара | 1000 | абзац о баре |
| весь бриф | 40 000 | агент перечитывает бриф целиком; мост MCP обрезает ответ длиннее 60 000 знаков — 40 000 оставляют запас на описание полей (~4 000) и экранирование JSON |

«Весь бриф» — сумма длин всех разделов, примеров и полей баров. Правка, после которой бриф
длиннее 40 000 **и** длиннее, чем был, — 400; правка, которая бриф сокращает, проходит даже сверх
предела. Пределы полей проверяются только у переданных полей. Пример: бриф 39 990 знаков, в «Тон»
дописали 20 -> 40 010 > 40 000 и больше, чем было -> 400 «Бриф длиннее 40 000 знаков (стало бы
40 010)».

Правила слияния (`PUT {sections: {...}}`):

- меняются только переданные поля, остальное остаётся как было;
- текстовый раздел и поле бара заменяются целиком; `null` — пустая строка;
- `examples` заменяется всем списком; пустые примеры (из одних пробелов) отбрасываются;
- `bars` сливается по барам и полям: `{bars: {ligovskiy: {hours: '…'}}}` меняет только часы
  Лиговского;
- неизвестный ключ тела, раздел, бар или поле, неверный тип, превышение предела — 400, не
  сохраняется **ничего** (проверка до записи);
- правка без изменений файл не пишет и `updated_at` не меняет;
- ответ `{brief, stored, total, changed: ['tone', 'bars.ligovskiy.hours', …]}`.

Файла нет — действует затравка в памяти: «О сети» — список баров с названием, адресом и числом
кранов из `core/venues_config`, остальное пусто (`stored: false`, экран пишет «Бриф ещё не
сохранён: в разделе «О сети» — затравка из справочника баров сервиса…»); на диск затравка
попадает вместе с первой правкой. Файл есть, но не
читается, не JSON, неожиданной структуры, с неизвестным разделом, баром, полем или версией новее —
503 `content_brief_unavailable` и на чтение, и на запись; файл **никогда** не перезаписывается.
Хранение — как у плана: `threading.Lock` + файловая блокировка, перечитывание внутри блокировки,
атомарная запись.

Карточка «Бриф для агента» на экране: все поля с автосохранением (одно поле — один PUT) и
счётчиками длины; поля, подписи и пределы — из `schema` ответа сервера; отклонённое значение
остаётся в поле с красным счётчиком, чтобы его можно было сократить; несохранённое уходит при
уходе со страницы. Пустой раздел брифа агент по правилам не додумывает: спрашивает владельца или
явно отмечает допущение.

### Что сломается, если менять неправильно

- **Подпись содержания** (`_content_signature`): убрать из неё поле — и правка этого поля
  после утверждения уйдёт в публикацию без повторного утверждения.
- **Снимок и ссылки на файлы:** если `_media_referenced` перестанет смотреть в снимки,
  удаление файла из материала сотрёт с диска картинку вышедшего поста.
- **Формат времени:** сравнения «прошло / впереди» — строковые по `YYYY-MM-DDTHH:MM` и
  текущей минуте. Секунды, пробел вместо `T` или часовой пояс в строке сломают `overdue`,
  `in_past`, паузу и сдвиг.
- **Пределы 4096 / 1024 / 2200 и 10 файлов** — факты платформ. Поднять их — значит
  утверждать посты, которые площадка отвергнет.
- **Пауза бара** не должна трогать `bar == 'all'`, иначе пауза одного бара остановит общий
  Instagram.
- **Опора копирования:** заменить на «самую раннюю дату» — дата темы копии уйдёт из месяца
  назначения, и материал «переедет» при первой правке. Ключ объединения серии без времени
  склеит разные посты одного бара в день.
- **Подстановка одним проходом:** цепочка `str.replace` разберёт скобки внутри названия
  пива как подстановку.
- **Ссылки таплиста:** `offset` и `length` сущностей — в единицах UTF-16. Посчитать их в
  символах Python — и после эмодзи в шаблоне ссылка съедет на соседние буквы (Telegram
  отвергнет сущность за концом текста). Сдвиг считается тем же проходом, что подстановка.
- **Словарь таплиста:** новый стиль без перевода просто пропадает из строки, новая пивоварня
  пишется полным именем Untappd. Тест `test_names_cover_registry` ловит это при пересборке
  реестра — не отключайте его, дополните словарь.
- **Новинка и свежесть:** правило новинки смотрит историю всех кранов бара. Если начать
  смотреть только `started_at`, новая кега того же сорта станет «новинкой» — пост пообещает
  гостям то, чего нет. Порог свежести ниже недели остановит пост бара, где просто не меняли
  кеги.
- **Битый файл:** если `_load` на ошибке вернёт пустой план, следующая запись сотрёт весь
  контент-план.
- **Счётчики полосы и вид «по всем месяцам»:** определения `attention_counts` и
  `state_payload` должны совпадать с подсказками полосы, иначе ссылка откроет не то, что
  посчитано.
- **Имя файла:** `NAME_RE` заканчивается `\Z`; с `$` имя с переводом строки в конце прошло
  бы проверку формы.
- **Экран:** цвет — по `display_state`, не по тону; поле `#cpFile` — вне карточки; дата и
  время — только целым значением. Каждое из этих правил закрывает найденную ошибку.
- **Склейка чипов и плашек** (`chipGroups`, `pillGroups`) — только при одинаковых площадке,
  дате, времени и **состоянии**: склеить без состояния — и утверждённый бар спрячется под чипом
  черновиков (или вышедший — под запланированными). Сводка дня (`dayStats`) считает размещения
  до склейки, иначе метка плотности и «пост + бот» поменяют смысл.
- **Дата темы в карточке** — только у темы без размещений. Вернуть её наверх карточки — и её
  снова будут менять, думая, что переносят пост (дата выхода — у размещения).
- **«Утвердить» внизу карточки и «Утвердить» отмеченные** берут готовность с сервера (`ready`
  размещения, `approve-preview`); посчитать её на клиенте — и кнопка утвердит то, что сервер
  считает неготовым (или наоборот), а рассылка бота уйдёт без подтверждения аудитории.
- **`origin` из тела запроса:** если принять его в POST или PATCH, агент сможет выдать свой
  черновик за работу людей, и «Удалить черновики ИИ» его не тронет (или удалит чужое).
- **`origin` копии по источнику** вместо «кто копирует»: человек, скопировавший месяц с
  материалами агента, получит копии с пометкой «ИИ», и массовое удаление снесёт его работу.
- **«Чинить» неизвестный `origin` в `human`:** следующая запись сотрёт значение, которого эта
  версия не понимает; поэтому битое значение — 503, как у типа материала.
- **Правило черновика ИИ:** если считать черновиком материал с утверждённым или вышедшим
  размещением, «Удалить черновики ИИ» удалит одобренное владельцем, а режим «Чтение и черновики»
  (`guard_draft_mode`) даст расписанию править утверждённое.
- **`guard_draft_mode`:** убрать проверку из правки материала, повтора или размещений — «команда»
  из отзыва через расписание в режиме `draft` перенесёт, размножит или поменяет публикации
  владельца. Добавить её в создание материала — расписание не сможет готовить черновики вовсе.
- **`agent_rationale` и `shot_list` в подписи содержания:** правка пояснения начнёт снимать
  утверждение, хотя в публикацию эти поля не уходят.
- **Бриф:** `_load` на ошибке вернёт затравку вместо исключения — следующая правка перезапишет
  весь бриф затравкой; предел всего брифа ближе к 60 000 — ответ MCP начнёт обрезаться, и агент
  прочтёт бриф не целиком; `examples` слиянием по индексу — удалённый на экране пример вернётся.
- **Отметка «отправляется» до вызова Telegram** (`_claim` под блокировкой плана): убрать — два
  воркера или «Отправить сейчас» во время прохода опубликуют пост дважды. Повторять «зависшее»
  вместо ошибки «статус неизвестен» — тоже дубль (пост мог уйти перед падением процесса).
- **Фильтр «раньше подключения»** (`since_for`): убрать — включение отправки выпустит или
  пометит ошибкой весь хвост просроченных утверждённых постов.
- **GRACE 120 минут:** убрать — после долгого простоя сервер разошлёт «Таплист пятницы» в
  субботу утром; «Повторить» без `retry_at` снова упрётся в «время прошло».
- **Прогресс рассылки** (`sent_to`, `pending`, `unknown_to`): писать реже или не писать — сбой
  посреди рассылки разошлёт второе сообщение тем, кто уже получил. `delivery_view` не должен
  отдавать списки получателей: это chat_id гостей.
- **`in_flight` и пороги отправщика** должны совпадать: иначе экран покажет «Отправляется», а
  отправщик уже поставит ошибку (или наоборот).
- **`safe_resend=True` у отправки** (`TelegramTransport`): убрать — после ReadTimeout запасной путь
  снова выпустит 2–4 копии поста. Считать «не ушло» ошибку, которая этого не доказывает
  (`_proves_not_sent`: ReadTimeout, обрыв соединения), — то же самое.
- **`_guard_not_sending` в `_auto_unapprove` и `shift`:** убрать — правка во время рассылки снова
  переведёт размещение в черновик, сотрёт прогресс, и гости получат рассылку дважды.
- **Перечитывание настроек перед пачкой и `stop_requested`:** убрать — выключатель и пауза не
  остановят идущую рассылку. Не получивших при остановке класть в `failed_to` обязательно: иначе
  «Повторить неудавшимся» им не отправит.
- **Бюджет прохода и порядок «посты раньше рассылок»:** убрать — большая рассылка задержит посты
  каналов на минуты; продолжение без `sent_to` — дубли.
- **«Отправить сейчас» — только очередь:** вернуть отправку в веб-запросе или поток — рассылка
  оборвётся при перезапуске воркера, два потока превысят темп Telegram.
- **`_ACTIVE_ATTEMPTS`:** убрать — долгая загрузка будет признана «зависшей» своим же проходом,
  а «Повторить» даст дубль.
- **Время поста для «поздно» и «раньше подключения» у Instagram** и **`reminded_for`:** считать от
  времени напоминания — пост, утверждённый днём, останется без напоминания; без `reminded_for` —
  перенесённый пост без напоминания.
- **Сбой связи при проверке канала** сохранять или сдвигать `connected_since` повторным успехом —
  рабочий канал выключится, а посты «раньше подключения» перестанут уходить.
- **Длина в UTF-16** (`text_units`): считать `len` — Telegram отклонит пост с эмодзи, прошедший
  проверку.
- **Проверка администратора** (`_require_admin`): убрать — любой аккаунт бара сможет подключить
  свой канал, утвердить и разослать публикацию гостям.
- **`reminder_conflict`:** убрать — чат напоминаний можно указать равным каналу бара, и служебная
  заметка «пора выложить» уйдёт подписчикам канала.
- **`agent_original` обновляют только правки агента:** если его обновят правки людей, учёт
  правок перестанет их видеть, и агент не узнает, что владелец поправил.
- **Токен бота** — только из окружения, в ответы и журнал не попадает (`public_view` убирает
  отпечаток; `_scrub` в транспорте вырезает токен из текста ошибок).

### Проверка локально

**Никогда не запускать `app.py` и не импортировать `app`** (в том числе Flask test client
над полным приложением): импорт сразу поднимает все шедулеры и Telegram long-polling с
боевыми токенами из `.env` — локальный `getUpdates` перетягивает апдейты у прода, а
догоняющая проверка открытых смен может написать в рабочий чат (см.
[lessons.md](lessons.md)).

Тесты:

```
py -3 -m pytest tests/test_content_plan.py tests/test_content_brief.py tests/test_guest_reviews.py tests/test_mcp_tools_content.py tests/test_content_publisher.py -q
node tests/test_content_plan_render.mjs
node tests/test_guest_hub_render.mjs
```

Отправка в тестах — только через поддельный транспорт (`FakeTelegram` в
`tests/test_content_publisher.py`); в `.env` лежат боевые токены, поэтому маршруты берут
транспорт через точки подмены `_transport` / `_bot_token` (как `_store`). Стенд со страницей —
с пустыми `TELEGRAM_BOT_TOKEN=`, `TELEGRAM_CONTENT_BOT_TOKEN=`, `TELEGRAM_OPEN_CHECK_BOT_TOKEN=`
в окружении процесса (`load_dotenv` не перезаписывает заданные переменные): «Подключить» и
«Отправить сейчас» тогда отвечают «бот не настроен» и в Telegram ничего не уходит.

Посмотреть страницу — голое Flask-приложение, как в тестах:

1. `PERSISTENT_DATA_DIR` и `TAPS_DATA_PATH` — на временный каталог (скопировать туда
   `taps_data.json` и `iiko_untappd_registry.json`, чтобы работал живой предпросмотр и не
   трогались файлы репозитория);
2. подменить `core.auth_guard.current_user` на тестового пользователя;
3. `Flask(__name__, template_folder='templates', static_folder='static')`,
   `context_processor` с `current_user`, `jinja_env.globals['app_version']`;
4. зарегистрировать только `content_plan_bp`, `reviews_bp` (и `guests_bp`, если нужна
   полоса на `/guests`);
5. `app.run(host='127.0.0.1', port=..., use_reloader=False)`.

Состояния `failed` и `overdue` через API сразу не создать (их ставит отправщик или время): в
тестах их ставят прямо в файл (`_set` в `tests/test_content_plan.py`, `Env.set` в
`tests/test_content_publisher.py`).
