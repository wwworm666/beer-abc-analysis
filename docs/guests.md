# Маркетинг — раздел `/guests`

## Что это

Единый инструмент маркетолога на странице `/guests` (в меню — **«Маркетинг»**):
аналитика гостей программы лояльности по ТЗ «Модуль аналитики гостей (CRM)» плюс
анализ эффективности акций. 16 отчётов: рост базы, когорты жизненного цикла,
активность, частота, retention, когортные доходы, RFM, LTV, **акции**, товары,
сочетаемость, точки, карточка гостя, динамика базы, сводка, не купившие.

**Прежняя страница `/discounts` («Анализ акций») слита сюда 2026-08-13.** Её режим
«Скидки» стал вкладкой «Акции», а режим «RFM» удалён как дубль — RFM в проекте
теперь ровно один. `/discounts` отдаёт 301 на `/guests#promo` (старый
`?mode=rfm` — на `/guests#rfm`).

Ключевое отличие от остальных разделов: метрики считаются не только за выбранный
период, но и за всю жизнь гостя (Lifetime). Для этого чеки гостей зеркалируются
в локальную SQLite-витрину — при просмотре обращений к iiko нет вообще.

**Временная логика (обязательная, из ТЗ):**
- **Primary Period** — неделя (ISO пн–вс) / календарный месяц (дефолт) / квартал / год;
- **YTD** — с 1 января года конца периода по конец периода;
- **Lifetime** — вся загруженная история (с 2017-12, первый чек с картой 2017-12-18).

## Как работает

### Источник данных и витрина

OLAP SALES отдаёт гостевые поля `Delivery.*` только у чеков с проведённой картой
лояльности (~43% чеков). Отдельного справочника гостей в серверном API iiko нет —
гость существует для нас, только если хоть раз купил (принято владельцем
2026-07-15: «новая карта по первой покупке»).

Следствие: карты, которые зарегистрировались и ни разу не пробили чек, в витрине
невидимы в принципе. Этот слой закрывает **вкладка «Не купившие»** — второй
источник данных раздела, внешняя система лояльности Orderia (эндпоинт
`never.php`, разбор в [technical/ORDERIA_CASHAPI.md](technical/ORDERIA_CASHAPI.md)).
Данные лежат в отдельной таблице `never_cards`, в `guests` не подмешиваются
(см. «Почему отдельная таблица» ниже).

Помесячный ETL двумя запросами: уровень чека (7 разрезов, суммы) и уровень
позиций (блюдо в чеке). Ресинк месяца идемпотентен: `DELETE` месяца + `INSERT`
одной транзакцией, затем пересчёт денормализации гостей. Ночью пересинкается
текущий месяц; предыдущий — только в первые 2 дня месяца (стык учётных дней;
ретро-правок чеков в барах не делают). Остальные месяцы `frozen`; полная
перезаливка — `POST /api/guests/sync?force=1` (админ).

Таблицы: `guests` (гость + денормализация), `receipts` (чеки), `receipt_items`
(позиции), `guest_aliases` (карта → телефон), `sync_state` (журнал месяцев),
`never_cards` + `never_sync` (карты без покупок из Orderia, схема v2).

### Второй источник: карты без покупок (Orderia)

`never.php` отдаёт карты, по которым нет ни одного чека. Синк живёт в том же
ночном прогоне (`guest_sync.sync_never_cards`), но от iiko не зависит и
вызывается первым: ответ приходит за ~50 мс, и недоступность iiko не должна
оставлять список протухшим. Ошибка Orderia не роняет синк чеков.

**Замена среза полная, а не upsert.** Карта исчезает из ответа Orderia, как
только гость совершил первую покупку — при upsert такие карты копились бы в
витрине вечно. Обратная сторона: пустой ответ затёр бы всё, поэтому
`orderia_client.fetch_never_cards()` на любой ошибке возвращает `None`, а не
`[]`, и синк в этом случае не трогает сохранённые данные.

**Почему отдельная таблица, а не строки в `guests`.** Инвариант «гость в
`guests` = купивший» держит все остальные отчёты: LTV делит выручку на число
гостей, когорты считают доли, активность строит население по первому заказу.
Добавление некупивших в `guests` сдвинуло бы каждую из этих цифр и всю историю.

### Сверка Orderia с витриной (ключевое)

Счётчик покупок в Orderia ошибается, поэтому список принимается не на веру:
каждая карта сверяется с витриной, и «не купившими» считаются только те, кого
в чеках iiko действительно нет. Арбитр — витрина: чек в iiko это факт продажи,
а `check_count` в Orderia — счётчик, который может не сработать.

Ключи сшивки по убыванию надёжности:

1. **канонический телефон** — он же `guest_id`, совпадение однозначно;
2. **номер карты** — только если он **уникален** в срезе Orderia. Номер там не
   первичный ключ (2002639 выдан трём записям, причём разным людям), и привязка
   по неуникальному номеру подтянула бы к гостю чужие карты.

Классификация ложных срабатываний:

| Вид | Что произошло |
|---|---|
| `same_card` | Тот же номер карты, и по нему в iiko есть чеки. Счётчик Orderia не сработал — чаще всего покупка была в день регистрации |
| `other_card` | Телефон или карта известны витрине, но покупки шли по другой карте: человек завёл вторую, старая работала |

Живая проверка 2026-08-12 на срезе из 326 карт: подтверждено 295, мусорных
записей 9, **ложных срабатываний 22** — за ними 235 904 руб реальной выручки,
включая гостя с 82 чеками на 105 367 руб (в Orderia его номер записан с лишней
цифрой: `20017111` вместо `2001711`).

Выручка ложных считается **по гостю, а не по строке**: на одного человека может
указывать несколько карт Orderia, и суммирование по строкам задваивало бы её.

### Вкладка «Акции»: единственная на живом iiko

Витрина не хранит тип скидки — в `receipts` только сумма, измерения
`ItemSaleEventDiscountType` нет. Отчёт по конкретной акции из `guests.db` не
собрать в принципе, поэтому вкладка ходит в iiko напрямую
(`POST /api/discount-analyze`, `GET /api/discount-names` в `routes/analysis.py`).

Отсюда три отличия от остальных вкладок, заложенные в архитектуру:

| Что | Как и почему |
|---|---|
| Свой период | Произвольный диапазон дат вместо Неделя/Месяц/Квартал/Год. Вид объявлен `{ ownPeriod: true }`, и `common.js` скрывает глобальную панель периода классом `.own-period` — иначе над живыми данными висела бы подпись покрытия витрины, которая к ним не относится |
| Загрузка по кнопке | Запрос в iiko идёт десятки секунд. Клик по вкладке ничего не грузит, отчёт строится по «Анализировать» — иначе каждое открытие вкладки било бы по iiko |
| Свой кэш | Ответ живёт в модульной переменной вида. Сдвиг глобального периода и ночной синк витрины эту вкладку НЕ инвалидируют (`onPeriodChanged` и `pollSync` чистят только вкладки без `ownPeriod`) |

Смена точки — новый запрос (точка уходит в OLAP-фильтр), смена акции — фильтрация
уже загруженного ответа без обращения к iiko.

**Что сознательно не перенесено со старой страницы:** вторая таксономия сегментов
по числу визитов и «доунат» по ней, «гистограмма recency» из flex-карточек,
модалка гостя, клиентский пересчёт RFM-сегментов, клиентский CSV — всё это либо
дублировало каноничные вкладки (Активность, Частота, RFM, Гость), либо было
недостижимым мёртвым кодом (`displayGuestResults` не вызывалась ниоткуда, а
`applyFilters` обращалась к несуществующей функции). Детализация блюд гостя
сохранена — раскрывается строкой в таблице из того же ответа.

### Что изменилось в цифрах после слияния

Три расчёта исправлены, поэтому знакомые числа сдвинулись — это не поломка:

1. **Число чеков выросло, средний чек упал.** Ключ чека стал «дата + точка +
   номер» вместо одного номера: раньше одинаковый `OrderNum` в разные дни
   склеивался в один чек. Баг был зафиксирован тестом с `@expectedFailure` —
   теперь тест обычный и зелёный.
2. **Средний чек считается на чеки, а не на визиты.** Два чека за один вечер
   больше не дают завышенный средний чек. Определение стало единым с остальным
   разделом.
3. **Порядок гостей в таблице.** Сортировка по давности использовала
   `recency_days or 999`: ноль тоже falsy, и гость, купивший в последний день
   периода, уезжал в конец списка вместо начала.

Отдельно: сегменты RFM изменились у всех, кто смотрел их на `/discounts`. Там
частота мерилась визитами в неделю за произвольный период (пороги 3/2/0,8/0,3),
гость опознавался по сырому номеру карты, а в население входил склеенный
псевдогость «Без карты» с визитами почти каждый день — он попадал в «Чемпионов» и
раздувал их выручку. Канон считает частоту визитами за фиксированное окно 365
дней (260/104/52/12), гость — канонизированный телефон с алиасами карт, продаж без
карты в витрине нет вовсе. Пороги канона утверждены владельцем 2026-07-18.

### Честная конверсия

Знаменатель появился только с этим источником: зарегистрировавшийся либо в итоге
купил (лежит в `guests` с датой регистрации), либо не купил (лежит в
`never_cards`). Третьего не дано, поэтому

```
зарегистрировались(P) = купившие с датой регистрации в P
                      + подтверждённые некупившие с датой регистрации в P
конверсия(P)          = купившие / зарегистрировались
```

Считается только для периодов внутри покрытия Orderia (самая ранняя карта —
2024-02-29). Порог берётся по МЕСЯЦУ этой карты: внутри месяца период стартует
раньше конкретной даты, и посуточное сравнение выключало бы конверсию на первом
же валидном месяце. Для более старых периодов отдаётся `None` и в UI стоит
прочерк — иначе конверсия ложно показывала бы 100%.

Оговорка: сам порог эвристический. Список Orderia — снимок тех, кто не купил
**до сих пор**; по нему нельзя отличить «до 2024-02 система не вела карты» от
«все, кто регистрировался раньше, в итоге что-то купили».

### Идентичность гостя (проверено на живых данных, Фаза 0 2026-07-15)

В 100% гостевых строк заполнены И номер карты, И телефон. Две популяции:
регистрация по телефону (карта = телефон с лишней ведущей 7: карта
`79XXXXXXXXX`, телефон `779XXXXXXXXX`) и пластиковая карта (карта `100XXXXX`,
телефон настоящий).

**Канонизация:** только цифры; если цифр ≥ 10 → `'7' + последние 10 цифр`;
меньше 10 (код пластика) — цифры как есть; цифр нет — строка без пробелов.
**guest_id = канонический телефон**; карта пишется псевдонимом в
`guest_aliases`. «Дата создания клиента» (`Delivery.CustomerCreatedDateTyped`)
заполнена в 100% строк — это дата регистрации; у кого пусто, регистрация
приравнивается к первой покупке (`registration_source='first_order'`, доля
отдаётся в meta каждого ответа).

### Определения (единые с /discounts и месячной витриной)

- **Заказ (чек)** = ключ `(учётный день, бар, номер чека, гость)`;
- **Визит** = уникальная пара `(гость, учётный день)`;
- **Выручка** = `DishDiscountSumInt` (что фактически заплатил гость);
- **Округления:** деньги — целые ₽, проценты — 1 знак, дни/частота — 1 знак.

### Формулы разделов (зеркало: `static/js/guests/formulas.js` и тултипы UI)

| Раздел | Формула |
|--------|---------|
| §1 Рост | Регистрации(P) = гости с датой создания в P; первые заказы(P) = гости с первым чеком в P; конверсия = зарегистрированные в P с заказом ≤ конца P / регистрации P (показывается справочно — источник видит только купивших); дни до заказа = AVG(MAX(0, первый чек − регистрация)) — MAX(0,·) гасит сдвиг учётного дня за полночь |
| §2 Когорты | Когорта = месяц регистрации, только когорты ≤ даты среза. Lifetime-доли: ≥2 / ≥5 чеков за жизнь; % активных = визит в окне [срез − 30 дн, срез]. Доли «≥1 чек» нет: в когорту входят только купившие, она тождественно равна 100% |
| §3 Активность | На дату конца периода, по дням с последнего визита: Active ≤30, Sleeping 31–90, At Risk 91–180, Lost >180; население = первый заказ ≤ срез; дельта — тот же расчёт на конец предыдущего периода |
| §4 Частота | Визиты гостя за P; сегменты 1 / 2–3 / 4–8 / 9+; средняя = визиты / гости с ≥1 визитом |
| §5 Retention | Когорта = месяц первой покупки; возврат = визит в (первая покупка, +N дней], N ∈ {30,60,90,180,365}; ячейка зрелая, если конец месяца когорты + N ≤ срез, иначе «—» |
| §6 Доходы | Базис когорты переключаемый (регистрация/первая покупка); накопительно за жизнь: выручка, чеки, LTV = выручка/гостей |
| §7 RFM | **Единственная RFM в проекте** (дубль со `/discounts` удалён). Фильтр по точке: `?store=<ключ>` — R/F/M считаются только по чекам этой точки, поэтому сумма по четырём точкам больше сетевой (гость двух баров в двух срезах). Окно 365 дней на срез; R = дни с последнего визита (пороги 7/14/30/60), F = визиты окна (пороги 260/104/52/12 — утверждены владельцем 2026-07-18: «постоянный» 5+/нед, «частый» 2+/нед, далее «раз в неделю» и «раз в месяц»), M = выручка окна; сегменты как в /discounts (CHAMPIONS/LOYAL/NEW/AT_RISK/CHURNED/POTENTIAL); CSV-экспорт |
| §8 LTV | Средний = вся выручка / все гости; YTD-вариант = выручка YTD / гости с визитом YTD; по точкам — гость закреплён за точкой первого заказа |
| §9 Товары | Топ по выручке за P; первые покупки = позиции в день первого заказа гостей с первым заказом в P (ранжир по гостям); повторные = позиции после дня первого заказа; динамика — топ-10 по месяцам за 12 мес |
| §10 Сочетаемость | Пары разных позиций одного чека; поддержка = чеки с парой / чеки с 2+ позициями; уверенность A→B = чеки с парой / чеки с A |
| §11 Точки | Первая = бар первого чека (tie-break — порядок PHYSICAL_VENUES); любимая = максимум дней-визитов; миграции = гости с 2+ барами + матрица первая→любимая |
| §12 Карточка | Все три среза: заказы/визиты/выручка/средний чек; LTV; топ-5 товаров; RFM и статус на срез; последние чеки |
| §13 Динамика | active_start = визит за 30 дн до начала месяца; new = первый заказ в месяце; reactivated = визит в месяце после паузы >30 дн; active_end = визит за последние 30 дн месяца; churned = баланс (start + new + react − end) |
| §14 Сводка | Композиция готовых функций; кэш `cached_olap` с ключом от `MAX(sync_state.synced_at)` + метки среза Orderia. **«Новые регистрации» и «Конверсия в заказ» берутся из §15**, если срез Orderia есть: только там полный знаменатель. Без него — прежнее поведение (видны лишь купившие, конверсия ~100% и помечена справочной), плюс карточка «Не купили ни разу» показывает причину недоступности |
| §16 Акции | Живой OLAP из iiko (витрина тип скидки не хранит). Выручка без скидки = `DishDiscountSumInt + DiscountSum`; отдали скидками = `DiscountSum`; глубина = отдали / без скидки; средний чек = выручка со скидкой / **чеки**; гости = уникальные карты (НЕ сумма по точкам); частота = визиты / длину выбранного диапазона в неделях; давность — до конца диапазона, а не до сегодня |
| §15 Не купившие | Карты Orderia без чеков, сверенные с витриной (см. «Сверка Orderia с витриной»). Подтверждённые = нет в чеках iiko; мусор = не телефон в поле телефона или болванка «Jane Doe» с пустым Telegram; конверсия периода — см. «Честная конверсия»; CSV только по подтверждённым |

### API

`GET /guests` — страница. Отчёты (все с `?period_type=&anchor=`):
`/api/guests/summary`, `base-growth`, `base-dynamics?months=`, `activity`,
`frequency`, `cohorts/lifecycle`, `retention?basis=`, `cohorts/revenue?basis=`,
`rfm[?store=&export=csv]`, `ltv`, `products?mode=top|first|repeat|trend`,
`product-pairs?scope=`, `venues`, `never[?export=csv]`, `search?q=`, `guest/<id>`.
Сервис: `POST /api/guests/sync[?force=1]` (админ), `GET /api/guests/sync-status`
(отдаёт в том числе состояние среза `never_cards`).

### Ограничения и принятые решения (владелец, 2026-07-15)

- Гости без покупок невидимы; «регистрации» = регистрации купивших; свежие
  периоды дорастают задним числом — принято, пометка в «Как считается»;
- карты сотрудников НЕ исключаются (сотрудник = такой же гость);
- ретро-правки чеков не делаются → пересинк истории не нужен (только вручную);
- конверсия регистрация→заказ на практике ≈100% (регистрация происходит при
  первой покупке) — показывается справочно;
- фильтра по точке в v1 нет (сеть целиком), точки раскрыты в §8/§11/§14.

### Что сломается, если менять неправильно

- Канонизация номера (`normalize_guest_id`) — менять только с полным ресинком
  (`?force=1`): guest_id хранится в БД, старые и новые записи разъедутся.
- Правая граница OLAP-запросов ЭКСКЛЮЗИВНАЯ — сдвиг на «включительно» задвоит
  чеки на стыках месяцев.
- Порядок запуска: `sync_month` сначала грузит чеки, потом позиции — связка
  позиция→гость строится по чекам того же месяца.
- `frozen`-месяцы пропускаются ночным синком — сброс флага без надобности
  устроит полный прогон по iiko каждую ночь.
- `replace_never_cards` — ПОЛНАЯ замена: вызывать только с результатом реального
  запроса. Передать туда `[]` при ошибке сети = стереть список не купивших.
- Сшивка по номеру карты работает только для номеров, уникальных в срезе
  Orderia. Убрать эту проверку — и один неуникальный номер привяжет к гостю
  чужие карты, а его выручка посчитается несколько раз.
- Даты в модуле берутся из `core/msk_time`, а не из `date.today()`. Вернуть
  наивную дату — значит вернуть UTC-контейнер и сдвиг границ суток на 3 часа.
