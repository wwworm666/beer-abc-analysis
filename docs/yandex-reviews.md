# Отзывы с Яндекс Карт — загрузка в «Отзывы» (`core/yandex_reviews_sync.py`)

> С 2026-10-09 отзывы читаются с **публичной страницы бара на Яндекс Картах** — как гость,
> без входа: раз в 3 часа первая страница, раз в сутки все страницы. Сторож пишет в Telegram,
> если загрузка сломалась. Кабинет Яндекс Бизнеса для загрузки больше не нужен.
> Только чтение: ответить на отзыв или удалить что-либо в Яндексе сервис не может.
> Постановка задачи кабинета — [апи яд](апи%20яд) (файл владельца в `docs/`).

## Что это

Отзывы с Яндекс Карт сами появляются на странице «Отзывы» ([reviews.md](reviews.md)) и
приходят в бот kulturaopenclosed, их не вносят руками.

С 28.09 по 09.10 их загружала сверка кабинета Яндекс Бизнеса (`yandex.ru/sprav`, сессия
личного аккаунта владельца). Вход протух сразу после первой сверки 28.09, и 11 дней отзывы не
обновлялись — на странице это было видно только строкой состояния. Поэтому (решение владельца
2026-10-09):

1. **Главный источник — без входа.** Публичная страница отзывов организации
   (`https://yandex.ru/maps/org/<id>/reviews/`) содержит отзывы прямо в коде страницы: id (те
   же, что в кабинете — владелец проверил на Кременчугской), оценки, тексты, авторы, даты и
   ответы организации, по 50 на страницу. Так же сервис с 2026-09-29 раз в 3 часа читает прайс
   бара на Картах ([yandex-feeds.md](yandex-feeds.md), «Сверка с Яндекс Картами»).
2. **Кабинет необязателен.** Он понадобится, только если отвечать на отзывы прямо из сервиса
   (этап «отвечать» ниже). Личный аккаунт владельца с сервера можно убрать совсем — см.
   «Кабинет Яндекс Бизнеса».
3. **Сторож.** Сообщение в Telegram, если отзывы не обновлялись больше суток или на Картах
   отзывов больше, чем у нас, дольше 6 часов. Следующую поломку видно в тот же день.

Заодно новые отзывы приходят в бот в течение трёх часов, а не раз в сутки.

| Этап | Что | Состояние |
|---|---|---|
| 0 | Клиент кабинета + диагностика на реальных данных | готово, проверено 2026-09-28 |
| 1 | Загрузка в `guest_reviews.json`: история, ответы организации, пропавшие, строка состояния | кабинет — 28.09 (вход протух в тот же день); с 2026-10-09 — публичная страница Карт |
| 1.1 | Проверка раз в 3 часа + полный проход раз в сутки + сторож | с 2026-10-09 |
| 2 | Ответ из сервиса прямо в Яндекс (`POST /api/ugcpub/business-answer`, нужен кабинет) | не начат, только по решению владельца |

## Как работает

### Решения владельца

| Вопрос | Решение |
|---|---|
| Источник (2026-10-09) | публичная страница бара на Яндекс Картах, без входа; кабинет — только для будущего ответа из сервиса |
| Частота (2026-10-09) | первая страница раз в 3 часа (4 запроса), остальные — если на Картах больше отзывов; полный проход раз в сутки в 08:30 |

| Старые отзывы без ответа (2026-09-28) | старше «первая загрузка − 30 дней» (граница 2026-08-29) -> «Без ответа по решению» с причиной «До подключения сервиса: в Яндексе без ответа»; моложе -> «Без ответа» |

### Страница Карт (`core/yandex_maps_reviews.py`)

`https://yandex.ru/maps/org/<id>/reviews/` — первая страница, `…/reviews/?page=N` — N-я.
Запрос — как у браузера (User-Agent Chrome, `Accept-Language: ru`), таймаут 10 с на соединение
и 40 с на ответ, между запросами подряд — пауза 1,5 с (`PAUSE_SEC`). Яндекс встраивает в
страницу её данные JSON-ом; разбор не привязан к месту блока:

- **отзывы** — все массивы `"reviews":[…]`, в которых есть записи с `reviewId`; повторы по
  `reviewId` отбрасываются; записи с другим `businessId` (блок «похожие места») пропускаются;
- **число отзывов организации** (`count`) — из блока `"params":{…}` списка (в нём `count` и
  `totalPages`, там же `page` и `limit` = 50); нет его — из микроразметки
  `<meta itemprop="reviewCount" content="N">`; нет и там — `None` (тогда проверка «на Картах
  больше, чем у нас» для бара не работает, сторож по ней молчит);
- капча («я не робот») без отзывов в странице — `MapsCaptchaError`; ни отзывов, ни нулевого
  числа — `MapsReviewsError` «Яндекс мог поменять разметку». Организация без отзывов
  (`count = 0`) — не ошибка.

| Наше поле | Со страницы | Правило |
|---|---|---|
| `external_id` | `reviewId` | ключ вместе с `source = 'yandex'`; тот же id, что в кабинете |
| `rating` | `rating` | целое 1..5 (`4.0` -> 4); иначе `None` и замечание |
| `author` | `author.name` | `''` — без имени |
| `text` | `text` | `''` — только оценка |
| `created_at` | `updatedTime` | ISO в UTC (`2026-10-01T10:00:00.123Z`) -> `YYYY-MM-DDTHH:MM` по Москве (+3 ч); время без пояса — UTC; Unix-время тоже принимается |
| `owner_reply` | `businessComment.{text, updatedTime}` | ответ организации или `None` (пустой текст — не ответ) |

`updatedTime` — время последней правки отзыва; у нового отзыва это момент публикации. У уже
загруженного отзыва дата не меняется (`created_at` при загрузке не обновляется), так что правка
отзыва автором не «омолаживает» его. Фото, аватар и `public_rating` страница не даёт — у
отзывов из кабинета они остаются как были, у новых — пусто (на странице они не показываются).

**Листание** (`collect_pages`): страницы 2, 3, … пока не набрано `count` отзывов, не пройдено
`totalPages`, не пришла пустая страница или не исчерпан предел 40 страниц (`MAX_PAGES`, 2000
отзывов). Страница с чужим номером (`params.page ≠ N`) или только с уже полученными отзывами —
ошибка «Карты не листают страницы отзывов»: загружается то, что успели получить, проход не
считается полным. Пример: у Кременчугской 108 отзывов, по 50 на странице — страницы 1, 2, 3.

### Проверка (`core/yandex_reviews_sync.sync_all`)

Для каждого бара (организация -> бар по `BAR_BY_PERMANENT_ID`, не по названию):

1. Первая страница.
2. **Защита от дублей**: если и на странице, и у нас по бару от 10 отзывов
   (`ID_MATCH_MIN_REVIEWS`), а знакомых id на странице меньше половины (`ID_MATCH_MIN_SHARE`),
   бар не загружается — ошибка «id не совпадают с сохранёнными». Иначе при другом формате id
   все отзывы задвоились бы и ушли в бот как новые. Новых отзывов за 3 часа единицы, поэтому при
   правильных id совпадает почти всё.
3. Догрузка остальных страниц:
   - полный проход (`full`) — всегда;
   - быстрая проверка (`quick`) — только если `count > |наши живые id бара ∪ id первой страницы|`
     (живые — без отметки «нет в Яндексе»). Пример: у нас 120, на первой странице новых нет, на
     Картах 121 — новый отзыв дальше первой страницы, листаем все. На Картах 121, новый — на
     первой странице: 120 ∪ 1 = 121, листать незачем.
4. Загрузка — `upsert_imported` (правила ниже). **Полный проход** = получено ровно `count`
   разных отзывов и листание без ошибки: только тогда отзывы, которых на Картах больше нет,
   получают `gone_at`. У бара с одной страницей (Лиговский, 50) полным бывает и быстрый проход.
5. Числа бара: `count` (на Картах), `received` (получено сейчас), `ours` (живых отзывов бара у
   нас после загрузки), `pages`, `synced_at` (последнее удачное чтение), `full_at`.
   **Отставание**: `count > ours` -> `behind_since` (с первой такой проверки; держится, пока
   отставание есть), иначе `null`.

Ошибка бара не стирает его прежние числа — сторож продолжает считать время от последнего
удачного чтения. Капча останавливает проверку сразу (остальные бары не запрашиваются): она на
все запросы с этого адреса. Новые отзывы рассылаются после проверки, если загружен хоть один бар.

Случай, который ловит только полный проход: за 3 часа один отзыв удалили, другой добавили не
на первую страницу — число на Картах не изменилось. Такой отзыв придёт не позже следующего
полного прохода (сутки).

| Статус | Когда | На странице |
|---|---|---|
| `ok` | все бары прочитаны | «Яндекс Карты: проверено <когда>. Проверка раз в 3 ч, полная — раз в сутки в 08:30.» |
| `partial` | часть баров с ошибкой (нет связи, не листается, id не совпали) | внимание, какие бары и почему |
| `captcha` | Яндекс попросил капчу | внимание, следующая попытка через 3 ч |
| `error` | ни один бар не прочитан | опасность, ошибки по барам |
| `running` | идёт проверка; дольше часа — считается прерванной | |
| `never` | проверки Карт ещё не было (в файле состояние кабинета) | «первая проверка ещё не прошла» |
| `disabled` | `YANDEX_REVIEWS_SYNC_ENABLED=0` | опасность: загрузка выключена |

Тревоги сторожа (`alerts` в `yandex_sync`) идут в начале строки и усиливают тон: «не
обновлялись больше суток» — опасность, «на Картах больше» — внимание. В подсказке строки —
по барам: на Картах, здесь, когда прочитано, ошибка.

**Состояние** — `yandex_reviews_sync.json` рядом с отзывами (поля — докстринг модуля). Файл,
оставшийся от кабинета (без `source = 'maps'`), при первом запуске заменяется; из него
переносятся граница истории (`history_cutoff` 2026-08-29), `notify_since`, `last_success_at`
и `synced_at` баров — поэтому сторож считает «не обновлялись» от последней удачной загрузки
кабинета (28.09), а не с нуля.

### Планировщик (`core/yandex_reviews_scheduler.py`)

Такт раз в 15 минут (первый — через 20 с после старта). На такте (`due_kind`):

1. полного прохода не было с последнего «08:30» (сегодня, если уже наступило, иначе вчера) ->
   полный проход;
2. с начала последней проверки меньше 3 часов -> ничего;
3. удачного полного прохода с последнего «08:30» нет -> снова полный (не чаще раза в 3 ч),
   иначе быстрая проверка.

Затем — сторож. Время — по Москве (`core/msk_time`). Первый запуск после выкладки — сразу
полный проход: в состоянии ещё нет прохода по Картам. Один поток на оба воркера gunicorn:
поток держит файловый замок `data/.yandex_reviews_thread.lock` (как сверка прайсов);
перезапущенный воркер забирает освободившийся замок. Проверка и сторож работают под замком
состояния (`state_lock`) — не пересекаются.

Запросов в сутки: 7 быстрых проверок × 4 бара + полный проход (Кременчугская 3, ВО 2,
Варшавская 3, Лиговский 1 при 108 / 99 / 101 / 50 отзывах) = 28 + 9 = 37, плюс догрузка страниц, когда на Картах больше.

| Переменная | По умолчанию | Что |
|---|---|---|
| `YANDEX_REVIEWS_SYNC_ENABLED` | 1 | 0 — не загружать (и сторож молчит) |
| `YANDEX_REVIEWS_SYNC_HOUR`, `_MINUTE` | 8, 30 | время полного прохода, МСК |
| `YANDEX_REVIEWS_NOTIFY` | 1 | 0 — не слать новые отзывы в бот |
| `YANDEX_REVIEWS_WATCHDOG` | 1 | 0 — сторож не пишет в Telegram (строка на странице остаётся) |

Cookies Яндекса для загрузки не нужны.

### Сторож (`core/yandex_reviews_watchdog.py`)

Кому: подписчикам бота kulturaopenclosed — тем же, кому приходят новые отзывы (тот же
транспорт, DRY-RUN и очередь досылки, `review_notify.notify_subscribers`).

| Условие | Правило |
|---|---|
| не обновлялись (`stale`) | `сейчас − synced_at бара > 24 ч`; если удачного чтения не было — от первой проверки Карт (`source_since`) |
| на Картах больше (`behind`) | `сейчас − behind_since бара > 6 ч`: две проверки подряд не смогли догрузить |

Границы строгие: ровно 24 ч или 6 ч — ещё не тревога. Одно сообщение на поломку: уходит, когда
в условие попал бар, о котором ещё не сообщали (в тексте — все бары в условии); бар
восстановился, а другие нет — молча убирается из списка; восстановились все — одно сообщение
«снова в порядке». Что сообщено — `watchdog` в состоянии. Не доставлено (нет токена,
подписчиков, Telegram не принял) — не отмечается, повтор через 15 минут.

```
Отзывы с Яндекс Карт не обновляются
Больше 24 часов нет удачной проверки:
Кременчугская — последняя удачная 9 октября 2026, 12:00. Ошибка: Яндекс показал проверку «я не робот», отзывы не получены

Новые отзывы не попадают ни на страницу, ни в бот. Сервис проверяет Карты раз в 3 часа и продолжит сам, когда страница откроется.
https://beerkultura.ru/reviews?month=all
```

```
На Яндекс Картах больше отзывов, чем в сервисе
Дольше 6 часов подряд:
Варшавская — на Картах 105, у нас 101 (с 10 октября 2026, 06:00). Ошибка: Карты не листают страницы отзывов: …

Часть отзывов не загрузилась: их нет ни на странице, ни в боте. Посмотрите их на Картах.
```

Восстановление: «Отзывы с Яндекс Карт снова обновляются» / «Отзывов на Картах и в сервисе снова
поровну» с временем последней проверки. Заголовок — жирным (HTML), данные экранируются, эмодзи нет.

### Статусы загруженных отзывов (`ReviewStore.upsert_imported`)

Ключ — пара (`source = 'yandex'`, `external_id` = id отзыва в Яндексе); повторная загрузка
дублей не создаёт. Id на публичной странице Карт те же, что в кабинете: отзывы, загруженные
кабинетом 28.09, продолжают обновляться с Карт без дублей.

| Было у нас | В Яндексе | Стало |
|---|---|---|
| отзыва нет | есть ответ организации | «Отвечен», ответ из Яндекса: `reply = {text, at: время ответа в Яндексе, by: 'Яндекс Карты', delivered: true, source: 'yandex'}` (у загруженных кабинетом `by: 'Яндекс Бизнес'`) |
| отзыва нет | ответа нет, дата раньше границы истории | «Без ответа по решению», причина «До подключения сервиса: в Яндексе без ответа» |
| отзыва нет | ответа нет, дата не раньше границы | «Без ответа» |
| «Без ответа» или «Без ответа по решению» | ответ появился | «Отвечен» с ответом из Яндекса |
| «Отвечен», ответ сохранён здесь | ответ появился | `delivered: true`, `published_at`, `source_text`; момент ответа (`reply.at`) прежний |
| «Отвечен», ответ из Яндекса | текст ответа изменили | новый текст, `edited_at`; `reply.at` прежний |
| «Отвечен», ответ из Яндекса | ответ удалили | «Без ответа», прежний ответ остаётся для истории (`removed_in_source_at`) |
| есть | отзыва нет (полный проход) | `gone_at`, запись остаётся |
| `gone_at` | отзыв снова есть | `gone_at` снимается |

Оценка, текст и автор обновляются при каждой загрузке — только поля, которые прислал
источник: фото, аватар и `public_rating` публичная страница не даёт, у отзывов из кабинета они
остаются. Дата отзыва (`created_at`) у загруженного не меняется. Отзыв без id, даты или оценки
1..5 не загружается и попадает в `stats.invalid` / `problems` (такой отзыв не считается
«пропавшим»).

На карточке ответ из Яндекса подписан «Ответ в Яндексе, <когда>»: у него только
«Скопировать» и «Сделать материалом» — править или возвращать его в работу здесь бессмысленно,
следующая загрузка вернула бы его как было. Ответ, сохранённый здесь и найденный в Яндексе,
подписан «Опубликован в Яндексе».

**Пробный прогон на реальных данных** (дамп 2026-09-28, без обращений к Яндексу, граница
истории 29.08.2026): 358 отзывов, отвечены 252, без ответа по решению 106, ждут ответа 0.
Средняя оценка по нашим правилам — Крем 4,6, ВО 4,5, Вар 4,4, Лиговский 4,5. Рейтинг на
карточке Яндекса другой (4,9 / 4,8 / 4,7 / 4,6): Яндекс считает его по своей формуле

### Новые отзывы — в бот kulturaopenclosed (`core/review_notify.py`)

Решение владельца 2026-09-28: «дублируй туда все новые отзывы». После каждой проверки Карт
каждый новый отзыв уходит отдельным сообщением **подписчикам** бота проверки открытых смен
(кто нажал в боте «Подписаться», [open-check-bot.md](open-check-bot.md)). Групповой чат смены
(`TELEGRAM_GROUP_CHAT_ID`) отзывы не получает: там бармены, а отзывы бывают резкими.

Отзыв, оставленный гостем в боте @kult_taplist_bot, приходит **сразу**, а не после проверки
Карт: бот после сохранения зовёт `notify_review_in_background` -> `notify_review_now` (тот же
транспорт, экранирование и отметка). Без дублей между двумя путями: оба держат одну блокировку
рассылки (`_notify_lock`: блокировка процесса + файл `<файл отзывов>.notify.lock` между
воркерами) на всё «выбрать — отправить — отметить», так что отзыв, отправленный сразу, уже
отмечен, когда проверка Карт выбирает кандидатов (тест с двумя потоками —
`test_daily_sync_and_immediate_notify_do_not_double_send`). Не получилось сразу (воркер
перезапустился, не было подписчиков, упёрлись в потолок) — отзыв не отмечен, и его подбирает
сам бот раз в 10 минут (`notify_pending_bot_reviews` из цикла опроса, под той же блокировкой):
проверка Карт для этого не нужна — она бывает раз в 3 часа и не проходит при капче.

**Личные данные.** Подписаться на бот персонала может любой (подписка одной кнопкой без списка
допуска — решение владельца), поэтому об отзыве из бота туда уходят **только бар, оценка,
дата и ссылка** на страницу отзывов — без имени, ника, телефона и текста; то же в «Последних
отзывах». Отзывы Яндекса — полностью: они и так публичны.

**Потолок для отзывов из бота:** не больше 20 в час по отдельности (`NOTIFY_BOT_PER_HOUR`,
считается по отметкам `tg_notified_at`); сверх — немедленная отправка пропускается
(`rate_limited`), а подбор шлёт накопившиеся одной сводкой «Новых отзывов из бота: N» со
ссылкой. Защита от спама с многих аккаунтов (с одного чата — не больше 3 отзывов в сутки).

| Правило | Как |
|---|---|
| Что новое | загруженный отзыв (из Яндекса или из бота, `origin = import`), добавленный не раньше `notify_since` и ещё не отправленный (`tg_notified_at` пуст); отзыв из бота — сразу, без `notify_since`; подбор — отзывы из бота, добавленные за 72 часа (`PENDING_WINDOW_HOURS`: старше — уже на сайте, лавину после простоя не шлём) |

### Кабинет Яндекс Бизнеса (необязателен)

С 2026-10-09 загрузка кабинет не использует. Он понадобится только для этапа «отвечать» —
ответа на отзыв прямо из сервиса (`POST /api/ugcpub/business-answer` с CSRF). Тогда:

- подключать **отдельный аккаунт Яндекса**, добавленный в Яндекс Бизнесе представителем
  четырёх организаций, а не личный аккаунт владельца: cookies `Session_id` / `sessionid2` —
  это вход во весь аккаунт (почта, Диск, платежи);
- cookies вставлять в форму на сайте (хранение на постоянном томе, без правки `.env` и
  перезапуска) — форма делается вместе с этапом «отвечать», пока её нет: хранить на сервере
  сессию, которой ничего не пользуется, — лишний риск.

**Убрать личный аккаунт с сервера** (сейчас там лежит вход в него):

1. В `/opt/beer/.env` на сервере удалить строки `YANDEX_BUSINESS_SESSION_ID=…` и
   `YANDEX_BUSINESS_SESSION_ID2=…`, затем `docker compose up -d app` (код их больше не читает,
   но файл — не место для чужого входа). То же — в локальном `.env`, если не нужен
   `scripts/yandex_reviews_probe.py`.
2. По желанию — в Яндекс ID «Выйти на всех устройствах»: копии cookies, где бы они ни остались,
   перестанут работать. Сессия на сервере и так протухла 28.09.

Ниже — справка по кабинету (этап 0 и сверка 28.09–09.10): пригодится для этапа «отвечать».

#### Вход в кабинет

Сессия — две cookies аккаунта Яндекса: `Session_id` и `sessionid2`. С 2026-10-09 их читает
только диагностика `scripts/yandex_reviews_probe.py` — из переменных окружения
`YANDEX_BUSINESS_SESSION_ID` и `YANDEX_BUSINESS_SESSION_ID2` (локально — из `.env`, он в
`.gitignore`). Сервер их не читает (до 2026-10-09 читала сверка — из `/opt/beer/.env`).

**Это сессия всего аккаунта Яндекса** (почта, Диск, платежи), а не ключ только к отзывам.
Поэтому:

- лучше завести отдельный аккаунт Яндекса, добавить его в Яндекс Бизнесе представителем
  организаций и брать cookies у него, а не у личного аккаунта владельца;
- cookies не присылать в чат и не класть в git — только в `.env`;
- клиент не печатает их, а из текста любой ошибки вырезает их значения (`_scrub`);
- сессия не вечная: выход из аккаунта («Выйти на всех устройствах») или смена пароля её
  убивает. Признак — переадресация на `passport.yandex.ru`, HTTP 401 или 488 →
  `YandexAuthError`: нужны новые cookies.

Как достать cookies (для `scripts/yandex_reviews_probe.py` и будущего этапа «отвечать»): войти в аккаунт в браузере, открыть отзывы организации в Яндекс
Бизнесе, DevTools → Application → Cookies → `https://yandex.ru`, скопировать значения
`Session_id` и `sessionid2`.

CSRF-токен для чтения не нужен (пакет `ya-business-api` тоже не шлёт его на чтении). Он
понадобится на этапе 2 для ответа на отзыв: `POST /api/view/chain/0/list/` отвечает 488 с
полем `csrf`.

#### Эндпоинты

`BASE_URL = https://yandex.ru/sprav`, все запросы без переадресаций (`allow_redirects=False`):

| Запрос | Ответ |
|---|---|
| `GET /api/companies?page=N` | `{limit, page, total, listCompanies: [...]}` — организации аккаунта, `type`: `ordinal` (точка) или `chain` (сеть) |
| `GET /api/chain/<tycoon_id>/branches/?chainPermalink=<permanent_id>&geoId=<geo_id>&page=N` | `{companyList: {pager, companies: [...]}, companyIds}` — филиалы сети |
| `GET /api/<permanent_id>/reviews?ranking_by=by_time&page=N` | `{page, currentState, list: {pager: {limit, offset, total, continue_token}, items: [...]}}` — отзывы, новые первыми |

Сети раскрываются в филиалы (`branches()`), повторы по `permanent_id` убираются. Связь с нашим
баром — по `permanent_id`, не по названию: название в кабинете могут поменять.

#### Пагинация отзывов

По номеру страницы: `page=1, 2, ...`. `continue_token` в ответе есть, но сервер принимает его
только вместе с `unread=true` (так же строит запрос пакет `ya-business-api`). Если листать все
отзывы по `continue_token`, как в примере постановки, сервер будет возвращать первую страницу
снова и снова.

`unread` — отметка «прочитано» в кабинете: отзыв могли открыть в Яндексе раньше нас. Поэтому
«новый отзыв» у нас = `id`, которого ещё нет в хранилище.

Обход останавливается:

- на пустой странице;
- когда `offset + число отзывов на странице >= total`;
- на пределе страниц (`MAX_REVIEW_PAGES = 200`: это тысячи отзывов, больше, чем у любого бара);
- ошибкой `YandexFormatError`, если страница повторила уже полученные отзывы (сервер
  проигнорировал `page`) — вместо бесконечного цикла.

#### Разбор отзыва (`parse_review`)

| Наше поле | Из Яндекса | Правило |
|---|---|---|
| `external_id` | `id` | ключ дедупликации вместе с `source = 'yandex'` |
| `rating` | `rating` | целое 1..5; иначе `None` и замечание в `problems` |
| `author` | `author.user` | `''` — нет имени; `author_privacy` — как пришло |
| `author_avatar` | `author.avatar` | ссылка или `None` |
| `text` | `full_text`, иначе `snippet` | `''` — только оценка |
| `created_at` | `time_created` | Unix-время → `YYYY-MM-DDTHH:MM` по Москве (формат хранилища отзывов); число больше 10^11 считается миллисекундами |
| `owner_reply` | `owner_comment.{text, time_created}` | ответ организации в Яндексе или `None` (пустой текст — не ответ) |
| `photos` | `photos[].{link, width, height}` | список |
| `lang`, `public_rating` | как есть | |

Неполная запись не бросает исключение: чего нет — `None` или `''` и строка в `problems`.
Служебные токены отзыва (csrf ответа, токены чата) не переносятся.

#### Ошибки и повторы

| Ошибка | Когда | Повтор |
|---|---|---|
| `YandexAuthError` | нет cookies; переадресация на вход; 401; 488 | нет — сессия сама не оживёт |
| `YandexCaptchaError` | 429 с заголовком `need-captcha: 1` | нет — повтор только продлит капчу |
| `YandexTemporaryError` | сеть, таймаут, 500/502/503/504, 429 без капчи | 3 попытки, паузы 2 и 6 с (`RETRY_DELAYS_SEC`) |
| `YandexFormatError` | не JSON, не объект, нет ожидаемых полей, иной код, пагинация не работает | нет |

Между запросами подряд — пауза 0,5 с (`REQUEST_PAUSE_SEC`), чтобы не частить в чужой
внутренний API. Таймаут одного запроса — 20 с.

#### Почему свой клиент, а не пакет `ya-business-api`

Постановка предлагает пакет `ya-business-api` 4.0.1 (MIT). Эндпоинты и приёмы взяты из него
(User-Agent браузера, cookie `i`, признаки протухшей сессии и капчи). Сам пакет не подключён:

- он требует `requests>=2.32.5` и `pydantic>=2.12.5`, а в образе закреплён
  `requests==2.31.0`, pydantic нет вовсе;
- в его модели отзыва около 14 обязательных полей, в том числе токены чата и csrf ответа.
  Если любое из них пропадёт у Яндекса, не разберётся вся страница отзывов. Здесь
  разбирается только нужное, остальное берётся по умолчанию;
- на ответ 5xx он падает на `assert` (`AssertionError`), а не понятной ошибкой;
- в примере постановки параметр `ranking=` — у пакета он называется `ranking_by`, а
  пагинация по `continue_token` без `unread` не работает (см. выше).

Весь код Яндекса — в одном файле. Если внутренний API изменится, правится только он.
